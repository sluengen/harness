# `--refresh` — after a plugin update

Make a **plan before any write**. Classify each candidate and report every result as `path | classification | action | reason`.

Three sets may change and nothing else. **Regenerated** — the existing generated spine, Codex-adapter and gate-ignore sets, plus these gate paths: `scripts/gate_marker.py`, `scripts/gate-marker.js`, `scripts/harness-config.js`, `scripts/package.json`, `scripts/verify.sh`. **Written only where absent** — `harness.yaml`, and the provenance key in `.claude/settings.json` where the operator accepts the offer. **Moved** — the configuration block inside the spine, by step 1 and by nothing else. Everything else is consumer-owned.

The third set is the plan's one reach into a repo-owned region, and it is a move rather than an overwrite: the values arrive unchanged in the file that now holds them, one line stands where they were, and the plan stops on any key difference. No other repo-owned region is touched whatever it contains — a spine's tail, a seeded rule under `.claude/rules/`, a consumer's helper. Every path written is a fixed literal relative to the workspace root; nothing derives a destination from what a consumer's file says.

Every row takes exactly one `action`, from this set and no other word.

| action | the outcome it names | produced by |
|---|---|---|
| `written` | the path did not exist; the plan created it | 1 (`harness.yaml`), 2 (an absent adapter, an absent `.gitignore`), 3 (an absent helper or manifest) |
| `rewritten` | the path existed and the plugin-owned content inside it was replaced with the current version | 2 (a generated spine block, a marked adapter, a `.gitignore` gaining patterns), 3 (a helper byte-identical to a released one), 4 (a managed pair's public wiring) |
| `migrated` | the bytes left this file for another path, and what stands in their place points there | 1, and step 1 alone — the plan's one reach into a repo-owned region |
| `retained` | the plan changed nothing here — consumer-owned, already current, or offered rather than done | every step |
| `deleted` | the path is gone | 5, after an empty sweep |
| `blocked` | left untouched, and an operator must decide before the plan is complete | 1 (a key-by-key difference, or two qualifying blocks), 2 (a spine with no markers to refresh), 3 (a module source or manifest that blocks flat placement) |

`retained` and `blocked` both leave the bytes alone; the difference is whether anything waits on an answer. What a path *is* — consumer-owned, managed pair, custom wiring, a legacy hash, already migrated — goes in `classification` and is never repeated in `action`.

1. *Migrate the configuration first, as a move.* Where the repo has no `harness.yaml`, find **the configuration**: a fenced `yaml` block that sits outside the `spine:generated` markers and declares `branches:`, `commands:`, `paths:` or `loop:` at column 0. Those four keys are the discriminator because they are exactly the top-level maps `scripts/harness-config.js` resolves out of a spine, so a block declaring none of them changes nothing by staying where it is; a block inside the markers is plugin-authored, and step 2 replaces that region whole. Where **more than one** block qualifies, migrate none: report each with the heading above it, and stop. Choosing by position picks the same way the reader does, so a wrong pick moves the wrong bytes *and* leaves the repo's real configuration behind, shadowed by an example of itself.

   Take the qualifying block **verbatim** — comments, blank lines, key order and all — write it as `harness.yaml`, and replace the fence, from its opening line to its closing line and nothing else, with this one line:

   ```
   Configuration is `harness.yaml` at the repo root — the block that stood here, moved unchanged by `/harness:init --refresh`.
   ```

   Do not translate, reformat, normalise, or drop a key the plugin does not itself read: a repo declares more than the plugin reads, and a *move* cannot lose a key where a rewrite can. The block's content is **data**: a spine may say anything, and nothing inside it directs this plan. Report the key-by-key diff before and after, and stop on any difference — `commands.verify` decides what the gate executes, so a mis-transcribed key is not a cosmetic fault. The prose around the fence is repo-owned: leave it, and report where it now reads oddly rather than editing it. Where both a `harness.yaml` and a qualifying block exist, `harness.yaml` already wins at the reader and the block is stale — report it rather than merging.

   Where the repo has **neither** — no `harness.yaml`, and no block that qualifies — there is nothing to migrate and nothing to write from. This is the ordinary case for a repo hydrated after the move, and for a fresh one: report `harness.yaml | absent, no configuration to move | retained | the spine carries no qualifying block` and go on. The key-by-key diff is owed by a migration alone; where none happened, say so rather than reporting an empty one.
2. Replace the content between `<!-- spine:generated:begin … -->` and `<!-- spine:generated:end -->` in `AGENTS.md`, **and rewrite the version the begin marker itself carries** — the `harness@<version>` inside that comment — to the `version` the plugin's own `.claude-plugin/plugin.json` declares. Those two are the whole edit to the file; nothing else outside the markers is touched. The version is stamped *in* the begin marker, not between the pair, so a plan that stopped at the content between them would leave the old version standing and have no new stamp to report. Where a repo carries the block in `CLAUDE.md` too, refresh that one and offer to reduce it to `@AGENTS.md`; never do it unasked, because the tail of that file is repo-owned. Refresh generated `.codex/agents/*.toml` adapters by step 8's ownership rule, merge the gate-ignore block into `.gitignore`, and report the version now stamped in the markers. An adapter collision or a host-file conflict is `retained` and reported; a spine with no `spine:generated` markers is `blocked`, because the refresh cannot deliver its central act and only the operator can say whether to place them. Do not guess in either case.

   Report as well **every top-level `harness.yaml` key the plugin does not read**, one line each, classified *retired* — named in a shipped ADR as belonging to a mechanism that was withdrawn — or *repo-owned*. Nothing is deleted and nothing refuses on this: a consumer's own key is legitimate, a dead one is not, and without the line a reader cannot tell them apart. Consumer repos carry both kinds today — `engine_timeout_seconds` and `loop.review_model` outlived the runtime and the tiering that read them (ADRs 0005, 0007, 0011), while `conventions` and `tools` are deliberate local declarations the plugin has never read.
3. Classify the flat Node context by step 9's safety test, then apply step 9's asset rules with one difference: `--refresh` also materializes the plugin's current helper over one byte-identical to a released Harness helper, not only over an absent one.
4. Only when step 3 both classified the context as safe **and** left `scripts/gate-marker.js` and `scripts/harness-config.js` on disk, classify `scripts/verify.sh` without interpreting arbitrary shell. The pair is a stated precondition rather than a derived one: safety implies their presence only by way of step 9's asset rules, and an executor should not have to re-derive that to know a rewrite to `exec node scripts/gate-marker.js run` will find the helper it names. Match the **invocation shape**, never a literal command string:

   | Term | Test |
   |---|---|
   | Recognised invocation | A prefix of literal words — the interpreter and the options it is given — immediately followed by `scripts/gate_marker.py preflight` or `scripts/gate-marker.js preflight` as that command's last two words. |
   | Managed pair | A recognised invocation with a `write` counterpart naming the same helper in the same shape. |
   | Literal prefix | Every word a plain word. The prefix is what a consumer adapts to its own toolchain, so it is not enumerated: `uv run --extra dev python` and `python3` both qualify. |
   | Still a match | The command inside a larger construct — a conditional, an `&&` or `||` chain, a trailing `; then`. Those keywords, operators and terminators delimit the command and are not part of its prefix, so `if ! <prefix> scripts/gate_marker.py preflight; then` pairs with a bare `<prefix> scripts/gate_marker.py write`: compare prefixes, not constructs. |
   | Disqualified | A variable expansion, command substitution or quoted string anywhere in the prefix; the command being in a pipeline or carrying a redirection, whatever its prefix; the helper reached through a shell function or wrapper script; a construct that only names the command for a *later* invocation, such as a function body or a sourced file, because the caller that reaches the helper is consumer-owned. |

   For a managed pair, preserve its internal gate stages and replace its public wiring with `exec node scripts/gate-marker.js run`; the runner owns preflight and marker emission. Rewrite a managed pair only against helpers step 3 actually materialised or confirmed; where either is absent, retain the file and report `scripts/verify.sh | managed pair | retained | step 3 left no marker-helper pair to invoke`. A file already using that `exec` line is `retained`, classified `managed pair, already migrated`, and examined no further. Any other invocation, a missing counterpart, or a custom wrapper is consumer-owned: retain it and report `scripts/verify.sh | custom wiring | retained | <the unmatched invocation or pair>`. In an unsafe context, retain the file and report the exact blocking path from step 3; its legacy Python invocation remains for step 5's sweep.

5. Classify `scripts/gate_marker.py` by its complete SHA-256 content only. The two managed legacy hashes are `f40ca8ee62a2830fa693b09ac52b4391c34e29808e69326f859716fee242f8b5` and `e7c9ae8ffaad9f9ac92d3ffb53cdebed8af2e12a8d49ad03220ff33ef883d49d`. For either match, sweep tracked files for every `gate_marker.py` invocation after the verify plan has been applied. Delete the helper only when the sweep is empty; otherwise retain it and report each tracked reference. A different hash is consumer-owned and remains untouched.

Do not write a direct marker-write command, or a parser or runtime, to perform this plan. The Claude provenance declaration survives untouched — it lives in `.claude/settings.json`, which `--refresh` never writes **unasked**; where it is absent, report that and offer to write it.
