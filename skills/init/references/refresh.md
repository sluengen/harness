# `--refresh` — after a plugin update

Make a **plan before any write**. Classify each candidate and report every result as `path | classification | action | reason`. The plan may change only the existing generated spine, Codex-adapter and gate-ignore sets, plus these gate paths: `scripts/gate_marker.py`, `scripts/gate-marker.js`, `scripts/harness-config.js`, `scripts/package.json`, `scripts/verify.sh`. Everything else is consumer-owned.

1. *Migrate the configuration first, as a move.* Where the repo has no `harness.yaml` and its spine still carries a fenced `yaml` block, take that block **verbatim** — comments, blank lines, key order and all — write it as `harness.yaml`, and replace the fence with a one-line pointer to it. Do not translate, reformat, normalise, or drop a key the plugin does not itself read: a repo declares more than the plugin reads, and a *move* cannot lose a key where a rewrite can. Report the key-by-key diff before and after, and stop on any difference. Where both exist, `harness.yaml` already wins at the reader and the fenced block is stale — report it rather than merging.
2. Replace the content between `<!-- spine:generated:begin … -->` and `<!-- spine:generated:end -->` in `AGENTS.md`, touching nothing outside the markers. Where a repo carries the block in `CLAUDE.md` too, refresh that one and offer to reduce it to `@AGENTS.md`; never do it unasked, because the tail of that file is repo-owned. Refresh generated `.codex/agents/*.toml` adapters by step 8's ownership rule, merge the gate-ignore block into `.gitignore`, and report the version stamped in the new markers. A missing spine marker, an adapter collision, or a host-file conflict is retained and reported; do not guess.
3. Classify the flat Node context by step 9's safety test, then apply step 9's asset rules with one difference: `--refresh` also materializes the plugin's current helper over one byte-identical to a released Harness helper, not only over an absent one.
4. Only when step 3 classified the context as safe, classify `scripts/verify.sh` without interpreting arbitrary shell. Match the **invocation shape**, never a literal command string:

   | Term | Test |
   |---|---|
   | Recognised invocation | A prefix of literal words — the interpreter and the options it is given — immediately followed by `scripts/gate_marker.py preflight` or `scripts/gate-marker.js preflight` as that command's last two words. |
   | Managed pair | A recognised invocation with a `write` counterpart naming the same helper in the same shape. |
   | Literal prefix | Every word a plain word. The prefix is what a consumer adapts to its own toolchain, so it is not enumerated: `uv run --extra dev python` and `python3` both qualify. |
   | Still a match | The command inside a larger construct — a conditional, an `&&` or `||` chain, a trailing `; then`. Those keywords, operators and terminators delimit the command and are not part of its prefix, so `if ! <prefix> scripts/gate_marker.py preflight; then` pairs with a bare `<prefix> scripts/gate_marker.py write`: compare prefixes, not constructs. |
   | Disqualified | A variable expansion, command substitution or quoted string anywhere in the prefix; the command being in a pipeline or carrying a redirection, whatever its prefix; the helper reached through a shell function or wrapper script; a construct that only names the command for a *later* invocation, such as a function body or a sourced file, because the caller that reaches the helper is consumer-owned. |

   For a managed pair, preserve its internal gate stages and replace its public wiring with `exec node scripts/gate-marker.js run`; the runner owns preflight and marker emission. A file already using that `exec` line is retained as migrated, but is still classified for its **internal-mode test**: where it compares `HARNESS_GATE_MARKER_RUNNER` against the literal `1`, rewrite that one comparison to `[ -z "${HARNESS_GATE_MARKER_RUNNER:-}" ]` guarding the public path and report `scripts/verify.sh | managed internal-mode test | rewritten | <the comparison>`; where the test is present but in an unrecognised shape, retain it and report the one-line edit for the operator. Without this a consumer migrated before #559 keeps comparing against a value the runner no longer sets, so step 3's new helper lands over a script that will take its public path forever: the second runner matches the inherited identity, refuses with exit 3, and the gate is unrunnable under a message that names the wrong cause. Any other invocation, a missing counterpart, or a custom wrapper is consumer-owned: retain it and report `scripts/verify.sh | custom wiring | retained | <the unmatched invocation or pair>`. In an unsafe context, retain the file and report the exact blocking path from step 3; its legacy Python invocation remains for step 5's sweep.

5. Classify `scripts/gate_marker.py` by its complete SHA-256 content only. The two managed legacy hashes are `f40ca8ee62a2830fa693b09ac52b4391c34e29808e69326f859716fee242f8b5` and `e7c9ae8ffaad9f9ac92d3ffb53cdebed8af2e12a8d49ad03220ff33ef883d49d`. For either match, sweep tracked files for every `gate_marker.py` invocation after the verify plan has been applied. Delete the helper only when the sweep is empty; otherwise retain it and report each tracked reference. A different hash is consumer-owned and remains untouched.

Do not write a direct marker-write command, or a parser or runtime, to perform this plan. The Claude provenance declaration survives untouched — it lives in `.claude/settings.json`, which `--refresh` never writes; where it is absent, report that and offer to write it.
