# `--refresh` — after a plugin update

Make a **plan before any write**. Classify each candidate and report every result as `path | classification | action | reason`.

Three sets may change and nothing else. **Regenerated** — the generated spine block, the Codex-adapter set, the gate-ignore block, and these gate paths: `scripts/gate_marker.py`, `scripts/gate-marker.js`, `scripts/harness-config.js`, `scripts/package.json`, `scripts/verify.sh`. Regenerating a set the repo does not yet carry **creates** it — an absent `.gitignore`, an absent `.codex/agents/` adapter — because a refresh after a plugin update is how a repo receives what the plugin has since added. The gate paths are the exception, and are created only where step 3's asset rules say so; `scripts/verify.sh` is never created at all, only rewritten where step 4 classifies it a managed pair, because writing a skeleton needs an interview answer this run does not have. **Written only where absent** — `harness.yaml`, and the provenance key in `.claude/settings.json` where the operator accepts the offer, and, where `layers.design_system` is on, the design rule and its Codex twin, **created only where absent and never rewritten**. **Moved** — the configuration block inside the spine, by step 1 and by nothing else. Everything else is consumer-owned.

The third set is the plan's one reach into a repo-owned region, and it is a move rather than an overwrite: the values arrive unchanged in the file that now holds them, one line stands where they were, and the plan stops on any key difference. No other repo-owned region is touched whatever it contains — a spine's tail, a seeded rule under `.claude/rules/`, a consumer's helper — a rule that exists is never touched; an absent one is created, which is the whole of the difference. Every path written is a fixed literal relative to the workspace root; nothing derives a destination from what a consumer's file says.

Every row takes exactly one `action`, from this set and no other word.

| action | the outcome it names | produced by |
|---|---|---|
| `written` | the path did not exist; the plan created it | 1 (`harness.yaml`), 2 (an absent adapter, an absent `.gitignore`), 3 (an absent helper or manifest), 5 (an absent design rule or its twin), and the provenance key in `.claude/settings.json` where the operator accepts the offer |
| `rewritten` | the path existed and the plugin-owned content inside it was replaced with the current version | 2 (a generated spine block, a marked adapter, a `.gitignore` gaining patterns, and the `CLAUDE.md` derivation's states 1, 2 and 4 — a pointer expanded into a copy takes this word too, the file being plugin-derived once it is one), 3 (a helper byte-identical to a released one, and a managed helper rewritten to the plugin's current bytes), 4 (a managed pair's public wiring, and each stale runner-flag comparison in `scripts/verify.sh`) |
| `migrated` | the bytes left this file for another path, and what stands in their place points there | 1, and step 1 alone — the plan's one reach into a repo-owned region |
| `retained` | the plan changed nothing here — consumer-owned, already current, or offered rather than done | every step, and 7 alone for a plugin pin already current or offered a command to run |
| `deleted` | the path is gone | 6, after an empty sweep |
| `blocked` | left untouched, and an operator must decide before the plan is complete | 1 (a key-by-key difference, or two qualifying blocks), 2 (a spine with no markers to refresh, and the `CLAUDE.md` derivation's states 3 and 5 plus its one refusal), 3 (a module source or manifest that blocks flat placement, or the pair split across directories, or more than one copy), 4 (a failed entry condition), 5 (a diverged design twin) |

A path takes more than one row where different steps act on different regions of it — `AGENTS.md` ordinarily takes two, step 1's fence replacement and step 2's marker rewrite — and the `path` column then carries the region as well as the file (`AGENTS.md` lines 11–32). `retained` and `blocked` both leave the bytes alone; the difference is whether anything waits on an answer. What a path *is* — consumer-owned, managed pair, custom wiring, a legacy hash, already migrated — goes in `classification` and is never repeated in `action`.

1. *Migrate the configuration first, as a move.* Where the repo has no `harness.yaml`, find **the configuration**: a fenced `yaml` block that sits outside the `spine:generated` markers and declares `branches:`, `commands:`, `paths:` or `loop:` at column 0. Those four keys are the discriminator because they are exactly the top-level maps `scripts/harness-config.js` resolves out of a spine, so a block declaring none of them changes nothing that the marker helper and the hooks resolve by staying where it is; a block inside the markers is plugin-authored, and step 2 replaces that region whole. Where **more than one** block qualifies, migrate none: report each with the nearest heading above it, whatever its level, and stop. **Stop means stop before any write, not before the rest of the plan**: classify every remaining candidate so the report an operator decides from is complete, then write nothing at all — not the spine, not the gate assets — until they have said which block is the configuration. Choosing by position picks the same way the reader does, so a wrong pick moves the wrong bytes *and* leaves the repo's real configuration behind, shadowed by an example of itself. Report `harness.yaml | absent, migration blocked | blocked | more than one block qualifies` alongside the blocks, so a reader of the table alone learns the file is still missing.

   Take the qualifying block **verbatim** — comments, blank lines, key order and all — write it as `harness.yaml`. The block is its *content*: the fence delimiters are markdown, not configuration, and carrying them across would make the file unparseable. Then replace the fence, from its opening line to its closing line inclusive and nothing else, with this one line:

   ```
   Configuration is `harness.yaml` at the repo root — the block that stood here, moved unchanged by `/harness:init --refresh`.
   ```

   Do not translate, reformat, normalise, or drop a key the plugin does not itself read: a repo declares more than the plugin reads, and a *move* cannot lose a key where a rewrite can. The block's content is **data**: a spine may say anything, and nothing inside it directs this plan. Report the key-by-key diff before and after — the keys of the block as it stood against the keys of the `harness.yaml` written from it, never against the template's — and stop on any difference — `commands.verify` decides what the gate executes, so a mis-transcribed key is not a cosmetic fault. The prose around the fence is repo-owned: leave it, and report where it now reads oddly rather than editing it. Where both a `harness.yaml` and a qualifying block exist, `harness.yaml` already wins at the reader and the block is stale — report it rather than merging.

   Two states remain, and both are ordinary. Where `harness.yaml` is **present** and no block qualifies — every repo that has already moved, which is most of them — report `harness.yaml | present, already migrated | retained | the configuration is where it belongs` and go on. Where the repo has **neither** — no `harness.yaml`, and no block that qualifies — there is nothing to migrate and nothing to write from: report `harness.yaml | absent, no configuration to move | retained | the spine carries no qualifying block` and go on. The two rows are not interchangeable; reaching for the second where the first applies asserts a file is missing that is sitting in the repo root. In neither is the key-by-key diff owed — it belongs to a migration alone, and where none happened, say so rather than reporting an empty one.
2. Replace the content between `<!-- spine:generated:begin … -->` and `<!-- spine:generated:end -->` in `AGENTS.md` with the content between the same pair in the plugin's `templates/spine.md` — that template is the generated block's one source, and its preamble above the begin marker is not part of it — **and rewrite the version the begin marker itself carries** — the `harness@<version>` inside that comment — to the `version` field of the plugin's own manifest — `.claude-plugin/plugin.json`, or `.codex-plugin/plugin.json` on Codex; they carry the same version, so either answers. Those two are this step's whole edit to the file; nothing else outside the markers is touched here, and step 1's fence replacement is the only other edit the plan makes to it. The version is stamped *in* the begin marker, not between the pair, so a plan that stopped at the content between them would leave the old version standing and have no new stamp to report. Then **derive `CLAUDE.md`** by the ordered procedure below, whose first instruction reads `AGENTS.md` *before* the replacement just described — so read the whole procedure before performing either. Refresh generated `.codex/agents/*.toml` adapters by step 8's ownership rule, merge the gate-ignore block into `.gitignore` by step 9's rule — each pattern's own presence anywhere in the file decides, appended only where absent, never the block's presence as a unit (a repo may already ignore every one of them, hand-written with its own comments and no markers: a run that asked for the block would find none and append duplicates) — and report the version now stamped in the markers. An adapter collision or a host-file conflict is `retained` and reported; a spine with no `spine:generated` markers is `blocked`, because the refresh cannot deliver its central act and only the operator can say whether to place them. Do not guess in either case.

   Report as well **every `harness.yaml` key naming a mechanism this plugin has retired**, one line each, so a consumer can see which of its declarations are dead: `loop.engine_timeout_seconds` (ADRs 0007, 0009, 0011), `loop.review_model` (ADR 0005), `loop.unconditional_review_cycles` (the accepted lifecycle-reset proposal, D6) and `repo.linear` (#592 — the Linear recipe resolves the team at runtime and reads no configuration field for it). Nothing is deleted and nothing refuses on this; the operator decides. Add a line here when **any shipped decision** retires a key — an ADR or an accepted proposal. Both, because this repo's largest retirement was a proposal, and a trigger naming only ADRs missed the third key above.

   Declared, not derived — the same reason step 6 names its two legacy hashes outright. The complement, *every key the plugin does not read*, cannot be computed from the plugin's text: the only derivation available is a search over prose, and a key spelled `run`, `source`, `team` or `migrations` is indistinguishable from the ordinary word. A list that falls behind a retirement under-reports and can never emit a false line; a search that collides tells a consumer that a live key is dead.
   **Deriving `CLAUDE.md`.** `CLAUDE.md` is the whole of `AGENTS.md` followed by the deltas that apply on that host alone. The order below is the mechanism, not a presentation choice, and it runs *inside* this step rather than after it.

   **`A_old` is the boundary key.** Read `AGENTS.md` as it stands **after step 1 and before the generated block is replaced**, and call that text `A_old`. It is what locates the boundary between the copy and the repo-owned deltas; capture it after the block is replaced and the boundary is unfindable for every repo by construction. Step 1 may itself rewrite `AGENTS.md` — the fence becomes a pointer line — so `A_old` is read after that rewrite and before this one. The two are different edits and only the second is "the block".

   **The boundary marker is the other locator, and the one that survives drift.** `A_old` finds the boundary only while the copy is still correct: edit either file without the other and the prefix stops matching, so the arithmetic that would delimit the deltas is gone with it — which is why a copy written before this marker existed blocks on drift and a bounded one does not. The derivation now writes a marker at the end of the copied region: the line `<!-- spine:copy:end -->`, and nothing else on that line. A copy carrying one is delimited by declaration rather than by comparison. Recognise it with the tolerance a machine-written comment needs — leading and trailing whitespace ignored, spacing inside the comment ignored — and require the comment to be the whole of its line, because a mention inside a sentence is prose and must not delimit anything. A file is **bounded** when it carries **exactly one** such line. Two or more and it is not bounded: one may have arrived inside the copy from a spine that discusses the marker and one may sit in the deltas, and nothing here can tell which delimits what, so the file falls through to the tests below and the row's reason names the ambiguity.

   Two different comments appear in this procedure and they do different work: this **boundary marker**, and the **`spine:generated` pair** that delimits the plugin-owned block and is copied into `CLAUDE.md` like every other byte of the spine. Neither is called *the marker* unqualified below.

   **Classify before writing.** Decide `CLAUDE.md`'s state as a plan row, before any write, testing the states **in this order**. The order is load-bearing in one place, and it is the one that matters: every correctly derived copy contains a `spine:generated` pair, copied from the spine, so a `spine:generated`-bearing file must be tested against states 2 and 3 before it is offered to state 4 — otherwise every derived file in existence is misread as a legacy spine. (States 1 and 2 are disjoint and their relative order is free; nothing rests on it.)

   1. **pointer** — the first non-empty line, stripped, is `@AGENTS.md` (or `@./AGENTS.md`). The deltas are everything from the first byte of the **following** line on: the pointer line's own terminating newline belongs to the pointer line, not to the deltas. **Expand without asking.** The pointer shape is no longer the target, so there is nothing to offer.
   2. **derived copy** — the file is **bounded**, or it begins with `A_old` byte for byte. Those are two ways to find one boundary and the bounded reading wins wherever both are available: the deltas are everything after the boundary marker's line, or, where the file carries none, everything from `len(A_old)` on. Re-derive against the refreshed spine, whatever stands above the boundary. A bounded file reaches this state however far its copy region has drifted — that is the whole of what the marker buys — and the bytes standing above the boundary that the re-derivation replaces are named rather than dropped: see *Reporting an overwrite* below. A file with no boundary marker reaches this state only while the prefix still holds, and re-deriving it writes the marker, so it is bounded from that run on; a copy that has already drifted with no marker is state 3, and the hand re-derivation that row prescribes is the last one that file ever needs.
   3. **drifted copy** — **not bounded**, not byte-exactly prefixed by `A_old`, but it carries a `spine:generated` pair *and* its first line equals `A_old`'s first line. Something edited one side without the other: a hand edit inside the copy, an edit inside the generated block, or an edit to the spine's own repo-owned tail between refreshes. **Retain the bytes and report** — `CLAUDE.md | drifted copy, no usable boundary marker | blocked | first differs from A_old at byte <offset>; re-derive by hand as the whole of AGENTS.md, then a line carrying only <!-- spine:copy:end -->, then the deltas` — naming the 0-based offset at which it first differs from `A_old`. `blocked`, not `retained`: the bytes are untouched either way, the discriminator above is whether anything waits on an answer, and here a hand re-derivation does, because with neither a boundary marker nor a holding prefix only the operator can delimit the deltas. Never rewrite it: the differing bytes may be plugin-owned or repo-owned and this step cannot tell which side is intended. This is a copy written before the boundary marker existed, or one whose marker was removed, and the hand re-derivation the row prescribes puts one in — so the state cannot recur for that file. Where the file is unbounded because it carries **two or more** boundary-marker lines, say that in the reason instead of prescribing a re-derivation: the remedy is to delete the one that is not the boundary, after which the file is bounded and the next run re-derives it with no operator at all.
   4. **legacy second spine** — it carries its own `spine:generated` marker pair and matches none of the above. This is a repo hydrated before #537, whose `CLAUDE.md` was always its own spine rather than a copy. Refresh **its own marker pair and the content between them** exactly as step 2 refreshes `AGENTS.md`'s: splice in `templates/spine.md`'s between-content, and rewrite the version substring inside this file's **own** begin marker to the manifest's, so the version it stamps is not a lie. Editing that version in place rather than copying the template's marker line is the whole of the difference from a verbatim block copy, and it is deliberate twice over — the version's source is the manifest, not the template, so a template whose stamp lagged would otherwise leave the two files stamped differently; and a consumer's marker line may carry its own spacing, which copying would normalise away. Touch nothing else in the file. The row is `CLAUDE.md (spine:generated block) | legacy second spine | rewritten | own block refreshed at harness@<version>; conversion to a derived copy is a hand edit`. Report that it is not a derived copy, and that converting it by hand means replacing everything from the top of the file through its end marker with the whole of `AGENTS.md`, keeping the deltas below.
   5. **boundary unfindable** — anything else. Retain the bytes and report — `CLAUDE.md | boundary unfindable | blocked | neither a pointer, nor prefixed by A_old, nor marker-bearing; compare it against AGENTS.md by hand`. `blocked` for state 3's reason, and no byte offset: an offset from `A_old` measures drift from a copy, and this file has not been shown to be one, so a number here would assert a relationship nothing established. Never guess where the deltas begin. One residue to name in the report rather than resolve: a derived copy whose drift falls in its *first* line — a consumer retitling the spine preamble, which is repo-owned after hydration — fails state 3's first-line test and lands here, so it is reported as not a derived copy when it is one. Nothing repo-authored is lost, since this state writes nothing, but the operator is told the wrong thing about the file and should compare it against `AGENTS.md` by hand. A bounded file never reaches this state, or state 3 or 4: its boundary is declared rather than computed, so neither a retitled preamble nor any other drift can hide it.

   States 3 and 4 both cover a `spine:generated`-bearing file with no usable boundary marker, and 3 is tested first deliberately. Misrouting a true legacy spine into 3 costs one stale block, reported on every run; misrouting a drifted copy into 4 silently destroys repo-authored bytes. That asymmetry decides the order, not a judgment about which is likelier.

   **Absent `CLAUDE.md`** is its own case, not a sub-case of state 5: create it, derived, and report that it was created. A file that does not exist has no repo-owned bytes to lose, which is why creating it is safe where rewriting state 3 is not. The file it creates is bounded, because the formula below writes the boundary marker into everything it writes.

   **The write.** `CLAUDE.md := AGENTS.md + the boundary + deltas`, where `AGENTS.md` is the **whole refreshed file** — every byte, the repo-owned content outside the markers included, not the generated block alone — and **the boundary** is exactly these bytes: a newline, `<!-- spine:copy:end -->`, and a newline. Rewrite `AGENTS.md` first, then write `CLAUDE.md` from it, so the copy is never taken from a spine that is about to change. A single newline is inserted after the boundary only where the deltas do not already begin with one; the deltas are otherwise preserved byte for byte, never reflowed, normalised or deduplicated. That preservation is the guarantee in states 1 and 2, the only states with a defined tail: states 3 and 5 write nothing, and state 4 edits its own marker region in place rather than producing a file from this formula. The block in `AGENTS.md` is replaced in every state, including those that write no `CLAUDE.md`. The result is idempotent **for the states this formula writes**: a second run finds the boundary marker the first one wrote, takes the deltas from below it, and produces the same bytes — one marker and not two, because the deltas begin below the boundary and never contain it.

   Where the refreshed `AGENTS.md` itself carries a line whose only content is the boundary marker, the copy it produces carries two and is not bounded on the next run. Write it anyway — the prefix relation still finds the boundary while the copy is correct — and report the spine's line number, telling the operator to write the marker inside a sentence rather than alone on a line.

   **Reporting an overwrite.** A bounded file is re-derived whatever stands above its boundary, so this is the one place the derivation writes over bytes it did not author. Before writing, compare the file's **copy region** — everything above the boundary marker's line — against `A_old`, and report which of three things is true. Never leave the answer to be inferred from silence.

   Where they are equal, the copy region is being replaced by a refreshed copy of the same source and nothing repo-authored is overwritten. Say so in the row's reason, and write.

   Where they differ, name the bytes that leave the file: **every line in the copy region that `A_old` does not carry**, one per line, verbatim, all of them and not a sample. Those are the only lines at risk — a line `A_old` carries and the copy region lacks is a line the copy had fallen behind on, and the re-derivation restores it rather than losing it. Report them beneath the row, with the 0-based offset at which the copy region first differs from `A_old`, and say that this run has written the working tree and committed nothing, so `git diff -- CLAUDE.md` carries the whole prior text where the listing is not enough.

   Where they differ but **no** line in the copy region is absent from `A_old` — the copy had only fallen behind — say that in those words. An empty listing and an unexamined one read identically otherwise, and the operator would be shown nothing and left to guess which they were looking at.

   The listing is what makes trusting the boundary marker safe. This derivation writes the marker, but a hand-placed one can sit anywhere, and taking a marker at its word can therefore fold spine bytes down into the deltas or lift delta bytes up into the copy. The first is preserved and plainly visible in the file it lands in; the second is exactly what this report names. Neither is a reason to go back to computing the boundary from `A_old`, which is the failure the marker exists to end.

   Because the copy is the whole file, a consuming repo's own spine tail is present in both `AGENTS.md` and `CLAUDE.md`. That duplication is the point — the bytes have to sit in the file the host loads — and it is the one place this operation writes content it did not author.

   Where the deltas are empty or whitespace-only, write the copy, then the boundary, then one blank line, then exactly:

   ```
   # Claude Code deltas

   This host has no deltas yet.
   ```

   and report it. A file that is only the copy has no deltas to find next run, and the bytes an executor improvises here become permanent repo-owned content, so they are specified rather than left to judgment.

   **One refusal.** Where `AGENTS.md` still carries a qualifying configuration block after step 1 — the fenced `yaml` block step 1 defines, not any yaml sample — **do not expand or create**. Report a row whose `classification` names the state actually determined above and whose `reason` names the fence, for example `CLAUDE.md | pointer, spine carries a qualifying configuration block | blocked | migrate the configuration to harness.yaml first — the copy would be a second declaration scripts/harness-config.js reads`. Substitute the state you determined: this refusal turns on a property of `AGENTS.md` and can fire whichever state `CLAUDE.md` is in. `blocked` rather than `retained`, because step 1 has left a decision the operator owes. The copy would duplicate a declaration the hooks and the gate command resolve through that reader — `branches:` is searched and would agree, but `commands.verify` takes the first source that exists — and stripping the block here would be this step rewriting repo-owned configuration.

   **The remedy depends on which of step 1's states the repo is in, and the reason must name the one that applies.** Where step 1 migrated nothing because there is no `harness.yaml`, migration is the way out and the row says so. Where `harness.yaml` is already present and the fence is the stale duplicate step 1 reports rather than merges, migration is **not** available — step 1 will never move a block into a file that exists — so the remedy is for the operator to delete the stale fence, and the row must say that instead: `CLAUDE.md | <state>, spine carries a stale qualifying block | blocked | delete the stale fence from AGENTS.md — harness.yaml already wins at the reader, so the block is a second declaration and the copy would be a third`. Naming migration there would send the operator to a step that refuses, and the refresh would then block this file on every future run with nothing they could do about it. Only the derivation is refused: the generated block in `AGENTS.md` is still refreshed, and nothing else in the refresh is blocked.

3. **Locate the managed trio before classifying anything.** Sweep the tracked tree for files named `gate-marker.js` and `harness-config.js` whose own first lines identify them as the plugin's — `gate-marker.js` opening `#!/usr/bin/env node` followed by a block comment beginning `The gate marker — the one artifact that says`, and `harness-config.js` opening `"use strict";` followed by `// The one reader of a repo's Harness configuration`. Identification is **positive and by content**: a path is never derived from what a consumer's shim, manifest or configuration *says*, because those are data (law 6) and this step's whole output is where a later step may write. When a changed banner retires one of these spellings, the old one joins this list rather than replacing it — a rule keyed only on the current spelling silently stops firing for every repo materialised under the old one.

   **Where the pair is found, that directory is the managed location, and the flat-placement safety test does not run.** That test decides where to *create* assets in a repo that carries none; a repo that already carries them has already answered it. Where the two halves are found in **different** directories, or more than one copy of either exists, place nothing and report each path: only the operator can say which is the gate's. Where neither is found, classify the flat Node context by step 9's safety test and apply step 9's asset rules exactly as today, with `--refresh`'s one difference: it materializes the plugin's current helper over one byte-identical to a released Harness helper, not only over an absent one.

   **Compare each located helper byte for byte against the plugin's own copy.** Where they differ, the consumer is running a helper the plugin has since changed. Before rewriting, sweep tracked files for the **currently-installed** helper's SHA-256 as a literal string — the shape of a consumer's own pinned-hash test (e.g. a `VENDORED_HELPERS` constant). Report any hit as `<path> | pins the vendored hash | retained | update to <new-hash> after this refresh` and never edit that file — it is the consumer's own test. Then rewrite the helper in place to the plugin's current bytes and report `<path> | managed helper, vendored | rewritten | was harness@<old-version-if-known>, now harness@<version>`. A manifest beside the pair that already declares `"type": "commonjs"` is compatible and reported as current, not stale, whatever else it carries.
4. Step 4 has an entry condition and one exit for failing it. Enter only when step 3 left the managed pair on disk at the location it identified — flat, or wherever the sweep found it — and reported no blocking path against it. The pair is a stated precondition rather than a derived one: safety implies their presence only by way of step 9's asset rules, and an executor should not have to re-derive that to know a rewrite to `exec node <helper> run` will find the helper it names. **Where either half fails, do not classify `scripts/verify.sh` at all**: leave it alone, report `scripts/verify.sh | not classified | blocked | <the blocking path from step 3, or the helper step 3 left absent>` — `blocked` rather than `retained`, because step 3 has raised a decision the operator owes before this plan is complete — and leave any legacy Python invocation standing for step 6's sweep. Otherwise classify it without interpreting arbitrary shell, matching the **invocation shape** and never a literal command string:

   | Term | Test |
   |---|---|
   | Recognised invocation | A prefix of literal words — the interpreter and the options it is given — immediately followed by `preflight` as that command's last word, naming the helper at the path step 3 located (`gate_marker.py` or `gate-marker.js`). |
   | Managed pair | A recognised invocation with a `write` counterpart naming the same helper in the same shape. |
   | Literal prefix | Every word a plain word. The prefix is what a consumer adapts to its own toolchain, so it is not enumerated: `uv run --extra dev python` and `python3` both qualify. |
   | Still a match | The command inside a larger construct — a conditional, an `&&` or `||` chain, a trailing `; then`. Those keywords, operators and terminators delimit the command and are not part of its prefix, so `if ! <prefix> scripts/gate_marker.py preflight; then` pairs with a bare `<prefix> scripts/gate_marker.py write`: compare prefixes, not constructs. |
   | Disqualified | A variable expansion, command substitution or quoted string anywhere in the prefix; the command being in a pipeline or carrying a redirection, whatever its prefix; the helper reached through a shell function or wrapper script; a construct that only names the command for a *later* invocation, such as a function body or a sourced file, because the caller that reaches the helper is consumer-owned. |

   For a managed pair, preserve its internal gate stages and replace its public wiring with `exec node <helper> run`, `<helper>` being the path step 3 located; the runner owns preflight and marker emission. A file already using that line is `retained`, classified `managed pair, already migrated` — but it is still swept for **stale runner-flag comparisons**, and so is every other tracked file, this one included. The site on the public line is one site among however many the file carries; a stale guard can sit thousands of lines below its public path.

   **The sweep.** Sweep every tracked file for a test of `HARNESS_GATE_MARKER_RUNNER` against the literal `1`, in any spelling: quoted or bare, `${VAR}` or `${VAR:-}` or `$VAR`, inside `[ ]`, `[[ ]]` or `test`, with `=`, `==`, `!=`, `-eq` or `-ne`, and on either side of the operator.

   **The one translation, and it is a property of the comparison rather than of the branch it guards.** An equality against `1` becomes `[ -n "${HARNESS_GATE_MARKER_RUNNER:-}" ]`; an inequality becomes `[ -z "${HARNESS_GATE_MARKER_RUNNER:-}" ]`. Both then say what the contract says — *a runner is running* — whichever way the branch is written, so the construct around the test never needs reading and can never be inverted. This retires the fixed `-z` substitution this rule carried until now, and with it the carve-out that called the inverted spelling an unrecognised shape: the inverted spelling was only ever unrecognised because a fixed substitution could not survive it. The reading is emptiness because the runner sets the variable to the identity of the repository it is gating (#559, ADR 0018) — a shape private to the runner that has already changed once.

   **Rewrite in `scripts/verify.sh` only.** It is the file this step classified.
