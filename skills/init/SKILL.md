# /harness:init — hydrate a repo

Usage: `/harness:init` (first-time setup) · `/harness:init --refresh` (after a plugin update)

Turns a repository into one this process can run in. The native plugin carries
the skills, role procedures, and hooks; this workflow writes the files that must
be **repo-owned**: both host spines, the Codex role adapters, the specs scaffold,
the infrastructure record, and the gate's ignore rule. In Claude Code, always
invoke it with its plugin prefix because bare `/init` is the host's own command.
In Codex, ask to initialize Harness or invoke the `command-init` skill.

## First-time setup

1. **Interview for the repo values.** From the repo itself where possible (language, test runner, existing branch names), from the operator where not: name, tracker backend and its addresses, stack, the five commands (install / lint / typecheck / test / verify), branch roles, and layer switches. The verify command is the one that matters most — it is the single command that decides green, and the hooks enforce against its marker. Record the answer exactly: `node scripts/gate-marker.js run` resolves the command it launches out of `harness.yaml`'s `commands.verify`, so this answer *is* the gate, whether it names a shell script, `npm run verify`, `make verify`, or `cargo test`.
2. **Write `harness.yaml`** from `templates/harness.yaml`, filled from the interview. This is the repo's configuration and the only place it is written: the hooks, the gate marker helper, and the skills all read it through `scripts/harness-config.js`. Never restate one of its values in prose — a value in two places is a value that disagrees with itself.
3. **Write the spine** — `AGENTS.md` from `templates/spine.md`: the generated block, with the repo section filled from the interview and no configuration in it. Merge an existing file: insert the generated block above its existing content, which remains repo-owned; do not discard the host's existing instructions. Then write `CLAUDE.md` as `@AGENTS.md` plus any Claude-specific deltas — it is a pointer file of a few lines, not a second copy, so the two hosts cannot drift apart. Both hosts read `AGENTS.md`, so one clone is usable from either without a second hydration.
4. **Scaffold the memory** — `specs/proposals/`, `specs/features/`, `specs/decisions/` (per the `paths:` just written), each with a `.gitkeep` where empty.
5. **Seed the infrastructure record** — `specs/infrastructure.md` from `templates/infrastructure.md`, with the branch topology from the interview as its first entry (`infrastructure` skill: this is the repo-owned *what*; the skill is the *how*).
6. **Declare where the plugin comes from.** Claude Code writes the *enablement* — `enabledPlugins: {"harness@harness": true}` — into whichever settings scope the install chose; at project scope that is the repo's own `.claude/settings.json`, the file shared with the team. Its marketplace is registered per machine, so a fresh clone can resolve the enablement to nothing. Merge the provenance into the same file, next to the enablement:

   ```json
   "extraKnownMarketplaces": {
     "harness": { "source": { "source": "github", "repo": "sluengen/harness" } }
   }
   ```

   Merge the key into an existing settings file rather than rewriting it, and leave the rest of the file byte-for-byte alone. Write both install routes into the spine's repo section: Claude Code uses `/plugin marketplace add sluengen/harness` then `/plugin install harness@harness`; Codex uses `codex plugin marketplace add sluengen/harness` then `codex plugin add harness@harness`. Codex marketplace registration is machine-local, so the committed spine is its provenance record and recovery instruction.

7. **Hydrate Codex role adapters** — copy the plugin's generated
   `.codex/agents/*.toml` into the repo's `.codex/agents/`. These repo-owned
   files are the Codex host adapters for named-agent workflows. They are separate
   from the native plugin skills packaged under `skills/`, which Codex loads from
   the installed plugin. Replace a file only when its first line says it was
   generated by `scripts/generate_codex_artifacts.py`; otherwise report the
   collision and leave it untouched. The adapters and portable skills carry the
   same four role procedures.
8. **Gate plumbing** — merge every pattern in this machine-identifiable block into `.gitignore`, appending only those absent so the operation is idempotent:

   <!-- harness:gate-ignore:begin -->
   ```gitignore
   .evidence/
   .worktrees/
   .claude/worktrees/
   ```
   <!-- harness:gate-ignore:end -->

   First make a **plan before any write**. The gate assets are managed only at `scripts/gate-marker.js`, `scripts/harness-config.js`, `scripts/package.json`, and a newly created `scripts/verify.sh`; do not place them elsewhere. The first two are a **pair** — the marker helper resolves the repo's declared gate command through the reader beside it, and a half-materialized install fails loudly at the preflight rather than running an undeclared command — so copy both or neither. Flat placement is safe only when every immediate module-bearing source (`*.js`, `*.mjs`, `*.cjs`, `*.ts`, `*.mts`, `*.cts`) is the recognised managed helper and `scripts/package.json` is absent or declares CommonJS. The absence of `*.js` does not establish consent. Copy `scripts/gate-marker.js` and `scripts/harness-config.js` only when absent; an existing non-Harness helper is retained and reported, and retaining either retains both. Write the plugin's `scripts/package.json` only when that file is absent, otherwise retain the compatible manifest. Any other module source or incompatible manifest retains every gate asset and reports each blocking path for an operator decision. In the safe case, the `scripts/verify.sh` skeleton is written **only when step 1's verify answer names it**. The runner resolves the command it launches from `commands.verify` — `harness.yaml` first, then `AGENTS.md`, `CLAUDE.md`, and legacy `CONTEXT.md` for a repo that has not migrated, and the historical `bash scripts/verify.sh` only when none of them exists — so a skeleton the spine does not declare is a file nothing ever executes. Where the answer names it, write a minimal skeleton whose public path is `exec node scripts/gate-marker.js run` and whose internal `HARNESS_GATE_MARKER_RUNNER=1` path runs `node scripts/gate-marker.js preflight` and then the interview's lint/typecheck/test commands in order. Where it names anything else, write no skeleton: that declared command is the gate the runner measures, so report that no skeleton was written and tell the operator that the nested-worktree preflight belongs at the head of *that* command. Either way the runner emits evidence only after the command it resolved from the spine exits successfully; never add a direct marker-write command. A repo with its own gate keeps its commands until `--refresh` classifies its wiring as managed.
9. **Report** what was written, what was skipped because it existed, and the one next step: file or pick a ticket and `/build` it.

Hooks need no per-repo wiring — the plugin's `hooks/hooks.json` registers them at install. The spine's `branches:` block is what the push and stop guards read; that is why step 1's answers land there.

## `--refresh` — after a plugin update

Make a **plan before any write**. Classify each candidate and report every result as `path | classification | action | reason`. The plan may change only the existing generated spine, Codex-adapter, and gate-ignore sets plus these gate paths: `scripts/gate_marker.py`, `scripts/gate-marker.js`, `scripts/harness-config.js`, `scripts/package.json`, and `scripts/verify.sh`. Everything else is consumer-owned.

1. **Migrate the configuration first, as a move.** Where the repo has no `harness.yaml` and its spine still carries a fenced `yaml` block, take that block **verbatim** — byte for byte, comments, blank lines, key order and all — and write it as `harness.yaml`, then replace the fence in the spine with a one-line pointer to it. Do not translate, reformat, normalise, or drop a key the plugin does not itself read: a repo declares more than the plugin reads (`tracker_address`, `conventions`, `tools`, an `architecture_watchlist` nesting a list of mappings), and a *move* cannot lose one where a rewrite can. Report the key-by-key diff of the block before and after, and stop on any difference. Where both files exist, `harness.yaml` already wins at the reader and the fenced block is stale — report it rather than merging.
2. Replace the content between `<!-- spine:generated:begin … -->` and `<!-- spine:generated:end -->` in `AGENTS.md`, touching nothing outside the markers. Where a repo hydrated before #537 has the block in `CLAUDE.md` too, refresh that one and offer to reduce it to `@AGENTS.md`; never do it unasked, because the tail of that file is repo-owned. Refresh generated `.codex/agents/*.toml` role adapters by step 7's ownership rule, merge the gate-ignore block into `.gitignore`, and report the version stamped in the new markers. A missing spine marker, adapter collision, or host-file conflict is retained and reported; do not guess.
3. Classify the flat Node context before touching its assets. It is safe only when every immediate module-bearing source (`*.js`, `*.mjs`, `*.cjs`, `*.ts`, `*.mts`, `*.cts`) is the recognised managed helper and `scripts/package.json` is absent or declares `"type": "commonjs"`; the absence of `*.js` is not consent. In that safe context, materialize the plugin's current `scripts/gate-marker.js` and `scripts/harness-config.js` when each is absent or byte-identical to a released Harness helper; retain and report a different helper as consumer-owned, and retaining the marker helper retains the reader with it. Add the plugin's `scripts/package.json` only when absent and otherwise retain the compatible manifest. Any other module source or incompatible manifest retains every gate asset and reports each blocking path.
4. Only when step 3 classified the Node context as safe, classify `scripts/verify.sh` without interpreting arbitrary shell. Match the **invocation shape**, not a literal command string: a recognised invocation is any prefix of literal words — the interpreter and the options it is given — immediately followed by `scripts/gate_marker.py preflight` or `scripts/gate-marker.js preflight` as that command's last two words, and a managed pair is one of those with a `write` counterpart naming the same helper in the same shape. The command may sit inside a larger shell construct — a conditional, an `&&` or `||` chain, a trailing `; then` — and the shell keywords, operators and terminators that delimit it are outside the command and not part of its prefix, so `if ! uv run --extra dev python scripts/gate_marker.py preflight; then` pairs with a bare `uv run --extra dev python scripts/gate_marker.py write`; the same shape compares the two prefixes, not the constructs they sit in. A construct that names the command for a later invocation is not one of those: a function body and a sourced file both leave the caller as the thing that reaches the helper, and that caller is consumer-owned. `uv run --extra dev python` and `python3` are both such prefixes; the prefix is the part a consumer adapts to its own toolchain, so it is not enumerated. A prefix is literal only when every word of it is a plain word: a variable expansion, a command substitution, or a quoted string anywhere in it disqualifies it, being part of a pipeline or carrying a redirection disqualifies the command whatever its prefix, and so does reaching the helper through a shell function or a wrapper script. For a managed pair, preserve its internal gate stages and replace its public wiring with `exec node scripts/gate-marker.js run`; the runner owns preflight and marker emission. A file already using that `exec` line is retained as migrated and is not classified further. Any other invocation, missing counterpart, or custom wrapper is consumer-owned: retain it and report `scripts/verify.sh | custom wiring | retained | <the unmatched invocation or pair>`. In an unsafe context, retain `scripts/verify.sh` and report the exact blocking path from step 3; its legacy Python invocation remains for step 5's tracked-reference sweep.
5. Classify `scripts/gate_marker.py` by its complete SHA-256 content only. The two managed legacy hashes are `f40ca8ee62a2830fa693b09ac52b4391c34e29808e69326f859716fee242f8b5` and `e7c9ae8ffaad9f9ac92d3ffb53cdebed8af2e12a8d49ad03220ff33ef883d49d`. For either match, sweep tracked files for every `gate_marker.py` invocation after the verify plan has been applied. Delete the helper only when the sweep is empty; otherwise retain it and report each tracked reference. A different hash is consumer-owned and remains untouched.

Do not write `node scripts/gate-marker.js write`, a direct marker-write command, or a parser/runtime to perform this plan. The Claude provenance declaration survives untouched — it lives in `.claude/settings.json`, which `--refresh` never writes; where it is absent, report that and offer to write it. The first downstream adoption performs the attended end-to-end QA for this guidance.

## What this never does

No tracker writes, no commits, no pushes — hydration is working-tree only, and the operator reviews and commits the result. It never overwrites a repo-owned section, never edits between another plugin's markers, and never touches an existing gate beyond reporting that it kept it.
