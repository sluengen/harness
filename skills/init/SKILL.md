# /harness:init — hydrate a repo

Usage: `/harness:init` (first-time setup) · `/harness:init --refresh` (after a plugin update)

Turns a repository into one this process can run in. The native plugin carries
the skills, role procedures, and hooks; this workflow writes the files that must
be **repo-owned**: `harness.yaml`, the spine (`AGENTS.md`) and the `CLAUDE.md`
derived from it, the path-scoped rules, the Codex role adapters, the specs scaffold, the
infrastructure record, and the gate's ignore rule. In Claude Code, always
invoke it with its plugin prefix because bare `/init` is the host's own command.
In Codex, ask to initialize Harness; it reads the same `init` workflow from `skills/`.

## First-time setup

1. **Interview for the repo values.** From the repo itself where possible (language, test runner, existing branch names), from the operator where not: name, tracker backend and its addresses, stack, the five commands (install / lint / typecheck / test / verify), branch roles, and layer switches. The verify command is the one that matters most — it is the single command that decides green, and the hooks enforce against its marker. Record the answer exactly: `node scripts/gate-marker.js run` resolves the command it launches out of `harness.yaml`'s `commands.verify`, so this answer *is* the gate, whether it names a shell script, `npm run verify`, `make verify`, or `cargo test`.
2. **Write `harness.yaml`** from `templates/harness.yaml`, filled from the interview. This is the repo's configuration and the only place it is written: the hooks, the gate marker helper, and the skills all read it through `scripts/harness-config.js`. Never restate one of its values in prose — a value in two places is a value that disagrees with itself.
3. **Write the spine** — `AGENTS.md` from `templates/spine.md`: the generated block, with the repo section filled from the interview and no configuration in it. Merge an existing file: insert the generated block above its existing content, which remains repo-owned; do not discard the host's existing instructions. Then write `CLAUDE.md` as **the whole of `AGENTS.md`, byte for byte**, followed by any Claude-specific deltas. The bytes sit in the file the host loads, so the spine arrives without an `@`-import resolution step the repo does not control. `AGENTS.md` stays the source and the file Codex reads; `CLAUDE.md` is derived from it, never the reverse — edit the source and re-derive. Keeping the two equal is this repo's obligation: `--refresh` re-derives the copy, and nothing else does. The plugin ships no guard for it — a repo that wants drift caught adds the comparison to its own gate, which is the one place that can fail a landing. Nothing else is restated: everything after the copy is the host deltas alone. `templates/spine.md` carries no configuration, so a fresh hydration's copy declares none. Both hosts read `AGENTS.md`, so one clone is usable from either without a second hydration.
4. **Seed the path-scoped rules.** Guidance that only matters in one part of the tree goes to `.claude/rules/<name>.md` with a `paths:` frontmatter of globs, not into the spine. Claude Code loads such a file only while working on a matching file, so it costs nothing on every other task and cannot fail to fire on the tasks it covers — where guidance that has to be *triggered* by description can. Seed one for the design layer when `layers.design_system` is on: copy `templates/rules/design-system.md` to `.claude/rules/design-system.md`, replacing its two placeholder globs with the design directory from `harness.yaml` plus the repo's UI source paths (ask once, and record the answer in the yaml). **Two bounds.** A rule is repo-owned once seeded: `--refresh` never overwrites it. And nothing that must be in force on *every* task belongs here — a scoped file is narrower than the spine, not a cheaper spine. Codex has no path-scoped rules, so seed the same rule as `AGENTS.md` inside the design directory, which Codex reads nearest-wins. **The shared region is everything from the first `##` heading down, and it is identical in both.** What differs is the preamble above it: the Claude form carries the `paths:` frontmatter and says it loads on those globs, while the Codex form carries neither, because its location is what scopes it. Say so in each preamble, so a later editor knows which half is shared. Report both paths written.
5. **Scaffold the memory** — `specs/proposals/`, `specs/features/`, `specs/decisions/` (per the `paths:` just written), each with a `.gitkeep` where empty.
6. **Seed the infrastructure record** — `specs/infrastructure.md` from `templates/infrastructure.md`, with the branch topology from the interview as its first entry — this is the repo-owned *what*, and `/promote` is the *how*.
7. **Declare where the plugin comes from.** Claude Code writes the *enablement* — `enabledPlugins: {"harness@harness": true}` — into whichever settings scope the install chose; at project scope that is the repo's own `.claude/settings.json`, the file shared with the team. Its marketplace is registered per machine, so a fresh clone can resolve the enablement to nothing. Merge the provenance into the same file, next to the enablement:

   ```json
   "extraKnownMarketplaces": {
     "harness": { "source": { "source": "github", "repo": "sluengen/harness" } }
   }
   ```

   Merge the key into an existing settings file rather than rewriting it, and leave the rest of the file byte-for-byte alone. Write both install routes into the spine's repo section: Claude Code uses `/plugin marketplace add sluengen/harness` then `/plugin install harness@harness`; Codex uses `codex plugin marketplace add sluengen/harness` then `codex plugin add harness@harness`. Codex marketplace registration is machine-local, so the committed spine is its provenance record and recovery instruction.

8. **Hydrate Codex role adapters** — copy the plugin's `.codex/agents/*.toml`
   into the repo's `.codex/agents/`. These repo-owned files are the Codex host
   adapters for named-agent workflows, and each mirrors the role in the plugin's
   `agents/<name>.md`. Replace a file only when its first line marks it as one of
   the plugin's own — either `# Codex's native adapter for the role in` (what the
   plugin writes now) or the legacy `# Generated by scripts/generate_codex_artifacts.py`
   (what a repo hydrated before that generator was retired still carries, and
   which must keep migrating). Anything else is a consumer's own file: report the
   collision and leave it untouched.

   Two markers rather than one because the plugin **changed its own marker**, and
   a rule keyed only on the current one silently stops firing for every repo
   hydrated under the old one — a collision reported forever, for a file the
   plugin wrote. Whenever this marker changes again, the previous spelling joins
   this list; it is never replaced.
9. **Gate plumbing** — merge every pattern in this machine-identifiable block into `.gitignore`, appending only those absent so the operation is idempotent:

   <!-- harness:gate-ignore:begin -->
   ```gitignore
   .evidence/
   .worktrees/
   .claude/worktrees/
   .harness/
   ```
   <!-- harness:gate-ignore:end -->

   First make a **plan before any write**. The gate assets are managed only at `scripts/gate-marker.js`, `scripts/harness-config.js`, `scripts/package.json`, and a newly created `scripts/verify.sh`; do not place them elsewhere. The first two are a **pair** — the marker helper resolves the repo's declared gate command through the reader beside it, and a half-materialized install fails loudly at the preflight rather than running an undeclared command — so copy both or neither. Flat placement is safe only when every immediate module-bearing source (`*.js`, `*.mjs`, `*.cjs`, `*.ts`, `*.mts`, `*.cts`) is the recognised managed helper and `scripts/package.json` is absent or declares CommonJS. The absence of `*.js` does not establish consent. Copy `scripts/gate-marker.js` and `scripts/harness-config.js` only when absent; an existing non-Harness helper is retained and reported, and retaining either retains both. Write the plugin's `scripts/package.json` only when that file is absent, otherwise retain the compatible manifest. Any other module source or incompatible manifest retains every gate asset and reports each blocking path for an operator decision. In the safe case, the `scripts/verify.sh` skeleton is written **only when step 1's verify answer names it**. The runner resolves the command it launches from `commands.verify` — `harness.yaml` first, then `AGENTS.md`, `CLAUDE.md`, and legacy `CONTEXT.md` for a repo that has not migrated, and the historical `bash scripts/verify.sh` only when none of them exists — so a skeleton the spine does not declare is a file nothing ever executes. Where the answer names it, write a minimal skeleton whose public path is `exec node scripts/gate-marker.js run` and whose internal `HARNESS_GATE_MARKER_RUNNER=1` path runs `node scripts/gate-marker.js preflight` and then the interview's lint/typecheck/test commands in order. Where it names anything else, write no skeleton: that declared command is the gate the runner measures, so report that no skeleton was written and tell the operator that the nested-worktree preflight belongs at the head of *that* command. Either way the runner emits evidence only after the command it resolved from the spine exits successfully; never add a direct marker-write command. A repo with its own gate keeps its commands until `--refresh` classifies its wiring as managed.
10. **Report** what was written, what was skipped because it existed, and the one next step: file or pick a ticket and `/build` it.

Hooks need no per-repo wiring — the plugin's `hooks/hooks.json` registers them at install. `harness.yaml`'s `branches:` block is what the push and stop guards read, through `scripts/harness-config.js`; that is why step 1's answers land there and not in the spine.

## `--refresh` — after a plugin update

Make a **plan before any write**. Classify each candidate and report every result as `path | classification | action | reason`. The plan may change only the existing generated spine, the `CLAUDE.md` derived from it, Codex-adapter, and gate-ignore sets plus these gate paths: `scripts/gate_marker.py`, `scripts/gate-marker.js`, `scripts/harness-config.js`, `scripts/package.json`, and `scripts/verify.sh`. Everything else is consumer-owned.

1. **Migrate the configuration first, as a move.** Where the repo has no `harness.yaml` and its spine still carries a fenced `yaml` block, take that block **verbatim** — byte for byte, comments, blank lines, key order and all — and write it as `harness.yaml`, then replace the fence in the spine with a one-line pointer to it. Do not translate, reformat, normalise, or drop a key the plugin does not itself read: a repo declares more than the plugin reads (`tracker_address`, `conventions`, `tools`, an `architecture_watchlist` nesting a list of mappings), and a *move* cannot lose one where a rewrite can. Report the key-by-key diff of the block before and after, and stop on any difference. Where both files exist, `harness.yaml` already wins at the reader and the fenced block is stale — report it rather than merging.
2. Replace the content between `<!-- spine:generated:begin … -->` and `<!-- spine:generated:end -->` in `AGENTS.md`, touching nothing outside the markers. Then **derive `CLAUDE.md`** by the ordered procedure below — whose first instruction runs *before* the replacement just described, so read the whole procedure before performing either. Where that procedure writes a derived file, the repo-owned tail is preserved byte for byte. Refresh generated `.codex/agents/*.toml` role adapters by step 8's ownership rule, merge the gate-ignore block into `.gitignore`, and report the version stamped in the new markers. A missing spine marker, adapter collision, or host-file conflict is retained and reported; do not guess.

   **Deriving `CLAUDE.md`.** The order is the mechanism, not a presentation choice, and it runs *inside* this step rather than after it.

   **`A_old` is the boundary key.** Read `AGENTS.md` as it stands **after step 1 and before the generated block is replaced**, and call that text `A_old`. It is what locates the boundary between the copy and the repo-owned deltas; capture it after the block is replaced and the boundary is unfindable for every repo by construction. Because step 1 may itself rewrite `AGENTS.md` (the fence becomes a pointer line), `A_old` is read after that rewrite and before this one — the two are different edits and only the second is "the block".

   **Classify before writing.** Decide `CLAUDE.md`'s state against `A_old` as a plan row, before any write, and test the states **in this order**. The order is load-bearing in one place, and it is the one that matters: every correctly derived copy now contains a `spine:generated` marker pair — copied from the spine — so a marker-bearing file must be tested against states 2 and 3 before it is offered to state 4, or every derived file in existence is misread as a legacy spine. (States 1 and 2 are disjoint and their relative order is free; nothing rests on it.)

   1. **pointer** — the first non-empty line, stripped, is `@AGENTS.md` (or `@./AGENTS.md`). The deltas are everything from the first byte of the **following** line on: the pointer line's own terminating newline belongs to the pointer line, not to the deltas. **Expand without asking.** The pointer shape is no longer the target, so there is nothing to offer.
   2. **expanded** — the file begins with `A_old`, byte for byte. The deltas are everything from `len(A_old)` on. Re-derive against the refreshed spine.
   3. **drifted copy** — it is not byte-exactly prefixed by `A_old`, but it carries a `spine:generated` marker pair *and* its first line is equal to `A_old`'s first line. Something edited one side without the other: a hand edit inside the copy, an edit inside the generated block itself, or an edit to the spine's own repo-owned tail between refreshes. **Retain it untouched and report**, naming the 0-based byte offset at which it first differs from `A_old`, and telling the operator to re-derive by hand — the whole of `AGENTS.md` followed by the deltas, which only they can now delimit. Never rewrite it. The differing bytes may be plugin-owned or repo-owned and the refresh cannot tell which side is the intended one; worse, once the prefix no longer matches, the boundary this operation uses to find the deltas is gone, so any rewrite would be guessing where the repo's own content begins.
   4. **legacy second spine** — it carries its own `spine:generated` marker pair and matches none of the above. This is a repo hydrated before #537, whose `CLAUDE.md` was always its own spine rather than a copy. Refresh **its own marker pair and the content between them** from the plugin's current spine — markers included, so the version it stamps is not a lie — touching nothing else in the file. Report that it is not a derived copy, and that converting it by hand means replacing everything from the top of the file through its end marker with the whole of `AGENTS.md`, keeping the deltas below.
   5. **boundary unfindable** — anything else. Retain it untouched and report. Never guess where the deltas begin. One residue to name in the report rather than resolve: a derived copy whose drift falls in its *first* line — a consumer retitling the spine preamble, which is repo-owned after hydration — fails state 3's first-line test and lands here, so it is reported as not a derived copy when it is one. Nothing repo-authored is lost (this state writes nothing), but the operator is told the wrong thing about the file and should compare it against `AGENTS.md` by hand.

   States 3 and 4 both cover a marker-bearing file, and 3 is tested first deliberately. Misrouting a true legacy spine into 3 costs one stale block, reported on every run; misrouting a drifted copy into 4 silently destroys repo-authored bytes. The asymmetry decides the order.

   Absent `CLAUDE.md` is its own case, not a sub-case of state 5: create it, derived, and report that it was created. A file that does not exist has no repo-owned bytes to lose, which is why creating it is safe where rewriting state 3 is not.

   **The write.** `CLAUDE.md := AGENTS.md + deltas`, where `AGENTS.md` is the **whole refreshed file** — every byte of it, the repo-owned content outside the markers included, not the generated block alone. Rewrite `AGENTS.md` first, then write `CLAUDE.md` from it, so the copy is never taken from a spine that is about to change. A single newline is inserted only where the deltas do not already begin with one; the deltas are otherwise preserved byte for byte, never reflowed, normalised or deduplicated. That preservation is the guarantee in states 1 and 2, the only states with a defined tail: states 3 and 5 write nothing, and state 4 edits its own marker region in place rather than producing a file from this formula. The `AGENTS.md` block is replaced in every state, including those that write no `CLAUDE.md`. The result is idempotent: a second run classifies its own output as *expanded* and inserts no second separator.

   Because the copy is the whole file, a consuming repo's own spine tail is present in both `AGENTS.md` and `CLAUDE.md`. That duplication is the point — the bytes have to sit in the file the host loads — and it is the one place this operation writes content it did not author.

   Where the deltas are empty or whitespace-only, write the copy, then one blank line, then exactly:

   ```
   # Claude Code deltas

   This host has no deltas yet.
   ```

   and report it. The copy alone is refused by the gate, and a written-out heading keeps the boundary findable next run — the bytes an executor improvises here become permanent repo-owned content, so they are specified rather than left to judgment.

   **One refusal.** Where `AGENTS.md` still carries a fenced `yaml` configuration block after step 1 — a fence declaring the keys `harness.yaml` holds, not any yaml sample — **do not expand or create**. Report a row whose classification field names the state actually determined above and whose reason names the fence, for example `CLAUDE.md | pointer, spine carries a fenced configuration block | retained | migrate the configuration to harness.yaml first — the copy would be a second declaration scripts/harness-config.js reads`; substitute the state you determined, since this refusal turns on a property of `AGENTS.md` and can fire whichever state `CLAUDE.md` is in. The copy would duplicate a declaration the hooks and the gate command resolve through that reader, and stripping it here would be this step rewriting repo-owned configuration. Only the derivation is refused: the generated block in `AGENTS.md` is still refreshed, and nothing else in the refresh is blocked.
3. Classify the flat Node context before touching its assets. It is safe only when every immediate module-bearing source (`*.js`, `*.mjs`, `*.cjs`, `*.ts`, `*.mts`, `*.cts`) is the recognised managed helper and `scripts/package.json` is absent or declares `"type": "commonjs"`; the absence of `*.js` is not consent. In that safe context, materialize the plugin's current `scripts/gate-marker.js` and `scripts/harness-config.js` when each is absent or byte-identical to a released Harness helper; retain and report a different helper as consumer-owned, and retaining the marker helper retains the reader with it. Add the plugin's `scripts/package.json` only when absent and otherwise retain the compatible manifest. Any other module source or incompatible manifest retains every gate asset and reports each blocking path.
4. Only when step 3 classified the Node context as safe, classify `scripts/verify.sh` without interpreting arbitrary shell. Match the **invocation shape**, not a literal command string: a recognised invocation is any prefix of literal words — the interpreter and the options it is given — immediately followed by `scripts/gate_marker.py preflight` or `scripts/gate-marker.js preflight` as that command's last two words, and a managed pair is one of those with a `write` counterpart naming the same helper in the same shape. The command may sit inside a larger shell construct — a conditional, an `&&` or `||` chain, a trailing `; then` — and the shell keywords, operators and terminators that delimit it are outside the command and not part of its prefix, so `if ! uv run --extra dev python scripts/gate_marker.py preflight; then` pairs with a bare `uv run --extra dev python scripts/gate_marker.py write`; the same shape compares the two prefixes, not the constructs they sit in. A construct that names the command for a later invocation is not one of those: a function body and a sourced file both leave the caller as the thing that reaches the helper, and that caller is consumer-owned. `uv run --extra dev python` and `python3` are both such prefixes; the prefix is the part a consumer adapts to its own toolchain, so it is not enumerated. A prefix is literal only when every word of it is a plain word: a variable expansion, a command substitution, or a quoted string anywhere in it disqualifies it, being part of a pipeline or carrying a redirection disqualifies the command whatever its prefix, and so does reaching the helper through a shell function or a wrapper script. For a managed pair, preserve its internal gate stages and replace its public wiring with `exec node scripts/gate-marker.js run`; the runner owns preflight and marker emission. A file already using that `exec` line is retained as migrated and is not classified further. Any other invocation, missing counterpart, or custom wrapper is consumer-owned: retain it and report `scripts/verify.sh | custom wiring | retained | <the unmatched invocation or pair>`. In an unsafe context, retain `scripts/verify.sh` and report the exact blocking path from step 3; its legacy Python invocation remains for step 5's tracked-reference sweep.
5. Classify `scripts/gate_marker.py` by its complete SHA-256 content only. The two managed legacy hashes are `f40ca8ee62a2830fa693b09ac52b4391c34e29808e69326f859716fee242f8b5` and `e7c9ae8ffaad9f9ac92d3ffb53cdebed8af2e12a8d49ad03220ff33ef883d49d`. For either match, sweep tracked files for every `gate_marker.py` invocation after the verify plan has been applied. Delete the helper only when the sweep is empty; otherwise retain it and report each tracked reference. A different hash is consumer-owned and remains untouched.

Do not write `node scripts/gate-marker.js write`, a direct marker-write command, or a parser/runtime to perform this plan. The Claude provenance declaration survives untouched — it lives in `.claude/settings.json`, which `--refresh` never writes; where it is absent, report that and offer to write it. The first downstream adoption performs the attended end-to-end QA for this guidance.

## What this never does

No tracker writes, no commits, no pushes — hydration is working-tree only, and the operator reviews and commits the result. It never overwrites a repo-owned section, never edits between another plugin's markers, and never touches an existing gate beyond reporting that it kept it.
