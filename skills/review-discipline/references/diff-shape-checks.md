# Diff-shape checks

Load only when the diff matches one of these shapes. These checks extend the
core Stage 2 bar; pre-existing violations in untouched files are not findings.

### Stage 2 — Diff-shape checks

**For code:**

- **Type predicate coverage** — for every user-defined type predicate (`value is T`), enumerate `T`'s required fields and confirm the guard checks each one. A predicate that validates a subset is a false assurance at the boundary it was added to protect — flag it as a defect, not a nit.
- **Security** — input validated at the boundary, no injection-prone string building, no dangerous eval/exec on input, no secrets in code, paths sanitised.
- **Principles** — does the change violate a named `engineering` tenet? Cite the principle, not a preference.
- **Structure** — size, layer boundaries, rule-of-three duplication, composition. Apply the `engineering` → *Structure* thresholds. Pre-existing violations in untouched files are not findings; only flag if this change makes them worse.
- **Dead surface after a deletion** — when a change retires a subsystem but keeps its module as a re-homed helper, each remaining public function needs a *production* caller, not just a test. Grep each one across the source tree, excluding its own module and tests (`grep -rn <fn> <src>/ | grep -v <its-module>`); one reached only by its own unit test is dead surface masquerading as a helper, its passing test hiding the rot rather than justifying it. Delete it with its tests.
- **Port-time orphan** — when a change *lifts a module from another repo*, confirm production code in **this** repo imports it before the lift lands. Grep the source tree for an importer, excluding the module itself and tests (`grep -rn <module> <src>/ | grep -v <its-own-path>`); a lifted module reached only by its own tests, or by nothing, is dead on arrival — a class no later per-change reviewer will catch, because no future change touches the orphan. Wire it to a production caller in the same change or leave it out.
- **Misplaced pure helper** — in a repo whose CONTEXT designates a home for testable client logic (e.g. a `lib/` directory under a coverage ratchet), a *pure* function — no hooks, no JSX/render — declared inline inside a view or screen file, that a **second** view also needs, belongs in that home before approval, not copied screen-to-screen. The class hides per-change because each ticket touches one screen, so catch it at the moment of reuse: when this change adds or copies an inline pure helper a sibling screen already declares, move it to the designated `lib/` (under its ratchet) as part of this change. Grep the source for a sibling declaration before approving (`grep -rn <fn> <src>/ | grep -v <its-screen>`); the same pure helper declared in two screens is the signal.
- **Cloned backend module helper** — Misplaced pure helper's sibling on the backend: when this change adds a new backend module (e.g. a per-feature directory shipping its own input-validation, service, or type file), grep the function and type names it declares against the equivalent files in the other modules beside it (`grep -rn <name> <modules-root>/*/<file> | grep -v <this-module>`). A name that already exists in a sibling module with a matching signature is a clone, not a coincidence — it belongs in the repo's shared home for that kind of logic (e.g. a common `lib/` or `db/` file) before approval, not copied module-to-module. The class hides per-change exactly like its frontend sibling: each ticket introduces one module, so no single reviewer ever sees the third strike.
- **Placeholder/stub reachability** — a function that returns hardcoded/faked/placeholder data in place of real logic (an OCR/share/scan stub, a `TODO: replace` body) must not be reachable from a user-facing control unless gated behind an off-by-default feature flag (`engineering` → *Scope*, placeholder and stub gating). A stub wired to a live, ungated control ships a CTA whose implementation is a constant — report it as a **blocking** finding; the fix is to wire the flag or remove the control.
- **"Mirrors/duplicates" admission comment** — a pure helper carrying a comment that it *mirrors*, *duplicates*, or must be *kept in sync with* a sibling is an explicit admission of duplication (`engineering` → *Structure*, "Extract on the third strike"): the author named the original, so the rule-of-three count no longer applies. Report an unextracted helper that carries such a comment as a **non-blocking** structural finding — the same call as the same logic in 3+ places — regardless of how small each copy is; the admission is the trigger, not the size. The fix is to extract it to its shared home in this change.
- **Partial hook/utility adoption** — when this change adds a data-fetching or write-then-refetch flow, check whether the repo's shared hook or utility built to replace a hand-rolled pattern (a `useResource`/`useRefusal`-shaped hook, a validator, a fetch wrapper) already covers the shape, whether or not it is imported at all: a call site that imports the hook and destructures only part of its contract — not reimplementing the rest by hand beside it — is a partial adoption; a call site that hand-rolls the same load/save/refusal/pending sequence without importing the hook at all is the same defect one step further. Grep the hook's other call sites and compare which fields of its return value each one destructures: check sibling call sites for the same hook to see which fields they use that this one does not, or whether a sibling screen with the same shape uses the hook at all.
- **Architecture watchlist** — in a repo whose `CLAUDE.md` declares an `architecture_watchlist`, compare the **actual diff** against `architecture_watchlist.files` (`git diff --name-only <integration-branch>...HEAD`, the integration branch from `CLAUDE.md` `branches.integration`; fall back to the working-tree diff when it is unknown — the mechanism is in `architecture` → *Architecture watchlist*). When the diff touches a watchlisted gravity-well file and *adds* inline state, orchestration, branching, or repeated rendering to it, the change must carry a `Watchlist trigger` outcome — a small behavior-preserving seam extraction, or a recorded deferral with a reason. A watchlisted file grown this way with **neither** recorded is a **non-blocking** structural finding: the gravity well got heavier and nothing was decided. When the recorded outcome is a *seam extraction*, also confirm the matching `architecture_watchlist.files` entry's own descriptive comment still names the file's current decomposition — the modules carved out beside it — and its current size state. An entry left describing the decomposition the extraction just replaced folds into the **same non-blocking finding**: that comment is the record read at the *next* touch, so a stale one mis-primes the builder who inherits the gravity well, and no future change re-touches the gap. Refresh it in this change, and describe the state rather than a line count — a number is accurate only on the day it is written. The same extraction also owes an answer about its tests: confirm the extracted module's tests moved with it — into a test module of their own, or stayed for a stated reason. Tests left behind with no reason stated fold into that **same non-blocking finding**: the extraction parted production structure from test structure, and the reviewer reading that diff is the only one looking at both halves. A repo with no `architecture_watchlist` skips this check (it is a no-op).
- **CLAUDE.md currency** — when a diff **adds or removes** a test runner, a gate step, a workspace, or a top-level path, confirm `CLAUDE.md`'s `stack` / `commands` / `layers` block names it correctly. A stale entry there is a **non-blocking** finding, because `CLAUDE.md` is the first file the next agent reads, so it mis-primes every later session rather than one review. The trigger is deliberately narrow — these four are the diff shapes that make the file stale, and each is visible in `git diff --name-only` plus the changed config; it is not "read `CLAUDE.md` every time". The class hides per-change because staleness begins at one commit and no future change re-touches the gap, so catch it at the commit that opens it: update the block in this change. The same staleness reaches a step further: when the diff changes CLAUDE.md's `tracker:` field or `branches:` roles, also confirm any repo-level release runbook it maintains (if one exists — a `RELEASING.md`, say) has its release checklist naming the current tracker and promotion path — a config correction that stops one commit short of its dependent doc is the same class of gap, just one hop downstream. When the diff edits an as-built record — a feature spec, `SPEC.md`, or a design-system layer doc — confirm its `last_updated` frontmatter moved to the date of this change. A record edited without its stamp moving folds into the same **non-blocking** finding.
