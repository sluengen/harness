## [Unreleased]

### Added — `review` requires recorded verify-gate evidence (CAL-1082)
- **The gate the verb loop never ran.** `close` checked three things — a run exists, the worktree is clean, a `verdict='pass'` is bound to HEAD — and **none of them was evidence that a test ever ran**. The only instruction to run the gate was prose addressed to a model (`commands/harness.md`: "Run the repo's verify gate locally as you go"), enforced by nothing. So a `pass` from a reviewer that merely *read the diff* was byte-identical in the ledger to one backed by a green suite. `verify` appeared **zero times** in `specs/features/verb-model.md`: the loop had no gate step at all.
- **Evidence, not execution — the harness stays a scaffold.** The first build of this ticket had `review` *execute* the gate in-container, and proved why it cannot: the image cannot carry every target repo's toolchain. `harness:dev` is built `--no-dev`, so not even this repo's own `ruff` is present (`bash scripts/verify.sh` exits 2 in-container — `Failed to spawn: ruff`); a Node target would need Node; an Xcode target can never run in a Linux container. An executing verb would therefore either bloat the image toward every ecosystem or hand a diff-only `pass` to the repos it could not run — and the harness could never close **its own** tickets. **Decision (Scott, 2026-07-16):** the gate runs where the toolchain lives (the orchestrating session, host-side); the verb enforces and records the evidence. CAL-1084's toolchain path is canceled as superseded.
- **`harness review --gate-exit <code> [--gate-log <path>]`.** The orchestrator runs `CONTEXT.md` → `verify:` in the worktree and hands over the result. Green → the engine runs and the `review` event carries `gate_ran=true`, the resolved `gate_command`, `gate_exit_code`, and a bounded (≤ 2 KB) `gate_output_tail`, all bound to `reviewed_sha`. Non-zero → the verb refuses **before** the engine (exit `5`, `reason=gate_failed`) with the tail on the refusal JSON, records no event, and spends no tokens on a red tree. Gate configured but **no evidence supplied** → exit `5`, `reason=no_gate_evidence`: silence is not a pass. No `verify:` configured → recorded honestly (`gate_ran=false, gate_reason="not_configured"`) and review proceeds — the harness cannot gate what a repo does not define.
- **`close` gains a fail-safe backstop, `no_gate_evidence`.** A pass written by a harness predating this change carries no `gate_ran` key, `json_extract` yields `NULL`, and close reads that as no evidence and refuses — so no ledger migration is needed and an old pass cannot be spent on a merge. This is a **refusal-reason addition**: the verb-contract lock (`test_verb_contract_locked.py`) caught it, and the snapshot was updated deliberately.
- **The evidence is self-reported, and that is deliberate.** It grants no new trust: any process that can write the workspace could already forge a ledger event, so this sits on the ledger's existing filesystem trust boundary rather than moving it. The authoritative control over what merges is server-side branch protection (CAL-1029). What the record buys is that a `pass` now *states* whether a gate ran, so a reader — and `close` — can tell the two apart. The container is also not loosened to run foreign toolchains: **ADR 0002** (CAL-925) weighed and rejected the Docker-socket path, and this design removes the reason to revisit it.
- New module `harness/gate.py`, mirroring `harness/loop_budget.py` — the standing precedent for reading config out of `CONTEXT.md` in its own module. It holds no execution path (pinned by a test). The watchlisted `harness/cli/review.py` grows a call site and three constants, not a subsystem. `commands/harness.md` **0.1.7 → 0.1.8**.
- Also corrected in passing: `specs/features/cli-surface.md`'s "Exit codes are a stable contract" table listed only 0/1/2/130 — omitting `review`'s existing `3` (infra) and `4` (breaker). Adding `5` beside that gap would have implied 3 and 4 were unused, so all three are now listed.
