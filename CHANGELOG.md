### Fixed — the image-freshness guard no longer disables itself silently on a detached copy (CAL-1153)

### Changed — the staging hop direct-pushes on a green gate; the no-auto-merge rule scopes to the release hop (CAL-1158)
- **A release-hop rule was binding both hops, and it foreclosed the automation the ADR exists to enable.** ADR 0003 said "Direct target-branch pushes and auto-merge are out of scope for v1", and the code implemented exactly that. So a nightly `dev → staging` cron would create the promotion branch, gate it, push it, open a PR into staging — **and stop**, waiting for a human to merge a PR with no reviewer and no question to answer. That is not automatic promotion. The ADR's own rationale never reached that far: it justified the rule with "merging the **release** PR stays a deliberate human/CI act", and the release is `staging → main`.
- **The distinction is that staging is *derived* and main is *decided*.** `dev` is unstable integration; `staging` is the nightly stable build derived from green dev, which the harness dogfoods; `main` is what other repos consume. Nothing is judged at the staging hop — the gate **is** the decision — so `promote pr` now advances `staging` to the gated SHA and opens no PR. `main` stays PR-only and remains the single human decision point. Auto-merge stays out of scope, and CAL-1140's `gh pr merge` deny stays as-is.
- **The new authority is bounded three ways, structurally.** It fires only on a green gate (a red gate never reaches `pr_ready`, so it cannot publish); it moves **exactly one ref**, via an explicit `<gated_sha>:refs/heads/<target>` refspec that pushes precisely the commit the gate covered rather than whatever a branch tip has since become; and the eligible target is an allowlist of `staging` alone (`DIRECT_PUSH_TARGET`), so `push_target_branch` refuses `main` with `direct_push_refused` **before any git runs** — a property of the code, not a convention a caller can quietly break. A test attempts the `main` push and asserts nothing reaches git.
- **New terminal state `promoted`.** The two hops finish differently: the staging hop is *done*, while `pr_opened` still waits on a human. Recording `pr_opened` for a promotion that opened no PR would be a false entry in the audit trail the ledger exists to keep honest, so the successes stay distinct. Additive — no existing state changes meaning.
- **Rejected: PR + auto-merge on the staging hop.** It would need `gh pr merge` un-denied, repo auto-merge enabled, and auto-merge permitted through staging's protection — more standing authority and more moving parts, to produce a PR nobody reads.
- **ADR 0003's mechanism wording is fixed too.** "Promotion merges `dev → staging`, runs the gate there" read as a direct merge onto staging while the PR-authority section forbade exactly that — topology-vs-mechanism looseness that misleads precisely the person configuring branch protection. The merge lands on the *candidate*; only a green candidate advances the target.
- Out of scope, deliberately: the cron itself (version the logic, not the schedule), the `staging → main` hop, CAL-1106 (reading the branch model from `CONTEXT.md` — `DIRECT_PUSH_TARGET` is a literal for the same reason `start.py` still hardcodes `dev`), and branch-protection config (CAL-1029, operator-run; staging blocks force-push and deletion with no PR requirement, which is forward-compatible either way).

### Fixed — `close` no longer merges into a base checkout it has not checked, and never hides a failed cleanup (CAL-1151)
- **The reported bug was real; its stated cause was not.** CAL-1151 was filed as *"`close` never aborts the merge it started"*, from a live CAL-1140 run that left `MERGE_HEAD`, a `UU` `CHANGELOG.md`, and five staged files in the main checkout. But `git merge --abort` has sat on the conflict path since CAL-777 (2026-06-18), a month before the incident, and `test_merge_and_push_conflict_refuses_cleanly` has asserted a clean checkout and no `MERGE_HEAD` the whole time — and passes. The abort was called. What was missing was everything around it, which is why the field failure and the green test could coexist.
- **Gap 1 — the base checkout is mutated without ever being validated.** The gate covers the *run worktree* (`dirty_worktree`); `close` then does `checkout` → `fetch` → `ff` → `merge` in the **base checkout**, which no conjunct covers. Git cannot reliably reconstruct uncommitted changes present when a merge began — its own docs call the state "hard to back out of in the case of a conflict" — so a conflict there is precisely the merge whose abort cannot restore what it found. `close` now refuses **before** the first mutation with `reason=dirty_base_checkout` when the base checkout carries uncommitted tracked changes or a merge already in progress. Tracked changes only: an untracked scratch file cannot affect a merge, and counting it would wedge every close, hourly.
- **Gap 2 — the abort's exit code was discarded.** `run_git(repo_root, "merge", "--abort")` ignored its result, so a cleanup that failed reported only the conflict and left the caller to discover the stranded checkout by tripping over it on the next close. The restore is now verified by re-reading `git status`, and any residue it could not clear is reported **alongside** the original conflict reason — never instead of it.
- **Gap 3 — two unrelated failures wore one error message.** A non-zero `git merge` means either *conflicted* (`MERGE_HEAD` present) or *refused to start* (no `MERGE_HEAD` — e.g. a dirty tree), and both were reported as "it conflicts with changes that landed on origin/dev", sending the caller to rebase work that would merge cleanly. The two are now told apart before the abort erases the evidence, and the second reports git's actual refusal.
- **Why this is the fix and not the throwaway-worktree redesign.** The ticket asks whether the merge should happen somewhere other than the main checkout at all — *"a verb that mutates the main checkout to test mergeability is the root of this class of bug"* — and that is right, but it is a different change: it alters where the local base branch advances, which `start` and the routine's pre-flight both read. Deferred to CAL-1154 with the reasoning, per the `architecture_watchlist` trigger this file carries (CAL-1139).
- **The tests drive the real failure, per AC-4.** `test_merge_and_push_refuses_base_checkout_already_mid_merge` reproduces the field symptom exactly — without the fix it raises git's misleading `you need to resolve your current index first`, the same error the live run hit while following close's own prescribed recovery. `test_close_recovery_after_conflict_refusal_succeeds` drives that documented recovery (rebase → re-review → close) end to end through the verb with no manual git. A `reason` is interface, so `dirty_base_checkout` is a deliberate addition to the locked contract in `test_verb_contract_locked.py`.

### Fixed — the wrapper rebuilds a stale `harness:dev` instead of silently running it (CAL-1144)
- **A verb that shipped was invisible to the next unattended tick.** Nothing rebuilt the `harness:dev` image after a merge to `dev` — `docker build` appeared only in docs and a test fixture, `docker/harness-wrapper.sh` never built, and none of `doctor`'s seven checks compared the image against the source. The failure was **silent**, which is what made it expensive: the loop saw only `No such command '<verb>'` and diagnosed missing code. It happened for real with the `defer` verb (CAL-1143, image built a day stale), costing a tick, after which three consecutive ticks each paid a manual `docker image inspect` / `git log` comparison — a hand-check an unattended run should never depend on remembering.
- **Fix: the staleness guard lives in the wrapper**, the one component every verb already goes through. An eighth `doctor` check was the other candidate and is rejected on the same ground the ticket names: `doctor` is not run every tick, so it detects the problem only when someone thinks to look — which *is* the failure mode being fixed.
- **It rebuilds rather than refuses, and that is the design call.** Both satisfy the criteria, but the loop is unattended: a hard error trades a silent stale image for a queue that wedges every hour until a human rebuilds. The rebuild fires only when the source actually moved (once per merge, warm cache), never per invocation — a cold `--no-cache` build costs ~165s. A rebuild that **fails** exits non-zero rather than falling through to the stale image, so the silent failure cannot reappear through the back door.
- **Three details are load-bearing.** The source root resolves from the wrapper's own symlink-resolved path, not `$(pwd)` — the CWD is the *target* repo, frequently not this one. Both clocks normalise to epoch seconds (`docker` and `git` report UTC, the host is UTC+10; `stat -f %SB` prints local time and is a trap). All guard output goes to **stderr**, because stdout carries the verbs' JSON contract that the orchestrating loop parses.
- **The tests execute the wrapper against stubbed `docker`/`git`** rather than grepping its text, because the criteria turn on behaviour a text guard cannot tell apart — stale rebuilds, fresh does not. `test_wrapper_image_staleness.py` pins both, plus the failed-rebuild refusal, the untouched pinned tag, and a one-second-either-side boundary case that would catch a timezone skew the hourly fixtures would miss.

### Added — the advisory `/assess` report commit is sanctioned; `gh pr merge` is denied (CAL-1140)
- **`settings/harness.json` `0.5.0` → `0.6.0`: a seventh `autoMode.allow` clause.** `/assess` steps 3–4 instruct the unattended Quality routine to commit its dated report — plus the `assessments/LOG.md` retention compaction — directly to `dev`, because the report carries nothing reviewable and a PR per run would pile up trivial approvals under a scheduled cadence. The posture never said so: the only dev-push clause is scoped to *"already-reviewed work"*, and an assessment report is committed **unreviewed**, so whether the write was sanctioned at all was ambiguous. This is the fifth instance of the shape CAL-1087/CAL-1108 fixed — guidance instructing a write the posture does not name — and the fix belongs here, where the posture is versioned and distributed, not in guidance degraded to match it.
- **The ambiguity had resolved *permissive*, which argues for the clause rather than against it.** The 2026-07-17 unattended tick pushed a report to `dev` with no denial (`d484116..98c8edc`) — satisfying the ticket's AC-4 demand for proof by an actual unattended commit, not merely a clause being present. But a posture that holds only because the classifier read an ambiguous clause charitably is one re-reading away from an idle arm that silently loses its report every tick. The clause states the intent so nothing has to be inferred.
- **The clause carries its bound, as every clause here must.** The commit may touch **only `assessments/`** — the dated report plus the rolling log — and never code, a spec, or configuration, so it changes no behaviour a review could gate; the retention half never folds away a report with an open finding; force-pushes to `dev` stay blocked; and it explicitly does not widen the reviewed-work-only dev-push clause to code. `test_automode_sanctions_the_advisory_assess_report_commit` pins each bound, not merely the permission — an allowance that lost its rationale would be a wider grant wearing the same name.
- **`Bash(gh pr merge *)` is now denied, discharging CAL-1142 AC-3.** CAL-1142 adopted four of the form repo's five deny rules and deferred this one under an explicit coupling — *"adopt it only in concert with CAL-1140"* — because the `/assess`-report PR fallback (report → branch → `gh pr create` → `gh pr merge`) was the idle arm's only route to landing a report, and the deny would have stranded it. The clause above removes that dependency, so the coupling is discharged and the deny lands: all integration goes through the `close` verb and its HEAD-bound gate, `gh pr merge` being the one route that lands work leaving the runs ledger with no record of it. The tripwire `test_gh_pr_merge_is_deliberately_not_denied_yet` is replaced by `test_gh_pr_merge_is_denied`; the harness deny block now matches the form repo's exactly.

The live stale claim sat in `assessments/2026-07-15-code.md` ("external writes are classifier-blocked"), which retention **keeps** because it carries an open finding, so a future agent could still read it as current policy — the belief that sent three ticks read-only. It now carries a dated correction banner that **annotates rather than rewrites**: the report stands as the record of what that run believed. ### Added — `harness promote start` / `continue` worktree + merge mechanics (CAL-1115)
- **The promotion openers now do real, deterministic git — no outer agent hand-rolls the merge.** CAL-1113/1114 locked the promote surface and read-path; CAL-1115 fills the two write-path openers on top of a new pure mechanics library `harness/promotion.py` (the promotion analogue of `harness/worktree.py`). `promote start` fetches `origin`, validates the `--from` → `--to` pair, creates a promotion worktree/branch **from the target** (`promote/<date>-<from>-to-<to>` based on `origin/<to>`, under `.worktrees/harness/<promotion_id>/` so `worktrees cleanup` reclaims it), attempts `git merge --no-ff origin/<from>`, and records the promotion. ### Fixed — the wrapper joins group 0 so the non-root container can reach the forwarded ssh-agent socket (CAL-1122)
- **The close verb could not push, and it was environmental, not a code regression.** Docker Desktop forwards the host ssh-agent into the container as `srw-rw---- root root`. Since CAL-1008 the image runs `USER harness` (uid 1000) — not root, not in group root — so it cannot `connect()` to the root-owned socket, and every `git push` over SSH (`close`, `checkpoint`) fails `git@github.com: Permission denied (publickey)` on an otherwise healthy host agent. The socket's ownership varies across Docker Desktop restarts, so the same wrapper pushed cleanly earlier the same day and then wedged — stranding a gate-green, review-passed CAL-1104 with no way to merge it.
- **Fix: `--group-add 0` in the ssh-agent forwarding block** of the canonical `~/bin/harness` wrapper (`docker/README.md`). The socket is group-rw, so gid-0 membership makes it reachable regardless of its runtime owner — a durable fix that does not depend on the socket's permissions. It does **not** weaken CAL-1008: `/root` stays mode 700, no mounted credential is group-root, and the only group-0-writable paths in the image are `/tmp`, `/var/tmp`, and `/run/lock`, all already world-writable `1777` (audited: 0 credentials exposed). ### Added — the verbs run tracker-less under `layers.linear: false` (CAL-1104)
- **The schema promised tracker-optionality the engine did not deliver.** `CONTEXT.md` has always advertised `linear: none` / `layers.linear: false`, but every verb hard-required Linear: `start` validated `LINEAR_API_KEY` and fetched the issue before doing anything local, `close` validated the key before any local side effect and transitioned Done, `reclaim` reverted the ticket. There was no code path to open or close a run without a tracker — the single biggest blocker to reuse in a repo not wired to Linear, and the seam a second tracker backend needs.
- **New module `harness/layers.py`**, mirroring `harness/loop_budget.py` and `harness/gate.py` — the standing precedent for reading config out of `CONTEXT.md` in its own module, by regex rather than a YAML dependency. It reads one key and owns no verb logic. It is a *separate* module from `loop_budget` because the concerns are separate: spend breakers are not layers.
- **The block scoping is the whole trick.** `linear:` appears **twice** in a real CONTEXT.md — `repo.linear: CAL` (the team prefix) and `layers.linear: true` (the switch) — and the prefix comes first. An unscoped match reads the prefix and never sees the switch, so a repo that plainly sets `layers.linear: false` would still be told to produce an API key. The reader resolves the `layers:` block before matching, and the mixed-key cases are pinned rather than left to a comment.
- **Layer off:** `start <id>` treats its argument as an **opaque run identifier** — taken verbatim so it still keys the open-run index (the duplicate-start guard holds) and emitted with every tracker-supplied field (`title` / `description` / `url` / `id`) left `None` rather than invented; `--resume` degrades to the clean start it already falls back to, both its sources being tracker comments. `close` skips the Done transition and reports `ticket_done: false` — an honest record of a remote side effect that did not happen, not a success flag. `reclaim` skips the revert and keeps its local half (reconcile the ledger, preserve the branch), which is the half that unblocks a fresh `start`. The `--stale` sweep is a clean **no-op**: staleness keys entirely on the tracker's `updatedAt`, so with no tracker there is nothing to enumerate — and it reports empty rather than failing because the Build routine runs it every tick as a pre-flight, where an error would wedge the loop it exists to unblock.
- **Tracker-less is not gate-less.** `close`'s review gate is untouched and runs *before* the tracker step, so a tracker-less close with no passing review still refuses `no_passing_review`. Turning off the tracker must not weaken the one thing protecting the merge; pinned by a test.
- **The layer defaults on**, and deliberately conservatively: a missing CONTEXT.md, a missing `layers:` block, a missing key, or an unrecognised value all read as on. A repo that has not opted out behaves exactly as before — including failing fast on a missing `LINEAR_API_KEY` — rather than silently degrading into a tracker-less run because a file could not be parsed.
- `review` needed no change: it has no tracker touchpoint today (the ticket's "review's transitions no-op" clause anticipates CAL-1103, which has not landed). `templates/CONTEXT.template.md` **0.1.9 → 0.1.10**: `repo.linear: none` and `layers.linear: false` are now documented as moving together, and the layer line names `layers.linear` as the switch the engine reads — the two fields were previously settable apart, so a repo reading as tracker-less to a human still made the verbs demand a key. The template is pinned against the reader itself, not against a copy of its own words.

### Added — `review` requires recorded verify-gate evidence (CAL-1082)
- **The gate the verb loop never ran.** `close` checked three things — a run exists, the worktree is clean, a `verdict='pass'` is bound to HEAD — and **none of them was evidence that a test ever ran**. The only instruction to run the gate was prose addressed to a model (`commands/harness.md`: "Run the repo's verify gate locally as you go"), enforced by nothing. So a `pass` from a reviewer that merely *read the diff* was byte-identical in the ledger to one backed by a green suite. `verify` appeared **zero times** in `specs/features/verb-model.md`: the loop had no gate step at all.
- **Evidence, not execution — the harness stays a scaffold.** The first build of this ticket had `review` *execute* the gate in-container, and proved why it cannot: the image cannot carry every target repo's toolchain. `harness:dev` is built `--no-dev`, so not even this repo's own `ruff` is present (`bash scripts/verify.sh` exits 2 in-container — `Failed to spawn: ruff`); a Node target would need Node; an Xcode target can never run in a Linux container. An executing verb would therefore either bloat the image toward every ecosystem or hand a diff-only `pass` to the repos it could not run — and the harness could never close **its own** tickets. **Decision (Scott, 2026-07-16):** the gate runs where the toolchain lives (the orchestrating session, host-side); the verb enforces and records the evidence. CAL-1084's toolchain path is canceled as superseded.
- **`harness review --gate-exit <code> [--gate-log <path>]`.** The orchestrator runs `CONTEXT.md` → `verify:` in the worktree and hands over the result. Green → the engine runs and the `review` event carries `gate_ran=true`, the resolved `gate_command`, `gate_exit_code`, and a bounded (≤ 2 KB) `gate_output_tail`, all bound to `reviewed_sha`. Non-zero → the verb refuses **before** the engine (exit `5`, `reason=gate_failed`) with the tail on the refusal JSON, records no event, and spends no tokens on a red tree. Gate configured but **no evidence supplied** → exit `5`, `reason=no_gate_evidence`: silence is not a pass. No `verify:` configured → recorded honestly (`gate_ran=false, gate_reason="not_configured"`) and review proceeds — the harness cannot gate what a repo does not define.
- **`close` gains a fail-safe backstop, `no_gate_evidence`.** A pass written by a harness predating this change carries no `gate_ran` key, `json_extract` yields `NULL`, and close reads that as no evidence and refuses — so no ledger migration is needed and an old pass cannot be spent on a merge. This is a **refusal-reason addition**: the verb-contract lock (`test_verb_contract_locked.py`) caught it, and the snapshot was updated deliberately.
- **The evidence is self-reported, and that is deliberate.** It grants no new trust: any process that can write the workspace could already forge a ledger event, so this sits on the ledger's existing filesystem trust boundary rather than moving it. The authoritative control over what merges is server-side branch protection (CAL-1029). What the record buys is that a `pass` now *states* whether a gate ran, so a reader — and `close` — can tell the two apart. The container is also not loosened to run foreign toolchains: **ADR 0002** (CAL-925) weighed and rejected the Docker-socket path, and this design removes the reason to revisit it.
- New module `harness/gate.py`, mirroring `harness/loop_budget.py` — the standing precedent for reading config out of `CONTEXT.md` in its own module. It holds no execution path (pinned by a test). The watchlisted `harness/cli/review.py` grows a call site and three constants, not a subsystem. `commands/harness.md` **0.1.7 → 0.1.8**.
- Also corrected in passing: `specs/features/cli-surface.md`'s "Exit codes are a stable contract" table listed only 0/1/2/130 — omitting `review`'s existing `3` (infra) and `4` (breaker). Adding `5` beside that gap would have implied 3 and 4 were unused, so all three are now listed.
