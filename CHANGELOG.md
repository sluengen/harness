## [Unreleased]

### Fixed — `harness.close_merge` and `harness.promotion_pr` can be imported first again (#269)
- `harness/cli/_git.py` was a pure leaf — it imports only `harness.branch_config` and `harness.identity`, and has never referenced anything under `harness.cli` — but living *inside* the `harness.cli` package meant importing it forced `harness/cli/__init__.py`, which eagerly imports all fifteen verb modules. Three modules **below** the CLI imported it, so entering the graph through any of them re-entered them mid-initialization: `close_merge` → `cli._git` → `cli.review` → `cli.review_inherit` → `from harness.close_merge import worktree_porcelain`, and the same shape for `promotion_pr` via `cli.promote`. `promotion` survived on ordering luck alone. Both failures were **latent**: a full-suite run imports `harness.cli` first, so `verify.sh` stayed green and only a single-file `pytest tests/unit/test_close_merge.py` ever hit it (it died at collection). Fixed at the root by re-homing the module to `harness/_git.py`, beside `harness/_time.py` — contents byte-identical, only the dotted path moves — rather than by a deferred import, which hides a cycle instead of removing it, or a re-export shim, which would have kept the up-import legal and forced the new guard to exempt the one module it exists for. Two guards, cause and symptom, because neither subsumes the other: an AST scan asserting no module under `harness/` outside `harness/cli/` imports from `harness.cli` (fires on the *edge*, so an up-import that happens not to close a loop is still caught), and a sweep importing every module of the package into a freshly-purged `sys.modules` in one child interpreter (catches a cycle formed wholly inside the CLI package, which the layering rule permits). Both derive their subject rather than enumerating it (#219), and the scan reads AST imports only — a grep would fire on the dozen-plus legitimate docstring cites of CLI internals across `events/`, `state/` and `close_merge.py`. Swept up: two comments in `close.py` and `promotion_pr.py` that justified themselves by this cycle, the latter also claiming a guard test that pins its lazy read — no such test exists. `S603`/`S607` move from the `harness/cli/**` per-file-ignore to an inline `noqa`; the glob stays for `doctor.py` and `worktrees.py`. `tests/unit/test_cli_git.py` → `test_git.py`. 17 new tests; 3 mutations, 3 caught. No registry bump.

### Added — `harness stats`, the aggregate ledger reader (#265)
- Breakdown item 5 of `verb-telemetry` (ADR 0009), and the last — deliberately, so it computes over the honest denominator items 1–4 established rather than one that excludes every refusal. `status`/`logs`/`events`/`runs` are all per-run readers; this is the aggregate one, a new noun over `runs` + `events` reporting per-verb attempts split ok/refused/failed with a success rate, verb and run latency (a **median and a max** — the 600 → 720s `engine_timeout_seconds` decision turned on the right tail a mean hides), review cycles per run, recovery counts, and verdicts by engine. `refused` and `failed` stay distinct and there is **no `failure_rate` field**: folding a correct refusal together with an error is the pressure toward weaker gates ADR 0009 names. **Two discriminators exclude the engine retired in CAL-574 and neither subsumes the other** — `runs.workflow_name` against the new `RETIRED_ENGINE_WORKFLOWS` (a *denylist*: that set is closed, while the verb model's own names grow), and the writable `EVENT_TYPES` allowlist. The run filter is the load-bearing one for `workflow_failed`, a *live* type the retired engine also wrote, where 25 rows of Python exception names would otherwise land in the recovery breakdown. The ticket's floated `worktree_path IS NOT NULL` was measured and **rejected**: it drops the 8 worktree-less `defer`/`release` rows. A verb's outcome key is **not uniform** — `design` splits on `$.status` (ADR 0007 D4 predates the field), `review`/`close` on `$.outcome`, and `review` has only two values, so its exit-5 refusals count as `failed` and its `refused` reads a truthful zero. Durations read `COALESCE(events.duration_ms, json_extract(data_json, '$.duration_ms'))`, the split #264 named. `--since` is resolved by **parsing** each timestamp, not by SQL string comparison: `runs.started_at` carries both the `Z` and `+00:00` spellings in live rows, which compare by byte value rather than by instant. Read-only by construction (`mode=ro`), and the covered window is stated in both output forms. 42 tests; 19 mutations, 19 caught. No registry bump.

### Added — `design` / `checkpoint` / `defer` / `release` record `duration_ms` (#264)
- Breakdown item 4 of `verb-telemetry` (ADR 0009), completing the pass over the live verbs. All four wrote events with a NULL duration: `design`'s latency had to be reconstructed by subtracting `invoked_at` from `designed_at` — the archaeology that raising `engine_timeout_seconds` 600 → 720 required — and `checkpoint` was unmeasurable outright. Each now passes the `duration_ms` keyword `EventEmitter.emit` has always accepted, landing in the ledger's typed **column**, computed by the shared `harness._time.elapsed_ms`. The clock is read **after** run resolution, mirroring `review`/`close`, so a latency never describes an invocation with no run behind it; one reading serves both the payload's terminal stamp and the duration's end. An **adopted** design (ADR 0008 D1) records `NULL`: its `designed_at` is the *source* run's, so subtracting this run's `invoked_at` measures backwards to a negative latency no engine spent — the guard reads `inherited_from`, not the sign, which would also swallow a real clock fault. No `outcome` field: none of the four writes an event on a non-success path, so there are no refusal rows to discriminate against. Residual, named not inherited silently: #262/#263 put theirs in the payload, so item 5 reads `COALESCE(events.duration_ms, json_extract(data_json, '$.duration_ms'))` for those two. No schema, payload or backfill change. 17 new tests. No registry bump.

### Added — `close` records its gate refusals, so the `stale_review` rate is measurable (#263)
- Breakdown item 3 of `verb-telemetry` (ADR 0009). All five gate refusals raised before any ledger write, so the close gate's refusal *rate* was unrecorded — which is why ADR 0010 had to accept a 24-excess-pass **upper bound** for `stale_review` instead of measuring it. The event type stays `close` and a new `outcome` discriminates, with **three** values where `review` had two, and they are the verb's own exit codes named: `ok` (0), `refused` (2 — declined before any side effect), `failed` (1). Keying on the exit code rather than on which `reason` fired means a `reason` added later cannot land on the wrong side of a membership table, because there is no table. Whether the merge **landed** is a separate fact carried by `merged_sha`, set the instant the merge returns and absent on every refusal — so a post-merge ticket failure is never misreported as a blocked close, and #233's "a `close` event means the tracker was confirmed Done" claim stays as narrow as it was, moving from event *existence* to `outcome='ok'`. The non-landed shape is a separate `CloseFailureEventData`: no reader `json_extract`s `merged_sha` today, but it is the only field answering "did this run land?", so loosening it on the success model would leave nothing to catch a success written without it. `no_run` stays unrecorded (`events.run_id` is `NOT NULL` with an FK to `runs`), so the rate is per *resolved-run* attempt — asserted by test so the hole stays deliberate. The never-raises write extracted to `harness/events/observation.py` on its second caller, `review_telemetry` rewired onto it: an observation that swallows in one verb and escapes in the other breaks ADR 0009 unevenly. 21 new tests; 3 existing "no close event" assertions restated as "none that landed". No registry bump.

### Added — `review` records every terminal path, so the ledger has a denominator (#262)
- `review` wrote an event only where a verdict parsed; an engine timeout, a tripped breaker, `no_design`, `no_gate_evidence`, a red gate and the sandbox wall all returned silently, so the ledger held 380 verdicts and no denominator. Per ADR 0009 the event type stays `review` and a new `outcome` field discriminates (`ok` / `failed`), with the refusal shape in a **separate** `ReviewRefusalEventData` — the fields a refusal lacks (`reviewed_sha`, `verdict`, `engine`, `gate_ran`) are exactly the ones the close gate reads, so loosening them on `ReviewEventData` would have re-opened the CAL-1012 hazard. One writer, `harness/cli/review_telemetry.py`, called from a single `except` around the resolved-run body, so a raise site added later is recorded whether or not its author remembers. Three properties are pinned by test: the close gate does not widen (no `verdict` key → `json_extract` NULL), a refusal consumes **no review cycle** (the counter now excludes non-`ok` outcomes as it already excluded `inherited_from` — otherwise collecting the telemetry would have shrunk the budget it measures), and the write never raises. Successes gain `invoked_at`/`duration_ms` via a shared `harness._time.elapsed_ms`, extracted on its second caller after #261's. 18 new tests (11 mutations, 11 caught); 11 existing "no event is recorded" assertions restated as "no *verdict* is recorded". No registry bump.

### Added — `close` stamps `completed_at` + `duration_ms` on the run row (#261)
- Breakdown item 1 of `verb-telemetry` (ADR 0009). Only 7 of 225 closed runs carried a completion timestamp: `cancel`/`reclaim` stamped `completed_at`, the success path never did, so a run's wall-clock was recoverable only by joining `runs.started_at` against the `close` event payload — archaeology for a datum the schema already has columns for. `_mark_run_closed` now sets both inside the **existing** `BEGIN IMMEDIATE` transaction, so the CAL-1002 rule extends verbatim: a rolled-back close leaves the run wholly open, stamps included. `completed_at` is the close event's own timestamp — one clock reading bound twice, not two that drift by the write latency. `duration_ms` floors the `timedelta` against `runs.started_at`, parsed with `parse_iso_z` since `start` writes the `+00:00` shape and the close clock trailing-`Z`. An absent, unparseable or tz-naive `started_at` yields `NULL` rather than raising: by then the merge has landed and the ticket is Done, so a retry would re-read the same bad cell forever. No schema change, no backfill. 6 tests; 8 mutations, 8 caught.

### Changed — one config value now drives both the wall-clock breaker and reclamation staleness, at 110 minutes (#260)
- "The longest a legitimate run may take" was stored twice: `loop.wall_clock_budget_minutes` (read by `review`'s breaker) and a hardcoded `--older-than` default of `"90m"` in `harness/cli/reclaim.py`, which read no config at all. `CONTEXT.md` documented the coupling as a rule for humans — *"if one moves, move both"* — and nothing enforced it. They were never two quantities: the breaker enforces the bound prospectively, reclamation applies it retrospectively, so divergence is a bug rather than a tuning option — a run aged between two values would be spared reclamation **and** refused at review, alive on the board and unable to finish. `--older-than` now defaults to a **sentinel** and resolves the loop budget when omitted (a default built *from* the config would move the literal, not delete it); an explicit value still overrides. Retuned 90 → 110: on the hourly Build tick a 90-minute threshold already first catches a run at the *second* tick (~120 min in), so 110 preserves that property with slack for jitter and lets a merely-slow run finish, at a ~22% higher per-run spend ceiling. `DEFAULT_WALL_CLOCK_BUDGET_MINUTES` is the shared fallback, so the no-CONTEXT.md path cannot drift either. D2 of `stale-run-reclamation` and D1 of `harden-loop-layer` amended in place. 5 tests, the anti-drift guard written first and watched fail; 4 mutations, 4 caught. `harness` 0.2.15 → 0.2.16, `reviewer` 0.1.7 → 0.1.8 (registry 0.5.105 → 0.5.106).

### Added — `harness review` inherits a prior pass on a resumed run at the same HEAD (#259)
- Breakdown item 5 of `resume-earned-stages`, implementing ADR 0008 **D3** — the proposal's highest-risk item, shipped last. `close`'s gate is run-scoped and `start --resume` mints a new `run_id`, so a predecessor's pass was invisible even at the **exact commit** that passed: the run re-reviewed a byte-identical tree and the operator re-ran the gate to get there. The gate query is **unchanged** — the resumed run records its *own* `pass` carrying the source's `reviewed_sha`, verify-gate evidence and `engine` verbatim, marked `inherited_from` (new optional `ReviewEventData` field; `exclude_none` keeps an engine-produced event byte-identical). Six conditions, all required: resume provenance, a recorded `design` attempt, no red `--gate-exit`, a clean worktree, an engine-produced (not itself inherited) pass at that SHA on another run **for the same ticket**, and that pass satisfying `has_gate_evidence` — imported from `_review_gate.py`, never restated. Two are additions on the principle that the short-circuit may skip *work*, never a refusal about this run's own state (`no_design` and `gate_failed` still fire); the spend breakers it does skip are why `_count_review_events` now excludes inherited events. New `harness/cli/review_inherit.py`; `read_run_resumed_from` moved to `_runs.py`. `close.py`/`_review_gate.py` untouched — the Watchlist trigger's extraction already shipped in #255. 31 tests, all six conditions mutation-checked. `harness` 0.2.14 → 0.2.15 (registry 0.5.104 → 0.5.105).
