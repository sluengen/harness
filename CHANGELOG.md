### Fixed — the private-surface guard was blind to the workspace's former slug (CAL-1029)
- **A rename silently re-opened a scrub the guard had closed.** `test_no_private_surfaces` forbids `linear.app/<workspace>`, but only ever knew the *current* slug. The workspace was `calibrate-coffee` before it was `form-coffee`, so the CAL-1027 scrub and the guard pinning it stripped the new-slug URLs and left **24 old-slug ones** standing across four files in `specs/` — invisible for being spelled with yesterday's name. A stale URL leaks exactly what a live one leaks: the private org's identity and a map of ticket ids. That it now 404s is not redaction. Redacted to the bare `CAL-xxx` ids the guard prescribes — every link's text already equalled its ticket id, so no information is lost. The forbidden tuple now **grows** on a rename instead of being swapped.
- **`SECURITY.md` states the ledger's trust boundary.** The repo's headline claim is an *audited* verb loop, which a reader can reasonably hear as tamper-evidence. It is not: the ledger is an ordinary SQLite file, so anything with workspace write access — the agent under review included — can forge an event, and the close gate is a workflow aid rather than a cryptographic attestation. Stated plainly so nobody builds a security control on top of it.
- **`ci.yml` declares `contents: read`.** It inherited the repo-level default — read-only today, so a missing block has no symptom until the day that setting is widened, at which point every workflow that stayed silent widens with it. The grant is now pinned where a reviewer sees it (`release.yml` already scoped its own, CAL-623). Not a fork-PR fix: a public repo hands fork PRs a read-only token regardless — it is the `push: [main]` trigger, running with the repo's own token, that a widened default would reach.

### Fixed — the wrapper rebuilds a stale `harness:dev` instead of silently running it (CAL-1144)
- **A verb that shipped was invisible to the next unattended tick.** Nothing rebuilt the `harness:dev` image after a merge to `dev` — `docker build` appeared only in docs and a test fixture, `docker/harness-wrapper.sh` never built, and none of `doctor`'s seven checks compared the image against the source. The failure was **silent**, which is what made it expensive: the loop saw only `No such command '<verb>'` and diagnosed missing code. It happened for real with the `defer` verb (CAL-1143, image built a day stale), costing a tick, after which three consecutive ticks each paid a manual `docker image inspect` / `git log` comparison — a hand-check an unattended run should never depend on remembering.
- **Fix: the staleness guard lives in the wrapper**, the one component every verb already goes through. An eighth `doctor` check was the other candidate and is rejected on the same ground the ticket names: `doctor` is not run every tick, so it detects the problem only when someone thinks to look — which *is* the failure mode being fixed.
- **It rebuilds rather than refuses, and that is the design call.** Both satisfy the criteria, but the loop is unattended: a hard error trades a silent stale image for a queue that wedges every hour until a human rebuilds. The rebuild fires only when the source actually moved (once per merge, warm cache), never per invocation — a cold `--no-cache` build costs ~165s. A rebuild that **fails** exits non-zero rather than falling through to the stale image, so the silent failure cannot reappear through the back door.
- **Three details are load-bearing.** The source root resolves from the wrapper's own symlink-resolved path, not `$(pwd)` — the CWD is the *target* repo, frequently not this one. Both clocks normalise to epoch seconds (`docker` and `git` report UTC, the host is UTC+10; `stat -f %SB` prints local time and is a trap). All guard output goes to **stderr**, because stdout carries the verbs' JSON contract that the orchestrating loop parses.
- **The tests execute the wrapper against stubbed `docker`/`git`** rather than grepping its text, because the criteria turn on behaviour a text guard cannot tell apart — stale rebuilds, fresh does not. `test_wrapper_image_staleness.py` pins both, plus the failed-rebuild refusal, the untouched pinned tag, and a one-second-either-side boundary case that would catch a timezone skew the hourly fixtures would miss.

### Added — `harness defer` verb: the triage write as an audited verb (CAL-1143)
- **Triage was the one lifecycle write the routine hand-rolled.** The unattended Build routine's triage step — `work-discovery` judging a picked ticket not-yet-actionable and recording "comment + apply the `decision` label" — was executed as a raw GraphQL script (`docker run python3 …`), because it is not a build-lifecycle transition and had no verb. Everything that touches the gate (`start`/`review`/`close`/`reclaim`) is already a verb; triage was not, so it left nothing in the runs/events ledger (only a Linear comment) and was the write the autonomous auto-mode classifier intermittently blocked — a bounded, named verb binds to its `autoMode.allow` clause far more reliably than an opaque script.
- **Fix: `harness defer <TICKET> --reason <text>`** (`--reason-file <p>` for long bodies). A ticket not found or on another project is refused (exit 2) with a structured `reason` before any write; a tracker-less repo is a clean no-op, consistent with the other verbs. The `work-discovery` skill and `/harness routine build` now call the verb instead of hand-rolling GraphQL.
- **Guarded by `test_cli_defer.py`** (happy path, additive-label behaviour, the not-found / not-on-Build-queue refusals, the tracker-less no-op, and `--reason`/`--reason-file` handling), plus `DeferEventData` in `test_event_payloads.py` and the canonical-set / CLI-surface locks. ### Added — `harness promote start` / `continue` worktree + merge mechanics (CAL-1115)
- **The promotion openers now do real, deterministic git — no outer agent hand-rolls the merge.** CAL-1113/1114 locked the promote surface and read-path; CAL-1115 fills the two write-path openers on top of a new pure mechanics library `harness/promotion.py` (the promotion analogue of `harness/worktree.py`). `promote start` fetches `origin`, validates the `--from` → `--to` pair, creates a promotion worktree/branch **from the target** (`promote/<date>-<from>-to-<to>` based on `origin/<to>`, under `.worktrees/harness/<promotion_id>/` so `worktrees cleanup` reclaims it), attempts `git merge --no-ff origin/<from>`, and records the promotion. A clean merge lands `status='opened'` with the merged HEAD in a new `Promotion.merged_sha` field; a conflict is **left in the worktree** (resumable) and classified. No PR, no push, no auto-merge, and **no gate** — a merge only reaches `pr_ready` once CAL-1116 runs the gate.
- **Conflict classification enforces ADR 0003 repair authority.** `classify_conflicts` returns `agent_may_fix` for a small, low-semantic conflict, and `needs_ticket` when the conflict touches a sensitive file kind (schema migration; auth/payment/security/release/deploy script; dependency lockfile) or spans more than `MAX_REPAIRABLE_CONFLICT_FILES` (10) files — the file-count bound carries a measuring test. `promote continue --promotion-id <id>` resumes an `agent_may_fix` promotion after one bounded repair: it commits the resolved merge, records the merged HEAD, and increments the `attempts` count; an unresolved worktree is refused `dirty_worktree`, a non-`agent_may_fix` promotion `not_resumable`, an unknown id `not_found`.
- **Guarded by `test_promote_mechanics.py`** (classification + branch naming, incl. the file-count measuring test) and **`test_cli_promote_start.py`** (the five AC-4 paths end-to-end over a real repo with an `origin` remote: clean merge, conflict + classification, invalid branch pair, dirty worktree, and resume). `merged_sha` was added to the locked `Promotion` output contract (`test_promotion_contract_locked.py`); the `promote` surface lock, contract lock, and ledger tests are updated, and SPEC §11 documents `continue`'s `--promotion-id`.

### Changed — the `~/bin/harness` wrapper is a versioned file, not a README heredoc (CAL-1123)
- **An unversioned copy-paste blob has no mechanism to propagate a fix.** The canonical wrapper's only source was a `bash` heredoc embedded in `docker/README.md` prose, and every `~/bin/harness` was a hand-copied snapshot. So fixes did not propagate: this machine's wrapper missed CAL-1008's `/root/... → /home/harness/...` credential-path correction for **12 days**, and `test_container_hardening.py` guarded the README *text* while the installed wrapper was broken in practice. The heredoc was never `bash -n`- or `shellcheck`-lintable in isolation, so a syntax error would surface at a user's next run, not in CI. This is the root cause behind both CAL-1122 (group-0 socket fix) and the CAL-1008 path drift landing in the host wrapper late.
- **Fix: promote the wrapper to `docker/harness-wrapper.sh`** — a real, executable (mode 755), `bash -n`-clean file that is the single source `docker/README.md` now *references* for installation rather than embedding as prose. It carries the CAL-1122 (`--group-add 0`) and CAL-1008 (`/home/harness/...`) fixes verbatim, so a fresh install is correct out of the box. The README recommends **symlinking** it onto `PATH` (`ln -sf "$(pwd)/docker/harness-wrapper.sh" ~/bin/harness`), which keeps the installed tool in lockstep with the repo on every `git pull` — closing the drift class rather than papering over it (and making a `doctor` checksum/version-stamp drift check unnecessary; that "consider" item from the ticket is deliberately not built).
- **Guarded by `test_container_hardening.py`**: the wrapper file exists with a bash shebang, is executable, is `bash -n`-clean (a new always-on gate; `shellcheck` runs opportunistically, skipped where absent), and `docker/README.md` references it without embedding the `exec docker run` invocation. Every prior container-hardening invariant (SSH/codex mount paths under `/home/harness`, no `/root` credential mount, `--group-add 0` in the ssh-forwarding block, `~/.codex` read-only) now asserts against the **versioned file**, not prose. The wrapper-code guards in `test_docs_consistency.py` (CWD mount + allowlist pin, ssh-agent host-gate) and the token-refresh guard in `test_wrapper_token_refresh.py` (CAL-941) were repointed to the versioned file for the same reason; the key-scoping *documentation* invariant stays on the README prose. Scope is the wrapper relocation and its guards only.

### Added — `code-quality` names a narrowing's worklist as the transitive consumers of the field, not the grep for the coercion (CAL-1100)
- **A narrowing at a boundary is a whole-call-graph change.** From the 2026-07-16 code assessment (CODE-INSIGHT-1): two High findings both survived a batch that was specifically hunting the same null-sentinel, because the batch grepped the coercion *operator* and cleared the callsites it found — while a downstream reader two files away still did arithmetic on the coerced value. ### Added — `spec-authoring` requires a scope-claim invariant to cite its enumeration or be recorded as a finding (CAL-1101)
- **An invariant stated as a scope claim is a claim about the whole call graph.** From the same 2026-07-16 pass (CODE-INSIGHT-2): a doc-only commit recorded two rules that both overstated what the tree keeps — one claimed a sentinel's "one consumer" when three others read it, one doing off-screen arithmetic on it. ### Fixed — `doctor` probes that the review engine can actually run, not just that it is on PATH (CAL-1083)
- **A PATH-only check let a broken host pass.** `doctor`'s reviewer check tested only whether `claude` / `codex` resolved on PATH (`shutil.which`). In the `harness:dev` container `codex` is always on PATH but a real review cannot run (its `bwrap` sandbox cannot open a user namespace under the unprivileged container — ADR 0002), so a doctor PASS did not mean `review` would work. The check could not tell *not installed* from *installed but unable to run here*.
- **Fix: a `--version` liveness probe per engine.** `_probe_engine` resolves the binary and runs `<binary> --version`, returning a three-way `EngineProbe` outcome (`absent` / `cannot_run` / `ok`). `claude` is the default engine, so every failure mode is fatal — absent → FAIL, on PATH but the probe cannot run → FAIL naming the wall. `codex` is the opt-in cross-model engine, so its modes differ: simply absent is a WARN (the default claude review still works), but on PATH yet unable to run is a misconfiguration → FAIL citing ADR 0002. A `--version` probe proves the binary *launches*, not that a cross-model review runs in-container — the PASS message says so. Both `--version` exit 0 in the container, so doctor does not spuriously FAIL there.
- **New `verify`-gate config check.** `doctor` now WARNs (never FAILs) when the repo's `CONTEXT.md` defines no `verify:` command, naming the CAL-1082 evidence-model consequence: `review` records the gate as `not_configured` and proceeds, so a `pass` for that repo carries no test evidence and the merge gate is unenforced. Reuses `harness.gate.load_gate_command` rather than re-parsing. A repo may legitimately define no gate, so it must not block doctor.
- **Guarded by `test_cli_doctor.py`**: the probe outcomes, each `check_reviewer` branch (incl. the ADR 0002 citation), the WARN-not-FAIL verify config, and an end-to-end CLI test that a present-but-unrunnable engine makes `doctor` exit 1. Scope is `harness/cli/doctor.py` and its tests only.

### Fixed — the wrapper joins group 0 so the non-root container can reach the forwarded ssh-agent socket (CAL-1122)
- **The close verb could not push, and it was environmental, not a code regression.** Docker Desktop forwards the host ssh-agent into the container as `srw-rw---- root root`. Since CAL-1008 the image runs `USER harness` (uid 1000) — not root, not in group root — so it cannot `connect()` to the root-owned socket, and every `git push` over SSH (`close`, `checkpoint`) fails `git@github.com: Permission denied (publickey)` on an otherwise healthy host agent. The socket's ownership varies across Docker Desktop restarts, so the same wrapper pushed cleanly earlier the same day and then wedged — stranding a gate-green, review-passed CAL-1104 with no way to merge it.
- **Fix: `--group-add 0` in the ssh-agent forwarding block** of the canonical `~/bin/harness` wrapper (`docker/README.md`). The socket is group-rw, so gid-0 membership makes it reachable regardless of its runtime owner — a durable fix that does not depend on the socket's permissions. It does **not** weaken CAL-1008: `/root` stays mode 700, no mounted credential is group-root, and the only group-0-writable paths in the image are `/tmp`, `/var/tmp`, and `/run/lock`, all already world-writable `1777` (audited: 0 credentials exposed). Mounting the key instead is a dead end — on macOS the signing key is passphrase-protected in the Keychain and unusable from the mounted file, as the README already documents.
- **Guarded by `test_container_hardening.py`**: a test extracts the populated `SSH_AGENT_ARGS` array and asserts `--group-add 0` sits beside the socket mount, so dropping the line fails the gate. The wrapper's real source of truth is still a README heredoc, which is how the host copy drifted from CAL-1008 for 12 days — versioning it as a real file is filed as a follow-up (CAL-1123).

### Added — the verbs run tracker-less under `layers.linear: false` (CAL-1104)
- **The schema promised tracker-optionality the engine did not deliver.** `CONTEXT.md` has always advertised `linear: none` / `layers.linear: false`, but every verb hard-required Linear: `start` validated `LINEAR_API_KEY` and fetched the issue before doing anything local, `close` validated the key before any local side effect and transitioned Done, `reclaim` reverted the ticket. There was no code path to open or close a run without a tracker — the single biggest blocker to reuse in a repo not wired to Linear, and the seam a second tracker backend needs.
- **New module `harness/layers.py`**, mirroring `harness/loop_budget.py` and `harness/gate.py` — the standing precedent for reading config out of `CONTEXT.md` in its own module, by regex rather than a YAML dependency. It reads one key and owns no verb logic. It is a *separate* module from `loop_budget` because the concerns are separate: spend breakers are not layers.
- **The block scoping is the whole trick.** `linear:` appears **twice** in a real CONTEXT.md — `repo.linear: CAL` (the team prefix) and `layers.linear: true` (the switch) — and the prefix comes first. An unscoped match reads the prefix and never sees the switch, so a repo that plainly sets `layers.linear: false` would still be told to produce an API key. The reader resolves the `layers:` block before matching, and the mixed-key cases are pinned rather than left to a comment.
- **Layer off:** `start <id>` treats its argument as an **opaque run identifier** — taken verbatim so it still keys the open-run index (the duplicate-start guard holds) and emitted with every tracker-supplied field (`title` / `description` / `url` / `id`) left `None` rather than invented; `--resume` degrades to the clean start it already falls back to, both its sources being tracker comments. `close` skips the Done transition and reports `ticket_done: false` — an honest record of a remote side effect that did not happen, not a success flag. `reclaim` skips the revert and keeps its local half (reconcile the ledger, preserve the branch), which is the half that unblocks a fresh `start`. The `--stale` sweep is a clean **no-op**: staleness keys entirely on the tracker's `updatedAt`, so with no tracker there is nothing to enumerate — and it reports empty rather than failing because the Build routine runs it every tick as a pre-flight, where an error would wedge the loop it exists to unblock.
- **Tracker-less is not gate-less.** `close`'s review gate is untouched and runs *before* the tracker step, so a tracker-less close with no passing review still refuses `no_passing_review`. Turning off the tracker must not weaken the one thing protecting the merge; pinned by a test.
- **The layer defaults on**, and deliberately conservatively: a missing CONTEXT.md, a missing `layers:` block, a missing key, or an unrecognised value all read as on. A repo that has not opted out behaves exactly as before — including failing fast on a missing `LINEAR_API_KEY` — rather than silently degrading into a tracker-less run because a file could not be parsed.
- `review` needed no change: it has no tracker touchpoint today (the ticket's "review's transitions no-op" clause anticipates CAL-1103, which has not landed). `templates/CONTEXT.template.md` **0.1.9 → 0.1.10**: `repo.linear: none` and `layers.linear: false` are now documented as moving together, and the layer line names `layers.linear` as the switch the engine reads — the two fields were previously settable apart, so a repo reading as tracker-less to a human still made the verbs demand a key. The template is pinned against the reader itself, not against a copy of its own words.

### Added — `review` requires recorded verify-gate evidence (CAL-1082)
- **The gate the verb loop never ran.** `close` checked three things — a run exists, the worktree is clean, a `verdict='pass'` is bound to HEAD — and **none of them was evidence that a test ever ran**. The only instruction to run the gate was prose addressed to a model (`commands/harness.md`: "Run the repo's verify gate locally as you go"), enforced by nothing. So a `pass` from a reviewer that merely *read the diff* was byte-identical in the ledger to one backed by a green suite. `verify` appeared **zero times** in `specs/features/verb-model.md`: the loop had no gate step at all.
- **Evidence, not execution — the harness stays a scaffold.** The first build of this ticket had `review` *execute* the gate in-container, and proved why it cannot: the image cannot carry every target repo's toolchain. `harness:dev` is built `--no-dev`, so not even this repo's own `ruff` is present (`bash scripts/verify.sh` exits 2 in-container — `Failed to spawn: ruff`); a Node target would need Node; an Xcode target can never run in a Linux container. An executing verb would therefore either bloat the image toward every ecosystem or hand a diff-only `pass` to the repos it could not run — and the harness could never close **its own** tickets. **Decision (Scott, 2026-07-16):** the gate runs where the toolchain lives (the orchestrating session, host-side); the verb enforces and records the evidence. CAL-1084's toolchain path is canceled as superseded.
- **`harness review --gate-exit <code> [--gate-log <path>]`.** The orchestrator runs `CONTEXT.md` → `verify:` in the worktree and hands over the result. Green → the engine runs and the `review` event carries `gate_ran=true`, the resolved `gate_command`, `gate_exit_code`, and a bounded (≤ 2 KB) `gate_output_tail`, all bound to `reviewed_sha`. Non-zero → the verb refuses **before** the engine (exit `5`, `reason=gate_failed`) with the tail on the refusal JSON, records no event, and spends no tokens on a red tree. Gate configured but **no evidence supplied** → exit `5`, `reason=no_gate_evidence`: silence is not a pass. No `verify:` configured → recorded honestly (`gate_ran=false, gate_reason="not_configured"`) and review proceeds — the harness cannot gate what a repo does not define.
- **`close` gains a fail-safe backstop, `no_gate_evidence`.** A pass written by a harness predating this change carries no `gate_ran` key, `json_extract` yields `NULL`, and close reads that as no evidence and refuses — so no ledger migration is needed and an old pass cannot be spent on a merge. This is a **refusal-reason addition**: the verb-contract lock (`test_verb_contract_locked.py`) caught it, and the snapshot was updated deliberately.
- **The evidence is self-reported, and that is deliberate.** It grants no new trust: any process that can write the workspace could already forge a ledger event, so this sits on the ledger's existing filesystem trust boundary rather than moving it. The authoritative control over what merges is server-side branch protection (CAL-1029). What the record buys is that a `pass` now *states* whether a gate ran, so a reader — and `close` — can tell the two apart. The container is also not loosened to run foreign toolchains: **ADR 0002** (CAL-925) weighed and rejected the Docker-socket path, and this design removes the reason to revisit it.
- New module `harness/gate.py`, mirroring `harness/loop_budget.py` — the standing precedent for reading config out of `CONTEXT.md` in its own module. It holds no execution path (pinned by a test). The watchlisted `harness/cli/review.py` grows a call site and three constants, not a subsystem. `commands/harness.md` **0.1.7 → 0.1.8**.
- Also corrected in passing: `specs/features/cli-surface.md`'s "Exit codes are a stable contract" table listed only 0/1/2/130 — omitting `review`'s existing `3` (infra) and `4` (breaker). Adding `5` beside that gap would have implied 3 and 4 were unused, so all three are now listed.
