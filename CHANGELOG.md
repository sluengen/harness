## [Unreleased]

### Fixed — `close`'s merge-conflict message no longer prescribes a rebase (#266)
- Breakdown item 1 of `rebase-stable-certification` (ADR 0010's cheapest slice). `close` merges the run branch into a detached throwaway worktree at the fetched `origin/<base>` tip, never touching the run worktree's HEAD — so base movement needs no rebase. The `merge_conflict` message said otherwise (*"rebase the run branch on the updated `<base>`…"*) and `commands/harness.md` repeated it; a rebase rewrites every SHA, so the HEAD-bound pass stops covering hunks it never touched (18 runs show ≥2 passing SHAs with no intervening `fail`, 24 empty review cycles). The message now names the non-rewriting route, and the doc gains a `#### Base movement needs no rebase` block covering clean advance, `push_rejected` (plain retry) and `merge_conflict`. Contract unchanged — one string moved. The guard pins the **absence of the word** `rebase`, since any rewording slips past a phrase regex. Two unnamed carriers swept up: `checkpoint.py`'s docstring calling rebase-before-close "the standing move", and `test_close_integrate_base.py`'s "the documented recovery, verbatim". A rebase stays pinned as still-working — this retires a prescription, not a capability. 8 tests. `harness` 0.2.16 → 0.2.17 (registry 0.5.106 → 0.5.107).

### Changed — one config value now drives both the wall-clock breaker and reclamation staleness, at 110 minutes (#260)
- "The longest a legitimate run may take" was stored twice: `loop.wall_clock_budget_minutes` (read by `review`'s breaker) and a hardcoded `--older-than` default of `"90m"` in `harness/cli/reclaim.py`, which read no config at all. `CONTEXT.md` documented the coupling as a rule for humans — *"if one moves, move both"* — and nothing enforced it. They were never two quantities: the breaker enforces the bound prospectively, reclamation applies it retrospectively, so divergence is a bug rather than a tuning option — a run aged between two values would be spared reclamation **and** refused at review, alive on the board and unable to finish. `--older-than` now defaults to a **sentinel** and resolves the loop budget when omitted (a default built *from* the config would move the literal, not delete it); an explicit value still overrides. Retuned 90 → 110: on the hourly Build tick a 90-minute threshold already first catches a run at the *second* tick (~120 min in), so 110 preserves that property with slack for jitter and lets a merely-slow run finish, at a ~22% higher per-run spend ceiling. `DEFAULT_WALL_CLOCK_BUDGET_MINUTES` is the shared fallback, so the no-CONTEXT.md path cannot drift either. D2 of `stale-run-reclamation` and D1 of `harden-loop-layer` amended in place. 5 tests, the anti-drift guard written first and watched fail; 4 mutations, 4 caught. `harness` 0.2.15 → 0.2.16, `reviewer` 0.1.7 → 0.1.8 (registry 0.5.105 → 0.5.106).

### Added — `harness review` inherits a prior pass on a resumed run at the same HEAD (#259)
- Breakdown item 5 of `resume-earned-stages`, implementing ADR 0008 **D3** — the proposal's highest-risk item, shipped last. `close`'s gate is run-scoped and `start --resume` mints a new `run_id`, so a predecessor's pass was invisible even at the **exact commit** that passed: the run re-reviewed a byte-identical tree and the operator re-ran the gate to get there. The gate query is **unchanged** — the resumed run records its *own* `pass` carrying the source's `reviewed_sha`, verify-gate evidence and `engine` verbatim, marked `inherited_from` (new optional `ReviewEventData` field; `exclude_none` keeps an engine-produced event byte-identical). Six conditions, all required: resume provenance, a recorded `design` attempt, no red `--gate-exit`, a clean worktree, an engine-produced (not itself inherited) pass at that SHA on another run **for the same ticket**, and that pass satisfying `has_gate_evidence` — imported from `_review_gate.py`, never restated. Two are additions on the principle that the short-circuit may skip *work*, never a refusal about this run's own state (`no_design` and `gate_failed` still fire); the spend breakers it does skip are why `_count_review_events` now excludes inherited events. New `harness/cli/review_inherit.py`; `read_run_resumed_from` moved to `_runs.py`. `close.py`/`_review_gate.py` untouched — the Watchlist trigger's extraction already shipped in #255. 31 tests, all six conditions mutation-checked. `harness` 0.2.14 → 0.2.15 (registry 0.5.104 → 0.5.105).

### Added — `/harness routine build` step 0 drains the sweep's `closable` list (#256)
- Breakdown item 2 of accepted proposal `resume-earned-stages`, settling **D2**: the pre-flight may close. #255 taught `reclaim --stale` to *report* a stranded-but-passing run as `closable` rather than revert it, which on its own trades "reclaimed and re-done" for "stranded indefinitely". Step 0 gains a third sub-step between the sweep and the worktrees housekeeping: read `closable` from the sweep (now invoked with `--json`, which defaults off) and run `harness close <ticket> --run-id <run_id>` on each, sequentially, from the **main repo root** and inside the `~/bin/harness` container — `runs.worktree_path` is recorded container-absolute, so a host-side close would report purely environmental failures. **Bounded** (once over the list the sweep produced, never re-sweeping) and **record-and-continue**: any refusal is recorded and the drain moves on, with no retry, no `reclaim` and no hand-rolled merge, because **D5** leaves no legal compensating action — a refused close leaves the ticket as step 0 found it. The drain adds no safety test of its own: liveness is decided upstream, so a live session paused at a clean, previously-passed HEAD never enters the list, and `close` re-runs the gate at execution time, so drift between the sweep and the drain is refused rather than merged. Ordering is load-bearing — `cleanup --age` reclaims a directory on mtime alone, and a closable run is by construction idle. Guidance-only; no harness-app change. 8 new guards. `harness` 0.2.13 → 0.2.14 (registry 0.5.103 → 0.5.104).

### Fixed — `reclaim --stale` classifies a closable stranded run instead of reverting it (#255)
- Breakdown item 1 of accepted proposal `resume-earned-stages` (ADR 0008). A run that passed `review` and then lost its session was reclaimed at the 90-minute threshold, throwing away a passing review and forcing a fresh run to re-design and re-review to reach a `close` that was one command away — but `close` has no spend breaker and the row is still `open`, so it was never stranded, only unfinished. `SweepOutput` gains a third, disjoint outcome `closable` (`scanned == reclaimed + skipped + closable`): a tracker-stale run whose **clean** worktree HEAD carries a gate-evidenced `pass` is reported and left completely alone — no revert, no label, no comment, no ledger write. Checked **after** liveness, so a live session paused at a previously-passed HEAD stays `skipped` (spared) rather than becoming drainable. The sweep stays a classifier; driving `close` is #256. The gate's ledger question moved from `close.py` to shared `harness/cli/_review_gate.py` so the prediction and the gate cannot drift — `close`'s gate tests pass untouched as the proof. Every uncertainty answers "not closable", i.e. today's behaviour. 16 new tests. `harness` 0.2.12 → 0.2.13 (registry 0.5.102 → 0.5.103).
