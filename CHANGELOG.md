## [Unreleased]

### Added — test-driven-development: cover each of a guard's trigger conditions, not just the one that trips first (#203)
- From an `/assess code` steward pass (2026-07-17, pass 3, CODE-INSIGHT-1) against a consuming repo: a multi-condition guard's own test suite exercised only one of its independent trigger paths, and deleting the other left every one of 422 assertions green — the guard as a whole was covered, but the untested condition was exactly what let a real defect through unseen. This generalises past the originating repo to any structurally-blind gate whose discriminating input is never actually sent. RED gains a new bullet, immediately after the existing "Cover the active loop, not just its exit" (the same failure shape in a loop's clothing): a guard with several independent trigger conditions needs one test per condition, each proven by deleting that condition in turn and confirming a named assertion goes red for it — a condition whose deletion leaves the suite green is untested, however many assertions surround it. New `test_tdd_guard_condition_coverage.py` pins the rule's content, its placement immediately after the active-loop bullet, and header/registry version sync. **`test-driven-development` 0.4.0 → 0.5.0** (registry **0.5.79 → 0.5.80**).

### Added — `/decision`: the versioned sweep that drains tickets held for a judgment call (#193)
- The operator drained the held-ticket pile by retyping an ad-hoc prompt into a fresh session; every unresolved `decision` hold was a permanently-skipped queue entry, so the Build arm fell through to idle assessment passes while real work sat held. New `commands/decision.md` (bare universal name, per the proposal's decision) is the versioned, **interactive** return path: pull tickets carrying the `decision` hold label (never `input`/`operator` — the exclusion ADR 0006 made machine-readable), order by the `work-discovery` ranking, present each with its deferring comment as context, capture the operator's call, and release. It delegates the clearable test and the "released" definition entirely to `work-discovery`'s Return path section (#192) rather than restating it, and stops after release — no handoff to `/harness run`; the Build arm picks a released ticket up on its own next tick. An empty pile is a clean, honest stop, not a manufactured decision. Tracker coupling was the proposal's own flagged risk: releasing a ticket needs a resolution written into the change spec, the hold label removed, and the operator unassigned — writes neither tracker backend exposed. New `harness release <ticket> --resolution <text>` verb (the `defer` shape in reverse) does this as one audited, ledger-recorded write rather than a hand-rolled tracker mutation: `Tracker.remove_label` / `unassign_viewer` / `update_issue_body` land on both `LinearClient` and `GitHubClient`, a new `release` event type joins the ledger, and `/decision`'s only tracker writes route through this verb — its own reads (listing/ordering the pile) go directly against `gh`/the `linear` skill, since a read carries none of the audit risk a write does. `release` composes the new body by replacing any prior `## Resolution` section (idempotent re-release) rather than appending a duplicate. New tests: `test_linear_release_primitives.py` and the `test_github.py` additions pin the three tracker primitives (idempotent no-op on an absent label, not-found/unsuccessful-mutation branches); `test_cli_release.py` pins the verb's happy path, write ordering (body → label → unassign, so a mid-sequence crash never silently drops the answer), Build-queue-membership refusal, the tracker-less no-op, and the idempotent-replace case. `SPEC.md` §11, `specs/features/cli-surface.md`, and the locked CLI-surface/event-type test fixtures (`test_cli_surface_locked.py`, `test_event_emitter.py`, `test_feature_specs.py`) all gained the new verb/event in lockstep — the registered surface is the single source those tests compare against. **`process-harness` 0.4.6 → 0.4.7, new `decision` 0.1.0** (registry **0.5.72 → 0.5.73**).

### Added — `work-discovery` gains the return path: when a held ticket is clearable and what released means (#192)
- `work-discovery` owned only the outbound half of held-ticket judgment (defer, then skip on assignment) — nothing said when a held ticket is ready to come back or what "released" means, so `/decision` (#193) would have had to restate the judgment, forking it from its single home. A new "Return path" section states the inverse test: a held ticket is **clearable** when the only thing missing is input the operator has now supplied (for a `decision` hold, an answer that makes the acceptance criteria checkable); **released** means all three of the resolution written into the ticket's change spec, the hold label removed, and the operator unassigned — the unassignment called out as **load-bearing**, since assignment is the authoritative skip signal and a sweep that records an answer without unassigning would leave the ticket held forever, the exact failure mode of the ad-hoc prompt this replaces. A ticket released but still not wholly actionable is **re-deferred** through the existing Actionability step, not left half-cleared. New tests in `test_work_discovery_skill.py` pin the section's presence and all three return-path pieces (clearable, the three release steps, the re-defer case). `/decision`'s own control flow (#193) and any change to the outbound deferral rules are out of scope. **`work-discovery` 0.5.0 → 0.6.0** (registry **0.5.71 → 0.5.72**).

### Added — `harness defer --needs` gains a third hold kind, `input` (#191)
- `--needs` took two hold kinds, `decision` and `operator`, which did not partition the space the operator actually cares about: a ticket waiting on the operator to *supply* something (a work item, a credential, infrastructure stood up) is neither a judgment call nor an interactive session, so a deferring run had to mis-file it under one of the two. This blocked the `/decision` return path (#193): without a third kind, `/decision` would have to re-triage every held ticket on every sweep, re-deriving a distinction the deferring run already knew and threw away. `DeferNeeds` (`harness/cli/defer.py`) gains `input`; the kind's value stays the label name applied via the existing additive `apply_label` primitive (never a full-set replace), so a held ticket keeps carrying both the machine-readable assignment and a label saying why. `work-discovery` now names all three kinds and states it skips all three — the outbound hold semantics are unchanged, and assignment stays the authoritative skip signal; only the return path (#193) reads the kind. The `operator` label's meaning **narrows** to interactive-session-only, no longer also covering "the operator owes this ticket something" — stated in `DeferNeeds`'s docstring, `work-discovery`, and the `linear` skill. Review caught that the as-built record (`specs/features/cli-surface.md`, `specs/features/run-ledger.md`), `commands/harness.md`'s deferral step, and the `linear` skill's label table/filing table/deferral section/sync rule 4 still documented only two kinds — all four updated in the same diff, plus stray `decision`/`operator`-only comments left inside `defer.py` and its test file. Decision recorded as ADR [`0006`](specs/decisions/0006-hold-kinds.md); proposal `specs/proposals/promote-and-decision-commands.md`. New tests in `test_cli_defer.py` (`--needs input` applies the `input` label, preserves a pre-existing label, and records `needs=input` in the ledger event) and `test_work_discovery_skill.py` (all three kinds named, the skip-all-three statement, and the narrowed-meaning statement). `/decision` itself (#193) and backfilling existing tickets (zero counted 2026-07-23) are out of scope. **`work-discovery` 0.4.0 → 0.5.0, `linear` 0.5.0 → 0.6.0, `commands/harness.md` (`harness`) 0.2.3 → 0.2.4** (registry **0.5.69 → 0.5.71**).

### Added — `/promote`: agent-orchestrated fallback for repos without the harness app (#190)
- `commands/promote.md` gains a `## Fallback: no harness app` section: a repo without the harness app (`harness` absent from `$PATH`) still drives `/promote <src> to <dst>` — the `/build`-is-available-everywhere pattern applied to release movement. Detection is specified (a `$PATH` check, mirroring `/harness run`'s own), not assumed. The loop is **deliberately reduced** per ADR 0003's 2026-07-23 amendment: worktree off the target branch, merge the source (conflict → stop and report, no repair attempt), run the repo's `CONTEXT.md` `commands.verify` gate (never hardcoded — read fresh every run; red → stop and report the captured output, no retry), then on green the same hop asymmetry as the verb-backed path (`--to` an intermediate branch pushes directly with no PR; `--to` the release branch pushes only the promotion branch and opens a PR). A stated "what you lose without the ledger" paragraph (no promotion id, no audit trail, no resumable state) and an explicit reduced-by-decision note guard against a later reader "completing" the fallback into a second, drifting implementation of the promotion lifecycle. `tests/unit/test_promotion_routine_docs.py` gains a section-scoped drift guard (`_fallback_section()`/`_normalized_fallback()`, since the verb-backed path already uses phrases like "opens no PR" that would otherwise false-positive an unscoped check) covering detection, no-repair-on-conflict, no-repair-on-red-gate, the `commands.verify` read, hop asymmetry, the ledger-loss paragraph, and the reduced-by-decision statement. **`promote` 0.1.0 → 0.2.0** (registry **0.5.68 → 0.5.69**).

### Added — `/promote`: a versioned command over the harness promotion verbs (#189)
- The promotion lifecycle shipped as five audited verbs (`harness promote start | continue | status | pr | escalate`, ADR 0003), but the caller never shipped — the orchestration (which state to branch on, when to run the gate host-side, when to stop) existed only as prose in `RUNBOOK.md`, unaddressable as a command and uninstalled into any other repo on this guidance. New `commands/promote.md` transcribes that loop into a version-stamped universal command: `/promote <src> to <dst>` resolves each word against `CONTEXT.md` `branches:` roles (`integration`/`staging`/`release`) first, falling back to a literal branch ref, so the identical invocation drives any repo's own branch names unchanged (a repo whose roles are `develop`/`staging`/`production` still runs `/promote develop to staging`). It documents the full loop, all ten lifecycle states (the six `start`/`continue` branches on plus the three terminals plus `cancelled`), the forbidden outer-agent actions, and the bounded-repair/escalation policy — content moved out of `RUNBOOK.md` §"The promotion routine", which now carries only this repo's own operational facts (its nightly/deliberate cadence) and points at the command, so the orchestration logic lives in exactly one place. Also documents that `promote pr`'s release-hop `gh pr create` step, previously blocked on a missing `gh` binary in the runtime image, is resolved (#187). The agent-orchestrated fallback for repos without the harness app is out of scope here (tracked separately, #190). `tests/unit/test_promotion_routine_docs.py` retargeted from `RUNBOOK.md` to `commands/promote.md` as the drift-guard's home (subcommands/states still derived live from the `promote` Typer app / `PROMOTION_STATUSES`), plus new coverage for the role-resolution example, the command's registration in the `CLAUDE.md` command table, and the RUNBOOK pointer's shortness. **`process-harness` 0.4.5 → 0.4.6, new `promote` 0.1.0** (registry **0.5.67 → 0.5.68**).

### Added — code-quality: a linter enforces the file-size limit where it can (#185)
- Part C mechanized marker *presence* as a tree-walking repo test (CAL-1155) but never said which mechanism to reach for first, so in practice the limit fell to the steward's weekly advisory pass: in nano-erp a 725-line file (44% over the hard limit) passed both a review and a green gate, and a repo-wide grep for the `// size:` marker returned zero matches — the justification rule had never once been exercised. The "auditable choice, not silent drift" subsection now orders the mechanisms: where the repo's linter already implements a file-length rule (`max-lines` in oxlint or ESLint), turn that rule on instead of writing the walker — it runs with the rest of lint on every commit, needs no repo-local code to maintain, and its escape hatch is the same auditable decision (an inline rule-`disable` carrying the `size: <reason>` justification) plus one property the walker cannot offer: an **unused** disable is itself reported, so a file that shrinks back under the limit cannot silently keep its exemption. The walker is the fallback for a toolchain whose linter has no such rule; the steward is the **backstop** only where neither can run. New `test_code_quality_linter_first_size_enforcement.py` pins the linter-first preference and the named rule, the auditable-disable escape hatch and the unused-disable property, and the steward's backstop placement — in the style of the sibling `test_code_quality_marker_presence_mechanized.py`. Guidance-source half only: the repo-local half (adding `max-lines` to nano-erp's `.oxlintrc.json`) stays in nano-erp ERP-151. From the nano-erp assessment (`assessments/2026-07-22-code.md`, CODE-INSIGHT-2); accepted as a split — note only. **`code-quality` 0.14.0 → 0.15.0** (registry **0.5.66 → 0.5.67**).

### Added — review-discipline: a CONTEXT.md currency trigger on the stage-two checklist (#184)
- `CONTEXT.md` is the first file every agent reads, so a stale entry there mis-primes every later session rather than one review — and the class is recurring, not incidental. In nano-erp it carried three stale frontend claims (no test runner, backend-only, a gate step omitting tests), each gone stale at an identifiable commit, and none of them pointed a reviewer at `CONTEXT.md`; a "D1–D12" line survived three assessment passes against a live D17. `review-discipline`'s Stage 2 "For code" checks gain a **CONTEXT.md currency** bullet, beside *Architecture watchlist*: when a diff **adds or removes** a test runner, a gate step, a workspace, or a top-level path, confirm `CONTEXT.md`'s `stack` / `commands` / `layers` block names it correctly — a stale entry there is a **Medium** finding. The trigger is deliberately narrow (those four are the diff shapes that make the file stale, and each is visible in `git diff --name-only` plus the changed config), not "read `CONTEXT.md` every time"; a hook was weighed and rejected because the condition needs judgement, not a path match. New `test_review_discipline_context_currency.py` pins the four trigger conditions, the both-directions wording, the named blocks, the Medium grade with its first-file-read rationale, and the rule's placement in the Stage 2 "For code" checks, in the style of the sibling structural-rule guards (`test_review_discipline_type_predicate_coverage`, `test_review_discipline_port_orphan`). Guidance-source edit from the nano-erp assessment (`assessments/2026-07-22-code.md`, CODE-INSIGHT-3 / nano-erp ERP-152); accepted as written. **`review-discipline` 0.6.2 → 0.6.3** (registry **0.5.65 → 0.5.66**).

### Added — code-quality: a security-contract test asserts the predicate, not the name (#183)
- A security-contract test that asserts a control *exists* (by name, by presence in a list) proves only that someone typed the right string. In nano-erp the tenancy gate the whole repo leans on (`test/catalog_security.test.ts`) verified a policy *called* `tenant_fence` exists — it never read `qual`/`with_check`, so `tenant_fence ... using (true)` passed. `code-quality`'s Part C — Verification gains a new subsection beside "A measurable criterion needs a measuring test": when a test proves a security control is in place — an RLS policy, an auth guard, a CSP directive, a permission grant — assert what it evaluates to (the policy's `USING`/`WITH CHECK` expression, the guard's refusal, the directive's value), not merely that it exists; pair it with a negative fixture whose control is present but wrong, and watch the test fail. New `test_code_quality_security_contract_predicate.py` pins the rule's presence, its concrete predicate language, the negative-fixture requirement, and its placement in Part C, in the style of the sibling structural-rule guards (`test_code_quality_duplication_threshold.py`). Guidance-source edit from the nano-erp assessment (`assessments/2026-07-22-code.md`, CODE-INSIGHT-1 / nano-erp ERP-150); accepted as written. **`code-quality` 0.13.0 → 0.14.0** (registry **0.5.64 → 0.5.65**).

### Added — spec-driven-development requires the as-built record before a surface accumulates a second ticket (#182)
- A missing join between two shipped tickets is invisible from inside either ticket. In nano-erp, ERP-114 built the receiving end of the quote share flow and ERP-109 built the list — each met every criterion — but no record described the *flow* (operator sends a quote, customer opens a link), so the missing share link (CODE-2) went unseen until an assessment wrote the record six tickets late. `spec-driven-development`'s step 8 (the reviewer's record-reality step) now states: when a surface's as-built record does not exist yet, the first ticket touching that surface creates it — a feature spec in `specs/features/` where `feature_specs` is on, otherwise the section of the design doc / `SPEC.md` that governs the surface — and a surface is not permitted to accumulate more than one shipped ticket without one. Review caught that the rule as first shipped lived only in `spec-driven-development`, a file `agents/reviewer.md`'s "Load these skills" list never loads (it loads `review-discipline`, `code-quality`, `engineering-principles`) — the acting reviewer could never see it. Propagated the cap into `review-discipline`'s as-built-record-gate bullet, `reviewer.md`'s on-PASS section, and `commands/review.md` step 4 — the three surfaces that already operationalize the sibling CAL-972 as-built-record gate — so it is reachable at review time. New `test_spec_driven_development_asbuilt_record_gate.py` pins the rule's presence in `spec-driven-development`, its placement at step 8, its layer-awareness, and its propagation to all three review-time surfaces, in the style of the sibling structural-rule guards (`test_review_discipline_asbuilt_record_gate`, `test_review_discipline_type_predicate_coverage`). Guidance-source edit from the nano-erp assessment (`assessments/2026-07-22-code.md`, CODE-INSIGHT-3); accepted with modification — the original named the "feature spec" specifically, reworded to reference the layer-appropriate as-built record so it holds for `feature_specs: off` (infra) repos too. **`spec-driven-development` 0.4.0 → 0.5.0, `review-discipline` 0.6.1 → 0.6.2, `reviewer` (agent) 0.1.6 → 0.1.7, `review` (command) 0.1.3 → 0.1.4** (registry **0.5.63 → 0.5.64**).

### Added — review-discipline verifies a type predicate covers every required field (#181)
- TypeScript takes `value is T` on faith — it cannot check a user-defined type predicate against the type it asserts. In the nano-erp assessment, `isMeResponse` validated four of six required fields and nothing (compiler, reviewer, tests) caught it; it was the highest-severity finding in the pass and survived two prior reviews. `review-discipline`'s Stage 2 "For code" checks gain a new **Type predicate coverage** bullet, beside Correctness: for every user-defined type predicate (`value is T`), enumerate `T`'s required fields and confirm the guard checks each one — a predicate that validates a subset is a false assurance at the boundary it was added to protect, flagged as a defect, not a nit. New `test_review_discipline_type_predicate_coverage.py` pins the rule's presence and its placement in the Stage 2 "For code" checks, in the style of the sibling structural-rule guards (`test_review_discipline_port_orphan`, `test_review_discipline_misplaced_helper`).
