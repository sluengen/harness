### Added — the interactive driver declares attendance, and a guard keeps every routine path out of it (#298)

`/harness run`'s prescribed `start` invocation now carries `--attended`, completing ADR 0011's opt-out: the one caller with an operator present declares it, and bounded stays the default everywhere else.

The half that keeps it honest is transitive. `/harness routine build` reaches `start` by handing the whole ticket to `/harness run`, so declaring the flag there would have handed every hourly tick an unbounded run — the failure the wall-clock breaker exists to prevent, arriving through the change meant to protect it. The routine preamble now states that no routine declares attendance whatever surface it drives, and the Build routine says so again at the point it delegates.

`tests/unit/test_attendance_declaration.py` derives both sets from the document's own headings, fence-aware, and asserts the obligation and the prohibition in both directions — including that a delegating routine declines in prose. It supersedes the interim #295 guards in `test_routine_commands.py`, whose hardcoded two-name list would have missed a third routine and whose substring predicate would have read the new declination sentences as the violation.

### Added — `harness start --attended` records the run's declared attendance mode (#295)
A run can now declare that an operator is present. `harness start --attended` writes `{"attended": true}` into the run row's `inputs_json` — a column that was free-form and dormant, so there is no schema migration — and `start --json` reports the resolved mode on both the new-run and the existing-run path. This is the carrier only: nothing reads it yet, and `review` and `reclaim --stale` behave exactly as before. [ADR 0011](specs/decisions/0011-attended-run-spend-scope.md) makes attendance a declared property because liveness cannot be inferred — a human thinking looks identical to a dead orchestrator — so the wall clock charges an attended session's human latency as autonomous spend.

Bounded stays the default, and every ambiguity resolves toward it. An undeclared run writes the byte-identical `"{}"` it has always written, so no existing row changes meaning and no backfill is needed; a test pins that exact string rather than its parsed form, because a default that started recording `{"attended": false}` would look equivalent and would not be. Only the literal JSON `true` declares attendance — a string `"true"`, a `1`, a non-object document and unparseable text all resolve unattended — since declaring it opts a run out of the only ceiling on autonomous spend, so a corrupted or hand-edited ledger can make a run more bounded but never less. Attendance is also fixed at `start`: a repeat `start --attended` against a run opened without it surfaces the existing run reporting the *recorded* mode and writes nothing, rather than upgrading it in place.

The writer and the reader ship together in `harness/cli/_runs.py`, next to `read_run_resumed_from`, for the reason that module already records — two consumers are coming (`review`'s wall-clock breaker, `reclaim --stale`'s threshold selection) and a second copy is how two paths start disagreeing. A guard also pins ADR 0011's stated consequence from the moment the flag exists: no `/harness routine` path may pass `--attended`, since an unattended loop declaring itself attended would buy the exemption with nobody watching the spend. That guard carries a non-vacuity floor — a renamed routine heading makes the section slice empty, which would leave the erosion check green while asserting nothing.

### Added — `review` events record the model the engine ran with (#293)

`harness review` resolved a per-ticket model tier (#177), passed it to the
claude engine as `--model`, and then dropped it. `design` records `model: opus`
on every event; `review` recorded no model key at all. That made review latency
uninterpretable — the per-engine-timeout proposal compared design and review
durations and had to state its conclusion as "the evidence does not support
splitting" rather than "the two are equivalent", because one side of the
comparison was a verb whose model varied per ticket and was unrecorded.

`ReviewEventData` gains an optional `model`, written from the same object handed
to `--model` rather than re-resolved from the ticket's label, which a mid-review
label edit would answer differently from what actually ran.

It is present **iff** `engine` is `claude`. The field keys off the engine that
*ran*, not the one requested — the same distinction the payload already draws
with `engine=engine_used` plus `fallback_from` — so a codex→claude usage-limit
fallback records the alias the claude re-invocation used, while a codex review
records no key at all: codex ignores `--model`, and an alias there would assert
a model that was never in force.

No backfill and no migration. A pre-existing row validates with `model is None`
and re-dumps without the key, so absence keeps reading as *unknown* rather than
as a default — consistent with ADR 0009 and with how `gate_ran` handled the same
situation. `engine` disambiguates the two ways a key can be missing: a `claude`
row without a `model` can only predate this change.

The inherit path needs no field-level work — it re-emits the validated source
payload through `model_copy`, so `model` rides along with `engine` exactly as
`reviewed_sha` and the gate evidence do, and a pre-#293 source stays keyless.
Both directions are now pinned by test; the absence case turned out to be the
only guard in that suite against the inherited dump losing `exclude_none=True`.

The printed `ReviewOutput` is unchanged: this is a ledger fact, and no
orchestrator branches on it.

### Changed — decision storage is repo-configurable, embedded-first (#330)

Universal `spec-authoring` stated a flat prohibition — "There is no separate `decisions/` folder and no standalone ADRs" — while this repo declares `paths.decisions` and keeps a growing numbered ADR set there. An agent applying the universal rule here was instructed to dismantle the repo's own canonical decision record, and a future decision could legitimately land in either of two homes.

Embedded stays the default and the optional `CONTEXT.md` `paths.decisions` key is now the **only** switch — no strategy enum, nothing that can disagree with the path. Declare it and that directory holds decisions that are cross-cutting, consequential, and expensive to reverse; a decision that merely touches several files does not clear the bar, and one that governs a single feature never does. Each qualifying decision has one canonical record, which affected feature specs **link** to rather than restate. Placement, numbering, and supersession inside the directory are deferred to the repo's architecture index, so universal prose names the key and never a concrete path.

Eight installed surfaces move with it: `spec-authoring` (the rule's home) `0.9.3` → `0.10.0`, `architecture` `0.7.0` → `0.7.1` (its pointer conditionalised), `architect` `0.2.0` → `0.3.0` (files an ADR where one is configured; still refuses to invent a directory the repo has not), `steward` `0.2.1` → `0.2.2` (its architecture read path covers the directory), `template-decision` `0.1.0` → `0.2.0`, `template-architecture` `0.1.0` → `0.2.0` (the section doubles as the ADR index), `template-context` `0.1.16` → `0.1.17` (the new optional key), `template-feature` `0.4.0` → `0.5.0` (link, never copy), and `propose` `0.2.0` → `0.2.1` (step 3 no longer routes every cross-cutting decision to the architecture-principles spec unconditionally).

Supersession is scoped the same way as placement: universal guidance keeps the in-place mechanic for an **embedded** decision and defers supersession inside a configured directory to the repo's index, so a repo whose convention is a superseding record is no longer denied by prose it installs.

No decision record moves: `specs/decisions/` stays as it is, and `CONTEXT.md`'s decisions index now states the threshold and the in-place supersession convention that universal guidance defers to it. `specs/architecture-principles.md` stops claiming decisions are never standalone files while this repo files them.

### Changed — one canonical review→fix stop policy, single-homed in `review-discipline` (#329)

The policy contradicted itself. `agents/reviewer.md`, `commands/build.md` and
`commands/harness.md` said cycles 1–3 run unconditionally with a hard stop at the
sixth; `skills/review-discipline/SKILL.md` and `commands/review.md` said a second
consecutive FAIL stops the loop — four cycles earlier. Which behaviour a run got
depended on which entry point it came in through, on a load-bearing spend breaker.

- **`review-discipline` now owns the rule**, written number-free: an unconditional
  window, a judged window whose convergence judgment must be *recorded*, a hard
  stop when the budget is spent, and an **operator hold** for the exhausted ticket.
  The other four files point at it and state no cycle count of their own.
- **`max_review_cycles` counts the cycles a run may spend** (5), not the ordinal of
  the call that trips. `unconditional_review_cycles` (3) becomes its own configured
  key: the old `max // 2` derivation returned the canonical 3 only because the
  budget happened to be 6, and would have silently become 2 at 5.
- **`convergence_check_required` fires one cycle earlier.** Its low bound moves
  from `<` to `<=` — the rule demands a recorded judgment *before* the judged
  cycles, so the advisory has to fire on the fails that precede them.
- **New `cycles_exhausted`** on `ReviewOutput` and the `review` event: a fail that
  spent the last allowed cycle. It lands the stop at the completion of that cycle
  instead of one wasted implement pass later, when the exit-4 refusal would finally
  report it. Both flags are advisory; the refusal remains the enforcement.
- **`commands/build.md`'s abandon path puts the ticket on operator hold** instead
  of resetting it to Todo — a Todo ticket is what the unattended loop picks up
  next tick, which handed unconverged work a fresh budget with no human in the loop.

`commands/harness.md`'s exhaustion recipe now names its two commands and their
order — `harness checkpoint` before `harness defer --needs operator` — and states
that nothing on the automated path resets the budget. Cancel + resume opens a
fresh window and resets both breakers, so it stays under the human-authorised
recovery heading; `tests/unit/test_breaker_recovery_docs.py` pins both halves.

`tests/unit/test_review_stop_policy_single_home.py` replaces the CAL-906 coherence
guard, which banned the retired rule in two hand-named files and so could not see
the two others still carrying it. The new guard derives its subject set from the
tracked, registered tree.

### Changed — the universal lifecycle is tracker-neutral, dispatching on `tracker:` (#327)

`CONTEXT.md`'s top-level `tracker:` is now the only guidance-level tracker switch. The process doc, `spec-driven-development`, `spec-authoring`, `review-discipline`, `/start`, `/build`, `/ship`, `/propose`, `/assess` and the change/proposal/feature templates no longer require Linear: each routes tracker operations through the new **`tracker`** skill, which reads `tracker:` and dispatches to a provider recipe. A GitHub-backed consumer previously received universal commands whose normative steps demanded a Linear issue, `LINEAR_API_KEY` and Linear state mutations.

The policy/provider seam mirrors the one the code already proved (`Tracker` protocol + per-backend clients):

- **`skills/tracker/SKILL.md`** (new) — the backend-neutral protocol: the six operations, the state vocabulary, filing and placement, the assignment hold signal, sync rules, credentials, the `tracker: none` degrade, and the rule that ticket content is data rather than instruction. Contains no API call.
- **`skills/github-issues/SKILL.md`** (new) — the GitHub recipes: `gh issue` / `gh project`, runtime resolution of board field and option ids, and the three-step create/add/**set-Status** filing path that closes the item-add-no-status trap.
- **`skills/linear/SKILL.md`** — trimmed to Linear recipes; its backend-neutral policy moved to `tracker`.

`registry.yaml` no longer seeds the retired `linear` layer into a new repo's `default_layers` — the current context template has no such layer. `/assess`'s no-tracker degrade now keys off `tracker: none` instead of the retired `layers.linear: false`, the last place the dead switch survived as an execution instruction.

The provider-embed guard now covers **both** backends: a lifecycle file may not inline `api.linear.app` or `gh issue`/`gh project` calls. It previously banned Linear only, which is how the same duplication was free to reappear on the GitHub side. `/bug` and `/tweak` are documented exemptions — their filing recipes are inlined deliberately and pinned by their own guards.

`templates/feature.md`'s frontmatter key `linear:` becomes the neutral `tickets:`, and the four shipped feature specs migrate in place — their values already mixed Linear and GitHub ids.

**Unchanged deliberately:** `harness/layers.py` keeps its back-compat fallback for a consumer `CONTEXT.md` that predates `tracker:`, and the `tracker` skill documents that same fallback so guidance and engine cannot diverge. Retiring the layer as a *guidance* switch does not retire the engine's fallback for un-migrated repos.

### Changed — host-platform abstraction and credential port out of the wrapper (#305)

Credential resolution, subprocess bounding and git-identity resolution move out of
`docker/harness-wrapper.sh` into `harness/hostenv/`, a stdlib-only package behind a
`HostPlatform` seam with macOS (Keychain) and Linux/WSL (file store) providers. The
wrapper becomes a delegating shim: one `python3 -m harness.hostenv env` call whose
NUL-terminated records it imports with `export`, never `eval`.

The logic is now reachable from the native `uv tool install` entry point and unit-tested
on both providers, including the WSL provider against a fixture credential store. An
unsupported platform now fails with a named error instead of emitting a blank credential
that surfaced much later as an in-container 401.

The `timeout`/`gtimeout` probe is replaced rather than ported for every path that can
reach Python — `HostPlatform.bounded_run` bounds its own child.

The image-freshness guard and source-checkout sync deliberately stay in shell: their job
includes detecting that the wrapper has no checkout behind it, which is exactly when
checkout-resident Python cannot be imported.

`tests/unit/test_wrapper_token_refresh.py` is retargeted from a text guard over shell to
the forwarding contract the shim still owns; its behavioural assertions moved to the new
`hostenv` modules, and the one property with no successor is named in that file.

### Changed — SPEC §16 records the persistent-runtime-host carve-out and its bound (#304)
The "long-running daemon / server" and "built-in scheduling" non-goals each gain a bounded exception clause pointing at ADR 0012 (`specs/decisions/0012-persistent-runtime-host.md`). Both entries keep their headline *and* their intent, because that intent — the CLI runs, completes, exits; cron/launchd/systemd trigger the harness — is exactly what bounds the exception; deleting it would leave the carve-out unbounded. The bound is now stated in §16 itself rather than only in the ADR: the host process holds no run state, and anything that outlives a request and describes a run has exceeded the carve-out and belongs in the ledger. That is a safety property, not documentation hygiene — the close gate's guarantee holds only because the ledger is a run's sole memory, so a host process caching run status would break it while appearing to work. Stating it in §16 makes an over-reaching future design reviewable against the spec, not only against the decision record. A new guard (`tests/unit/test_persistent_runtime_host_decision.py`) pins the coupling: while the ADR exists §16 must cite it by its real filename, the cited path must resolve on disk, and each amended entry must retain its intent — so reverting §16 to unannotated bullets, replacing an entry with a bare "see ADR 0012" stub, or renaming the ADR without following the link all fail the gate rather than silently leaving §16 contradicting a live decision.

### Changed — `close` absorbs transient merge and transition failures itself (#301)

`harness close` now retries the failures whose only recovery was "run it again" — a
push rejected by a concurrent close, a network blip on fetch or push, a tracker
request error, and a transition whose own post-write response did not confirm the
requested state. Up to 3 attempts with 2s then 8s of backoff, so an orchestrating
agent's decision after a pass is simply **exit 0 → done; non-zero → escalate**.

Deterministic failures are untouched and still reported on the first attempt: a
merge conflict, a failed merge, a failed git status or worktree creation, a ticket
the tracker reports as not found, and every exit-2 gate refusal. Exit codes,
`reason` tags and printed JSON are unchanged on every path — retry changes latency,
never the contract.

What the retry absorbed is recorded on the ledger's `close` event as `retries` and
`retried_reasons`, so a degrading tracker stays observable rather than being
silently ridden out.

### Changed — the attended-run spend scope is recorded where it is read (#299)

ADR 0011 scoped `loop.wall_clock_budget_minutes` to unattended runs, but the prose
that *defines* the knob still opened universal — in `CONTEXT.md`, in the
`templates/CONTEXT.template.md` block every self-hosting repo inherits, and in the
`commands/harness.md` stop rule an orchestrating session reads while deciding
whether a breaker refusal is legitimate. Each now states the mode it bounds in the
sentence that defines it, and names `loop.attended_idle_minutes` as where the other
half of the rule lives.

`specs/features/verb-model.md` recorded `reclaim --stale` as "the remaining reader"
of the mode; both readers have shipped, so it now says so and names the routine-path
guard. ADR 0011's status line and the source proposal's `status:` record the five
changes that implemented it, completing its breakdown.

Two new guards keep the correction from eroding: the wall clock's comment must scope
itself in its *first* sentence (a whole-comment containment test passes on the exact
defect, so the predicate is positional), and every sentence in `commands/harness.md`
naming the knob must name the mode it bounds.

### Changed — `reclaim --stale` measures an attended run against `attended_idle_minutes`, not the wall clock (#297)

The sweep now selects its staleness threshold by the run's declared mode: `loop.wall_clock_budget_minutes` (110m) for an unattended run, the new `loop.attended_idle_minutes` (480m) for one started `harness start --attended`. A longer threshold, not an exemption — a session abandoned overnight is still reclaimed by morning, so the board self-heals and worktrees do not accumulate.

This closes the half of [ADR 0011](specs/decisions/0011-attended-run-spend-scope.md) that no measurement can fix. A session paused on a question to the operator touches none of the three liveness clocks the sweep reads, because a human thinking looks exactly like an orchestrator that died; the operator would answer and find the ticket reverted to Todo underneath them.

The three-clock idle rule is unchanged, and the mode is not a fourth signal — it selects the *value* all three clocks are compared against, including the tracker's. Because the attended threshold is the longer of the two, the mode can only ever spare a run, never condemn one. An explicit `--older-than` still overrides both modes, and a ticket with no resolvable run row has no mode to read and falls to the wall clock, the bounded default. `SweepOutput` reports the applied attended threshold as `attended_older_than` beside `older_than`.

`attended_idle_minutes` follows the other `loop:` knobs: configurable in `CONTEXT.md`, shipped in `templates/CONTEXT.template.md`, and backed by `DEFAULT_ATTENDED_IDLE_MINUTES` so a repo with no `loop:` block runs the decided 480.

### Changed — the review wall-clock breaker applies to unattended runs only (#296)

`harness review`'s per-run wall-clock breaker measured raw age since `started_at`,
so an attended session's elapsed time included however long the operator took to
answer a mid-run question — time during which the run spent nothing. Past the
budget the finished work became un-certifiable and could not close.

The clock now applies to unattended runs only ([ADR 0011](specs/decisions/0011-attended-run-spend-scope.md)).
`evaluate_breakers` takes the mode as a keyword argument and skips **that check
alone**; `review` resolves the mode from the run row's `inputs_json` through the
shared `resolve_attended` helper #295 shipped.

Three properties bound the change:

- **The cycle ceiling stays unconditional.** It bounds the fix loop itself, which
  an operator's presence does not make cheaper. With both breakers eligible the
  reported reason is still `review_cycle_ceiling`, in either mode.
- **The exemption is never acquired by omission.** `attended` defaults to `False`,
  so a caller with no view of the mode inherits the bounded behaviour, and only
  the literal JSON `true` on the run row reads back as attended. A corrupt or
  hand-edited ledger can make a run more bounded, never less.
- **Neither threshold moves**, and no reason tag, exit code or output field changes.

`reclaim --stale` still applies the same threshold to every run; aligning the
sweep's scope is #297.

### Changed — the one-ceiling rationale cites the measurement instead of a refuted premise (#292)

`CONTEXT.md`'s `engine_timeout_seconds` comment ended by calling the single
ceiling a mis-fit: the design engine "studies a whole worktree" and is
"systematically slower" than the review engine, which "reads a diff", so one
knob for two workloads was a defect awaiting a split.

That premise was never measured, and could not have been. ADR 0009 records that
`review` carried no duration until #264/#265, so the 600 → 720 retune saw only
design's distribution and assumed review's. Once both were on record the claim
did not survive: design leads by 45s at the median (366s vs 321s) and *trails*
at both q3 (447s vs 457s) and max (561s vs 587s) — and the tail is the only part
a timeout ceiling interacts with. `specs/proposals/per-engine-timeout-ceiling.md`
rejected the split on that evidence; the sentence it refuted was still sitting in
the one file every agent is told to read first.

The comment now states why one ceiling is right — one distribution with noise,
not two — quotes the tail pair, and cites the proposal as the record. The
ceiling itself is untouched at 720s.

The correction is guarded rather than hand-checked, in the module #291 already
built for this comment (`tests/unit/test_context_template_loop_block.py`) rather
than a parallel one. It takes the same two-step shape: the premise is **derived**
from the proposal's committed latency table, and only then is the prose required
not to contradict it and required to quote it. Neither half stands alone — a
derivation nothing reads goes green while the sentence rots, and a phrase pin
goes green on a reword.

The coupling runs both ways on purpose. A re-measurement that inverts the tail
fails the derivation, because `CONTEXT.md` and the rejection both rest on the
premise it would overturn; a proposal that is renamed, deleted, or flipped to
`accepted` fails the citation. The parse answers `{}` rather than raising when
the table moves, so a non-vacuity anchor asserts it first — otherwise a reshaped
table would let every derivation range over an empty dict and quietly stop
measuring.

Honest residual, stated in the test as it is for the sibling divergence guard: a
false speed claim phrased without any of the markers still passes the marker
check. It is the same class the ticket names, not all possible false prose.

### Changed — the loop knobs carry one value in three places (#291)

`DEFAULT_ENGINE_TIMEOUT_SECONDS` moves 600 → 720, matching what this repo has
configured since 2026-07-30 and the treatment the other two loop knobs already
get. A repo with no `loop:` block now resolves the ceiling this repo's ledger

restated (the constant's name is `DEFAULT_` + the key upper-cased), so a fourth
knob is covered the day it is added, and the parse is the runtime reader's own
regex rather than a copy of it.

`CONTEXT.md`'s `engine_timeout_seconds` rationale no longer claims the code
default is deliberately held apart from the configured ceiling — they are now
the same number. That correction is measured, not hand-checked: the guard
derives the relation from the two values and then requires the sentence naming

The one-knob-two-workloads mis-fit the old sentence also named is unchanged and

### Changed — the async-runner helper has one home in the test tree, guarded against copy 27 (#279)

The same five-line event-loop runner — `new_event_loop` / `run_until_complete` /
`close` — was defined **26 times** across `tests/` under three names (`_sync`,
`_run_sync`, `run_sync`), two of them side by side inside the shared-helper
package itself, one private and one public. That contradicted the membership rule
`tests/_reclaim.py` states in its own docstring.

The cost was never the duplicated lines — they were byte-identical — but the
rationale. Exactly one of the 26 copies carried the docstring explaining *why* a
fresh loop is built instead of calling `asyncio.run`: `asyncio_mode = "auto"`
means pytest-asyncio can leave a loop dangling on the thread, and `asyncio.run`
refuses to run when one is already running. That reasoning was invisible from the
other 25 sites, so each new copy was written without it.

`tests/_asyncutil.py` is now the single home. It takes the `<domain>util`
spelling of `_gitutil` / `_cliutil` rather than the test-family spelling of
`_ledger` / `_reclaim`, and is stdlib-only, so it can never join an import cycle
or pull the CLI into collection. Its docstring carries the dangling-loop
rationale plus the two properties a careless rewrite would drop: the
`finally: loop.close()` that keeps a suite calling this hundreds of times from
leaking descriptors, and the absence of an `except` clause, since a helper that
caught and returned would turn a real ledger error into a green test.

`tests/unit/test_async_runner_single_home.py` holds the invariant. It derives its
subject set from `tracked_py_sources("tests")` rather than listing modules, so a
new test module is in scope the moment it is committed, and it matches on the
**AST** — any call to a `run_until_complete` or `new_event_loop` attribute —
rather than on text. That covers every prefixed, aliased and renamed form, and is
why the guard needs no self-exemption despite naming both constructs in its prose
and embedding the wrapper as a string literal: neither is an `ast.Call`. A
companion test pins that the canonical module defines exactly one runner, so the
guard cannot go vacuous by having nothing left to find.

**The move was less mechanical than the finding assumed.** The two loose
signatures (`(coro: Any) -> Any` and `(coro: object) -> object`) were the only
textual difference among the 26 copies, and the reason 10
`# type: ignore[return-value]` comments existed at call sites. The shared helper
is generic — `Coroutine[Any, Any, T] -> T`, `Coroutine` rather than `Awaitable`
because that is what `run_until_complete` accepts — typing every call site
precisely, so those 10 ignores were deleted rather than carried.

Converting the suite to `pytest-asyncio` or `asyncio.run` stays out of scope, and
the guard's docstring records that limit rather than leaving it implicit.

### Changed — a seam extraction must also say where the extracted module's tests went (#276)

- `review-discipline`'s **Architecture watchlist** check gains a second clause on the same *seam extraction* branch #273 amended: confirm the extracted module's tests moved with it — into a test module of their own, or stayed for a stated reason. ### Fixed — the feature-spec currency guard no longer reads a shallow clone's graft boundary as every spec's last commit (#326)

`tests/_gitutil.last_commit_date` (#280) asked git for the last commit touching a path and returned
the answer as if it were always real. In a shallow clone it is not: a grafted commit has no known
parents, so history simplification reports the graft boundary for **every** path whose true last
commit was never fetched. `actions/checkout` defaults to `fetch-depth: 1`, so CI read all four
feature specs as touched at HEAD and went red on whichever ones were not edited that day. `dev` was
red this way from #280's merge until now, and because `verify.sh` runs pytest first, the CLI smoke,
landing-page, design-token and changelog-fragment steps had not executed in CI for two commits.

The premise that made this hard to see is that a normal checkout has full history. This repo's own
checkout does not: it reports `is-shallow-repository: true` while carrying ~1200 commits behind two
grafted roots. The local gate is green only because no feature spec's last commit happens to sit at
a boundary — so refusing on the shallow *flag* would have turned every developer's gate red while

right is safe; returning one that is wrong is the defect.

The feature-spec guard deliberately does **not** catch the new error. A truncated tree must surface
as a red, named failure rather than a silent skip — skipping would restore the same invisibility one
layer down, and the guard's old skip message claimed to cover shallow clones when it never could.

Both workflows that run the gate now check out full history (`ci.yml`, and `release.yml`'s `verify`

from a throwaway worktree and never touches the main checkout (CAL-1154 Option 1),

### Fixed — the verb container no longer writes bytecode into the mounted host tree (#278)

Both container-invocation seams — the versioned `~/bin/harness` wrapper
(`docker/harness-wrapper.sh`) and `docker/docker-compose.yml` — now pin
`PYTHONDONTWRITEBYTECODE=1`.

Previously any Python run inside the container left `__pycache__/*.pyc` in the
bind-mounted host tree whose embedded source paths were the container's
(`/workspace/...`). CPython revalidates a cache entry against the source's
recorded mtime and size rather than its content, so a subsequent **host-side**
`bash scripts/verify.sh` loaded those entries and every test relying on
`inspect.getsource` / `linecache` failed with `OSError: could not get source
code` — a false red on the gate that certifies a review, in the window where a
red is most expensive.

The flag is pinned to the literal `1` rather than forwarded as a bare
`-e PYTHONDONTWRITEBYTECODE`, because CPython treats only a non-empty value as
on and a host exporting it empty would silently disable the protection — the
same reason `HARNESS_WORKSPACE_ROOTS` is pinned. It is set at the seams rather
than as a Dockerfile `ENV` because the wrapper's staleness guard compares the
image against `git log -1 --format=%ct -- harness/`, a path a `docker/`-only
change never touches, so an image-level default would not take effect until
something unrelated forced a rebuild.

The fix is preventive. A worktree that already contains container-authored
`.pyc` stays poisoned, because the stale entries are still mtime-valid; clear
them once with `find . -name __pycache__ -not -path './.venv/*' -exec rm -rf {} +`.

### Fixed — a failed `design` SUBMIT parse now records what would not parse (#277)

`harness design` fails its SUBMIT contract on 12.5% of attempts against
`review`'s 0.24% — the same engine, the same contract — and ADR 0007 D4 makes

### Fixed — the force-push guard resolves the real command, not just the first token (no ticket — see below)
- **Source: the idle-arm `/assess code` pass of 2026-07-15**, which found the guard recognised exactly one command wrapper (`env`) and matched the git executable by exact string. Both gaps were confirmed by driving the hook with real payloads before any change: `nohup git push --force origin dev` was **allowed**, as were the `command` / `exec` / `timeout 60` / `nice` / `stdbuf` / `xargs` spellings, `env nohup …`, and `sh -c "nohup …"` — nine plain force-push forms in total. So was `/usr/bin/git push --force origin dev`, an entirely ordinary invocation. The anchored deny globs did not backstop any of them: **both layers missed the same class.**
- **One root cause, two symptoms.** The guard's recognition of *which token is the git command* was too narrow — it basename-matched nested shells but not `git`, and stripped only the `env` wrapper. Executables are now matched on their **basename**, and a leading wrapper is resolved past to the command it runs.
- **The guard scans a wrapper's operands rather than modelling its option grammar.** A wrapper can carry its own options and even a mandatory operand (`timeout 60 git …`, `nice -n 5 git …`), so stripping the wrapper name alone still misses the command. Modelling each wrapper's flags is the brittle half — one unmodelled option silently re-opens the class, which is how this survived four rounds of hardening. Scanning has the safe failure mode: over-broad matching denies a non-force command (recoverable), under-broad lets a force-push through (not). The scan runs only when a wrapper prefix is present, so `echo git push --force …` is untouched.
- **The literal `xargs git push --force` form is now caught**, and the documented scope boundary is narrowed to match: a dispatcher that runs a command it *builds* (`find -exec`, `xargs` fed generated input) remains out of scope, but the literal spelling is a wrapper, not a generated command.
- **Every member of the wrapper set is now pinned by a test.** The set's original lone member, `env`, had **zero** cases despite the header claiming to cover "env-prefix" commands — the one untested recognition set is the one that turned out short. 31 new cases; the gate went 1475 → 1506.
- **This hook is defence-in-depth, not the control of record** — now stated in the header. It is a denylist parser over a Turing-complete surface, hardened four times in one release window with this as the fifth finding. The authoritative protection for `dev`/`main` is **server-side branch protection**, which no client-side parse can be argued past. Recommend adding it as an acceptance criterion on **CAL-1029** (go-public, already unblocked); an unattended run cannot file or edit tickets, so this note is the durable record.
- **No ticket:** found by an unattended routine whose Linear writes are classifier-blocked, so none could be filed. Full report: `assessments/2026-07-15-code.md`.

### Added — inbound grant covers patents and right-to-submit (CAL-1080)
- **Source: a review of the CAL-1078 inbound grant before the CAL-1029 flip.** That grant covered **copyright** only, leaving two gaps every standard contributor agreement closes. **Patents:** a contributor could contribute code reading on their own patent and later assert it against the project or its users — a copyright licence does not reach patent claims. **Right to submit:** nothing asked a contributor to affirm the code was theirs to give, which is the Developer Certificate of Origin's entire purpose; without it someone can contribute an employer's code, or code copied from an incompatible source, and the project has no recorded basis for having believed otherwise.
- **Standard text, not bespoke drafting.** The patent grant is Apache ICLA §3 plus Apache-2.0 §3's defensive termination (an entity that sues over the contribution loses its patent licence the day it files); the representation carries the DCO 1.1's substance — original work or a right to submit, employer entitlement addressed, third-party material identified, contributions as-is. Language argued over for twenty years beats anything drafted fresh for this repo, and `CONTRIBUTING.md` says so rather than implying the wording is original.
- **One assent mechanism, deliberately.** The DCO is normally a per-commit `Signed-off-by`. This repo already binds the copyright grant to the act of opening a PR, so the representation binds the same way — a second mechanism would be ceremony for a contributor base of zero. The existing "if you would rather not, say so in the PR" escape hatch now covers the whole grant.
- **Guards `test_contributing_states_patent_grant` / `test_contributing_states_right_to_submit`** pin both alongside the existing copyright-grant pin, including the defensive-termination clause (without which the patent grant is one-way) and the employer-IP limb (the most common way a contributor lacks the right to grant).
- **Legal review declined** (operator, 2026-07-15): with no other contributors and the going rate for an AI harness at zero, the lever these protect is largely theoretical and a review would cost more than it guards. Recorded so the decision is not silently re-litigated.

### Changed — relicensed: AGPL-3.0 engine, MIT installed guidance (CAL-1078)
- **Source: a pre-go-public licence review (blocks CAL-1029).** The repo shipped MIT (CAL-1025), which permits precisely what it should not: a fork taken proprietary and sold on with nothing returned. The licence had to become copyleft before the visibility flip made the grant public and, in practice, irrevocable.
- **The split, and why it is not one licence.** A single copyleft licence over the whole tree is the wrong instrument, because the repo holds two artifacts with different distribution models. The **engine** (`harness/`, `bin/`, `docker/`, `scripts/`) is a CLI someone would fork and productize — it is now **AGPL-3.0-only**: use it for anything, including commercially, but a derivative you distribute or offer over a network carries the same freedoms. The **installed guidance** is physically copied into a third-party repo and committed there (the copy-in model); copyleft on it would put AGPL files inside a proprietary codebase and block adoption of the very thing the harness exists to spread, while protecting nothing — a licence covers expression, not method, so anyone may read a skill and reimplement it. It stays **MIT** (`LICENSE-GUIDANCE`).
- **`registry.yaml` `files:` is the boundary, not a hand-kept directory list.** That block is by construction the set the installer copies out, so it *defines* what is MIT, and a newly registered file inherits the correct side with no licence edit. It spans whole directories today (`skills/`, `agents/`, `commands/`, `templates/`, `hooks/`, `process/`, `settings/`), which is what `LICENSE-GUIDANCE` declares as its scope.
- **The AGPL body is verbatim and pinned.** `LICENSE` carries the canonical gnu.org text with a *prepended* scope note (the body is never edited), verified word-for-word against the SPDX license-list copy before landing — 5,535 words, identical. `tests/unit/test_license_boundary.py` pins its sha256, so any edit to the operative text fails the gate.
- **The scope note is deliberately terse, and that bound is measured.** GitHub detects a licence with `licensee`, which needs a **98%** Dice score against the known text to report a match instead of "Other" — and the sidebar badge is the most visible signal that this repo is copyleft. Prepended prose dilutes that score: a first draft ran 157 words and scored ~98.6%, a 0.6-point margin on an estimate. The note was cut to a 47-word pointer (~99.6%), with the rationale left to `README.md` and `LICENSE-GUIDANCE` where it belongs anyway. `test_scope_note_stays_within_licence_detection_margin` bounds the note at 100 words, derived from the 99%-Dice inequality rather than guessed, so the margin cannot silently erode.
- **Guard `tests/unit/test_license_boundary.py`** holds the registry and the declared MIT scope in correspondence in **both** directions — nothing distributed escapes MIT (a file that did would ship AGPL into a consuming repo), and the scope neither reaches the engine nor claims a directory the registry does not distribute. Non-vacuity is anchored: a scope-parse returning everything, or a registry-parse returning nothing, fails.
- **`CONTRIBUTING.md` gains an inbound relicensing grant.** Under inbound-equals-outbound, one accepted outside PR would permanently foreclose dual-licensing, since nobody can relicense code they do not own. The grant keeps that option open; the section says so plainly rather than burying it, and states what to do if a contributor declines.
- **`BOOTSTRAP.md` `0.4.8` → `0.5.0`** — the installer copies `LICENSE-GUIDANCE` into the target repo root and commits it in **both** visibility modes. Without it the carve-out is invisible where it matters: the receiving repo holds unmarked prose cloned from an AGPL-licensed source, and a compliance scanner assumes the worst. It is a licence, not guidance, so it carries no `guidance:` header, has no version, and is not a `registry.yaml` entry — the lock records it, and the settings-JSON no-clobber rule applies. **`registry.yaml` `0.5.37` → `0.5.38`** (self-version bumped in header + `meta:` self-entry).
- **`pyproject.toml` declares `AGPL-3.0-only`.** The built wheel is `packages = ["harness"]` — engine only — so the carve-out does not apply to it.
- **Not done here:** the CAL-1029 visibility flip itself (this blocks it), and CLA automation. The inbound grant's wording is bespoke and carries legal weight — worth a professional read before the flip.
