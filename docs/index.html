Claude Code plugin

A spec-driven development process
for agent-driven repos.

harness is a development process shipped as a Claude Code plugin: nine lifecycle commands, the craft skills behind them, four agent roles, and enforcement hooks that make a green gate the only path to a shared branch. Install it, run /harness:init, and the repo owns its own contract from then on.

Let the agent do the judgement work; make the repo own the evidence.

What the harness owns

An AI agent does everything that needs judgement — the design, the code, the fixes, the answer to a review finding. The harness owns only the parts that must not depend on an agent remembering them.

One verification gate

The repo's verify command decides green and writes a marker named after the exact git tree it verified. Green over those exact bytes is the only evidence a completion claim may cite; one more edit invalidates it.

The spine

A repo-owned CLAUDE.md carries the iron laws, the lifecycle contract, and the repo's own config block — always loaded, never optional. Skills carry the depth and load by task.

Builder ≠ recorder

The agent that promises delivery is never the one that records it. The reviewer writes the as-built record from the diff, which is what keeps that record honest.

How a repo adopts it

The guidance ships as a plugin from this repo, which is also its marketplace. Three steps, then the process is live in every session.

1

Add the marketplace

/plugin marketplace add sluengen/harness

Points Claude Code at this repository as a plugin source.

2

Install the plugin

/plugin install harness@harness

Brings the commands, skills, agents, and hooks into your sessions.

3

Hydrate the repo

/harness:init

Interviews for the repo's values and writes the files that must be repo-owned: the spine, the specs scaffold, the infrastructure record, and — where there is no gate yet — a scripts/verify.sh skeleton with the marker write. After a plugin update, /harness:init --refresh regenerates the spine's generated block and nothing else.

How work arrives

Three routes, by weight. All three take the same isolation and the same gate — what differs is how much is decided before the first line of code.

Fast lane

No ticket · ask and it ships

A small fix needs no command and no ticket. It still runs on its own branch, in its own worktree, through the same gate. Anything that changes documented behaviour, spans commits, or needs independent review becomes a ticket instead.

A ticket

The unit of tracked work

A change spec lives on the tracker issue and is built end to end by one command. The reviewer is a separate agent in a fresh context, and its verdict binds to the exact git tree it read — the tree that ships must be that tree.

A proposal

Decide before spending build time

For work that is unconfirmed, risky, or too big for one change. It ends in one explicit state — never half-decided — and an accepted proposal spawns the tickets that build it.

The gate, and what a green means

Green is a claim about bytes, not about a session

Every repo names its own verify command; here it is bash scripts/verify.sh, and it runs the same way in a checkout, in CI, and in the nightly promotion. The last thing it does on green is write a marker named after the git tree object it just verified.

That is what makes the evidence checkable by something other than the agent's memory. A review verdict binds to a tree oid; the gate marker names a tree oid; the push guard reads the tree being pushed. An amend that rewrites no bytes voids nothing, and one more edit voids everything.

The marker

<git-common-dir>/harness/gate/<tree-oid>.json

Written last, so a failing stage means no marker. The claim it licenses is narrow and exact: green over these exact bytes. Hooks are evidence plumbing, not authority — the controls of record stay server-side, in branch protection and gate output in CI.

What the plugin installs

The whole surface, as the repository carries it. Commands are the entry points; skills are the depth they load by task; agents are the roles a run dispatches; hooks are the enforcement.

Commands 9

The entry points. Only /harness:init needs its prefix spoken.

  • /buildImplement, verify, review, and ship a ticket — the one lifecycle driver.
  • /captureFile an already-decided change straight to Todo.
  • /proposeWork an idea before it becomes work; accepted proposals spawn tickets.
  • /reviewReview the current branch, when a branch needs only that.
  • /routineOne unattended cycle: discover the next ticket, build it, ship it.
  • /promoteMove completed work toward release along the repo's role branches.
  • /digestThe operator's console: report, then drain held decisions.
  • /assessRun a periodic whole-system health assessment.
  • /harness:initHydrate a repo — the one command that needs its prefix.

Agents 4

The roles a run dispatches, each in its own fresh context.

  • devImplementation — test-first, strictly in scope, verified before handoff.
  • reviewerThe final gate before merge; records what actually shipped on PASS.
  • architectData models, contracts, decisions — design artifacts, never code.
  • stewardPeriodic health assessment: the cross-file patterns no per-change review sees.

Hooks 5

Three refuse, two advise. What a refusal rests on is evidence — a gate marker over the tree being pushed, or the shape of the command itself — never a branch name granting an exemption.

  • gate-evidence-guardRefuses ending a turn that claims completion with no fresh marker over the worked tree.refuses
  • push-target-guardRefuses a push to a protected branch unless a fresh marker covers the pushed tree.refuses
  • git-push-guardRefuses a history rewrite — --force in any spelling.refuses
  • prompt-guardFlags injection-shaped content on write.advises
  • workflow-guardFlags a source edit made on the default branch or outside a worktree.advises

Skills 14

Loaded by task, not all at once. The builder and the reviewer read the same files, so the bar is identical on both sides.

  • engineeringThe build leg of the triad: durable principles, test-first method, scope, the gate.
  • architectureThe design leg: cross-cutting decisions, recorded in the spec they govern.
  • infrastructureThe operate leg: promotion, release, CI/CD, what a gate means at each boundary.
  • spec-authoringThe craft of writing any spec — proposal, change, or as-built.
  • review-disciplineSpec compliance then quality, and the defect classes that read as green.
  • systematic-debuggingReproduce, isolate the root cause, fix minimally, prove it fixed.
  • worktree-isolationEvery multi-commit task on its own branch in its own worktree.
  • work-discoveryHow an unattended routine picks its own next ticket, and what it must skip.
  • assessment-craftThe finding bar for a periodic audit, and the insight-versus-finding test.
  • ux-designDesigning a user-facing surface — flow, information architecture, every state.
  • design-systemBuilding UI with a repo's own tokens and primitives rather than degrading them.
  • writing-qualityPlain prose; kill the predictable AI-writing patterns.
  • github-issuesThe GitHub provider recipes for reading and updating the queue.
  • linearThe Linear provider recipes for the same backend-neutral contract.

This repository

The plugin's source, dogfooding itself

Every change here ships through the process the plugin publishes, against the same gate. Three parts: the guidance surface above, the gate (scripts/verify.sh), and the guards — admitted by a written rule rather than by momentum, so a guard exists because a class of defect exists, not because someone once had a hunch.

No runtime, nothing to install

There is no CLI and no service behind any of this. Python here is tooling only — the gate, the token generator, the Codex compile step, the mutation instrument. Work moves dev → main, and what lands on release is exactly the tree that was gated.
