A plugin for Claude Code + Codex

Ticket to merged,
run by agents.

harness ships as native plugins for Claude Code and Codex that run a repo's delivery loop with agents: ticket to spec, test-first build, independent review, gated merge — on demand or unattended. Install the plugin, hydrate the repo, and every agent session in it works the same process.

Built on Lean principles: do less, build quality in, reduce waste, flow, stop the line, improve continuously.

What it does

The agent does the judgement work — the design, the code, the answer to a review finding. The plugin gives that work one loop, and every stage ends on a pass/fail signal the agent can act on.

Spec, then build

/capture files a decided change as a ticket with its change spec and acceptance criteria; /propose works an undecided one to a decision first. /build takes the ticket onto its own branch in its own worktree, locks the tests, and builds against them test-first.

Independent review

A separate agent in a fresh context reviews the diff against the spec and runs the gate itself. It returns PASS, FAIL or DEFER, and on PASS it — never the builder — writes the as-built record of what shipped.

Gated merge

/promote rebases onto the integration branch, runs the gate again over the exact tree that will land, pushes, and closes the ticket. The same command moves completed work along the repo's release branches.

/routine runs the loop unattended: it picks the next ready ticket, builds it and lands it, and holds the ticket for a person rather than push past a red gate or a review that will not converge. Every build ends with a short reflection filed to an improvement ledger; /assess runs periodic health checks and /drain clears what has accumulated.

How it decides

Hydration writes the process into the repo as the spine — AGENTS.md, loaded in every session. CLAUDE.md imports it and adds that host's deltas, and the repo's commands, branches and tracker live in harness.yaml.

An operating context

The stage the repo is at and the risk it accepts, stated once so every rule is read against it. A pre-user repo accepts a defect a revert fixes in an hour; it never accepts losing user data, leaking a credential or moving money wrongly.

Six principles, seven laws

Lean, applied to agent-run repos, each principle stating what it refuses — with do less overriding the rest. The laws are the per-change obligations derived from them: no claim of done without gate output read this session, and no editing a test while building against it.

Lanes and holds

Three assurance lanes — fix, change, feature — so a one-line fix and a contract change are not weighed the same. Work that reaches user data, credentials or money stops and waits for a person, and a ticket held for a person is never picked up by the unattended loop.

How a repo adopts it

This repo is the plugin marketplace for both hosts. In Claude Code the install steps are slash commands typed in a session; in Codex they are shell commands run in your terminal.

1

Add the marketplace

# Claude Code, in a session
/plugin marketplace add sluengen/harness
# Codex, in your terminal
codex plugin marketplace add sluengen/harness

Points either host at this repository as a plugin source.

2

Install the plugin

# Claude Code, in a session
/plugin install harness@harness
# Codex, in your terminal
codex plugin add harness@harness

Brings the host-native workflows, skills, roles, and hooks into your sessions.

3

Hydrate the repo

# Claude Code, in a session
/harness:hydrate
# Codex, in a session
ask to hydrate Harness

Writes the repo-owned files — harness.yaml, the spine, rules, role adapters and the specs scaffold — but never a gate: that stays the repo's own. Run it again after a plugin update; it refreshes the plugin-marked blocks and leaves repo-owned files alone.

How work arrives

Three routes, by weight. All three take the same isolation and the same gate — what differs is how much is decided before the first line of code.

The fix lane

No ticket · ask and it ships

A small fix needs no command and no ticket. It still runs on its own branch, in its own worktree, through the same gate. Anything that changes documented behaviour, spans commits, or needs independent review becomes a ticket instead.

A ticket

The unit of tracked work

A change spec lives on the tracker issue. One command takes it to a reviewed branch and a second lands it. The reviewer is a separate agent in a fresh context; its verdict covers the tree it read, and a second gate over the tree that lands is what licenses the push.

  1. spec
  2. build
  3. review
  4. gate
  5. land

A proposal

Decide before spending build time

For work that is unconfirmed, risky, or too big for one change. It ends in one explicit state — never half-decided — and an accepted proposal spawns the tickets that build it.

  1. draft
  2. decide
  3. spawn tickets

The gate, and what a green means

Green is a claim about bytes, not about a session

Every repo names its own verify command; here it is bash scripts/verify.sh, and it runs the same way in a checkout, in CI, and in the nightly promotion. It runs its stages and exits: it writes no evidence of its own.

What makes the claim checkable is that it is narrow enough to re-run. A green is green over the exact bytes it ran on — nothing else — so an amend that rewrites no bytes changes nothing, and one more edit invalidates the run. The builder who ran it and read the output is who holds that claim, which is why the gate runs again over whatever the branch has become at landing.

  • mypy
  • pytest + coverage floor
  • design-token drift

What a green licenses

green over these exact bytes — and no others

Any stage failing means no claim at all. The assurance is this gate, run and read by the builder, plus the independent review — one hook refuses and three advise, and none of them is the assurance. Whatever server-side controls a repository runs are its own.

What the plugin installs

The whole surface, as the repository carries it. Both hosts read the same skills/ — the lifecycle workflows and the craft skills behind them — and four hooks sit behind them as a backstop.

Workflows 9

The entry points, on both hosts. Each ships once, as a skill; three are operator-triggered only, and /routine, /build, /review, /drain, /assess and /promote stay model-invocable because each answers to a caller that is not a human at a prompt. In Claude Code each runs as /harness:<name>; in Codex, ask for it by name.

  • /buildImplement, verify and review a ticket, ending at PASS.
  • /captureFile an already-decided change straight onto the queue.
  • /proposeWork an idea before it becomes work; accepted proposals spawn tickets.
  • /reviewReview the current branch, when a branch needs only that.
  • /routineOne unattended cycle: discover the next ticket, build it, land it.
  • /promoteLand a reviewed branch, or move completed work toward release along the repo's role branches.
  • /drainClear what has accumulated for the operator: held tickets, then the improvement ledger.
  • /assessRun a periodic whole-system health assessment.
  • /harness:hydrateHydrate a repo — first time or after a plugin update.

Agents 5

Claude's roles. Codex dispatches the same roles through its native adapters in .codex/agents/.

  • devImplementation — test-first, strictly in scope, verified before handoff.
  • reviewerThe final gate before merge; records what actually shipped on PASS.
  • architectData models, contracts, decisions — design artifacts, never code.
  • stewardPeriodic health assessment: the cross-file patterns no per-change review sees.
  • harness-auditHydration's close-out: reads a hydrated repo and reports drift against the current plugin.

Hooks 4

One refuses, three advise. The refusal is the test lock, and it rests on what the run declared about itself — never on a branch name granting an exemption. The assurance is not the hooks: it is the gate the repo declares, run and read, plus the independent review.

  • test-lock-guardRefuses an edit to a test file while a run has declared its tests locked.refuses
  • push-target-guardFlags a push aimed at a branch the repo declares under branches:.advises
  • prompt-guardFlags injection-shaped content on write.advises
  • workflow-guardFlags a source edit made on the default branch or outside a worktree.advises

Craft skills 8

Loaded by task, not all at once, alongside the workflows above. Both hosts read the same files.

  • engineeringThe build half of how and what: durable principles, test-first method, scope, the gate.
  • architectureThe design leg: cross-cutting decisions, recorded in the spec they govern.
  • authoringThe craft of anything a downstream agent reads and acts on — a spec, a ticket body, a design hand-off, and the prose all three are written in.
  • review-disciplineSpec compliance then quality, and the defect classes that read as green.
  • worktree-isolationEvery multi-commit task on its own branch in its own worktree.
  • work-discoveryHow an unattended routine picks its own next ticket, and what it must skip.
  • trackerOne set of ticket semantics — lanes, holds, dependencies, priority, the ledger — over whichever backend the repo declares.
  • design-systemThe eight-tier design system itself — structure, token model and token builder — carried as assets hydration copies into the repo that turns the layer on.

This repository

The plugin's source, dogfooding itself

Every change here ships through the process the plugin publishes, against the same gate. Three parts: the guidance surface above, the gate (scripts/verify.sh), and the guards — admitted by a written rule rather than by momentum, so a guard exists because a class of defect exists, not because someone once had a hunch.

No runtime, nothing to install

There is no CLI and no service behind any of this. Python here is tooling only — the gate, the token generator, the mutation instrument — and the hooks run on Node. Work moves dev → main, and what lands on release is exactly the tree that was gated.
