### Fixed — the verb container no longer writes bytecode into the mounted host tree (#278)

Both container-invocation seams — the versioned `~/bin/harness` wrapper
(`docker/harness-wrapper.sh`) and `docker/docker-compose.yml` — now pin
`PYTHONDONTWRITEBYTECODE=1`.

Previously any Python run inside the container left `__pycache__/*.pyc` in the
bind-mounted host tree whose embedded source paths were the container's
(`/workspace/...`). CPython revalidates a cache entry against the source's
recorded mtime and size rather than its content, so a subsequent **host-side**
`bash scripts/verify.sh` loaded those entries and every test relying on
`inspect.getsource` / `linecache` failed with `OSError: could not get source
code` — a false red on the gate that certifies a review, in the window where a
red is most expensive.

The flag is pinned to the literal `1` rather than forwarded as a bare
`-e PYTHONDONTWRITEBYTECODE`, because CPython treats only a non-empty value as
on and a host exporting it empty would silently disable the protection — the
same reason `HARNESS_WORKSPACE_ROOTS` is pinned. It is set at the seams rather
than as a Dockerfile `ENV` because the wrapper's staleness guard compares the
image against `git log -1 --format=%ct -- harness/`, a path a `docker/`-only
change never touches, so an image-level default would not take effect until
something unrelated forced a rebuild.

The fix is preventive. A worktree that already contains container-authored
`.pyc` stays poisoned, because the stale entries are still mtime-valid; clear
them once with `find . -name __pycache__ -not -path './.venv/*' -exec rm -rf {} +`.
