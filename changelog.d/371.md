### Fixed — worktree teardown no longer deregisters worktrees it was not asked to touch (#371)

`teardown_worktree` removed its own worktree correctly and then ran a bare,
repo-wide `git worktree prune`. That command takes no path. Every verb runs in
the container, where the repo is mounted at `/workspace` and nothing else on the
host filesystem exists — so the prune read every worktree registered outside the
mount as missing and deleted its admin entry under `.git/worktrees/<name>/`. The
directory survived on the host, so nothing looked wrong until something read that
tree and git answered `fatal: not a git repository: <repo>/.git/worktrees/<name>`
with exit 128, arriving as a wall of red in tracked-tree guards the change never
touched. A host-side prune does not do this, which is why the failure was twice
recorded as a race between concurrent sessions rather than as this.

Teardown now names the one path it was asked to reclaim: `git worktree remove
--force <path>` clears that worktree's directory *and* its admin entry, and
provably leaves every other registration alone. It runs whether or not the
directory is still present — git clears a registration whose directory is already
gone — which is what keeps a stale entry from accumulating in place of the
retired prune, and what stops a later `git worktree add` at the same path being
refused. The registry clear now answers to the same `.worktrees/harness/` area
guard as directory removal, so a path teardown may not delete is also a path it
may not deregister. The two `git worktree add` rollback paths
(`harness/worktree.py`, `harness/promotion.py`) carried the same unscoped prune
and the same exposure; both are scoped the same way.

`tests/unit/test_no_unscoped_worktree_prune.py` bans the call outright across
`harness/` — `git worktree prune` has no scoped form, so the token pair is the
defect rather than an argument to check — and
`tests/integration/test_docker_worktree_prune.py` proves the fix in a real
container: a worktree registered outside the mount survives a teardown run
inside it.

**Departure from the design, recorded.** The design specified a new
`prune_worktree_entry` primitive that located the entry itself by resolving each
`.git/worktrees/*/gitdir` and comparing paths. Probing git 2.50.1 — the version
the image pins — established that `git worktree remove --force <path>` already
clears the admin entry for a worktree whose directory is missing, in both the
absolute and the relative (`worktree.useRelativePaths=true`) pointer forms, and
that it prunes no other entry while doing so. Scoping through git rather than
reimplementing a slice of its on-disk registry keeps the fix to three call sites
and leaves no second copy of git's layout to rot. It also preserves the retired
prune's treatment of a locked worktree, which git refuses to remove and which the
design's primitive would have deleted.
