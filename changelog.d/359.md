### Added — `review` refuses a polluted run worktree before spawning the engine (#359)

A run worktree carrying thousands of untracked files drowns the review engine's
tool-using pass. #205 traced that cause and answered it with a rule an operator
has to keep — "never gate in the run worktree" — and #208 kept the rule and still
arrived at review with 3,555 files against 578 tracked: the review burned the
whole 720-second engine ceiling and returned `engine_timeout` having reviewed
nothing, while the same tree cleaned to 586/578 returned a real verdict in ~9
minutes.

`harness review` now measures the tree before it spawns anything and refuses
exit 5 with `reason=polluted_worktree` when the excess is past the new
`loop.untracked_file_limit` (default 1000; `0` disables it, the escape hatch for
a repo whose gate genuinely needs a large untracked tree). The refusal names the
counts, the largest top-level entries and the remedy, costs no review cycle and
no wall-clock budget, and leaves the ticket where it stopped. Measured at ~90ms
on a real polluted worktree, against the 720 seconds it replaces.

The `reason` and the exit code are both distinct from `engine_timeout`, which is
the point rather than a formality: a polluted tree *presents* as a timeout, so a
shared tag would leave the ledger unable to say whether the engine hung or the
harness refused to let it.

The check fails **open** without exception — a disabled bound, a path that is not
a git top-level, a wedged or failed `git ls-files`, an empty index all proceed to
review, because a guard that stops a run may rest only on evidence it gathered.
Its scan reads directory entries only, never following symlinks and never
descending into `.git`, and is capped so an enormous tree costs what a small one
does. Only depth-1 path segments are ever reported, so a secret at the worktree
root is aggregated rather than named.
