### Fixed — a reviewer that emits no SUBMIT line is infra, not a `fail` verdict (#270)
- `review` recorded a missing, malformed, or unknown-verdict `SUBMIT` line as an ordinary code-review `fail` carrying a sentinel issue. The reviewer had delivered no verdict at all, so this cost the run one of six review cycles with nothing to fix, bounced the ticket back to In Progress as though the diff were rejected, and was indistinguishable in the ledger from a real finding — **38 of 115 recorded fails, 33% of the rate #262 had just made queryable**. It now exits `EXIT_INFRA_FAILURE` (3), the same classification the engine timeout and both sandbox walls already carried on the same principle, so the existing #262 `except` wrapper records it as a refusal (`outcome='failed'`, no `verdict`): no cycle consumed, no gate opened, and the ticket rests In Review where the other infra walls leave it. The orchestrator's correct response was already "re-run review", which is what exit 3 means — the old contract instead invited it to fix a sentinel naming no defect.
- Two `reason` tags rather than one, mirroring what `design` resolved for the identical failure first: `no_submit` (no `SUBMIT:` line anywhere) and `malformed_submit` (one was seen but none parsed), so "did the reviewer stop submitting, or start submitting badly?" is answerable instead of collapsing into a single bucket. Being the second copy of the pair, the literals move to `harness/events/payloads.py` beside the other shared telemetry vocabulary and `design` imports them, so one protocol failure has one name across both engine verbs. `scan_submit_line` stays pure and gains a `submit_failure` discriminator — the verb branches on structure, so a reviewer whose genuine finding happens to be worded like a sentinel is still a `fail`. `commands/harness.md` 0.2.17 → 0.2.18 (registry 0.5.108 → 0.5.109).
