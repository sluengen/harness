### Added — a shared mutation harness, so its rules are structural not remembered (#360)

`scripts/mutate.py` takes the one genuinely bespoke part of proving a new guard —
the mutation table, which stays outside the repo — and makes everything around it
structural: backup and restore, landing, containment, the green-baseline
precondition, the runner, and the kill/survive determination.

An entry **declares the tests it must kill**, and the harness compares the
observed failure set to that prediction by **equality**. That is one rule
covering both directions of the failure this ticket exists to remove: a no-op's
observed set is empty and a collection-breaker's is a strict superset, so neither
can be recorded as the kill it appears to be (#207's aggregate assert, #336's
four no-ops that evaluated to the original value). There is deliberately no flag
that rewrites a prediction from what was observed.

Every refusal happens before any file is written, in order: table, containment
(a caller-supplied sentinel proves the tree is the intended one), landing (`old`
occurs exactly once, with zero and two as distinct messages), a green baseline,
and a prediction that names tests the baseline actually passed. Restoration reads
only from byte-for-byte backups; the harness spawns no `git` at all, which
`tests/unit/test_mutate.py` pins structurally.

`scripts/_mutate_outcomes.py` reads node ids from pytest verbatim rather than
reconstructing them from `--junitxml`'s `classname` — reconstructing instead of
observing is the step that lied in #207. The runner takes a pytest selection, so
a tick can mutate against `-m "unit or guard"` rather than the whole suite.

The child pytest gets a fresh `PYTHONPYCACHEPREFIX` per run. CPython validates a
`.pyc` on the source's `(mtime, size)`, and a mutation is very often the same
size as what it replaced — `a + b` → `a - b` — so an in-tree `__pycache__`
written in the same clock second serves the unmutated module and the entry
reports SURVIVED having never run.

A build-time instrument, not a gate stage: `scripts/verify.sh` does not run it,
and a guard keeps it that way.
