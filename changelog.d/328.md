### Fixed — promotion escalation routes through the tracker seam, so the terminal works on GitHub (#328)
- `promote escalate` constructed a `LinearClient` directly, read `LINEAR_API_KEY`, required a Linear team and caught Linear-specific errors — while this repo runs `tracker: github`. Backend selection had two sources of truth: every other writing verb follows `CONTEXT.md` → `tracker:` through `tracker_client()`, and escalation silently followed Linear, so the prescribed non-success terminal was unreachable on the backend the repo dogfoods — a blocked promotion refused `blocked` however the repo was configured. It now resolves the client from the factory and catches only the tracker-agnostic errors; `harness/cli/promote.py` imports nothing from `harness.linear` or `harness.github`, pinned by an AST scan rather than only behaviourally.
- **`Tracker.create_issue` loses its Linear addressing**, becoming `(*, title, description, project)`. `team_key` is deleted rather than renamed: a team is a Linear concept GitHub can never honour, so a caller supplying one is a caller that knows which backend it holds. The team moves into `LinearClient` as config (`repo.linear`, already threaded in by the factory for #174), and a client built without one raises `LinearConfigError` before any request. This retires the `--team` flag and with it the `unresolved_target` refusal, whose only trigger was that missing team; `--project` remains the one nullable scope flag, unset meaning the backend's natural queue.
- **`GitHubClient.create_issue` now sets the new item's board Status to Todo**, not merely adding it to the board. An item added with no Status is invisible to every Todo-scoped reader, so add-only filed an escalation nobody was queued to act on — the terminal would have stayed broken on GitHub even after the routing fix. The old test asserted `"AddItem" in ops`, which stayed green through exactly that gap; it now asserts the `SetStatus` option id.
- `tracker: none` gains a `no_tracker` refusal carrying the rendered title/body. Recording `escalated` with a null ticket was rejected — that state means a ticket is waiting for a human — as was `defer`'s exit-0 `skipped_no_tracker` shape, which is honest only because that write decorates a ticket that already exists; here the escalation *is* the terminal, and the payload is the only place the evidence can go.
- `harness/cli/promote.py` joins the `architecture_watchlist`. **Departure from the design, recorded:** the design read the trigger as prescribing a `promote_escalate.py` extraction. Declined — the file's `# size:` marker records a deliberate decision that the CLI surface stays whole, the design did not engage with it, and the extraction is orthogonal to the backend-coupling defect. ADR 0003 and the `local-promotion-steward` proposal still call the terminal a Linear ticket; both are point-in-time records, left for their own correction ticket on the #315 precedent.
