### Added — `harness serve`: a persistent host process spawning one-shot verb containers (#307)

ADR 0012's runtime host. `harness/hostenv/spawn.py` becomes the one home for
`docker run` construction, shared by the socket path and the client's
direct-spawn fallback so the two cannot drift into different security postures.
The spawner's load-bearing property — the caller never specifies the mount,
image, privilege or env — is enforced positionally: every caller-derived token
lands after the image, where docker parses a command rather than options.

`docker/harness-wrapper.sh` is that spawner's live caller: its tail execs
`harness.hostenv.client`, which routes the verb through a running `harness serve`
when one is listening and spawns the identical container itself when none is. The
wrapper fell from 158 to 116 executable lines; its ratchet was re-baselined
165 → 120. Credentials and git identity are resolved on **every** request through
the `harness.hostenv.host` providers, against the repo the request names — where
both paths previously forwarded whatever ambient environment existed at bind time,
so a `harness serve` started from a shell without credentials spawned
credential-less containers and an expiring token was never renewed.

A host Python 3.11+ with the harness package importable is now **required** by the
wrapper; a missing interpreter is a hard error naming `HARNESS_HOST_PYTHON` where
it used to be a warning. The image-freshness guard and source-checkout sync stay
in bash deliberately: they must work when no checkout-resident Python exists.
