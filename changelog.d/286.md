### Fixed — the image-staleness guard now measures the ref the loop ships to (#286)

The wrapper's staleness guard compared the image against `refs/heads/<base>` — the
one ref the verb loop never advances. `close` merges and pushes `origin/<base>`
from a throwaway worktree and never touches the main checkout (CAL-1154 Option 1),
and `start` bases each worktree off the remote ref. So once nobody ran `git pull`
by hand, the measured value was frozen and non-increasing and the guard could
never fire again — failing open in exactly the scenario it was written for.

Observed: the checkout sat 37 commits behind `origin/dev`, and #278's shipped,
reviewed, closed fix was not in effect on the machine running the loop, with no
signal that the engine and the record disagreed.

The wrapper now fast-forwards its own checkout to `@{upstream}` before measuring
it. Notes on the shape of the fix:

- It advances the checkout rather than measuring `origin/<base>` and building from
  a detached worktree, because `~/bin/harness` is a symlink into the working tree:
  measuring the remote would rebuild the image correctly while still executing
  stale wrapper text, leaving a wrapper fix (which #278 was) just as un-live. A
  fast-forward cannot re-exec the running script, so a wrapper change takes effect
  on the next invocation.
- `fetch` + `merge --ff-only`, not `pull --ff-only`: operator gitconfig
  (`pull.rebase`, `pull.ff`) must not be able to change what the guard does, and a
  network failure and a divergence need different messages.
- A successful fast-forward that touched `harness/` is itself a rebuild trigger.
  `git log -1 --format=%ct -- harness/` is not monotonic across a fast-forward —
  history simplification resolves a merge to the feature commit's own committer
  date, which can predate the image — so the timestamp comparison alone can stay
  false while the tree really did move.
- It only ever fast-forwards. A diverged checkout is reported on stderr with both
  counts and left untouched; a missing upstream, unreachable remote, or refused
  fast-forward each warn and continue. No outcome changes the exit code, and
  nothing is written to stdout. An explicit `HARNESS_IMAGE` suppresses the sync
  along with the rebuild.
