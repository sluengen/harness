### Fixed — `close` reports the merge/push failure reason it already computed (#300)

`harness close` classified its own step-6 failures precisely — `close_merge`
raises seven distinct reasons — and then discarded every one of them, so a
merge conflict (needs work on the run branch) and a lost push race (a plain
retry) both surfaced as a bare exit 1 with no `reason` key. An orchestrating
agent had to parse the human message or guess.

The reason is now propagated rather than translated: `close_merge` owns the
vocabulary as a `CloseMergeReason` literal, and `close` passes it through at
both boundaries that can raise it — step 6's merge/push and step 3's
`worktree_porcelain`, the only path from which `git_status_failed` is
reachable. Exit codes are unchanged and no exit-2 refusal gains or loses a
reason.

`close`'s exit-1 vocabulary is now two named, disjoint families —
`TicketFailureReason` (the merge landed, the ticket did not follow) and
`MergeFailureReason` (the merge did not land) — so which side of the merge a
failure sits on is readable from the tag alone. The ledger benefits too: a
classified merge failure records its own reason instead of collapsing into the
unexpected-error tag, so conflicts can finally be counted against lost races.

A totality test derives the expected reason set from `harness/close_merge.py`
by AST rather than hand-listing it, so a reason added there later fails the
gate instead of silently arriving untagged.
