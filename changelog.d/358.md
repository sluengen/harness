### Changed — the verify gate runs the suite across the host's cores (#358)

`scripts/verify.sh` ran the whole suite in one serial pytest process. It now runs
two stages partitioned by the `docker` marker: `-m docker` serially — those tests
build and run the shared `harness:test` image tag, so no two of them may run
concurrently — then `-m "not docker"` across `-n "${HARNESS_TEST_WORKERS:-auto}"`
workers. One coverage floor, `--cov-fail-under=90`, is evaluated last on the union
of both stages, so it measures exactly the population it measured before.

Measured on an 8-core host at `6e4174b`: the pytest stage goes from ~224s to ~64s.

The ticket asked to parallelise "the unit tier". Re-measuring after #336 landed
honest tiers showed that tier is already 9.1s of the 224s — the cost is the ~1,933
process-spawning `integration` tests. The boundary that buys the win, and the one
the ticket's own dependency argument and AC-2 name, is the shared image tag rather
than the tier; everything outside that capability is safe to distribute.

`pytest-xdist>=3.5` joins the `dev` extra, and the gate preflights `import xdist`
so a venv predating this change exits the reserved `GATE_UNRUNNABLE_EXIT` (97,
`blocked`) instead of pytest's usage error, which the promotion classifier cannot
tell from a red tree. `addopts` deliberately does not gain `-n`: an ad-hoc
`pytest <file>::<test>` stays serial, live-output and debuggable.

`test_tiers_corpus.py::test_the_gate_still_runs_the_whole_suite` (#336) banned any
`-m` on the gate's pytest lines as a proxy for "the gate does not narrow the
suite". It is superseded by
`test_verify_parallel_tiers.py::test_the_gate_stages_partition_the_whole_suite`,
which asserts the property itself by collecting each selection: no test in two
stages, none in neither. That is strictly stronger — the ban would have passed a
gate that added `--ignore` or `--deselect`.
