How we build · operating model

The Four Loops

Four nested loops, one inside the next. The innermost — Build — spins fastest and does the work; each loop that encloses it runs on a longer cycle and steers the ones within. Intent flows inward (strategy becomes specs becomes tasks becomes code); feedback flows back outward. Ring size = cycle length.

How the loops are triggered

Scheduled locally — by choice

Claude Code can schedule these routines itself; the only question is where they run. The Build loop drives the local harness Docker app (it needs the Mac Keychain token and your ~/.codex auth), so the autonomous loops run on this machine. That's a deliberate choice — and local scheduling is actually finer-grained than the cloud.

Local routines today

A local trigger (launchd / cron, a desktop scheduled task, or a kept-open /loop session) fires each run on your Mac with full local credentials. Granularity down to 1 minute, so Hourly Build and Weekly Quality are trivial. Trade-off: the machine has to be awake.

/schedule Cloud routines if ever needed

Cloud Routines run on Anthropic's infrastructure even with the laptop closed — but each run is a fresh clone that can't reach the local harness app. The escape hatch for laptop-off operation: you'd run Build via the agent-led /start → /review → /ship flow instead of the Docker app.

Version the logic, not the schedule. Each loop's prompt lives in the repo as a slash command (/build, /assess, /propose); the scheduled routine is a thin trigger that just calls it. That gives you the consistent, versioned, shareable repo of routines you're after — the command logic is git-controlled and reviewable, whether the trigger fires locally or in the cloud.

The specs — types & lifecycles

Specs come in two families. Lifecycle specs flow with a task — an idea becomes confirmed work becomes the permanent record. Reference specs document standing parts of the system. And decisions are recorded inside whichever spec governs them — there is no separate decisions/ folder.

Lifecycle · before work

Proposal spec

"Should we do this — and how big is it?"

Lives in
specs/proposals/<slug>.md
Raised
via /propose, by whoever sees the need
Holds
Problem · Options · Recommendation · Open decisions · Breakdown · Risks
draft→under-decision→ acceptedrejectedsplit

Only when work is unconfirmed, risky, or too big for one change. Ends in one explicit state — never half-decided.

Lifecycle · the record

Feature spec · the as-built source of truth

"What does the product do today?"

Lives in
specs/features/<feature>.md
Written by
the reviewer, on PASS, from the diff — never the builder
Holds
Behaviour (by surface) · Data model · Interface surface · Known limitations · embedded Decisions
permanent · as-built record

The central source of truth, grouped by user-visible behaviour. The reviewer records reality as the last commit before merge — the agent that promises is not the one that records delivery.

Architecture-principles Reference · standing

How the system is built — the technical principles governing design here, extending the universal engineering-principles. Also the home for cross-cutting decisions.

specs/architecture-principles.md

Updated when the architecture changes, not per task.

Infrastructure Reference · standing

The operational reality — repo, CI, packaging, accounts, secrets. The source of truth for a deployment or configuration decision.

specs/infrastructure.md

Now instantiated for the harness — repo, GitHub Actions CI, the Docker wrapper, Linear, and where each credential lives. Updated when infra changes, not per task.

Decisions embedded · not a folder

No standalone ADRs. A consequential decision is recorded inside the spec it governs — a local one in its design spec, a cross-cutting one in architecture-principles.

Context · Decision · Alternatives · Consequences
