## Findings

### CODE-1 — The four-verb lifecycle is stale across four live canonical documents, including the as-built record — Medium

**What:** ADR 0007's `design` verb shipped (#210–#213) and is registered. The guarded surfaces were updated: `specs/features/cli-surface.md:21` documents `harness design` in full, `SPEC.md:297` (§11) lists `start / design / review / close`, `commands/harness.md` is current, `CONTEXT.md:70` reads "Four verbs". Every **unguarded prose surface** was missed. `specs/features/verb-model.md` is the worst case: beyond stale counts it structurally omits the verb — `start`, `review`, and `close` each have a `### <verb>` section (`:16`, `:37`, `:103`); `design` has none, surviving only as a scenario nested under `review` (added by #212).

**Where:**

- `specs/features/verb-model.md` — `:8` title "Verb model — start / review / close"; `:10` "The three audited verbs"; `:14` "three one-shot, ledger-backed verbs — `start`, `review`, `close`" and "The lifecycle of one run is `start → implement → review → (fix → review)* → close`"; `:185` names only `start.py` / `review.py` / `close.py`, omitting `harness/cli/design.py`; and the missing `### design` section.
- `SPEC.md` — `:7` (the Execution model banner), `:63` (principle 1's lifecycle), `:67` (principle 5, "the three audited verbs"), `:92` (the lifecycle diagram), `:138` (§4.2's intro).
- `specs/architecture-principles.md:17` — the **live** "Orchestration boundary" principle under `## Principles`.
- `README.md` — `:26`, `:57`, `:72` (the diagram), `:177`.

Excluded as correct history, not drift: `README.md:240` (under `## Changelog → ### 2026-06`), `specs/architecture-principles.md:82` (inside a dated `### Decision:` block), and the proposals. A point-in-time record of a 2026-06 decision is *supposed* to say three.

**Why:** `CLAUDE.md` — "Read the relevant as-built record before changing behaviour… It is the contract." `CONTEXT.md` sets `feature_specs: true`, so `specs/features/verb-model.md` is that record for the verb model. An agent following its lifecycle string runs `start → implement → review` and gets a hard exit-5 `no_design` refusal, because `review` now enforces the stage the record never mentions as a verb. The record also contradicts its own sibling spec: `cli-surface.md` documents four verbs, `verb-model.md` says three.

**How:** Sweep the four live documents in one change. In `verb-model.md`: retitle `:8`, correct `:10` and `:14`, add `harness/cli/design.py` to `:185`, and add a `### design — produce the run's technical design` section between `start` and `review`, relocating or cross-referencing the ADR 0007 scenarios currently nested under `review`. Correct the counts, diagrams, and lifecycle strings at the `SPEC.md`, `architecture-principles.md:17`, and `README.md` sites. Land CODE-INSIGHT-1 and CODE-INSIGHT-3 in the same change so the surface cannot silently re-stale on a fifth verb.

**On severity:** High was considered — this is a clear contract violation in the repo's most actively-changed area. Medium per `assessment-craft`'s "a borderline High is a Medium": `commands/harness.md`, which the verb loop actually drives from, is fully current, so the damage falls on spec-driven development rather than on runtime.

### CODE-2 — #222's extraction left three sub-app copies its adoption lock cannot see — Low

**What:** #222 extracted `tests/_cliutil.registered_command_surface(app)`, which accepts any Typer app, and landed an adoption lock deriving its file set from the tracked test sources. Three inline derivations of the same concern survive, against the `promote` sub-app: `{c.name for c in promote_app.registered_commands if c.name}`. The lock cannot see them — its predicate is `_INLINE_SURFACE_READ = re.compile(r"\bapp\.registered_(?:commands|groups)\b")`, and `\bapp\.` does not match `promote_app.registered_commands` because there is no word boundary between `_` and `a` (verified by executing the regex).

**Where:** `tests/unit/test_cliutil.py:60` (the predicate) and its exemption comment at `:55–59`; the three copies at `tests/unit/test_promotion_routine_docs.py:132`, `tests/unit/test_local_orchestrator_stack_docs.py:121`, and `:211`.

**Why:** `code-quality` Part B — "Extract on the third strike" — and "An extraction sweeps for its copies": three copies of a load-bearing pattern with the canonical helper already in the tree. The copies also read `registered_commands` only, omitting the `registered_groups` half the shared helper unions in; two of the three are doc guards asserting documented == registered, so they would silently under-report if `promote` ever gained a nested sub-group.

**How:** Replace all three with `registered_command_surface(promote_app)`, wrapping in `sorted()` at the two sites that want a list — strictly stronger, and it retires the last inline copies in the tree. Then broaden the predicate to `r"\b\w*app\.registered_(?:commands|groups)\b"` and delete the now-false exemption comment at `:55–59`.

**On severity:** Low, not Medium. The exclusion is *documented and deliberate* (`:55–59` states the `\b` is load-bearing and that sub-app readers stay out of scope by design), and the under-reporting consequence is contingent on `promote` gaining a sub-group it does not have. The rule-of-three violation is real today; the harm is not.

## Systemic insights

### CODE-INSIGHT-1 — The SPEC enumeration lock exempts exactly the slash-list shape that went stale

`test_cli_surface_locked.py:328` (`_is_subset_surface_enumeration`) fires only when a slash-list names an ops command *and* an audited verb *and* is a proper subset of the registered surface. A run naming audited verbs alone is exempt by design — the comment at `:300–307` reasons that "the audited set alone (no ops command)… left alone". That was sound while the audited set was frozen at three: a set that never changes cannot drift. ADR 0007 made the audited set mutable, and #211 updated `_AUDITED_VERBS` (`:258`) to include `design` **for anchoring purposes** while leaving the exemption's premise unexamined. Executing the predicate against `SPEC.md` confirms the surviving slash-lists evaluate `guard_fires=False` — the guard built for this class is green over it.

**The edit:** in `_is_subset_surface_enumeration`, additionally return true when the run names two or more audited verbs and `names & _AUDITED_VERBS` is a **proper subset** of `_AUDITED_VERBS` — a list presenting itself as "the audited verbs" while omitting one. This prevents a fifth verb re-staling these same sections silently. Evidence: CODE-1.

### CODE-INSIGHT-2 — `code-quality`'s guard rule covers the subject set but not the matching predicate

Both findings share one root. `test_cliutil.py` derives its subject set from `git ls-files` — textbook-correct per the existing rule — and then fails to recognize the pattern in three of the files it correctly enumerated. `test_cli_surface_locked.py` scans every live SPEC section and then exempts the one shape that drifted. Both satisfy `skills/code-quality/SKILL.md` "A guard derives its subjects; it does not list them" in full, because that section governs only *which units are checked*, never *what counts as a hit*. A hand-written predicate narrows a guard exactly as a hand-written subject list does, and with the same signature: a green run over a shrinking fraction of the surface, invisible from the test's output.

**The edit:** add a paragraph to that section stating that the matching predicate is subject to the same rule as the subject set — any literal in a predicate (a variable name, a separator, an exempted shape) must either be derived or justified against the rule's full surface, and a reviewer rejects a guard whose predicate is narrower than the rule it claims to enforce. Evidence: CODE-1 and CODE-2. The highest-leverage of the three, since it is the only one that generalises past this verb.

### CODE-INSIGHT-3 — Nothing asserts the as-built record covers every audited verb

`test_feature_specs.py:160` (`test_cli_surface_spec_matches_registered_commands`) locks `cli-surface.md` against the registered surface, which is precisely why that file is current while its siblings are not. No equivalent guard covers `verb-model.md`, the as-built record for the verb model — which is how an entire registered lifecycle verb came to have no section in it.

**The edit:** add a test to `tests/unit/test_feature_specs.py` asserting that `specs/features/verb-model.md` carries a `### ` section for every audited verb, with the verb set derived from the registered surface (via `tests/_cliutil.registered_command_surface`) rather than listed. This turns "the canonical record omits a verb" from something a steward finds two weeks later into a gate failure in the commit that adds the verb. Evidence: CODE-1.
