### CODE-2 — `.claude/worktrees/` (34 dirs, 454 MB) is untracked and unguarded by the committed `.gitignore`; only a local, non-committed exclude keeps it out of `git status` — Medium

**What:** `.gitignore:35` ignores `.worktrees/` — the harness's *own* verb-created worktree root (`harness/identity.py`'s `WORKTREES_SUBDIR = Path(".worktrees/harness")`), correctly. It has no entry for `.claude/worktrees/`, a *different* directory — the Claude Code CLI's own agent-dispatch worktree-isolation artifacts. 34 such directories currently sit on disk (454 MB), fully-formed git worktrees each carrying their own `.git`, `skills/`, `agents/`, etc. `git check-ignore -v` on one of them resolves to `.git/info/exclude:12:**/.claude/worktrees/` — a *local*, machine-specific exclude file that is never committed and is not part of a fresh clone.

**Where:** `.gitignore:35` (`.worktrees/` — present, but does not match `.claude/worktrees/`); `.git/info/exclude:12` (the only thing currently suppressing the noise, confirmed via `git check-ignore -v .claude/worktrees/reverent-rhodes-481aa2`); `git ls-files .claude/worktrees/` returns zero — confirmed untracked.

**Why:** `engineering-principles` — "atomic, reversible increments" and general repo hygiene; this repo's own operational memory names the exact failure mode this gap enables: an operator running `git add -A` (a pattern this repo's guidance explicitly warns against, `code-quality` Part A: "do not commit files that appeared in `git status` from another session") on a machine without the local exclude would stage up to 34 nested git repositories as gitlinks. `.claude/` itself *is* tracked (settings.json, agents, commands, hooks, skills), so a blanket `.claude/` ignore is not the fix — only the `worktrees/` subpath needs one.

**How:** Add `.claude/worktrees/` to the committed `.gitignore` alongside the existing `.worktrees/` entry, and clean up the 34 stale directories from disk (a disk-hygiene action, not a code change — outside this read-only pass's mandate to perform, but straightforward for the ticket that picks this up).

**On severity:** Medium, not High — no data has actually leaked into a commit (the local exclude has protected this operator's actual `git status` throughout), so this is a latent gap, not an active incident; but it is trivially reproducible on any fresh clone or CI runner and the failure mode it enables (a git-add-all sweeping in nested worktrees) is exactly the class this repo's own memory already flags as a standing trap.

## Systemic insights

### CODE-INSIGHT-1 — The subset-enumeration slash-list guard is scoped to `SPEC.md` alone, though the same file already defines a live-doc set that includes README.md

`test_cli_surface_locked.py`'s `_is_subset_surface_enumeration` / `_subset_enumeration_offenders` is a fully generalized detector — it derives both the registered surface and the audited-verb set live, and would have caught CODE-1's README `:16` (`` `start` / `review` / `close` ``) and `:29` mechanically, since both are the exact slash-list idiom the guard already recognizes. But `test_no_live_spec_section_handlists_a_command_subset` calls it against `_live_text(SPEC)` only. The same file defines `_live_docs()` — a list that already includes README.md, CONTEXT.md, CLAUDE.md, `commands/*.md`, `skills/*.md`, and non-superseded `specs/**/*.md` — for a *different* guard (`test_live_docs_have_no_retired_surface_reference`), two hundred lines below. The subset-enumeration guard and the live-doc set already coexist in one file; they were never wired together.

**The edit:** change `test_no_live_spec_section_handlists_a_command_subset` (or add a sibling parametrized over `_live_docs()`) to run `_subset_enumeration_offenders` against every doc in `_live_docs()`, not `SPEC` alone. This is a reuse of two already-tested, already-derived functions in the same file — no new detection logic, just a wider scan target. Evidence: CODE-1.

### CODE-INSIGHT-2 — The `architecture` skill's watchlist mechanism names review as the enforcement point but not the unconditional design stage that runs first

The `architecture` skill's Architecture watchlist section frames the trigger as something "confirmed at review" — correct, but review is the *last* checkpoint, and CODE-3 shows it is not a reliable one (missed twice in a row). `harness/cli/design_protocol.py`'s `DESIGN_SECTIONS` is explicitly built as the single source that "cannot drift from what is asked for" — it runs unconditionally on every ticket (ADR 0007), before any code is written, and already carries a comment noting its list is single-sourced against the `architecture` skill's "what a design produces." It has no entry for the Watchlist trigger, even though `templates/change.md:34` already carries a `## Watchlist trigger` heading the design output is meant to fill when applicable.

**The edit:** add a paragraph to the `architecture` skill's Architecture watchlist section naming the design stage (not just review) as the mechanized carrier: when a repo's `design` verb grounds a change against a diff or ticket that touches `architecture_watchlist.files`, the design output should include the `Watchlist trigger` section conditionally, the same way `DESIGN_SECTIONS` already conditions other content. This gives a future ticket implementing it a guidance anchor to build against, rather than leaving watchlist enforcement solely to reviewer memory. Evidence: CODE-3 (both misses happened at review time; catching it one stage earlier, unconditionally, removes the dependency on reviewer recall).
