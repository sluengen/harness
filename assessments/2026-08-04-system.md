## Why this pass

The user requested a full system/process assessment focused on process theatre, accumulated cruft, duplicated or contradictory guidance, stages that do not earn their keep, and simpler ways to preserve the intended outcomes. The pass read the registered guidance surface, its derived process entry point, the repo-specific `CLAUDE.md`, the assessment history, and the live workflow commands against the MECE, Lean, and Correct lenses in `guidance-coherence`.

## Verdict

The mechanical distribution layer is healthy: all 84 focused registry/header, universal-prose, derived-entry-point, and routine-command integrity tests pass. The semantic process layered on top is not coherent. The recent Linear-to-generic-tracker migration reached the application and the lightweight capture commands but stopped short of the main lifecycle; two different review-loop ceilings remain simultaneously normative; and decision storage is governed by mutually exclusive rules.

The process also carries ceremony that is not coupled to its promised outcome. The mandatory design stage gates only that an attempt occurred, not that a design exists; the as-built record is added after the supposedly final review and verification; and every empty Build tick can launch another assessment that creates more Build work. Those mechanisms produce evidence that a stage ran, but do not consistently prove the quality property the stage is meant to protect.

## Findings

### SYSTEM-1 — The tracker migration left the core lifecycle Linear-only — High

**Filed as:** [#327](https://github.com/sluengen/harness/issues/327).

**What:** The repository declares `tracker: github` as the single source of truth and `/bug` and `/tweak` correctly branch on `tracker:`, but the universal process, lifecycle skill, `/start`, `/build`, `/ship`, `/propose`, and `/assess` still require Linear or test the retired `layers.linear` switch. A GitHub-backed consumer is therefore told that the universal commands work everywhere while their normative steps require a Linear issue, `LINEAR_API_KEY`, the `linear` skill, and Linear state mutations. `registry.yaml` also still seeds `default_layers: { linear: true, ... }`, although the current context template no longer has a `linear` layer.

**Where:** `CLAUDE.md` YAML (`tracker`, lines 13–23); `process/harness.md` “Layers” and “The shape of a task” (lines 10–30); `registry.yaml` profile defaults (lines 26–40); `skills/spec-driven-development/SKILL.md` “Three specs” and “The flow” (lines 8–37); `commands/start.md` steps 1, 2, and 5; `commands/build.md` title/setup and prerequisite; `commands/ship.md` step 3; `commands/propose.md` steps 1 and 4; `commands/assess.md` step 2 (lines 35–36). The already-correct counterexample is `commands/bug.md` lines 33–65 and `commands/tweak.md` lines 50–82, which resolve `tracker:` and branch by backend.

**Why:** This violates the Correct lens and `guidance-coherence`'s CONTEXT-currency rule: the universal workflow must follow the repo's declared backend, not a retired boolean or one provider. It also violates MECE by maintaining two tracker models in the same installed surface. For a GitHub consumer, these are execution instructions, not harmless terminology.

**How:** Make `tracker:` the only guidance-level switch. Replace the process table's `linear` layer and the registry default with tracker-backend language; introduce one tracker-neutral protocol/home for issue read/create/transition/comment operations; and update every lifecycle command and template to dispatch through that protocol. Keep provider recipes in backend-specific sections, following the working `/bug` and `/tweak` pattern.

### SYSTEM-2 — Review has two incompatible stop rules — High

**Filed as:** [#329](https://github.com/sluengen/harness/issues/329).

**What:** The reviewer agent and autonomous build loop say cycles 1–3 always run and the hard stop is the sixth review/fix cycle. The review-discipline skill and `/review` command instead require escalation after the second consecutive FAIL. An executor following the skill stops four cycles before the agent and harness contract; one following the agent violates the skill that supposedly owns the review standard.

**Where:** `agents/reviewer.md` “The review→fix stop rule” (lines 42–48); `commands/build.md` “Fix loop” (lines 36–49); and `commands/harness.md` verdict handling (lines 135–148) conflict with `skills/review-discipline/SKILL.md` “On a FAIL” (lines 98–100) and `commands/review.md` PASS/FAIL handling (lines 19–21). `CLAUDE.md` `loop.max_review_cycles` (line 40) explicitly claims there is one coherent rule.

**Why:** This is a direct Correct and MECE failure on a load-bearing spend breaker. The same policy is copied into multiple files and has diverged, so run duration depends on which entry point the agent happens to read.

**How:** Choose one canonical stop policy and place its semantics in `review-discipline`; make the agent and commands point to it. Keep only repo-tunable numeric thresholds in `CLAUDE.md`, and add a source-tree semantic check that rejects contradictory literal stop rules in distributed prose.

### SYSTEM-3 — Decision storage is governed by mutually exclusive contracts — High

**Filed as:** [#330](https://github.com/sluengen/harness/issues/330).

**What:** The universal spec-authoring standard prohibits a `decisions/` folder and standalone ADRs, while this repo declares `specs/decisions/` as the active home for architecture decisions, maintains a growing numbered ADR set there, and indexes the active subset from `CLAUDE.md`. An agent applying the universal rule to this repo is instructed to dismantle or bypass the repo's canonical decision record.

**Where:** `skills/spec-authoring/SKILL.md` “Decisions live in the spec they govern” (lines 35–42) says, “There is no separate `decisions/` folder and no standalone ADRs.” `CLAUDE.md` “Decisions index” (lines 90–102) says, “Architecture decisions live in `specs/decisions/` (ADRs, `0001`+),” and `paths.decisions` points there.

**Why:** This violates the universal/repo boundary and Correct lenses. A universal default may recommend embedded decisions, but it cannot state that a repo-configured decision architecture does not exist. The contradiction makes future decisions fork between two canonical homes.

**How:** Make decision storage a repo-declared path/strategy in `CLAUDE.md`. Phrase embedded Decision blocks as the default when no ADR path is configured; when `paths.decisions` exists, require the repo's architecture spec/index to define which decisions belong there and make skills defer to it.

### SYSTEM-4 — The final review does not cover the final commit — High

**Filed as:** [#331](https://github.com/sluengen/harness/issues/331).

**What:** The reviewer runs the independent verification and decides PASS, then writes and commits the as-built record. `/build` likewise reviews the staged implementation, then adds the as-built record in its Ship phase and commits it without another verification or review. `/ship` nevertheless treats the resulting branch as review-passed and gate-green. The last commit is therefore outside the evidence called “final,” and in the harness verb path any post-PASS record commit necessarily invalidates the SHA-bound pass.

**Where:** `agents/reviewer.md` review sequence (lines 20–30); `commands/review.md` steps 3–4 (lines 16–20); `commands/build.md` Ship phase (lines 181–193); `commands/ship.md` preconditions (lines 8–14). The incompatibility is explicit in `commands/harness.md`: review is bound to `reviewed_sha` (lines 121–125), while `close` rejects a moved HEAD as `stale_review` (lines 150–170).

**Why:** This violates the no-completion-without-fresh-evidence rule and the stated separation that a reviewer records what actually shipped. A documentation-only edit is still part of the delivered tree and may be subject to link, generated-doc, or drift guards. Evidence over a predecessor SHA is not evidence over the final commit.

**How:** Put the as-built update into the candidate diff before the final verification and verdict. In the agent-led flow, let the reviewer draft the record, then run the gate and review the complete staged diff before PASS. In the harness flow, stage and commit the record before `harness review`, so the recorded SHA exactly matches what `close` integrates.

### SYSTEM-5 — The mandatory design gate proves an attempt, not a design — Medium

**Filed as:** [#332](https://github.com/sluengen/harness/issues/332), shared with CODE-1 and ARCH-2 because all three findings govern the same design-stage decision.

**What:** Every harness run must invoke a dedicated Opus design stage even though the ticket already carries a required Design section. If the engine fails to produce any design, that failed event still satisfies the review prerequisite and the run is told to implement and ship without a design. The mandatory gate therefore measures ceremony (“an attempt event exists”) rather than its stated outcome (“implementation follows a reviewed technical design”), while charging the most expensive model tier on every ticket, including trivial changes. Live ledger telemetry (`.venv/bin/harness stats --json`, 2026-08-04) records 90 design attempts: 74 succeeded and 16 failed (17.8%). Only 29 of 90 attempts have duration telemetry; those 29 total 2.82 hours (mean 350.3 seconds), while 61 predate duration recording, so total spend is not measurable from the ledger. A first-review cross-tab does not show an obvious outcome advantage: failed-design runs recorded 10 first-pass / 3 first-fail outcomes, while successful-design runs recorded 55 first-pass / 11 first-fail, plus 1 defer and 1 blank. This is a small, non-random operational sample, so it does not establish that design has no effect; it shows measured runtime and failure without an observable first-review signal strong enough to justify treating the stage's value as self-evident.

**Where:** `skills/spec-authoring/SKILL.md` requires every change spec to contain scaled design (lines 27–33 and the “Change spec” section); `commands/harness.md` design stage (lines 52–77) makes Opus unconditional, says failure should proceed without a design, and makes any failed attempt satisfy `review`; `CLAUDE.md` architecture and ADR 0007 summary (lines 72–76 and 102) repeat the same contract.

**Why:** This violates Lean: the stage duplicates an existing artifact and its enforcement is disconnected from the quality property that justifies it. A mandatory stage that explicitly permits the target artifact to be absent is process evidence, not design assurance.

**How:** Collapse to one design source. Either use the ticket's scaled Design section and invoke a separate design engine only when the change is classified non-trivial, or make the verb-owned design the source and require a valid artifact before non-trivial implementation/review. In either form, allow trivial fixes to bypass the extra engine and record that classification instead of recording a knowingly failed design attempt as satisfaction.

### SYSTEM-6 — The idle quality loop self-feeds repeated assessment work — Medium

**Filed as:** [#333](https://github.com/sluengen/harness/issues/333).

**What:** Every Build tick that finds no actionable ticket immediately runs `/assess code`; `/assess` files every finding and insight directly into Todo, and the same routine actions the highest-priority result. This makes an empty queue manufacture its own next Build task without a minimum elapsed time, changed-SHA check, or minimum-delta threshold. The history shows the consequence: three code assessments were committed on 2026-07-26 and three more on 2026-08-01, including multiple same-day supersession/fold cycles.

**Where:** `commands/harness.md` Build step 5 and Quality routine (lines 290–301); `commands/assess.md` filing and retention steps (lines 35–44); `assessments/LOG.md` entries for 2026-07-26 and 2026-08-01; git history commits `b952059`, `bba8523`, `6d511d7`, `2f007f6`, `fb0a7dd`, and `1ad4e3f`.

**Why:** This violates Lean and the command's own premise that assessment catches drift accumulated “across many changes.” Reassessing nearly the same tree several times in one day spends review capacity, creates report/retention churn, and lets an advisory loop recursively populate the production queue.

**How:** Keep the weekly deep pass, but gate the idle pass on new evidence: record the last assessed SHA/time and skip unless a defined commit-count or elapsed-time threshold is met. Do not immediately action assessment-created work in the same idle tick; file it for the next normal prioritised Build selection so the advisory loop cannot recursively drive itself.

## Systemic insights

### SYSTEM-INSIGHT-1 — Add a configuration-to-guidance matrix check

**Filed as:** [#342](https://github.com/sluengen/harness/issues/342).

SYSTEM-1 and SYSTEM-3 are both migrations/configurations that reached `CLAUDE.md` but not every installed instruction. Add a “configuration matrix” check to `skills/guidance-coherence/SKILL.md`: for each enum or optional path in `templates/CONTEXT.template.md` (`tracker`, feature-spec mode, decision-store path, branch roles), enumerate the commands/skills that consume the concept and verify that every supported value has a coherent instruction path. This prevents a new backend or storage strategy from landing in configuration while universal prose remains pinned to the predecessor.

### SYSTEM-INSIGHT-2 — Make semantic policy ownership part of the MECE check

**Filed as:** [#343](https://github.com/sluengen/harness/issues/343).

SYSTEM-2 and SYSTEM-4 show that file existence and header parity do not protect lifecycle semantics. Extend `skills/guidance-coherence/SKILL.md`'s MECE check with a small set of load-bearing workflow invariants—stop condition, final-evidence ordering, mutation owner—and require each invariant to name one canonical skill plus pointer-only mentions elsewhere. Add source tests for any copied numeric threshold or ordered phase list. This catches contradictions that are syntactically valid and fully versioned.

### SYSTEM-INSIGHT-3 — Require an outcome test for mandatory process stages

**Filed as:** [#344](https://github.com/sluengen/harness/issues/344).

SYSTEM-5 and SYSTEM-6 are recurring ceremony classes: mandatory stages can run successfully while failing to establish the outcome that pays for them. Add a Lean subsection to `skills/guidance-coherence/SKILL.md` requiring every unconditional or scheduled stage to name (1) the outcome it uniquely establishes, (2) the evidence that proves that outcome, and (3) its skip/cadence condition. A stage whose evidence proves only invocation, or whose trigger ignores unchanged input, fails the guidance assessment.
