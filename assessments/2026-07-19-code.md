**Why:** `code-quality` Part C — "A measurable criterion needs a measuring test" is already satisfied here (the gate exists and runs), but the accumulated state it measures is now one normal-sized entry away from blocking the next ticket that touches the CHANGELOG — which is effectively every shipped ticket, since the standing convention is a CHANGELOG entry per change. A gate that goes red for the *next* unrelated ticket, not the one that trips it, is exactly the kind of drift a per-change reviewer has no visibility into (they see only their own entry's marginal size, not the file's total).
**How:** The rotation mechanism (`CHANGELOG-archive/2026.md`) already exists and is designed to run "at each dev→main release" (`RELEASING.md`). Either path is a one-line operational decision, not a code change — flagging it now, while there is still headroom to make the decision calmly, is the point.
