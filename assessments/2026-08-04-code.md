## Why this pass

This deep pass was requested to look specifically for architectural and logic decay, cruft, complexity that does not earn its keep, and features whose outcomes can be reached more simply. It read the full `harness/`, `tests/`, `scripts/`, `specs/`, design-system and dependency surfaces; compared size and churn; ran the coverage suite; and queried the live ledger to test the cost rationale behind the unconditional design stage. The finding bar is cumulative: isolated line-level nits were dropped.

## Verdict

The codebase remains highly verified, but verification quantity is masking three kinds of accumulated drag. First, the mandatory design stage has become a 747-line subsystem and an unconditional Opus spend even though its gate accepts a failed attempt and the live ledger does not show the promised reduction in review cycles. Second, promotion escalation is the one remaining verb that bypasses the tracker seam, so it cannot use the GitHub backend this repository declares. Third, several guards and abstractions are narrower than their names: the token guard covers only a generated root block, the `unit` tier contains real Git/SQLite/CLI integration tests, and shared test infrastructure coexists with 29 local Git runners.

One High and five Medium findings clear the future-work bar. None is a coverage-floor failure or a speculative rewrite; each names a smaller contract or seam that removes repeated machinery.

## Findings

### CODE-1 — The unconditional design stage spends on every run but enforces only that an attempt was recorded — Medium

**Filed as:** [#332](https://github.com/sluengen/harness/issues/332), shared with ARCH-2 and SYSTEM-5 because all three findings govern the same design-stage decision.

**What:** Every run launches the Opus design stage, while review refuses an omitted attempt but explicitly accepts a failed attempt and proceeds without design context. The live ledger contains 90 design attempts (74 `ok`, 16 `failed`); the 29 events carrying direct duration telemetry total **2.82 hours** and average about **5.8 minutes per attempt** (61 older events have no duration, so the whole-stage total is unknown). Among runs that reached review, the observed first-review outcomes and average review-cycle counts do not show the promised cycle reduction for successful designs (the small failed-design cohort averaged about 1.31 cycles versus 1.50 after an `ok` design). This observational sample does not prove designs have no qualitative value, but it means reduced review cycles are not demonstrated justification for unconditional spend. The implementation cost is also now material: `harness/cli/design.py` is 747 lines, has changed in 14 commits since 2026-07-01, and mixes engine-channel lifecycle, ticket/spec orchestration, adoption, concurrency detection, telemetry and ledger persistence.

**Where:** `CONTEXT.md:74-75` declares the stage unconditional; `harness/cli/review_protocol.py:233-281` refuses no event but accepts a failed event; `specs/decisions/0007-design-verb.md:50-58,66-74,90-99` records the unconditional choice, the label-gated relief valve and the review-cycle rationale; `harness/cli/design.py:354-421,424-504,524-623,664-724` contains the accumulated subsystem. Ledger evidence was derived from `.harness/harness.db` by grouping `design` and `review` events per `run_id` and summing only non-null `duration_ms` values.

**Why:** This violates simplicity over cleverness and smallest mechanism that satisfies the contract. A gate that treats “failed to produce the artifact” as sufficient is an audit-presence check, not a quality or safety gate; paying one top-tier call on every ticket needs evidence that the outcome improves. ADR 0007 itself names label gating as the relief valve if universal spend proves too high.

**How:** Amend ADR 0007 in place to activate its recorded relief valve: run Opus design only for an explicit hard-work signal (for example `design:opus` or the existing judged build tier), make review consume and authenticate design when present without refusing ordinary undesigned runs, and retain the ledger event for attempted designs. Measure the tiered policy against first-pass rate and review cycles before widening it again.

### CODE-2 — Promotion escalation bypasses the tracker seam and is unusable on this repo's GitHub configuration — High

**Filed as:** [#328](https://github.com/sluengen/harness/issues/328), shared with ARCH-1 because both findings identify the same production boundary violation.

**What:** `harness promote escalate` imports and constructs `LinearClient` directly, reads `LINEAR_API_KEY`, requires a Linear team and catches Linear-specific errors. This repository declares `tracker: github`, and the as-built tracker contract says no verb constructs a backend client directly. All other tracker-writing verbs resolve `tracker_client(repo_root)` and catch tracker-agnostic errors. Promotion escalation therefore cannot file into the configured GitHub queue (and `tracker: none` cannot cleanly no-op); it still depends on retained legacy Linear configuration.

**Where:** `harness/cli/promote.py:52-58,102-108,707-788`; `specs/features/verb-model.md:188-196` states the one-factory/no-direct-client contract; `CONTEXT.md:10-18` configures GitHub and marks Linear fields legacy. `tests/unit/test_cli_promote_escalate.py:1-14,62-101` stubs only the direct Linear construction and has no GitHub or tracker-less case.

**Why:** This is an architecture-boundary and stable-contract violation, and it produces a current functional failure at a write boundary. Backend selection has two sources of truth: every ordinary verb follows `tracker:`, while promotion escalation silently follows Linear.

**How:** Route escalation through `tracker_client(repo_root)` and `Tracker.create_issue` / `post_comment`, catch `TrackerConfigError`, `TrackerNotFound` and `TrackerRequestError`, remove the Linear-only `--team` vocabulary in favour of backend-owned addressing, and add GitHub plus `tracker: none` lifecycle cases to the promotion escalation suite.

### CODE-3 — The design-token guard certifies one block while the consuming page bypasses it in 82 colour literals — Medium

**Filed as:** [#335](https://github.com/sluengen/harness/issues/335).

**What:** The design system says nothing is hardcoded and that `tokens.json` captures every colour/elevation value rendered by the page, but the guard compares only the marker-bounded `:root` block. Outside it, `docs/index.html` contains **82 raw hex occurrences across 52 distinct values** plus six raw `rgba(...)` values: hero chrome, repeated chips/cards, and the SVG loop palette all bypass semantic tokens. It also contains 300 `px` occurrences despite the stated “never a raw hex or pixel value” rule. A green drift check therefore proves the generated declarations match, not that the page adopts them.

**Where:** `design/README.md:38-48,54-61` states the no-hardcoding/full-capture contract; `scripts/build_design_tokens.py:91-104,168-192` emits and checks only the generated region; examples occur at `docs/index.html:35-72`, `docs/index.html:120-143`, `docs/index.html:129-184`, and `docs/index.html:255-303`.

**Why:** This violates the design-system token-discipline and deep adherence lenses. The source-of-truth claim is materially broader than the checked surface, so the gate is green over a page with a second, larger visual-value source.

**How:** Keep the system lean for its one-page product: extend semantic colour/elevation tokens to the repeated hero, chip, card and SVG roles and replace every raw colour outside the token source with CSS variables; explicitly narrow the written contract to leave one-off geometry/typography outside the token system rather than creating dozens of single-use spacing tokens. Then make `--check` reject raw colour/elevation literals outside the generated declarations.

### CODE-4 — The unit tier contains real Git, SQLite, filesystem and full-CLI integration tests — Medium

**Filed as:** [#336](https://github.com/sluengen/harness/issues/336).

**What:** The test tree exposes one integration module (Docker), while 53 modules under `tests/unit/` import `subprocess`, four import `aiosqlite`, and 31 drive `CliRunner`. Representative “unit” suites create and clone real repositories, commit/push/merge branches, create real SQLite databases and invoke whole CLI verbs. The suite is valuable and hermetic, but its tier labels do not describe what it proves; `pytest tests/unit` is effectively the broad integration gate, not a fast isolated tier.

**Where:** `tests/unit/test_cli_start.py:23-82` uses real Git, filesystem and SQLite around the CLI; `tests/unit/test_close_merge.py:10-19,36-95` explicitly drives real merge mechanics against a bare origin; `tests/unit/test_state_store.py:20-47` opens real SQLite files. By contrast, `tests/integration/test_docker.py:58-60` is the only module marked integration, and `pyproject.toml:62-73` defines the tier marker.

**Why:** This violates the test-tier placement standard. It prevents contributors and CI from selecting a meaningful fast unit signal separately from process/database/repository integration, and makes the single integration directory misleadingly narrow.

**How:** Define the tiers by dependency boundary, move/mark real Git, SQLite, filesystem-lifecycle and full-Typer-command tests as integration, retain pure protocol/parser/model tests as unit, and expose separate unit and integration commands while keeping the full verification gate unchanged.

### CODE-5 — Twenty-nine test modules hand-roll the same Git subprocess helper beside a shared Git utility module — Medium

**Filed as:** [#337](https://github.com/sluengen/harness/issues/337).

**What:** There are 29 local `def _git(...)` implementations across the test tree, overwhelmingly wrapping list-form `subprocess.run(["git", ...], cwd=..., check=True, capture_output=True, text=True)`. The repository already has `tests/_gitutil.py`, whose own opening states that shared Git helpers exist to avoid hand-rolling Git in test modules, but it does not expose the general runner those 29 modules need. Variants now disagree on return type (`CompletedProcess`, `str`, `None`) and default behaviour.

**Where:** The shared-home claim is `tests/_gitutil.py:1-9`; representative copies are `tests/unit/test_cli_start.py:46-53`, `tests/unit/test_close_merge.py:36-39`, `tests/unit/test_cli_review.py:51`, `tests/unit/test_changelog_fragments.py:52`, and `tests/unit/test_worktree.py:29`. A repo-wide `rg '^def _git\(' tests` finds 29 definitions.

**Why:** This is far past the third-strike threshold and adds incidental test API diversity around a load-bearing external process. Updating timeout, environment, diagnostics or return handling requires a broad manual sweep.

**How:** Add one configurable `run_git(cwd, *args, check=True) -> CompletedProcess[str]` to `tests/_gitutil.py`, migrate every semantically identical wrapper, and leave only genuinely specialised adapters (for example a helper intentionally returning stdout) as thin calls to that function.

### CODE-6 — Defer and release duplicate the same tracker/queue/ledger lifecycle and explicitly require synchronized edits — Medium

**Filed as:** [#338](https://github.com/sluengen/harness/issues/338).

**What:** `_run_defer` and `_run_release` independently implement the same orchestration shell: read the clock; handle `tracker: none`; resolve project and tracker client; translate the same config/not-found/request failures; fetch and validate queue membership; derive effective project; perform a verb-specific tracker mutation; create a synthetic closed run; emit a terminal event; map output. The release code comments repeatedly say it “mirrors `defer`” and “mirrors exactly,” which is the code-quality extraction trigger. The duplicated part is a domain rule that must stay synchronized, not merely similar presentation.

**Where:** `harness/cli/defer.py:135-180,183-247,259-281` and `harness/cli/release.py:115-153,156-210,224-247`; the explicit synchronization admission is `harness/cli/release.py:115-123,169-177`.

**Why:** This violates separation of concerns and the explicit-mirroring third-strike rule. Queue semantics and failure classification already changed together in #248; keeping two copies makes the next tracker backend or error change touch two orchestration bodies and two ledger writers.

**How:** Extract a narrow internal ticket-action runner that owns tracker-less/config resolution, queue membership, effective-project calculation and common error translation, plus one terminal-run/event anchoring helper. Pass the distinct mutation and typed payload/output builders from defer and release; do not merge their business actions.

## Systemic insights

**Filed as:** [#339](https://github.com/sluengen/harness/issues/339).

Extend `tests/unit/test_cli_module_boundaries.py` with an AST-derived guard: modules under `harness/cli/` may import `harness.tracker` / `harness.tracker_errors`, but may not import or construct `harness.linear.LinearClient` or `harness.github.GitHubClient`; keep an explicit, documented exemption only if a command is deliberately backend-specific. Extend `scripts/build_design_tokens.py --check` and its tests to scan the full consumer region of `docs/index.html` for raw colour/elevation literals outside the generated source block, resolving SVG attributes as well as CSS declarations. The check should derive allowed literals from `tokens.json`, not carry a second hand-list. This prevents the false-green class in CODE-3.
