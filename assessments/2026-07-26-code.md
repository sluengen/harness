## Findings

### CODE-1 — The design gate reads its payload keys as raw literals, and the two constants that exist for it have no consumer — Medium

**What:** `resolve_design_gate` reads the `design` event's payload with hardcoded string keys — `event.get("status")` and `event.get("design_hash")`. The constants written to prevent exactly that are never used: `DESIGN_HASH_PATH` has **zero** readers anywhere in `harness/` or `tests/`, and `DESIGN_STATUS_PATH` has one, a test that asserts it equals the literal `"$.status"`. Meanwhile `payloads.py` documents both, twice, as the keys the review linkage "reads back out". The two `_PATH` constants are also the wrong *shape* for their stated consumer: `_field_path` yields a `json_extract` path (`$.status`), while `resolve_design_gate` works on an already-parsed dict and needs the bare field name that `_field_name` produces.

**Where:** `harness/cli/review_protocol.py:234` and `:238` (the raw literals); `harness/events/payloads.py:214-215` (the unused constants), `:149-152` and `:209-213` (the claim that review reads them); `tests/unit/test_review_design_linkage.py:618-620` (the value-only test). The in-repo precedent for the correct pattern is `harness/cli/query_status.py:110`, `data.get(WORKFLOW_FAILED_REASON_KEY)`, against `harness/events/payloads.py:218`.

**Why:** CAL-1012's AC-1 — recorded in `tests/unit/test_event_payloads.py:288` as "the payload key strings are NOT duplicated in reader modules" — is enforced by two source-scan guards, `test_close_gate_source_holds_no_raw_review_key_literals` (`:292-298`) and `test_query_status_source_holds_no_raw_reason_extraction` (`:301-305`), the second of which forbids precisely the `.get("<key>")` form the design gate now uses. #212 added the third reader module and neither followed the convention nor extended the guard. It also trips `assessment-craft`'s dead-code lens (an export nothing imports) and its weak-assertion lens: `test_design_status_path_is_derived_from_the_model` asserts a constant's literal value rather than that any consumer uses it, so it is structurally incapable of detecting the drift it appears to guard. The live consequence is latent but real: the unused constants are currently the *only* thing that would make a `DesignEventData.status` rename fail loudly (`_field_path` raises at import), so deleting them as dead code — the obviously correct cleanup — would leave `event.get("status")` silently returning `None` on a rename, which the gate reads as "not ok" and every review would then proceed with no design context and no error.

**How:** Add `DESIGN_STATUS_KEY = _field_name(DesignEventData, "status")` and `DESIGN_HASH_KEY = _field_name(DesignEventData, "design_hash")` beside `WORKFLOW_FAILED_REASON_KEY` (`harness/events/payloads.py:218`); use them in `resolve_design_gate` (`harness/cli/review_protocol.py:234,238`); delete `DESIGN_STATUS_PATH`/`DESIGN_HASH_PATH`, since no `json_extract` reader of the `design` payload exists, and correct the two docstrings that describe them. Add `test_design_gate_source_holds_no_raw_design_key_literals` next to the two existing source-scan guards in `tests/unit/test_event_payloads.py`, asserting `'.get("status")'` and `'.get("design_hash")'` are absent from `review_protocol.py`, and replace `test_design_status_path_is_derived_from_the_model` with one that asserts the consumer, not the constant's spelling.

### CODE-2 — The `design` verb has no tracker-less test, and `review` now refuses unconditionally on its event — Medium

**What:** `tests/unit/test_tracker_less_layer.py` is the repo's dedicated suite for the `tracker: none` configuration; it walks `start` (`:269`, `:286`), `close` (`:348`, `:383`), `reclaim` (`:449`), and the stale sweep (`:474`). It has no `design` case. Correspondingly, `fetch_ticket_spec`'s tracker-less branch and its no-ticket branch are both unexecuted by the suite (coverage marks `harness/cli/design_tracker.py:99` and `:110` uncovered), as are the tracker fetch-failure branch (`:115-116`), the comment-post failure branch (`:150-151`), and the verb's handler for it (`harness/cli/design.py:395-396`). `design_tracker.py` sits at **79%**, the lowest of the new modules. `grep -rn 'TicketCommentFailedError\|post_design_comment' tests/` returns nothing.

**Where:** `tests/unit/test_tracker_less_layer.py` (the missing cases); `harness/cli/design_tracker.py:98-101`, `:109-112`, `:113-116`, `:148-155`; `harness/cli/design.py:386-396`.

**Why:** `tracker: none` is a first-class layer (`CONTEXT.md` `tracker:`, `harness/layers.py`), and #212 made `review` refuse `no_design` for **every** run. The whole tracker-less lifecycle therefore now depends on the claim in `fetch_ticket_spec`'s own docstring — "The `no_design` check (#212) is satisfied by that attempt, so a tracker-less repo's build is never wedged" — and nothing proves it. That claim is correct as written (I traced it: `TicketSpecUnavailableError` → `_DesignNotProducedError(no_ticket_spec)` → a `failed` design event → `resolve_design_gate` returns a bare `DesignGate()`), but an untested load-bearing claim about a supported configuration is exactly what `test-driven-development`'s handoff checklist ("every acceptance criterion has at least one test", "tests cover error and edge cases") forbids, and the repo has already chosen to prove this property for every other verb. The comment-post branch is separate but adjacent: it is the one *expected* exit-1 path in the verb, it deliberately records **no** ledger event at all, and `design.py`'s module-level exit-code list (`:47-53`) describes exit 1 only as "unexpected error (git failure, DB error)" — so the documented contract and the code disagree, with no test on either side.

**How:** Add to `tests/unit/test_tracker_less_layer.py`: (1) `design` on a `tracker: none` repo exits 3, records a `design` event with `status='failed'` and `reason='no_ticket_spec'`, and posts no comment; (2) a subsequent `review` on that run is **not** refused with `no_design` and records `design_context=false`. Add to `tests/unit/test_cli_design.py`: (3) a run whose `runs.ticket` is NULL degrades with the same reason without invoking the engine; (4) `fetch_issue` raising `TrackerRequestError` degrades with `no_ticket_spec`; (5) `post_comment` raising `TrackerRequestError` exits **1** and leaves **no** `design` event on the run. ### CODE-3 — The CLI command-module boundary guard enumerates a set the package outgrew — Low

**What:** `_COMMAND_MODULES` is a hardcoded set of eight stems — `start`, `review`, `close`, `checkpoint`, `reclaim`, `cancel`, `worktrees`, `doctor`. The CLI now registers four more command surfaces that are absent from it: `defer`, `release`, `design`, and the `promote` sub-app. Because `test_no_command_imports_a_sibling_commands_private_helper` iterates the set for *both* the importing module and the import target, each omission is a double blind spot: a private import **from** `design.py` and a private import **into** `design.py` are both invisible. The guard is green today because no live violation exists, not because it checked.

**Where:** `tests/unit/test_cli_module_boundaries.py:27-36` (the set) and `:72-85` (the loop that consumes it); the unguarded registrations are `harness/cli/__init__.py:78` (`defer`), `:81` (`release`), `:89` (`design`), and `:106` (`promote`).

**Why:** The test's own docstring states the invariant universally — "No verb command imports another command module's private helper" — and its hand-written enumeration no longer satisfies that statement for a third of the package's command surface. This is accumulated drift, not one change's oversight: the set has fallen behind across at least three separate additions (`defer`/`release` with the tracker-protocol work, `promote` with ADR 0003, `design` with #211). It is the same class #215 just fixed on the other side of the suite, where four `rglob` scans hand-rolled their own skip lists until `tracked_py_sources` derived the set from `git ls-files` instead.

**How:** Derive `_COMMAND_MODULES` from the registry rather than listing it: parse `harness/cli/__init__.py` with `ast` for `app.command(name=...)` and `app.add_typer(..., name=...)` calls and map each registered name to its defining module, so a verb added tomorrow is guarded the day it lands. Keep `test_reclaim_does_not_import_from_worktrees` as the explicit CAL-1013 regression.

## Systemic insights

### CODE-INSIGHT-1 — A guard test that hand-lists its subjects narrows silently; require it to derive them from the artifact it guards

The class this prevents: any repo test that enforces a rule across a *set* — of modules, files, payload keys, or commands — by naming the set inline. It passes forever while the surface it was written for grows past it, and nothing anywhere reports that the guard stopped covering anything. This is now the dominant failure mode in this repo's structural test layer, and it has produced three separate instances: CODE-3 (`_COMMAND_MODULES` four modules behind across three additions), CODE-1 (`test_event_payloads.py:292-305` hand-lists `$.reviewed_sha`/`$.verdict` and two reader modules, so #212's third reader arrived unguarded and its constants dead), and #215's own fix, which had to replace four hand-rolled `rglob` skip lists with `tests/_gitutil.tracked_py_sources` deriving from `git ls-files`. The exact edit: add a subsection to **`skills/code-quality/SKILL.md` Part C**, immediately after "A file over the hard limit is an auditable choice, not silent drift", titled **"A guard derives its subjects; it does not list them"** — *a repo test that enforces a rule across a set of files, modules, or keys computes that set from the artifact that defines it (the command registry, the constants module, `git ls-files`), never from a literal list in the test body. A hand-written list silently narrows to the surface that existed the day it was written, and the guard then reports green for everything added since. Where the set genuinely cannot be derived, the test asserts its own completeness against the deriving source and fails when the two diverge.* `code-quality` is the right home because it is the one file both `dev` and `reviewer` load, so the rule binds when the guard is written and again when it is reviewed.

### CODE-INSIGHT-2 — Adding a stage to a lifecycle owes a case in every cross-cutting suite that walks that lifecycle

The class this prevents: a new verb or lifecycle stage ships with a thorough suite of its own while the suites that exercise the lifecycle *end to end under a configuration* — a layer being off, a tracker being absent, a breaker being tripped — are never extended, leaving a whole supported configuration unproven precisely when a new mandatory stage was inserted into it. Evidence: CODE-2, where `design` became a stage every run must record and `review` began refusing without it, yet `tests/unit/test_tracker_less_layer.py` — which deliberately walks `start`, `close`, `reclaim`, and the stale sweep for `tracker: none` — gained no `design` case, so the docstring claim that a tracker-less build is "never wedged" is the only thing standing behind that configuration. The exact edit: add a bullet to **`skills/test-driven-development/SKILL.md`**, in the RED section beside "Cover each of a guard's conditions, not just the one that trips first" — **"Cover the new stage under every configuration the lifecycle supports."** *When a change adds a stage to a documented lifecycle, grep for the suites that exercise the sibling stages under a configuration or layer (`CONTEXT.md` `layers:` / `tracker:`) and add the new stage's case to each; name those suites in the change spec. A stage's own unit suite proves the stage. It does not prove that the lifecycle still holds under every configuration the repo claims to support — and a stage that other stages now refuse without is the case where that gap is most expensive.*

No third insight this cycle.
