# CODE Assessment — harness repo (2026-06-11)

Run via `/assess code` (autonomous scheduled run). Steward: code-steward.

## Summary

The repo is in good shape post-CAL-574: the deterministic engine is genuinely
deleted (not just deprecated), the verb surface is clean, security primitives
(workspace allowlist, colon-injection defense, list-form subprocess everywhere)
are well-built and well-tested, and the gate passes (447 tests). The one
material finding is **spec divergence in `intake/`**: the Linear webhook still
shells out to `harness run <workflow>`, a command that no longer exists — a whole
module (plus its tests) frozen against the retired contract. Secondary findings
are config/housekeeping drift, all low-severity.

## Findings

### CODE-1 — `intake/linear_webhook.py` targets the retired `harness run` command — HIGH
- **What:** `run_harness()` spawns `[harness, "run", <workflow>, "--linear=...", "--base=..."]`
  (default workflow `"build"`, plus a `workflow_map` and `--base` plumbing). The CLI no
  longer registers a `run` command — CAL-574 retired the engine and `harness/cli/__init__.py`
  exposes only `start/review/close/status/logs/events/cancel/runs/doctor/serve/worktrees`. Any
  webhook fire would invoke a non-existent subcommand and exit 2.
- **Where:** `intake/linear_webhook.py:191-229` (config defaults `:79-83`, routing `:179-188`);
  contract asserted by `tests/unit/test_linear_webhook.py:384` (`["harness","run","build",...]`).
- **Why:** This is the autonomous/Hermes intake path the new model leans on. 568 lines of
  production code + 899 lines of tests now encode a dead contract, and the tests give false
  green — they pass because they mock the subprocess, so they assert the *wrong* argv. No
  per-change review catches this because nothing imports `run_harness` from the live CLI.
- **How:** Decide intake's post-verb shape (most likely: drive the launcher control socket /
  `start` verb instead of `harness run`), then update both the module and its tests to the verb
  contract. **Needs a design decision** (what replaces engine-era `run`) → not a drop-in fix.
- **Severity:** High.

### CODE-2 — Two conflicting mypy pins across two dependency mechanisms — LOW
- **What:** `[project.optional-dependencies].dev` pins `mypy>=1.7` (`pyproject.toml:24`) while
  `[dependency-groups].dev` pins `mypy>=2.0.0` (`pyproject.toml:79`). Both are satisfied today
  (uv resolves 2.3.0), but the same dev tool is declared twice with different floors in two
  competing systems.
- **Where:** `pyproject.toml:24` vs `:79`.
- **Why:** Ambiguous source of truth; a future bump to one and not the other silently diverges
  what the gate runs from what a fresh `uv sync --extra dev` installs.
- **How:** Consolidate to one mechanism — drop the single-entry `[dependency-groups]` block and
  raise the extras pin to `>=2.0.0`, or move all dev tooling into `[dependency-groups]`.
- **Severity:** Low.

### CODE-3 — Agent-process artifacts shipped inside the package tree — LOW — ✅ FIXED in this run
- **What:** `harness/changes/H-021/review.md` and `harness/lessons/H-028-10min-test.md` were
  git-tracked under `harness/` and bundled into the wheel as package data; neither referenced
  by code.
- **Where:** (removed) `harness/changes/H-021/review.md`, `harness/lessons/H-028-10min-test.md`.
- **How:** Moved to top-level `lessons/`; added `tests/unit/test_package_hygiene.py` guarding
  against any non-source file under `harness/`.
- **Severity:** Low. **Status:** fixed on branch `assess/code-2026-06-11`.

## Systemic insights

1. **CODE-1-INSIGHT — Retirement was applied to the engine but not swept through its consumers.**
   CAL-574 deleted the engine and added a regression test asserting the *verb modules* don't
   import the engine — but nothing asserts that *callers of the old CLI surface* (the webhook)
   were updated. Mock-based tests let `intake/` keep asserting the dead `harness run` argv and
   stay green. Guidance note: when retiring a command/contract, grep for every string-literal
   invocation of it (including sibling packages and their tests), not just the import graph.

2. **CODE-2-INSIGHT — `test_docs_consistency.py` exists but doesn't cover CLI-contract-in-prose
   drift.** SPEC §11 still documents the full `harness run <workflow>` surface and exit-code-3
   "contract violation" semantics from the engine era alongside the new verbs. A check that the
   documented command surface matches `harness/cli/__init__.py`'s registered commands would have
   flagged both the SPEC drift and CODE-1.

3. **CODE-3-INSIGHT — Dual dependency declaration (extras + dependency-groups) is an emerging
   foot-gun.** The single-entry `[dependency-groups]` block is the seam where CODE-2 crept in. A
   convention ("dev tooling lives in exactly one place") removes the ambiguity before it spreads.
