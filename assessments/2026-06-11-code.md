## Findings

### CODE-1 — `close` gate has a dirty-worktree bypass — **[High]** · `CAL-586`
- **What:** `close` binds the gate to `head_sha` captured *before* merge, then `_merge_and_push` runs `git status --porcelain` and, if dirty, `git add -A && git commit` — committing and merging content that was never part of `head_sha` and never had a `review` event. The gate catches *commit-after-review* (HEAD advances → `stale_review`) but not *edit-without-committing*.
- **Where:** `harness/cli/close.py:175` (capture HEAD), `:182` (gate), `:384-392` (auto-commit dirty inside `_merge_and_push`).
- **Why:** Breaks the verb's own guarantee (`close.py:7`: "a merge can never land on an unreviewed or stale tree"). The pivot's thesis is that the deterministic verb is the guardrail — it must not rely on the agent having committed before review. **Confirmed untested.**
- **How:** Refuse when `git status --porcelain` is non-empty at gate time (add a `dirty_worktree` refusal reason), or commit-then-re-evaluate the gate (which then correctly yields `stale_review`). Add the test.

### CODE-2 — `harness cancel` is vestigial against the verb model — **[Medium]** · `CAL-587`
- **What:** `cancel` SIGTERMs `runs.pid` expecting a long-running `harness run` process; `start` writes `os.getpid()` then exits, so the PID is dead on arrival and runs are `open`/`closed`, never `running`. `cancel` can only hit its refusal paths.
- **Where:** `harness/cli/cancel.py`; PID write `harness/cli/start.py:362`; registered `harness/cli/__init__.py:66`.
- **Why:** A public verb that cannot perform its function is a contract-level dishonesty (SPEC §1 lists it as real).
- **How:** Remove `cancel` (and the stale `pid` write), or redefine it for the verb model (abandon / close-without-merge).

### CODE-3 — `intake/` shells out to the deleted `harness run` — **[High]** · `CAL-601` *(both passes found this; canonical = CAL-601, HIGH + `decision`-parked; my CAL-588 closed as duplicate)*
- **What:** The Linear-webhook receiver's only action is `Popen(["harness","run",workflow,…])`; `run` was deleted (CAL-574). Every routed webhook fails; `test_linear_webhook.py` mocks the subprocess, so the suite asserts the *wrong* argv and stays green.
- **Where:** `intake/linear_webhook.py:191-229`; contract asserted at `tests/unit/test_linear_webhook.py:384`.
- **Why:** A reachable-but-broken path in the autonomous/Hermes intake the new model leans on; mock-based tests give false green.
- **How:** Decide intake's post-verb shape (likely: drive the launcher socket / `start` verb), then update module + tests. **Needs a design decision** → `decision`-parked.

### CODE-4 — `query.py` dead engine-era branches, locked green by synthetic-event tests — **[Medium]** · `CAL-589`
- **What:** `status --json` derives `current_node`/`failure_*` from `node_started`/`workflow_failed` events no live verb emits; `runs --by-reason` groups by them. `test_cli_query.py` manufactures those events and asserts they populate — dead code reads as covered.
- **Where:** `harness/cli/query.py:81,159,484`; tests `tests/unit/test_cli_query.py:620+`.
- **Why:** Dead code disguised as live by tests exercising retired-era data — false confidence.
- **How:** Delete the branches + synthetic-event tests, or mark them reserved-dormant for Hermes observability and stop claiming them live.

### CODE-5 — worktree path/branch convention duplicated across three modules — **[Low]** · `CAL-590`
- **What:** The `.worktrees/harness/<run_id>` root and `harness/<run_id>` branch scheme appear independently in three places; a layout change needs all three in lockstep.
- **Where:** `harness/worktree.py:91`, `harness/cli/worktrees.py:69`, `harness/cli/start.py:14`.
- **Why:** DRY / single source of truth.
- **How:** Hoist a `WORKTREES_SUBDIR` constant + `worktree_path(repo_root, run_id)` helper into `harness/worktree.py`; import in `worktrees.py`.

### CODE-6 — two conflicting mypy pins across two dependency mechanisms — **[Low]** · `CAL-602` *(from the autonomous pass)*
- **What:** `[project.optional-dependencies].dev` pins `mypy>=1.7` while `[dependency-groups].dev` pins `mypy>=2.0.0`. Both satisfied today, but the same tool is declared twice with different floors in two competing systems.
- **Where:** `pyproject.toml:24` vs `:79`.
- **Why:** Ambiguous source of truth; a future bump to one silently diverges the gate from a fresh `uv sync --extra dev`.
- **How:** Consolidate to one mechanism (drop the single-entry `[dependency-groups]` and raise the extras pin to `>=2.0.0`, or move all dev tooling into `[dependency-groups]`).
