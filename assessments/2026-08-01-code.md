## Findings

### CODE-1 — `test_cli_reclaim.py` is the single 2,768-line test home for four production modules the `close`/`review` families each split into their own test module — Medium

**What:** `reclaim` is decomposed in production across four modules — `harness/cli/reclaim.py` (685 lines), `reclaim_closable.py` (35 stmts), `reclaim_liveness.py` (57 stmts), `reclaim_undo.py` (387 lines) — carved out over five tickets (#216, #235, #254, #255, #256). All four are tested from **one** file: `tests/unit/test_cli_reclaim.py` imports the whole family on a single line (`:48`) and holds **96 test functions and 23 private helpers** in **2,768 lines**. It is not a case table; the 23 helpers are inlined setup logic.

The repo's own convention says otherwise, and the contrast is same-window and unambiguous. The `close` and `review` families were decomposed by the same discipline in the same period and **each extraction got its own test module**: `test_close_tracker.py` (80 lines, for `close_tracker.py`), `test_close_terminal_telemetry.py` (734, for `close_telemetry.py`), `test_review_terminal_telemetry.py` (564, for `review_telemetry.py`). `reclaim` is the outlier, and the divergence is invisible per-change because each of the five tickets only appended to a file that was already large.

It is also the worst place for it to happen. `test_cli_reclaim.py` has been touched by **12 commits since 2026-07-01** — the highest-churn test file in the repo — so every reclaim ticket pays the navigation cost, and the `reclaim_undo` block alone (roughly `:2110–2570`, ~460 lines) is a coherent, self-contained arm sitting inside it.

Nothing catches this: `test_source_file_size_justification.py:114` globs `tracked_files_under("harness")` only, and its docstring (`:22–28`) records the `tests/` exclusion as an explicit, never-revisited deferral.

**Where:**
- `tests/unit/test_cli_reclaim.py:48` (the four-module import), `:1337–1485` (the `reclaim_liveness` arm), `:1828–2068` (the `reclaim_closable` arm), `:2110–2570` (the `reclaim_undo` arm) — 2,768 lines total
- `tests/unit/test_close_tracker.py`, `tests/unit/test_close_terminal_telemetry.py`, `tests/unit/test_review_terminal_telemetry.py` — the same-window precedent the reclaim family diverges from
- `tests/unit/test_source_file_size_justification.py:22–28` (the recorded `tests/` deferral), `:114` (the `harness`-only glob)

**Why:** `code-quality` Part B — the 500-line hard limit, with a 1.5× (750) ceiling for genuinely declarative files; this file is 5.5× the hard limit and 3.7× the declarative ceiling, and is not declarative. Part B's *Compose, don't inline* — "when a unit mixes two concerns, split by concern, named by the symbols that handle each" — reads directly onto a test module covering four separately-named production modules. Part C's rule that an over-limit file is "an auditable choice, not silent drift" is the one this most squarely misses: the file carries no `size:` marker and no one ever decided it should grow, which is the definition Part C gives of silent drift.

**How:** Split along the seams production already established, mirroring the close/review precedent: move the `reclaim_undo` arm to `tests/unit/test_reclaim_undo.py` and the `reclaim_liveness` / `reclaim_closable` arms to `tests/unit/test_reclaim_liveness.py` and `tests/unit/test_reclaim_closable.py`, leaving `test_cli_reclaim.py` as the verb-level suite. Take the `reclaim_undo` arm first — it is the largest coherent block, has the clearest boundary, and covers the module with the lowest coverage of the four (88%). Where a split is genuinely not worth it, the alternative is the one Part C names: add a `# size:` marker recording the decision, so it is auditable rather than silent. Land under CODE-INSIGHT-1, which stops the next one being invisible.

**On severity:** Medium, not High. Nothing is broken and nothing is untested — coverage across the four modules is 93%, 100%, 100%, 88% and the suite is green — so this is structural drift and churn concentration, which the severity table places at Medium. It is not Low because 5.5× the hard limit on the repo's highest-churn test file is not minor drift, and because the deferral that let it happen is a standing open decision rather than an accident.

## Systemic insights

### CODE-INSIGHT-1 — the mechanized size guard's `tests/` exclusion is an open deferral, not a decision; close it at the declarative ceiling

**The class:** every over-limit test module, forever. `code-quality` Part C mechanizes the size rule precisely so it is "enforced at the gate at commit time rather than waiting for a reviewer to remember it or the steward's next pass" — but the repo's implementation scopes to `harness/` and defers `tests/` (`test_source_file_size_justification.py:22–28`). In the interval, `tests/` grew to **29 files over the 500-line hard limit and 14 over the 750 declarative ceiling**, none of them carrying a recorded decision, and no per-change review sees a file that was already large. CODE-1 is one instance; the guard's own docstring predicted the rest.

**The edit:** extend the guard's glob in `tests/unit/test_source_file_size_justification.py:114` to cover `tracked_files_under("tests")` under Part B's **declarative ceiling of 750** rather than the 500 hard limit — the higher bar is the honest one for a test module, whose length is substantially case enumeration. Mirror the same two-tier config into `templates/size-guard.md`, which ships the reference implementation to every consuming repo and today names only the production glob. The 14 files already over 750 each take a one-line `# size:` marker or a split — which is the point: the deliverable is that each becomes an auditable choice, not that every file shrinks. Evidence: CODE-1.

### CODE-INSIGHT-2 — a production seam extraction should ask where the extracted module's tests go, the same way #273 made it ask about the watchlist entry

**The class:** test structure silently failing to follow production structure. `review-discipline`'s Architecture-watchlist bullet was extended one commit ago (#273, `01dbd20`) so that a seam extraction must refresh the `CONTEXT.md` entry it invalidates. The adjacent question — *where do the extracted module's tests now live?* — is asked nowhere, in either `code-quality` Part B (*Extract on the third strike*, which governs production structure only) or `review-discipline`. The repo demonstrably has the convention: `close_tracker`, `close_telemetry`, and `review_telemetry` each got their own test module on extraction. Nothing states it, so adherence is coincidental — and `reclaim`'s four extractions, in the same window, all landed back in one file (CODE-1).

**The edit:** add one clause to the same `skills/review-discipline/SKILL.md` Architecture-watchlist bullet #273 just amended: when the outcome is a seam extraction, confirm the extracted module's tests moved with it — either into a test module of its own or with a stated reason they stayed. This reuses the bullet's existing severity and trigger rather than adding machinery, and puts the check at the one moment the information is free (the reviewer is already looking at the extraction). Evidence: CODE-1, plus the three-file close/review precedent it diverges from.
