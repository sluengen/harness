## Findings

### CODE-1 — Force-push guard recognises only the `env` wrapper; siblings pass a literal `--force` through — Medium

**What:** The guard strips leading command wrappers before deciding whether a command is a `git push`, but its wrapper set has exactly one member: `const WRAPPERS = new Set(["env"]);`. A command prefixed with any sibling wrapper is never recognised as `git`, so a **literal, unobfuscated** force-push is allowed. Verified by driving the hook with exact JSON payloads (not reasoned about):

```
DENY  | env git push --force origin dev          ← the one member
ALLOW | nohup git push --force origin dev
ALLOW | command git push --force origin dev
ALLOW | exec git push --force origin dev
ALLOW | timeout 60 git push --force origin dev
ALLOW | nice git push --force origin dev
ALLOW | env nohup git push --force origin dev    ← composes past the handled member
ALLOW | sh -c "nohup git push --force origin dev" ← and past the nested-shell recursion
```

The deny globs in `.claude/settings.json` do not backstop this: they are anchored (`Bash(git push --force *)`, `Bash(git -C * push --force *)`), so a `nohup ` prefix defeats them too. **Both layers miss the same class.**

**Where:** `hooks/git-push-guard.js:360` (`WRAPPERS`), consumed by `stripPrefixes` at `hooks/git-push-guard.js:384-388`; deny globs at `.claude/settings.json` (`permissions.deny`). Tests: `tests/unit/test_git_push_guard_hook.py` (40+ deny cases, **zero** exercise `WRAPPERS` — `FOO=bar git push --force` at line 89 tests the `ASSIGNMENT` regex, not the wrapper set); `tests/unit/test_force_push_denylist.py` likewise has no wrapper case.

**Why:** The guard's own header sets the bar it fails here — it enumerates an explicit out-of-scope list (parameter expansion, script *files*, `base64`/`xargs`/`find -exec`) and then states: *"Adding a new obfuscation vector to this list (with a one-line justification) is a valid resolution — the hook must never **silently** miss a class."* The wrapper family is neither closed nor listed, so it is silently missed. It is also incoherent with the guard's demonstrated threat model: the hook decodes `$'\x67it'` → `git` (an *only*-adversarial vector, confirmed DENY in probing) while a one-word `nohup` prefix walks through. `env` being implemented proves the wrapper class was recognised at design time; only its membership is short. Contrast `SHELLS`, whose every member (`sh`/`bash`/`zsh`/`dash`/`ash`/`ksh`) was probed and correctly denies — that set is complete and tested.

**How:** Extend the set to the wrapper family that re-execs its argv — `WRAPPERS = new Set(["env", "nohup", "command", "exec", "timeout", "nice", "stdbuf", "setsid", "time"])` — noting that `stripPrefixes` must skip each wrapper's *own* options and operands (`timeout 60 …`, `stdbuf -o0 …`, `nice -n 5 …`) before the next token is treated as the executable, or `timeout 60 git push --force` will still slip. Add a `_MUST_DENY` block to `tests/unit/test_git_push_guard_hook.py` covering one case per member plus the two composing forms above (`env nohup …`, `sh -c "nohup …"`), and a `_MUST_ALLOW` case (`nohup git push origin dev`) pinning against over-denial. Any member deliberately left out belongs in the header's out-of-scope list with its one-line justification, per the guard's own rule.

*Severity note:* Medium, not High — the guard is explicitly defence-in-depth atop the deny globs and (once public) server-side branch protection, it is not the sole gate, and no code path in the tree invokes these wrappers. Erring toward the lower severity per `assessment-craft`.

## Systemic insights

### CODE-INSIGHT-1 — Record server-side branch protection as the authoritative force-push control, so the parser stops being the gate

**The class it prevents:** another force-push-bypass finding every pass. Inside this single window the guard shipped and was then hardened **four times** (`bc8ed52` → `c7b6007` command substitution → `7759a06` `sh -c`/`eval`/ANSI-C → `4d8745a` nested shells/brace groups), each commit closing a class discovered *after* the last one shipped — and CODE-1 shows a fifth still open. The guard's header already concedes the endgame: *"A shell is Turing-complete, so no static parser can catch every way to reach `git push --force`."* A denylist parser chasing an unbounded class will keep generating exactly this finding, one class per pass. The durable control is the one the guard's header already names as a backstop but that nothing in the repo tracks: server-side branch protection. `grep -rn "branch protection"` over the tree returns **nothing** — it is named only in the hook's own comment (`hooks/git-push-guard.js:62`, "once the repo is public").

**The exact edit:** two parts. (1) In `hooks/git-push-guard.js`, promote the parenthetical at line 62 into a short **Authoritative control** paragraph in the header: the parser is best-effort defence-in-depth whose job is catching *accidents and casual evasion*, the authoritative control is a server-side branch-protection rule on `dev`/`main` rejecting non-fast-forward pushes, and a newly discovered parser bypass is therefore a Low/Medium finding rather than an escalation. (2) Add server-side branch protection on `dev` and `main` as an explicit acceptance criterion on the go-public ticket (**CAL-1029**, currently unblocked and operator-run), since protection rules are exactly what the public flip makes available. **Evidence:** CODE-1, plus the four-commit hardening sequence above.

### CODE-INSIGHT-2 — Pin every recognition-set member with a test case, since that is where the guard's silent gaps live

**The class it prevents:** a security guard whose behaviour is driven by set membership (`WRAPPERS`, `SHELLS`, `GIT_GLOBAL_WITH_ARG`) silently under-covering, because the set is code but its *membership* is untested. Probing showed the difference sharply: every `SHELLS` member denies correctly and 22 test lines reference its members, whereas `WRAPPERS`' one member (`env`) has **zero** test cases — and it is precisely the untested set that turned out short (CODE-1). The 40+ deny cases in `tests/unit/test_git_push_guard_hook.py` are organised by *narrative vector* (substitution, ANSI-C, nested shell), which is why an entire set slipped through with full-looking coverage.

**The exact edit:** in `tests/unit/test_git_push_guard_hook.py`, add a parametrised test that imports each recognition set's membership from `hooks/git-push-guard.js` (parse the `new Set([...])` literals — the file already reads the hook as text) and asserts that **every member** denies a canonical force-push through that construct — one case per `WRAPPERS` member, one per `SHELLS` member. This makes adding a member to a set without a matching deny case a **gate failure**, so the next set to grow cannot repeat CODE-1. **Evidence:** CODE-1.

## Addendum — CODE-1 actioned, and a second symptom found while fixing it

*Added by the routine (`/harness routine build`, idle arm) after the steward's pass, on the same tick. Recorded here because this report is the only durable evidence: no ticket could be filed.*

**CODE-1 was reproduced independently before being touched** — the hook was driven with the same payload shapes, confirming nine literal force-push forms allowed (`nohup`, `command`, `exec`, `timeout 60`, `nice`, `stdbuf -o0`, `xargs`, `env nohup`, `sh -c "nohup …"`) against a correctly-denied `$'\x67it'`.

**A second symptom of the same root cause, which the steward's pass did not surface:** the guard matched the git executable by **exact string** (`tokens[0] !== "git"`), while basename-matching nested shells one function away (`tokens[0].split("/").pop()`). So a path-qualified invocation was allowed:

```
ALLOW | /usr/bin/git push --force origin dev
ALLOW | ./git push -f origin dev
ALLOW | env /usr/bin/git push --force origin dev
```

This is arguably the plainer gap of the two — `/usr/bin/git` is an ordinary spelling, not an evasion. Both symptoms share one root cause: **the guard's recognition of which token is the git command was too narrow.** Fixing only the wrapper set would have left it open, which is why the fix addresses the root cause rather than the cited line.

**Resolution shipped** (branch `quality/push-guard-command-resolution`, PR opened for review — an unattended run does not self-merge a security control): executables matched on basename; a leading wrapper resolved past to the command it runs. The wrapper's operands are **scanned** rather than its option grammar modelled — the steward's `How` correctly noted `stripPrefixes` must skip `timeout 60` / `nice -n 5`, but modelling each wrapper's flags is the brittle half, since one unmodelled option silently re-opens the class. Scanning fails safe: over-broad denies a non-force command (recoverable), under-broad lets a force-push through (not).

**CODE-INSIGHT-1 partially actioned:** the *Authoritative control* paragraph is now in the guard's header. The second half — branch protection on `dev`/`main` as an AC on **CAL-1029** — needs a human, as an unattended run cannot edit tickets.

**CODE-INSIGHT-2 not actioned as specified, and its rationale is worth keeping.** Every wrapper-set member is now individually pinned (31 new cases; gate 1475 → 1506), which closes the concrete gap. The proposed *mechanism* — parsing the sets out of the hook so an unpinned member fails the gate — was **not** built: it is a real change of its own, and a test that parses JavaScript source with a regex adds a brittleness the finding did not ask for. The insight stands as filed.

**CODE-2 (retention) not actioned:** the compaction is `/assess`'s own committing step, and folding 24 reports is its own change rather than a rider on a security fix. Still open.
