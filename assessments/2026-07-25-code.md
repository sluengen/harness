## Findings

### CODE-1 — Two abandoned promotion worktrees live at an undocumented, non-canonical path — High

**What:** `git worktree list` (run from the repo root) currently reports two live worktrees nested *inside* the `harness/` package directory — `harness/.worktrees/harness/01KY9WNC39HZ20K738FSD1SHZB` (branch `promote/2026-07-24-dev-to-staging`, tip `126c769`, committed 2026-07-24T11:02:42Z) and `harness/.worktrees/harness/01KY9WTJ3R38F8DKKFHSD4QB2E` (branch `promote/2026-07-24-staging-to-main`, tip `76de5b7`, committed 2026-07-24T11:05:32Z) — instead of the documented `<repo-root>/.worktrees/harness/<id>` (`harness/identity.py:26`, `WORKTREES_SUBDIR = Path(".worktrees/harness")`, described as "the single source of the harness worktree layout"). Both branches are already merged into `origin/staging` and `origin/main` (`git branch --merged origin/main` includes both), so the promotions themselves succeeded — only the worktree cleanup never happened, and it happened at the wrong path.
**Where:** on-disk state at `harness/.worktrees/harness/{01KY9WNC39HZ20K738FSD1SHZB,01KY9WTJ3R38F8DKKFHSD4QB2E}`; root cause in `harness/workspace.py:102` (`resolve_repo_root`) and `harness/cli/_repo.py:28` (`resolve_repo_root_or_exit`), and the promote CLI's `--repo` default at `harness/cli/promote.py:267` (`Path(".")`).
**Why:** `resolve_repo_root` resolves `--repo` (default: CWD) with `Path(path).resolve()` and an allowlist check only — it never verifies the candidate is an actual git top-level (e.g. via `git rev-parse --show-toplevel`). Because the package directory is also named `harness`, invoking a verb (here, `promote`) with CWD set to `<repo>/harness/` instead of `<repo>/` is a one-`cd`-away mistake, and it silently succeeds: `create_promotion_worktree` (`harness/promotion.py:232`) plants the worktree at `<resolved-repo-root>/.worktrees/harness/<id>`, which becomes `<repo>/harness/.worktrees/harness/<id>` with no error or warning. This directly contradicts the "single source of the harness worktree layout" comment in `identity.py:26` and the CONTEXT.md/RUNBOOK invariant that verbs run with CWD at the main-repo root. `harness worktrees cleanup` (`harness/cli/worktrees.py:58`, `_worktrees_root`) only scans the canonical `<repo-root>/.worktrees/harness/` — it cannot see or reclaim a worktree at this nested path, so these two are permanently invisible to the harness's own cleanup tooling until removed by hand.
**How:** (1) **Done during this pass** — both worktrees were confirmed clean (no uncommitted changes) and their tips confirmed already merged (`origin/staging`, `origin/main` respectively), then reclaimed by hand: `git worktree remove` on both paths, followed by `git branch -d` on both promotion branches and removal of the now-empty `harness/.worktrees/` directory tree. (2) Still open — harden `resolve_repo_root` (`harness/workspace.py:102`) to reject a candidate that is not an actual git top-level (compare against `git rev-parse --show-toplevel` run at that path, or check for a `.git` entry), so a verb invoked from inside `harness/` fails loudly with a clear message instead of silently writing state to the wrong place. Tracked as CODE-INSIGHT-1 below.

### CODE-2 — Three tree-walking test guards share one missing exclusion, and reproduced failing this pass — High

**What:** Running the full unit suite this pass (`uv run --extra dev pytest -m 'not slow and not integration'`) produced **7 failures** before the CODE-1 cleanup (confirmed by re-running the same three files after the cleanup: 557 passed, 0 failed): `test_time.py::test_z_substitution_lives_only_in_the_time_helper`, two parametrized instances of `test_cli_surface_locked.py::test_py_docstrings_have_no_retired_cli_reference`, and four parametrized instances of `test_engine_retired.py::test_living_source_has_no_intake_module_reference`. None of these are code regressions — they fired because the abandoned worktrees under `harness/.worktrees/` carried old copies of `tests/unit/test_time.py`, `tests/_gitutil.py`, and `tests/unit/test_engine_retired.py` from a point before those retired-pattern guards existed in their current form, and the scans below walk straight into them. The zombie worktrees are gone now (CODE-1), but the guards themselves are still exposed to the same class recurring after any future stray worktree.
**Where:** `tests/unit/test_time.py:66` — `for path in sorted((_REPO_ROOT / "harness").rglob("*.py")):`; `tests/unit/test_cli_surface_locked.py:647` inside `_py_sources()` (defined at `:642`) — `files += sorted((REPO_ROOT / base).rglob("*.py"))` for `base in ("harness", "tests")`; `tests/unit/test_engine_retired.py:540` inside `_living_source_relpaths()` (defined at `:530`) — `for p in sorted(pkg.rglob("*.py"))`, which only filters `__pycache__`.
**Why:** all three functions walk `harness/` (two of them also `tests/`) with `Path.rglob("*.py")` and no guard against a nested git worktree or any dot-prefixed directory living inside the scanned tree — a real, standing possibility in this repo, since `.worktrees/` is `harness/`'s own designed run-artifact location (`.gitignore:35`) and CODE-1 shows it can end up nested one level deeper than intended. The fix pattern already exists a few lines away in the *same file*: `test_engine_retired.py`'s sibling function `_living_doc_relpaths` (`:507`) explicitly excludes any path segment starting with `.` (`if any(p in _HISTORY_SEGMENTS or p == "node_modules" or p.startswith(".") for p in parts)`), but that exclusion was never applied to the source-scanning function three lines below it, nor to the equivalent scans in the other two files — the same missing guard, independently absent in three places. Per `code-quality`'s size/duplication lens, this is exactly the "load-bearing pattern needing a shared helper" case: a repo-tree Python-source walk is a one-purpose operation used in at least three test modules, and none of them share it.
**How:** Add a `.`-prefix (and `.worktrees` specifically) exclusion to each of the three `rglob` call sites — the same one-line filter `test_engine_retired.py:507` already uses (`if not any(part.startswith(".") for part in path.relative_to(_REPO_ROOT).parts)`), or better, extract one shared helper (e.g. `tests/_gitutil.py` or a new `tests/_treewalk.py`) that both files import, since the pattern now appears in three test modules with no common home — matching the rule-of-three in `code-quality` Part B. This restores the gate to green independent of local worktree cleanliness and prevents the same false failure recurring after every future promotion/build run that leaves a worktree behind.

## Systemic insights

### CODE-INSIGHT-1 — `resolve_repo_root` accepts any resolvable path as a repo root with no git-toplevel check, so a `cd`-into-the-package-dir mistake silently corrupts state instead of failing loudly

The class this prevents: any verb (`start`, `promote`, `review`, `close`) invoked with `--repo`/CWD pointing at a *subdirectory* of the real repo root — not just the `harness/` package-dir collision CODE-1 hit, but any nested directory an operator or script CDs into by mistake — silently writes ledger rows, worktrees, and branches under that wrong root instead of refusing. The exact edit: in `harness/workspace.py:102` (`resolve_repo_root`), after `Path(path).resolve()`, verify the candidate is a real git top-level — run `git rev-parse --show-toplevel` at the candidate and assert it equals the candidate (or walk up to find `.git` the way `harness/cli/_git.py:git_common_dir` already does for a different purpose) — and raise `WorkspaceNotAllowed` (or a new, equally-typed refusal) when it is not. Evidence: CODE-1's two zombie worktrees, which the harness's own `worktrees cleanup` command cannot see or reclaim because they were planted one level below the true root.
