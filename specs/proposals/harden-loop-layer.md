# Proposal: Harden the autonomous loop layer

> An assessment of the *Loop Engineering* field study (Osmani / Anthropic / Stripe) graded the harness against the five moves and four costs of a self-running loop. We score strongly on the **machine-honesty** guards — SHA-bound verdict, ledger, builder ≠ recorder — and thinly on three **operator-facing** loop concerns: no spend ceiling, discovery logic that has drifted from what actually runs, and a scheduling story that is local-only by default rather than by decision. This proposes to close the three.

## Problem / motivation

The harness is the *harness layer* of the playbook's stack (it arms one run), but `/harness routine build` is a *loop* (it discovers its own work, runs unattended, feeds itself across runs via Linear + the ledger). Read as a loop, three gaps are real and confirmed in the code:

1. **No spend ceiling (token blowout).** The autonomous Build routine and the review → fix → re-review cycle have **no per-run budget, no daily cap, and no max-retry ceiling**. The only spend-related mechanism is graceful Codex→Claude fallback on tier depletion (`harness/cli/review.py`) — degradation, not a circuit breaker. The playbook's one cost that "hits the bill directly" is exactly the one we have not bounded. A single bug that spins the fix loop overnight is, today, unbounded.

2. **Discovery logic has drifted from what runs (manual/blind-loop smell).** The pick logic lives as **inline prose in `commands/harness.md` step 1**, and the *actual* local scheduled tasks (`~/.claude/scheduled-tasks/harness-work-pull`, `harness-code-assess`) still carry **pre-reclamation logic and say "use /build"** instead of invoking the versioned `/harness routine build` / `quality`. So the CAL-734…739 reclamation work — and the routine logic generally — **is not in the nightly runs**. The principle the repo already states, *version the logic, not the schedule*, is being violated in practice: the logic that runs ≠ the logic that is versioned.

3. **Scheduling is local-only — and we assumed cloud was out of reach (it largely isn't).** Cloud routines are "empty by design"; everything runs on a machine that must stay on. The playbook is blunt: the overnight sweep belongs in the cloud because "laptops get their lids closed." The first draft of this proposal assumed cloud was "a project" because the Docker wrapper sources credentials from the macOS Keychain / `.env` / `~/.codex`. **On review that was wrong.** The full gate (`scripts/verify.sh`) already runs green on `ubuntu-latest` in CI on every main PR; there are **zero** Xcode/Swift/macOS/Homebrew dependencies; the verbs run **in-process** (native `uv tool install .` entry point — no Docker-in-Docker; the one daemon-needing test is `integration`-marked and self-skips when `docker info` fails). The Mac-local pieces are credential *sourcing*, not execution, and each becomes a standard cloud secret (`LINEAR_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_API_KEY`, push creds). The one residue — Codex review's `~/.codex` subscription auth — is moot: Codex-in-container is already bwrap-blocked (CAL-866) and the engine already falls back to Claude. So for the harness's **own** loop, cloud is a secrets-wiring + engine-selection job, not a re-architecture. **The real constraint is per-target-repo:** the harness is infrastructure other repos self-host, and a target whose gate needs Xcode (e.g. an iOS repo) must stay on macOS — cloud-viability is set by the *target's* gate, not the harness's auth.

The meta-read worth stating: we over-invested in the machine's honesty and under-invested in the operator's. For a largely solo operator, the playbook's sharpest warning lands — "one person plus a pile of loops easily becomes an echo chamber where no one argues." Caps and a non-drifted, consciously-scheduled loop are part of the answer. (Sampling discipline — the other half — was considered and deferred; see Out of scope.)

## Options

These are three loosely-coupled workstreams, not mutually-exclusive options. Within each, the design choice that matters:

**WS1 — Spend ceiling. What does the harness actually meter?**
- **A1 — Deterministic, ledger-backed proxies.** Enforce the breakers the harness can observe without new infrastructure: a **max review-retry count per run** (the `events` ledger already records each review verdict — refuse/escalate after K fails), a **per-run wall-clock budget** (`runs` has the start timestamp), and a **daily routine run-cap** (count runs the routine has opened today). · *Trade-offs:* every signal already exists in the ledger; deterministic and testable; honours the verb model. Does not meter dollars/tokens directly — it bounds the *behaviours* that burn them.
- **A2 — True token/cost metering.** Track actual tokens/$ spent and stop at a ceiling. · *Trade-offs:* the harness cannot see the orchestrating Claude session's token meter — the verbs are one-shot CLI calls, not the session. True metering needs session-budget integration (the kind the Workflow harness exposes as `budget`, which the routine is not). Higher fidelity, materially more plumbing, and partly outside the harness's reach. *Premature for v1.*

**WS2 — Discovery drift. Where is the fix?**
- **B1 — Re-sync the triggers; keep the logic where it is.** The discovery logic is already versioned (repo-owned `commands/harness.md`, per CAL-650). The defect is the *trigger* drift, not the logic's home. Make each local scheduled task a **thin invocation of the versioned routine** (`/harness routine build` / `quality`) and add a guard/check that flags when a trigger inlines logic instead of calling the versioned surface. · *Trade-offs:* smallest change that fixes the actual failure; no new abstraction. The scheduled-task files live *outside* the repo (`~/.claude/...`), so part of this is an operational runbook + a drift check, not only code.
- **B2 — Extract a `work-discovery` skill and have the routine call it.** Move the pick logic into `skills/`. · *Trade-offs:* matches the playbook's "discovery is a skill" literally, and a skill is reusable across repos. But moving prose into a skill purely to relocate it, when it is already versioned and single-homed, risks abstraction without payoff (`engineering-principles`: no premature abstraction). Justified only if a *second* consumer needs it.

**WS3 — Cloud vs local. Now that cloud is cheap for the harness's own loop, how far to go?** (See the corrected finding above — the gate is already Linux-proven by CI; only credential sourcing was ever local-bound.)
- **C1 — Stay local-only, by decision.** Record local as the deliberate choice and defer cloud. · *Trade-offs:* cheapest, but now hard to justify — the blocker we thought existed does not. Leaves overnight autonomy unbuilt (lids still close) for no real technical reason.
- **C2 — Wire the harness's own Build/Quality loops to a cloud schedule.** Provide credentials as cloud secrets, select the Claude review engine (already the in-container reality), and run the loop on a cloud schedule against the existing reclamation (which already keys on Linear, so the fresh-clone / no-local-DB case is handled). · *Trade-offs:* modest and buildable — not the "real proposal of its own" the first draft imagined. Must also document the per-target-repo gate constraint so nobody assumes every self-hosting repo can go cloud. The 1-hour-min cloud interval is fine for an overnight sweep.

## Recommendation

- **WS1 → A1, with the breakers set.** Ship deterministic, ledger-backed breakers against state we already record: (a) a **hard ceiling of 6 review→fix cycles per run** — cycles 1–3 stay unconditional, after which the build agent assesses convergence on each FAIL before continuing, and at **6** the run stops and escalates regardless; and (b) a **per-run wall-clock budget** (90 minutes as shipped; 110 since #260), deliberately mirroring the reclamation staleness threshold so a runaway run trips the breaker right as reclamation would call it stale — a mirroring #260 later replaced with identity, the two becoming one configured value. The build ticket must **reconcile these with `agents/reviewer.md`'s current "2nd consecutive FAIL → escalate"** so the loop has one coherent stop rule. Daily run-cap dropped from v1 (per-run bounds + reclamation cover the blowout risk; revisit only on an observed daily-volume blowout). True token/$ metering (A2) deferred until a clean session-budget hook exists; don't build metering the harness can't observe.
- **WS2 → B1 + B2 (recommended).** Fix the trigger drift *and* extract the discovery logic into a `work-discovery` skill the routine invokes. The skill-extraction is justified *here specifically* because the harness is **distributed guidance other repos self-host** — a `work-discovery` skill has a genuine second consumer (every self-hosting repo's routine), so it is reuse, not premature abstraction. It also matches the playbook's "discovery is a skill" and pays off intent-debt. The triggers become thin callers of the versioned surface; the pick logic gets a maintainable home; the routine command still invokes the skill.
- **WS3 → C2, as the close-out (revised on review).** The original recommendation (C1, "cloud is a project") rested on a premise that turned out false: CI already proves the gate runs on Linux, the verbs run in-process, and the only Mac-local pieces are credential sourcing. So wire the harness's **own** loop to a cloud schedule (secrets + Claude engine), and record — as the durable decision — that cloud-viability is **per-target-repo, set by that repo's gate** (Xcode-bound repos stay local or on macOS runners). Sequenced **last, after WS1**: an unbounded loop must not run unattended in the cloud, so the spend-breakers land first and the cloud wiring is the capstone (the playbook's "add scale last, after the checks are proven").

All three trace to `engineering-principles`: smallest change that fixes the real failure (A1's bounded breakers, B1's de-drift), justified-not-premature abstraction (B2 has a real second consumer — every self-hosting repo; A2 metering deferred until observable), and decisions recorded where they are governed (WS3).

### Resolved 2026-06-30 — all three closed, no open decisions remain

- **D1 → A1, breakers set.** Hard ceiling **6** review→fix cycles per run (cycles 1–3 unconditional; after 3, the build agent assesses convergence on each FAIL; hard stop + escalate at 6) and a **90-minute** per-run wall-clock budget (mirrors the reclamation staleness threshold). *Superseded by #260: the budget is 110 minutes and is no longer a mirror — `loop.wall_clock_budget_minutes` is the one value both the breaker and `reclaim --stale` read.* Daily run-cap dropped from v1 (per-run bounds + reclamation suffice). True token/$ metering deferred. **Build note:** reconcile with `agents/reviewer.md:34` ("2nd consecutive FAIL → escalate") so there is one coherent stop rule — the current doc and the 3-unconditional/6-ceiling posture must be made consistent.
- **D2 → B1 + B2 (recommended).** Extract a `work-discovery` skill the routine invokes *and* de-drift the triggers. In a normal single-app repo the extraction would be premature, but the harness is distributed guidance other repos self-host, so the skill has a real second consumer — reuse, not premature abstraction, and a direct match to the playbook's "discovery is a skill." The skill holds the discovery *knowledge* (what to read, how to judge actionable); the routine command still invokes it.
- **D3 → C2, as the close-out (revised same day, on review of the auth path).** The first pass chose C1 on the belief that cloud was "a project." Re-examined: the full gate already runs on `ubuntu-latest` in CI, the verbs run in-process (native install, no Docker-in-Docker), and the only Mac-local dependencies are credential *sourcing* → cloud secrets. So wire the harness's own Build/Quality loops onto a cloud schedule (Claude review engine) as the **final step, after WS1 (hard — breakers) and WS2 (deploy the de-drifted loop, not a mid-refactor one)**, and record that cloud-viability is per-target-repo (Xcode targets stay local / macOS-runner). In Linear: CAL-908 is *blocked by* both CAL-906 and CAL-907; CAL-906 ∥ CAL-907. No separate `cloud-overnight-sweep` proposal is needed — it folds into WS3.

## Breakdown

The change specs this spawns (each shippable alone):

1. **WS1 — Ledger-backed spend breakers** (CAL-906). Enforce a **hard ceiling of 6 review→fix cycles per run** (cycles 1–3 unconditional; after 3, assess convergence per FAIL; hard stop + escalate at 6) and a **90-minute per-run wall-clock budget** (retuned to 110 and made the single source for reclamation staleness too by #260), against the existing `runs`/`events` ledger; surface both in `CONTEXT.md`. Reconcile with `agents/reviewer.md`'s current "2nd consecutive FAIL → escalate" into one coherent stop rule. No daily run-cap in v1; no token metering. Test-first — each numeric bound (6 cycles, 90 min) needs a measuring test.
2. **WS2 — `work-discovery` skill + trigger de-drift + drift guard** (CAL-907). Extract the routine pick/discovery logic into a `work-discovery` skill the routine invokes; make the local scheduled tasks thin callers of the versioned routine; add a runbook for the operational sync; add a guard/test that fails if a trigger inlines logic instead of calling the versioned surface.
3. **WS3 — Make the harness's own loop cloud-runnable + record the per-repo gate rule** (CAL-908; *blocked by WS1 + WS2*). Wire the Build/Quality loops to a cloud schedule: credentials as secrets (`LINEAR_API_KEY`, Claude token / API key, push creds), select the Claude review engine, confirm a clean-clone run against the Linear-keyed reclamation. Document — in a `specs/decisions/` ADR + `CONTEXT.md` — that the harness's own loop runs in the cloud, and that cloud-viability is per-target-repo (a target whose gate needs Xcode/macOS tooling stays local or on macOS runners). **Sequenced last:** WS1 (the breakers) is a *hard* prerequisite — no unbounded loop runs unattended in the cloud — and WS2 should land first too, so what gets cloud-deployed is the de-drifted, skill-based loop rather than a mid-refactor one. WS1 ∥ WS2 (independent of each other).

## Risks / unknowns

- **The wall-clock budget can false-positive.** A run legitimately longer than the budget trips the breaker — the same hazard `stale-run-reclamation` faced at the same threshold, which is why the two are deliberately aligned. **Amended by #260:** "keep them in step, if one moves move both" is no longer a rule anyone has to obey. The two are now one value — `loop.wall_clock_budget_minutes`, read by the breaker and by `reclaim --stale` alike — so they cannot move independently, and the alignment is structural rather than remembered. The threshold was retuned 90 → 110 min at the same time. Tighten or loosen it on observed false positives, in the one place.
- **The breakers protect the *next* run, not the in-flight session.** Ledger-backed caps are checked at verb boundaries; a session that runs away *between* verbs is bounded by the wall-clock check at the next boundary, not interrupted mid-thought. This is the honest limit of A1 and the reason A2 (true metering) is the eventual want.
- **WS2's real fix is partly outside the repo.** The scheduled-task files are user-local; the repo can ship the versioned routine + a drift guard, but the actual re-sync is an operational step that has to be done (and stay done) on the operator's machine.
- **A cloud loop reviews via Claude, not Codex.** Codex subscription auth (`~/.codex`) doesn't travel as a cloud secret, so a cloud loop uses the Claude review engine. That is already the in-container reality (Codex is bwrap-blocked there), but it means the cloud loop loses the model-*family* diversity of a Codex reviewer — worth flagging against the generator/evaluator point, even if acceptable.
- **The per-target-repo constraint must be documented loudly.** "The harness runs its own loop in the cloud" must not be mistaken for "the harness runs any repo in the cloud." An Xcode-bound target's gate is Mac-only. The decision record has to state this so a future cloud rollout to a self-hosting iOS repo does not silently assume Linux.
