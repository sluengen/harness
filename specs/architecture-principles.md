# Architecture Principles

How this system is built — the technical principles that govern design *here*. They extend the universal `engineering-principles` with this repo's specifics, and they are where **cross-cutting decisions** are recorded (`spec-authoring`, `architecture`). A **reference spec**: update it when the architecture changes.

> Distinct from product principles (what we build and why). These define *how* we build it.

## Principles

### What this repo is

**The harness is a set of deterministic gates plus the guidance and hooks that route an agent through them — it runs nothing of its own.** ADR 0015 retired the runtime: there is no verb, no ledger, no container, no CLI. What remains executes only when a person or an agent asks for it — `scripts/verify.sh` and the drift guards it calls, `scripts/mutate.py`, and the agent-host hooks. Everything else this repo publishes is prose an agent reads. *Derived from: `engineering-principles` (do the simplest thing that works) and [ADR 0015](decisions/0015-harness-v4-thin-verification-layer.md).*

### Enforcement is a gate a change must pass, not a process it must follow

**Every invariant this repo enforces is expressed as something that fails `bash scripts/verify.sh`.** A rule that lives only in prose is advice; a rule with a test is a bound. This is why the guidance surface carries so many tree-reading guards — a version stamp, a mirror's byte-identity, a registry entry's resolution — each is an invariant that would otherwise depend on an agent remembering it. The corollary bites hardest on deletions: a guard whose subject is removed must be removed with it, because a sweep over an empty set passes and reports a property nothing holds. *Derived from: `code-quality` Part C (no completion claim without fresh evidence) and product requirement — nothing merges unverified.*

### Self-enforcing guardrails

**A deterministic guardrail must self-enforce its invariant, never assume the calling agent established the precondition.** An invariant the caller can violate by accident is not enforced. A step that depends on a precondition checks it itself and refuses on violation — it does not auto-correct the tree into compliance, and it does not trust an upstream step to have held the line. The worked example is `scripts/promotion-step.sh`: it asserts every required environment input *before* any mutation, and it never pushes on a red gate or a non-fast-forward, rather than trusting the workflow that invoked it to have checked either. Trusting the caller leaves the invariant to chance; repairing the tree into compliance hides the violation instead of surfacing it. *Derived from: CODE-INSIGHT-2 (evidence CODE-1 / CAL-586) and the Enforcement principle above — a gate's correctness depends on the state it binds to being exactly the state it checked.*

### CI logic lives in a script, not in a `run:` block

**A workflow step carrying logic is extracted to `scripts/`; the workflow calls it and nothing more.** A `run:` block is unreachable by the test suite, so the only instrument left for asserting anything about it is reading its text — and a text guard over shell is a proxy that degrades in one direction: it can be defeated by a spelling it does not know, and it constrains the file to the spellings it does. The nightly promotion guard is the worked example. It took four tickets (#390, #391, #393, #394), each teaching its regex one more way shell writes the same call, and it went **red** on the single-source refactor that would have made a wrong `--repo` unrepresentable — so the instrument required the workflow to keep repeating the literal at three call sites, which is the repetition it existed to police. A guard that forbids its own fix is the signal the instrument is wrong, not the pattern inside it.

Extraction makes the logic ordinary shell that a test can execute against stubbed binaries, so the assertion moves from *what the file says* to *what the invocation does* — which is the property that was always meant. `bash scripts/verify.sh` in `ci.yml`, and `bash scripts/promotion-step.sh` in the nightly promotion, are the existing shape. The rule does not reach steps that carry no logic: `actions/checkout`, a single `uv sync`, or a one-line invocation stays inline, because there is nothing there for a test to hold. *Derived from: proposal `promotion-guard-instrument` (2026-08-11), and the Self-enforcing guardrails principle above — a guard that cannot execute the thing it guards is assuming what it should be checking.*

### App vs. installed surface

**One repo holds two things that must never bleed into each other: the harness *app*, and the *surface* it installs into other repos.** After the guidance merge the boundary is a convention inside a single tree rather than a repo wall, so it is recorded here to stay enforceable.

- **App** — `scripts/ specs/ tests/`. This is the harness itself: its build/verify scripts, its design specs, its test suite. The app **never** installs into a target repo. (`harness/ docker/ bin/` were on this side until #435 deleted them.)
- **Surface** — *exactly* the `files:` membership of `registry.yaml`: `commands/ skills/ agents/ templates/ hooks/ process/ settings/`, plus the artifacts the installer derives in the target tree (`AGENTS.md` / `CLAUDE.md` / `GEMINI.md` and `.claude/settings.json`). Nothing is surface unless `registry.yaml` lists it.
- **Discriminator** — *must it be in the target repo's tree for that repo's local tooling to find or run it?* Yes → surface; no → app. **Default to the app**: a file is surface only when it earns its way onto the registry.
- **The four trees the two enumerations do not name are all app**, by that default and on their own merits: `design/` is this repo's own design-system source (the surface distributes the *contract*, `templates/design-system.md`, never a vendored tree); `docs/` is the derived landing page built from it; `assessments/` is advisory records of steward passes; and `.codex/` is a generated artifact tree rebuilt by `templates/generate_codex_artifacts.py` and never hand-edited. None appears in `registry.yaml`'s `files:` block, which is what settles it — a consuming repo needs none of them to run the process.

One boundary case the enumeration must keep straight: `scripts/` is **app** today (`scripts/verify.sh` is the app's own gate), not surface. The app has zero coupling to the surface, and the footprint test (CAL-648) mechanically holds that line by asserting `registry.yaml`'s `files:` excludes every app path — `commands/` is itself a surface directory, so a `commands/` entry is always legitimate.

The boundary survived the teardown intact, which is the useful thing to notice about it: #435 deleted an entire side of the app (`harness/`, `docker/`, `bin/`) without a single surface unit needing to change shape, because nothing on the surface ever reached into the app. A boundary that costs nothing to hold and saves a whole class of entanglement is the one to keep. *Derived from: the "Merge the guidance repo into the harness" decision below (D1/D2/D5) and `specs/proposals/merge-guidance-into-harness.md` breakdown item 2.*

### Surface is a versioned interface

**The installed surface is a versioned interface, governed by semver on the `guidance:<id>@x.y.z` header — a consuming repo never sees an unannounced breaking change.** Each installed unit carries that per-unit version; the bump level *is* the compatibility promise, and there is no separate interface-registry file — the header plus `registry.yaml` are the record.

- **Patch** — wording only, no behaviour change.
- **Minor** — an *implementation swap*: the body changes (e.g. a command becomes a thin client over the harness app) but invocation, output, and refusal reasons are unchanged. Auto-pulls. **The stopgap→app migration is a minor bump by definition** — that is the whole point of holding the surface stable while the implementation moves underneath it.
- **Major** — an *interface change*: a command renamed, or an argument, output schema, or refusal reason changed. Surfaces to the consuming repo as a **decision**, never an auto-pull.

The contract this governs is a command's **name, its arguments, and the shape of what it obliges the reader to do**. Until #435 it also covered a second contract — the JSON an agent read back from the app's verbs, locked by a golden snapshot against the emitted payload — and that half was retired with the app that emitted it (ADR 0015). What is left is prose, so the discipline is the header: a rename or an argument change is major and reaches the consumer as a decision, a reworded body is patch, and the `guidance:<id>@x.y.z` stamp plus `registry.yaml` are the whole record. *Derived from: the "Merge the guidance repo into the harness" decision below (D3/D5) and `specs/proposals/merge-guidance-into-harness.md` breakdown item 4.*

### Assessment layering

**A periodic assessment is one process applied to many domains: the command names the *scope*, the agent is the *process*, and the domain standards are *skills pulled just-in-time*.** There is a **single steward** agent (`steward`), not one per domain. `/assess <scope>` (optionally `--deep`) selects the *what*; the steward runs the same methodology (`assessment-craft` — the finding bar, severity, the insight test) for every scope and pulls only the *domain-standard* skills that scope needs: `code-quality`, `test-driven-development`, `architecture`, `engineering-principles`, and `design-system` when its layer is on. This is the same discipline the lifecycle follows — a repeatable job is expressed *once* as a process, parameterised, never copied into a second file that can drift. The prior split into two steward agents put the *identical* process in two files and differed only by domain standards, which is exactly the MECE duplication an assessment exists to flag. *Derived from: `engineering-principles` (DRY / one source per piece of knowledge) and `specs/proposals/pre-launch-consolidation.md` workstream B.*

### A task is command + role + skill + template — there is no `tasks/` artifact

**A unit of repeatable work decomposes into four durable artifacts plus one instance: the *command* (the trigger + scope), the *agent role* (who runs it + which skills it pulls), the *skill* (the *how* — the method), and the *template* (the output format); the specific instance lives in the tracker the repo configures — whichever backend `CONTEXT.md`'s `tracker:` field names — not in a file.** There is no standalone `tasks/` artifact — a "task file" is always one of those four in disguise, so keeping it as a fifth thing duplicates one of them and drifts out of step. This generalises "Assessment layering" above: the steward task *is* `/assess` (command) + `steward` (role) + `assessment-craft` (skill) + `templates/assessment.md` (template), and a single pass is a tracker issue, not a checked-in `steward-<domain>-<date>.md`. The retired `agents/tasks/` directory held exactly this anti-pattern: `agents/tasks/steward.md` re-encoded the steward procedure (a *skill* + *role* concern) and its report shape (a *template*), and `agents/tasks/release.md` re-encoded a release procedure that belonged in the repo's own release doc — both un-versioned, outside `registry.yaml`, and free to dangle. Eliminating the layer removes the dangling-reference + stale-procedure class at its root. *Derived from: "Assessment layering" above + `engineering-principles` (one source per piece of knowledge); `assessments/2026-06-15-system-and-code.md` SYSTEM-3 / SYSTEM-INSIGHT-3 (CAL-716).*

The two Decision blocks at the end of this section predate the ADR set and stay where they are — they are decisions about the guidance system itself, not the architecture invariants the ADRs hold.

### Decision: Invert the orchestration boundary — harness becomes verbs, the agent orchestrates

*Decided 2026-06-09. **Superseded 2026-08-15** by [ADR 0015](decisions/0015-harness-v4-thin-verification-layer.md), which retires the verbs, the ledger and the gate this decision built. Kept as the record of what was decided and why; nothing below describes current behaviour.*

**Context.** The original design (`SPEC.md` §1–2, `specs/retired/hermes-control-model.md`) made the **harness the orchestrator**: a deterministic mega-workflow (`build.yaml`) owned the entire build loop — fetch ticket → In Progress → worktree → implement → review → loop → merge → close — and spawned its own `ClaudeAgent` / `CodexAgent` subprocesses to do the implementing and reviewing. An external agent only launched a run and polled it. In practice this produced four recurring costs: brittle hand-encoded git/Linear `script` nodes that fail the whole run with no agent in the loop to adapt; lost context (the implementing agent is a fresh subprocess, not the one that understood the ticket); all-or-nothing failure; and a whole second runtime (the Hermes supervisor + async bridge) that had to be built before the deterministic model even worked unattended. The harness is, today, a tool a developer reaches for interactively — a setting where reproducibility of the *journey* is worth little, yet all four costs are paid every run.

**Decision.** Adopt **Option C** of proposal [`harness-as-tool`](proposals/harness-as-tool.md). One Claude session orchestrates **and** implements; the harness is reduced to three deterministic, audited verbs — `start`, `review`, `close` (ADR 0007 later added a fourth, `design`) — over the existing SQLite ledger, with enforcement as a **gate inside `close`** (HEAD-bound passing review; decision D2). The deterministic workflow engine is retired (D1). There was **one execution model** (an agent using the harness as a tool) with **two triggers**: a human (`/harness run <ticket>`) or Hermes occupying the trigger slot a human would (D3) — both producing the identical execution path.

**Alternatives.**
- *Option A — status quo (harness orchestrates the whole build; a supervisor drives it)* — maximal determinism and an un-skippable in-run gate, but pays all four costs above and requires building the unbuilt supervisor runtime + async bridge for a headless mode we do not run.
- *Option B — pure agent orchestration, no harness in the loop (today's actual practice)* — maximal flexibility and full context, but no audit trail and nothing enforces the review gate; the agent can skip codex and merge.
- *Option D — coroutine handshake (harness stays top-level, hands control to the interactive agent mid-run and takes it back)* — the literal "best of both worlds" sketch and the hardest to build: two orchestrators passing a baton across the host↔container boundary, reintroducing the brittle machinery, with handshake faults the agent cannot rescue. Right division of labour, wrong shape — Option C delivers it by collapsing the two orchestrators into one and turning "hand back" into "a function returns."

**Consequences.** Keeps full context (the orchestrator is the implementer); removes mechanical toil from the agent's hands without losing the audit trail; degrades gracefully (a verb failure drops to Option-B manual driving). Gives up end-to-end reproducibility — SPEC principles #2/#4 now apply to the verbs, not the journey (own this; it is acceptable because we are not running deterministic autonomy). Softens enforcement from "cannot skip" to "caught at the gate"; the gate's correctness therefore hinges on `review` and `close` binding to the **same** SHA (D2) — if they do not, the gate is theatre. Requires retiring the engine, which also removes `release.yaml`/`steward.yaml` (never run; both convert cleanly to verb-shaped agent tasks). Audit completeness depends on routing discipline (D5): a hand-rolled commit or Linear mutation leaves a hole in the ledger. Hermes' separate-runtime + async-bridge design is superseded (D3); the remaining integration is a thin launch handle (follow-up CAL-576) plus a host-side launcher that exposes the verb operations without the docker socket (CAL-579).

**Supersedes.** The harness-as-orchestrator framing in `SPEC.md` §1–2 (reconciled to the verb model, CAL-575) and the control half of `specs/retired/hermes-control-model.md` (dated supersede note, CAL-575).

### Decision: Merge the guidance repo into the harness — one source, app/surface boundary, branch-based distribution

*Decided 2026-06-13.*

**Context.** The harness was a *consumer* of a separate shared-guidance ("agents") repo: it carried installed copies of the universal commands/skills and a `.guidance-lock.yaml` pinning `source: agents`, while the agents repo held `registry.yaml` (the copy-list, serving a `standard` and a `harness` profile) and the installer. Cross-cutting changes — a harness change needing a guidance/doc change, or distributing the harness's own `/harness run` command (since retired) through a channel it did not own (CAL-624) — could not be made atomic. The product-agnostic, many-consumers premise that justified the split is speculative: there is one consumer (the author), and the guidance is a stopgap the harness is meant to absorb. Two repos institutionalised a separation the roadmap intends to erase.

**Decision.** Adopt **Option C** of proposal [`merge-guidance-into-harness`](proposals/merge-guidance-into-harness.md): collapse the two into one source tree by **promoting the harness to be the guidance source**, with a durable boundary between the harness **app** (`harness/ scripts/ specs/ tests/` — never installed into a target repo) and the installed **surface** (`commands/ skills/ agents/ templates/ hooks/ process/ settings/` + derived `AGENTS.md`/`CLAUDE.md`/`GEMINI.md` — installed via `registry.yaml`). The sub-decisions: **D1** harness becomes the source; **D2** surface at root with skills in the Agent Skills `skills/<id>/SKILL.md` shape (the source's shape; the harness's flattened copies migrate to it — flattening breaks the `SKILL.md` refs in `dev.md`/`start.md`, CAL-654), `registry.yaml` is the copy-list, no `surface/` tree (it would break the `.claude/` discovery symlinks); **D3** the surface is a *versioned interface* — the `guidance:<id>@x.y.z` header is the per-unit version, semver-governed (minor = invisible implementation swap, major = interface change), with a test locking the verb JSON / refusal-reason contract; **D4** clean copy-in; **D5** the harness owns `registry.yaml` + the installer and is **source-only** (drops its own `.guidance-lock.yaml`; the app's release tag is a separate version line walled off by a footprint test); **D6** all guidance comes home (both profiles) and the agents repo is **retired**; **D7** distribution is branch-based and pulled from GitHub — the harness authors and dogfoods on `dev`, external repos pull `main`, and `/update-guidance` + bootstrap fetch the harness repo at a branch ref (`source: { repo, branch, ref }`).

**Alternatives.**
- *Option A — stay split (agents source + harness consumer)* — preserves a product-agnostic source in principle, but pays the cross-cutting tax every change and maintains a separation the roadmap removes. Inferior with one consumer.
- *Option B — fully fuse, no internal boundary* — discards the working `registry.yaml` ↔ `.guidance-lock.yaml` + source/consumer freshness-hook mechanism to save a boundary that costs almost nothing to keep. Destructive of working infrastructure.
- *Option D — keep two repos + cross-repo sync tooling* — lipstick; straddling changes still are not atomic.

**Consequences.** Cross-cutting changes become one PR / one review / one atomic commit. The boundary is preserved structurally — the app has **zero coupling** to the surface (verified), and a **footprint test** asserts `registry.yaml`'s `files:` excludes every app path, eliminating (not merely mitigating) version entanglement. The harness's own role changes from consumer to source: it runs the freshness hook in SOURCE mode and carries no lock. Target-repo install footprint is unchanged (the channel, not the repo count, gates it). New coupling to own: branch-based release ties guidance to the app's `dev → main` cadence — a guidance-only hotfix cannot ship independently of an app release. **Coupling resolved (CAL-653, 2026-06-14): accept it.** The harness authors and dogfoods the surface on `dev` (the canary); the `dev → main` promotion *is* the guidance release; external repos pull `main`, never in-flight `dev`. `/update-guidance` + the installer fetch the GitHub repo (`github.com/sluengen/harness`) at the branch recorded in the consumer lock's `source: { repo, branch, ref }`. **No** independent tag-based promotion path is built now — it is premature (real tag-cut + ref-resolution machinery before any evidence it is needed; the harness gates app *and* guidance through the same canary, and app releases here are cheap). **Escape hatch (recorded, not built):** if a guidance-only hotfix is ever blocked by risky in-flight app work on `dev`, introduce a guidance release tag then. The agents repo is retired (CAL-652). Spawned as **CAL-646 … CAL-653**.

**Supersedes.** The "guidance stays in a separate product-agnostic repo" framing in `CLAUDE.md` and `CONTEXT.md` (reconciled to the one-repo source model, CAL-651). CAL-624 (distribute `/harness run` via the agents-repo channel) was subsumed (CAL-650); the command itself was later deleted (ADR 0015).

**Refinement (2026-06-13) — one profile; the branch carries what D6's profiles did.** D6/D7 evolve. The `standard` vs `harness` **profile** split is retired: there is **one** surface, and the harness is the source of truth for all of it. The distinction *what the harness itself uses* vs *what every other repo pulls* is carried by the **branch**, not a `profiles:` flag — **`dev`** is the Harness (the latest, unstable surface the harness dogfoods); **`main`** is what other repos pull (today's "standard" flavor). Where a unit genuinely differed for the harness's own use — e.g. the harness *sourced* the canonical `/build` while driving its own work with `/harness run`, since **retired** (CAL-657) — the steer lived in **guidance** (`process/harness.md`), not a profile flag. That divergence is gone: ADR 0015 deleted the repo's own command namespace, so every repo now drives work the same way. This re-frames item 7 (CAL-652) as *complete and stabilise the single surface and retire the agents repo* (not "bring a second profile home"), and makes item 8 (CAL-653)'s `dev → main` promotion the distribution mechanism the profile split used to be. *Native-discovery note (CAL-654): skills keep the Agent-Skills `skills/<id>/SKILL.md` shape (D2) and the `.claude/skills -> ../skills` symlink makes them discoverable — verified empirically, since the harness already discovers its `commands/*.md` through the analogous `.claude/commands` symlink; flattening to `skills/<id>.md` is what broke discovery.* **Resolved (2026-06-13) — maturity-only.** `dev` and `main` carry the **same** surface content; they differ only by **release maturity** (`dev` = latest/unstable, `main` = released/stable). There is **no** per-branch content fork. The standard/harness profile split was never really about repo *type* — it existed because the harness dogfooded a tool (`/harness run` + the harness app) that other repos did not yet have; once the harness app is universal every repo has the same tools and guidance, so the two "flavors" collapse into one shared surface. Repo-type variation the old profiles encoded (`feature_specs` on/off, the design-system layer) is **per-repo configuration** (`CONTEXT.md` `layers:`), not a profile. **Transitional gap (closed 2026-08-15).** Full content-identity was blocked while the harness drove its own tickets through a command no other repo could run. ADR 0015 closed it from the other end: rather than making that command universal, the teardown deleted it, so `process/harness.md` is now the single process doc and every repo — this one included — drives work the same way. The target was **one profile, one surface, branches differ only by maturity**, and it is reached.
