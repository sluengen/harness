# Architecture Principles

How this system is built — the technical principles that govern design *here*. They extend the universal `engineering` skill with this repo's specifics, and they are where **cross-cutting decisions** are recorded (`authoring`, `architecture`). A **reference spec**: update it when the architecture changes.

> Distinct from product principles (what we build and why). These define *how* we build it.

## Principles

### What this repo is

**The harness is a set of deterministic gates plus the guidance and hooks that route an agent through them — it runs nothing of its own.** ADR 0015 retired the runtime: there is no verb, no ledger, no container, no CLI. What remains executes only when a person or an agent asks for it — `scripts/verify.sh` and the drift guards it calls, `scripts/mutate.py`, and the agent-host hooks. Everything else this repo publishes is prose an agent reads. *Derived from: `engineering` (do the simplest thing that works) and [ADR 0015](decisions/0015-harness-v4-thin-verification-layer.md).*

### Evidence follows the subject it protects

**[ADR 0019](decisions/0019-purpose-before-proof.md) is the sole evidence matrix.** This architecture keeps drift and generator checks only where they prove artifact integrity, not prose meaning. Changes challenge a wrong criterion through an owner-approved tracker amendment before implementation; they never descope silently. *Derived from: [ADR 0019](decisions/0019-purpose-before-proof.md).*

### Enforcement is a gate a change must pass, not a process it must follow

**Executable and mechanically decidable invariants fail the gate.** This is why the guidance surface carries tree-reading checks for a version stamp, mirror byte-identity, and registry resolution: each proves an artifact contract rather than a prose claim. The corollary bites hardest on deletions: remove a guard whose subject is gone, because a sweep over an empty set reports a property nothing holds. *Derived from: `engineering` (no completion claim without fresh gate evidence) and product requirement — nothing merges unverified.*

### Self-enforcing guardrails

**A deterministic guardrail must self-enforce its invariant, never assume the calling agent established the precondition.** An invariant the caller can violate by accident is not enforced. A step that depends on a precondition checks it itself and refuses on violation — it does not auto-correct the tree into compliance, and it does not trust an upstream step to have held the line. The worked example is `scripts/promotion-step.sh`: it asserts every required environment input *before* any mutation, and it merges nothing on a red gate, on a target carrying content the candidate's history does not, on a source branch that moved past the gated commit, or on a required check that failed or never completed — rather than trusting the workflow that invoked it to have checked any of them. Trusting the caller leaves the invariant to chance; repairing the tree into compliance hides the violation instead of surfacing it. *Derived from: CODE-INSIGHT-2 (evidence CODE-1 / CAL-586) and the Enforcement principle above — a gate's correctness depends on the state it binds to being exactly the state it checked.*

### CI logic lives in a script, not in a `run:` block

**A workflow step carrying logic is extracted to `scripts/`; the workflow calls it and nothing more.** A `run:` block is unreachable by the test suite, so the only instrument left for asserting anything about it is reading its text — and a text guard over shell is a proxy that degrades in one direction: it can be defeated by a spelling it does not know, and it constrains the file to the spellings it does. The nightly promotion guard is the worked example. It took four tickets (#390, #391, #393, #394), each teaching its regex one more way shell writes the same call, and it went **red** on the single-source refactor that would have made a wrong `--repo` unrepresentable — so the instrument required the workflow to keep repeating the literal at three call sites, which is the repetition it existed to police. A guard that forbids its own fix is the signal the instrument is wrong, not the pattern inside it.

Extraction makes the logic ordinary shell that a test can execute against stubbed binaries, so the assertion moves from *what the file says* to *what the invocation does* — which is the property that was always meant. `bash scripts/verify.sh` in `ci.yml`, and `bash scripts/promotion-step.sh` in the nightly promotion, are the existing shape. The rule does not reach steps that carry no logic: `actions/checkout`, a single `uv sync`, or a one-line invocation stays inline, because there is nothing there for a test to hold. *Derived from: proposal `promotion-guard-instrument` (2026-08-11), and the Self-enforcing guardrails principle above — a guard that cannot execute the thing it guards is assuming what it should be checking.*

### Installed surface vs. the source's own

**One repo holds two things that must never bleed into each other: the *surface* the plugin installs into other repos' sessions, and the *source's own* machinery.** Since ADR 0017 the boundary is the plugin, not a copy-list: `registry.yaml` and the installer are gone.

- **Surface** — what the plugin manifests carry into a consuming session: `agents/`, `skills/` (with their reference assets, and the nine lifecycle workflows among them, each shipping once), `hooks/`, `settings/`, and `templates/` (the output shapes the skills and `/harness:hydrate` instantiate — skill assets, not standalone units).
- **Source-only** — the remainder: `scripts/` (the gate and its instruments), `tests/` (the guards), `specs/`, `docs/` (the landing page), `assessments/`, and the Codex adapters under `.codex/` — authored since #537 retired the generator, and held in correspondence with `agents/*.md` by `tests/unit/test_codex_agent_adapters.py`. A consuming repo needs none of them; nothing in the surface reaches into them.
- **Discriminator** — *does an installed plugin put it in front of a consuming repo's agent?* Yes → surface; no → source-only.

  **The design system crossed that line at #626**, and it is the first unit to do so in the direction of the surface. Its eight tiers, token source and token builder were a source-only `design/` tree; they are now `skills/design-system/assets/`, which `/harness:hydrate` step 11 copies into a consumer's `paths.design_system`. This repo did not keep a second copy behind — it consumes the shipped assets in place, which is why its own `paths.design_system` points inside `skills/`. A tree serving both roles is the shape to watch: it is legitimate where the consumer *owns* the copy from the moment it lands (ADR 0022 point 1), and would not be where the plugin kept refreshing it. **Default to source-only**: the surface grows only by deliberately shipping a unit.

The boundary earned its keep twice — #435 deleted the runtime and v5 deleted the package manager, and neither teardown forced a single surface unit to change shape, because nothing in the surface ever reached back into the source's machinery. *Derived from: [ADR 0017](decisions/0017-harness-v5-plugin-shaped-guidance.md) (D1, D4) and the "Merge the guidance repo into the harness" decision below, whose app/surface split this supersedes in mechanism.*

### Surface is a versioned interface

*Superseded in mechanism 2026-08-18 by [ADR 0017](decisions/0017-harness-v5-plugin-shaped-guidance.md): per-file `guidance:` headers and `registry.yaml` are deleted; the surface carries **one** semver, the plugin's, bumped at release. The compatibility grammar below — patch = wording, minor = implementation swap, major = interface change — still governs what a bump means; it just applies to the plugin as a whole. Kept for that grammar and the audit.*

*Amended 2026-09-06 (#556): the note above says the one semver is "bumped at release". It is not, and in this repo it cannot be. The automated release hop has no authoring step — `scripts/promotion-step.sh` opens a pull request whose head is the integration branch itself and pushes nothing new — and a bump written onto the release branch by hand leaves that script's content-divergence pre-condition non-empty from that night on, wedging every later nightly until somebody performs the back-merge `specs/infrastructure.md` records this repo as deliberately not doing. The version is raised **at the start of the release cycle, on the integration branch**: the first change to land after a release raises it above the release branch's, and every later change in that cycle leaves it alone. The occurrence: the release merged on 2026-09-05 (`a609d5b`) carried both manifests at `6.0.1`, and `7.0.0` was written onto the integration branch the next day, so a consumer updating in between was told it was already current over bytes that had changed. Only the **moment** moves. The **level** is still governed by the compatibility grammar below, which this amendment leaves unchanged, and the surface still carries one semver. This does not re-open the colliding monotonic append point [ADR 0017](decisions/0017-harness-v5-plugin-shaped-guidance.md) retired with the per-file headers (#461): that scheme derived the next value from whatever the branch said at the time, so two concurrent worktrees produced one number over two different predecessors and the number meant two things; this one derives it from the release branch, which is fixed for the whole cycle, so two worktrees produce one number over the same predecessor and their agreement is the correct outcome rather than a collision. `tests/unit/test_release_version_cycle.py` fails the gate when the integration branch's content differs from the release branch's and its version does not.*

*Superseded 2026-09-07 (#588), and the replacement is an open question rather than a mechanism.* The obligation above is retired and `tests/unit/test_release_version_cycle.py` is deleted with it. Over one cycle that guard failed the nightly promotion it was written to protect, and on every `push: dev` before that it reported `NO_RELEASE_REF` and skipped — 713 lines enforcing an obligation that went unenforced exactly where it mattered (P0: a mechanism added where a number would do). #588 intended to give the bump to `scripts/promotion-step.sh` at the hop, and that implementation was built and then removed at review: the hop's commit slot has to be created by writing a ref, a commit written with `GITHUB_TOKEN` raises no workflow run, and the bumped head would therefore carry no required check and wedge the promotion permanently. So the bump has **no automated owner**; it is a hand step at a release, until the note below gives it one. Only the **moment** and its **owner** are in question; the **level** is still the compatibility grammar below, unchanged by any of this.*

*Amended 2026-09-07 (#589) — the bump has an owner, and its floor is minor.* `/build` raises the version at step 1, in the new worktree, before the first edit of the change it is about to build, by running `scripts/plugin-version.js`. It raises the minor and zeroes the patch when the integration branch's manifest still carries the release branch's version, writes nothing when the cycle has already moved it, and **refuses rather than skipping** when the declared release ref cannot be resolved — the silent `NO_RELEASE_REF` skip is the failure the paragraph above measures, and this design refuses it by construction. The raise lands inside the ticket's own certified tree, so law 3 covers it and no second commit follows the verdict; that is why the landing script is the wrong home despite being the obvious one. The credential question is not answered but **superseded**: a builder pushes with ordinary credentials, so `ci.yml`'s `push: dev` trigger fires and the required check exists, and the hop authors nothing. **The floor is minor, not patch.** The grammar below defines patch as "wording only, no behaviour change", and that definition predates [ADR 0015](decisions/0015-harness-v4-thin-verification-layer.md): when the harness still had a runtime, a reworded skill body changed nothing a consumer executed. The runtime is retired and the shipped product *is* prose, so a reworded skill body **is** a behaviour change and patch is very nearly vacuous — whether it retains any meaning at all is #590, deliberately left open here. Minor is therefore the honest floor for any cycle that ships anything, and the grammar's major clause still governs a raise above it: a renamed command, a changed argument, or a changed refusal reason surfaces to a consuming repo as a decision. A major raise is a hand edit to the version homes inside the candidate, before the certifying gate, and the review is where that class is judged (`skills/review-discipline/references/certifying.md`) — a script that guessed it would guess wrong at the one moment it matters. Two things this does not own: a cycle whose changes all ship through the **fix lane**, which runs no command and therefore raises nothing; and the release hop itself, whose credential constraint stands untouched, because the bump now happens before the hop rather than at it.*

*Amended 2026-09-08 (#590) — patch is retired, and the grammar carries two levels.* #589 left open whether the level keeps any meaning. It does not, on a narrower ground than emptiness. A level earns its place by the consumer action it names, and only major names one: a decision rather than an auto-pull. Patch and minor both leave the release to arrive on its own, so a consuming repo reading either does the identical thing, and patch subdivides the half nobody acts on. The inert class it was reached for is real — a comment inside a shipped hook cannot change what the hook does — and calling that change a patch rather than a minor still buys its consumer nothing. D3 in the *Merge the guidance repo into the harness* decision below, which this grammar derives from, named two levels; patch entered at the restatement above and never gained a consequence of its own.

Patch had inhabitants, and they are the argument, though fewer than a first count suggests and not the count this note first shipped with. Before #589 a cycle opened at a patch by default, and the record holds two opens, not three: `6.0.1` reached the release branch on 2026-09-05 (`a609d5b`) and shipped uncorrected — the same "told they were already current over bytes that had changed" failure `:50` records at that commit — and `7.0.1`, #565's declared open, was raised to `8.0.0` at review — the same open [ADR 0018](decisions/0018-gate-marker-convention-is-node.md)'s corrected amendment names again, not a third. One of the two opens was caught; one was not. Either way patch named nothing a consumer could act on. #589 answered the caught half with a minor floor. This amendment removes what the floor was defending against.

Three things it does not touch. The version keeps three components: `scripts/plugin-version.js` writes `X.Y.0` at a cycle-opening raise and a review-time major writes `X.0.0`, so the third position holds a zero rather than a level, and no manifest, marker or parity guard changes — retiring a level is not retiring a component. A reworded body lands on minor, whose condition it already meets, with invocation, output and refusal reasons unchanged, so the class patch used to name keeps a home. And the major clause stands as written: a renamed command, a changed argument, or a changed refusal reason reaches a consuming repo as a decision, which remains the only distinction a consumer acts on.

A change the installed surface never carries announces nothing of its own. `specs/` is source-only, so an edit here reaches no consuming repo, and the cycle's minor raise carries it because that raise is per cycle rather than per change. That is the case patch would otherwise have been reached for, and *no bump* is the honest answer to it rather than the smallest one.

Two alternatives rejected. **Narrowing patch to a provably inert class** fails twice over: the bright line is applied by judgment on every diff, which is process weight P0 refuses without a recorded reason, and both sides of the line auto-pull, so the judgment decides nothing. **Keeping the level as near-vacuous against a future architecture** is designing for a requirement nobody has (`engineering`: no speculation); an architecture that gives an inert change its own consumer consequence gets a grammar written for it, and this note plus git history are the record until then.

The dated notes above still name the retired level — the 2026-08-18 note's "patch = wording, minor = implementation swap, major = interface change", and #589's amendment naming patch three times over, down to leaving the question "deliberately left open here" for this one to close. Both stand as history, like every superseded note in this section. The closing paragraph below is live text, and it loses its "a reworded body is patch" clause.

**The installed surface is a versioned interface, governed by semver on the `guidance:<id>@x.y.z` header — a consuming repo never sees an unannounced breaking change.** Each installed unit carries that per-unit version; the bump level *is* the compatibility promise, and there is no separate interface-registry file — the header plus `registry.yaml` are the record.

- **Minor** — an *implementation swap*: the body changes (e.g. a command becomes a thin client over the harness app) but invocation, output, and refusal reasons are unchanged. Auto-pulls. **The stopgap→app migration is a minor bump by definition** — that is the whole point of holding the surface stable while the implementation moves underneath it.
- **Major** — an *interface change*: a command renamed, or an argument, output schema, or refusal reason changed. Surfaces to the consuming repo as a **decision**, never an auto-pull.

The contract this governs is a command's **name, its arguments, and the shape of what it obliges the reader to do**. Until #435 it also covered a second contract — the JSON an agent read back from the app's verbs, locked by a golden snapshot against the emitted payload — and that half was retired with the app that emitted it (ADR 0015). What is left is prose, so the discipline is the header: a rename or an argument change is major and reaches the consumer as a decision, and the `guidance:<id>@x.y.z` stamp plus `registry.yaml` are the whole record. *Derived from: the "Merge the guidance repo into the harness" decision below (D3/D5) and the `merge-guidance-into-harness` proposal's breakdown item 4 (settled; in git history).*

### Assessment layering

**A periodic assessment is one process applied to many domains: the command names the *scope*, the agent is the *process*, and the domain standards are *skills pulled just-in-time*.** There is a **single steward** agent (`steward`), not one per domain. `/assess <scope>` selects the *what*; the steward runs the same methodology (`skills/assess/references/finding-bar.md` — the finding bar, severity, the insight test) for every scope and pulls only the *domain-standard* skills that scope needs: `engineering`, `architecture`, `skills/assess/references/process-economy.md`, and the design layer's rule when it is on. Scope is the only parameter. This is the same discipline the lifecycle follows — a repeatable job is expressed *once* as a process, parameterised, never copied into a second file that can drift. The prior split into two steward agents put the *identical* process in two files and differed only by domain standards, which is exactly the MECE duplication an assessment exists to flag.

**A scope is admitted by its report contract, not by its subject.** A lens inside `code` already catches its defect *as a finding*, and that is sufficient for as long as the finding-engine contract fits: every finding is a ticket, and a clean pass files nothing. A new scope is earned only where that contract squeezes the answer out. `architecture` qualifies because the positive bets to preserve and the trade-offs worth keeping are not findings at all — they fall out at the every-finding-is-a-ticket bar, and a holistic verdict needs a different *report contract* rather than a different lens. `process` qualifies on the same test and no weaker one: its answer is mostly *delete this*, and a deletion candidate is an improvement rather than a place the tree contradicts itself, so filing each as a ticket would grow the backlog in order to shrink the suite. Three contracts, three scopes. A fourth scope needs a fourth contract; a subject that fits an existing contract is a lens inside it, and the one genuine exception — a codebase too large for a single run — is about size, not shape, and is handled per-repo in `skills/assess/SKILL.md`. *Derived from: `engineering` (DRY / one source per piece of knowledge) and the `pre-launch-consolidation` proposal's workstream B (settled; in git history).*

### A task is command + role + skill + template — there is no `tasks/` artifact

**A unit of repeatable work decomposes into four durable artifacts plus one instance: the *command* (the trigger + scope), the *agent role* (who runs it + which skills it pulls), the *skill* (the *how* — the method), and the *template* (the output format); the specific instance lives in the tracker the repo configures — whichever backend `harness.yaml`'s `tracker:` field names — not in a file.** There is no standalone `tasks/` artifact — a "task file" is always one of those four in disguise, so keeping it as a fifth thing duplicates one of them and drifts out of step. This generalises "Assessment layering" above: the steward task *is* `/assess` (command) + `steward` (role) + `skills/assess/references/finding-bar.md` (the standard) + `templates/assessment.md` (template), and a single pass is a tracker issue, not a checked-in `steward-<domain>-<date>.md`. The retired `agents/tasks/` directory held exactly this anti-pattern: `agents/tasks/steward.md` re-encoded the steward procedure (a *skill* + *role* concern) and its report shape (a *template*), and `agents/tasks/release.md` re-encoded a release procedure that belonged in the repo's own release doc — both un-versioned, outside `registry.yaml`, and free to dangle. Eliminating the layer removes the dangling-reference + stale-procedure class at its root. *Derived from: "Assessment layering" above + `engineering` (one source per piece of knowledge); the 2026-06-15 `system-and-code` pass, SYSTEM-3 / SYSTEM-INSIGHT-3 (CAL-716), folded into `assessments/LOG.md` by retention.*

### Decision: Invert the orchestration boundary — harness becomes verbs, the agent orchestrates

*Decided 2026-06-09. **Superseded 2026-08-15** by [ADR 0015](decisions/0015-harness-v4-thin-verification-layer.md), which retires the verbs, the ledger and the gate this decision built. Kept as the record of what was decided and why; nothing below describes current behaviour.*

**Context.** The original design (`SPEC.md` §1–2, and the retired `hermes-control-model` design, removed from the tree by #547 and kept in git history) made the **harness the orchestrator**: a deterministic mega-workflow (`build.yaml`) owned the entire build loop — fetch ticket → In Progress → worktree → implement → review → loop → merge → close — and spawned its own `ClaudeAgent` / `CodexAgent` subprocesses to do the implementing and reviewing. An external agent only launched a run and polled it. In practice this produced four recurring costs: brittle hand-encoded git/Linear `script` nodes that fail the whole run with no agent in the loop to adapt; lost context (the implementing agent is a fresh subprocess, not the one that understood the ticket); all-or-nothing failure; and a whole second runtime (the Hermes supervisor + async bridge) that had to be built before the deterministic model even worked unattended. The harness is, today, a tool a developer reaches for interactively — a setting where reproducibility of the *journey* is worth little, yet all four costs are paid every run.

**Decision.** Adopt **Option C** of the `harness-as-tool` proposal (settled; removed from the tree by #547, kept in git history). One Claude session orchestrates **and** implements; the harness is reduced to three deterministic, audited verbs — `start`, `review`, `close` (ADR 0007 later added a fourth, `design`) — over the existing SQLite ledger, with enforcement as a **gate inside `close`** (HEAD-bound passing review; decision D2). The deterministic workflow engine is retired (D1). There was **one execution model** (an agent using the harness as a tool) with **two triggers**: a human (`/harness run <ticket>`) or Hermes occupying the trigger slot a human would (D3) — both producing the identical execution path.

**Alternatives.**
- *Option A — status quo (harness orchestrates the whole build; a supervisor drives it)* — maximal determinism and an un-skippable in-run gate, but pays all four costs above and requires building the unbuilt supervisor runtime + async bridge for a headless mode we do not run.
- *Option B — pure agent orchestration, no harness in the loop (today's actual practice)* — maximal flexibility and full context, but no audit trail and nothing enforces the review gate; the agent can skip codex and merge.
- *Option D — coroutine handshake (harness stays top-level, hands control to the interactive agent mid-run and takes it back)* — the literal "best of both worlds" sketch and the hardest to build: two orchestrators passing a baton across the host↔container boundary, reintroducing the brittle machinery, with handshake faults the agent cannot rescue. Right division of labour, wrong shape — Option C delivers it by collapsing the two orchestrators into one and turning "hand back" into "a function returns."

**Consequences.** Keeps full context (the orchestrator is the implementer); removes mechanical toil from the agent's hands without losing the audit trail; degrades gracefully (a verb failure drops to Option-B manual driving). Gives up end-to-end reproducibility — SPEC principles #2/#4 now apply to the verbs, not the journey (own this; it is acceptable because we are not running deterministic autonomy). Softens enforcement from "cannot skip" to "caught at the gate"; the gate's correctness therefore hinges on `review` and `close` binding to the **same** SHA (D2) — if they do not, the gate is theatre. Requires retiring the engine, which also removes `release.yaml`/`steward.yaml` (never run; both convert cleanly to verb-shaped agent tasks). Audit completeness depends on routing discipline (D5): a hand-rolled commit or Linear mutation leaves a hole in the ledger. Hermes' separate-runtime + async-bridge design is superseded (D3); the remaining integration is a thin launch handle (follow-up CAL-576) plus a host-side launcher that exposes the verb operations without the docker socket (CAL-579).

**Supersedes.** The harness-as-orchestrator framing in `SPEC.md` §1–2 (reconciled to the verb model, CAL-575) and the control half of the retired `hermes-control-model` design (dated supersede note, CAL-575; in git history).

### Decision: Merge the guidance repo into the harness — one source, app/surface boundary, branch-based distribution

*Decided 2026-06-13.*

**Context.** The harness was a *consumer* of a separate shared-guidance ("agents") repo: it carried installed copies of the universal commands/skills and a `.guidance-lock.yaml` pinning `source: agents`, while the agents repo held `registry.yaml` (the copy-list, serving a `standard` and a `harness` profile) and the installer. Cross-cutting changes — a harness change needing a guidance/doc change, or distributing the harness's own `/harness run` command (since retired) through a channel it did not own (CAL-624) — could not be made atomic. The product-agnostic, many-consumers premise that justified the split is speculative: there is one consumer (the author), and the guidance is a stopgap the harness is meant to absorb. Two repos institutionalised a separation the roadmap intends to erase.

**Decision.** Adopt **Option C** of proposal `merge-guidance-into-harness` (settled; removed from the tree by #547, kept in git history): collapse the two into one source tree by **promoting the harness to be the guidance source**, with a durable boundary between the harness **app** (`harness/ scripts/ specs/ tests/` — never installed into a target repo) and the installed **surface** (`commands/ skills/ agents/ templates/ hooks/ process/ settings/` + derived `AGENTS.md`/`CLAUDE.md`/`GEMINI.md` — installed via `registry.yaml`). The sub-decisions: **D1** harness becomes the source; **D2** surface at root with skills in the Agent Skills `skills/<id>/SKILL.md` shape (the source's shape; the harness's flattened copies migrate to it — flattening breaks the `SKILL.md` refs in `dev.md`/`start.md`, CAL-654), `registry.yaml` is the copy-list, no `surface/` tree (it would break the `.claude/` discovery symlinks); **D3** the surface is a *versioned interface* — the `guidance:<id>@x.y.z` header is the per-unit version, semver-governed (minor = invisible implementation swap, major = interface change), with a test locking the verb JSON / refusal-reason contract; **D4** clean copy-in; **D5** the harness owns `registry.yaml` + the installer and is **source-only** (drops its own `.guidance-lock.yaml`; the app's release tag is a separate version line walled off by a footprint test); **D6** all guidance comes home (both profiles) and the agents repo is **retired**; **D7** distribution is branch-based and pulled from GitHub — the harness authors and dogfoods on `dev`, external repos pull `main`, and `/update-guidance` + bootstrap fetch the harness repo at a branch ref (`source: { repo, branch, ref }`).

**Alternatives.**
- *Option A — stay split (agents source + harness consumer)* — preserves a product-agnostic source in principle, but pays the cross-cutting tax every change and maintains a separation the roadmap removes. Inferior with one consumer.
- *Option B — fully fuse, no internal boundary* — discards the working `registry.yaml` ↔ `.guidance-lock.yaml` + source/consumer freshness-hook mechanism to save a boundary that costs almost nothing to keep. Destructive of working infrastructure.
- *Option D — keep two repos + cross-repo sync tooling* — lipstick; straddling changes still are not atomic.

**Consequences.** Cross-cutting changes become one PR / one review / one atomic commit. The boundary is preserved structurally — the app has **zero coupling** to the surface (verified), and a **footprint test** asserts `registry.yaml`'s `files:` excludes every app path, eliminating (not merely mitigating) version entanglement. The harness's own role changes from consumer to source: it runs the freshness hook in SOURCE mode and carries no lock. Target-repo install footprint is unchanged (the channel, not the repo count, gates it). New coupling to own: branch-based release ties guidance to the app's `dev → main` cadence — a guidance-only hotfix cannot ship independently of an app release. **Coupling resolved (CAL-653, 2026-06-14): accept it.** The harness authors and dogfoods the surface on `dev` (the canary); the `dev → main` promotion *is* the guidance release; external repos pull `main`, never in-flight `dev`. `/update-guidance` + the installer fetch the GitHub repo (`github.com/sluengen/harness`) at the branch recorded in the consumer lock's `source: { repo, branch, ref }`. **No** independent tag-based promotion path is built now — it is premature (real tag-cut + ref-resolution machinery before any evidence it is needed; the harness gates app *and* guidance through the same canary, and app releases here are cheap). **Escape hatch (recorded, not built):** if a guidance-only hotfix is ever blocked by risky in-flight app work on `dev`, introduce a guidance release tag then. The agents repo is retired (CAL-652). Spawned as **CAL-646 … CAL-653**.

**Supersedes.** The "guidance stays in a separate product-agnostic repo" framing in `CLAUDE.md` and `CONTEXT.md` (reconciled to the one-repo source model, CAL-651). CAL-624 (distribute `/harness run` via the agents-repo channel) was subsumed (CAL-650); the command itself was later deleted (ADR 0015).

**Refinement (2026-06-13) — one profile; the branch carries what D6's profiles did.** D6/D7 evolve. The `standard` vs `harness` **profile** split is retired: there is **one** surface, and the harness is the source of truth for all of it. The distinction *what the harness itself uses* vs *what every other repo pulls* is carried by the **branch**, not a `profiles:` flag — **`dev`** is the Harness (the latest, unstable surface the harness dogfoods); **`main`** is what other repos pull (today's "standard" flavor). Where a unit genuinely differed for the harness's own use — e.g. the harness *sourced* the canonical `/build` while driving its own work with `/harness run`, since **retired** (CAL-657) — the steer lived in **guidance** (`process/harness.md`), not a profile flag. That divergence is gone: ADR 0015 deleted the repo's own command namespace, so every repo now drives work the same way. This re-frames item 7 (CAL-652) as *complete and stabilise the single surface and retire the agents repo* (not "bring a second profile home"), and makes item 8 (CAL-653)'s `dev → main` promotion the distribution mechanism the profile split used to be. *Native-discovery note (CAL-654): skills keep the Agent-Skills `skills/<id>/SKILL.md` shape (D2) and the `.claude/skills -> ../skills` symlink makes them discoverable — verified empirically, since the harness already discovers its `commands/*.md` through the analogous `.claude/commands` symlink; flattening to `skills/<id>.md` is what broke discovery.* **Resolved (2026-06-13) — maturity-only.** `dev` and `main` carry the **same** surface content; they differ only by **release maturity** (`dev` = latest/unstable, `main` = released/stable). There is **no** per-branch content fork. The standard/harness profile split was never really about repo *type* — it existed because the harness dogfooded a tool (`/harness run` + the harness app) that other repos did not yet have; once the harness app is universal every repo has the same tools and guidance, so the two "flavors" collapse into one shared surface. Repo-type variation the old profiles encoded (`feature_specs` on/off, the design-system layer) is **per-repo configuration** (`CONTEXT.md` `layers:`), not a profile. **Transitional gap (closed 2026-08-15).** Full content-identity was blocked while the harness drove its own tickets through a command no other repo could run. ADR 0015 closed it from the other end: rather than making that command universal, the teardown deleted it, so `process/harness.md` is now the single process doc and every repo — this one included — drives work the same way. The target was **one profile, one surface, branches differ only by maturity**, and it is reached.



### Decision: One licence — everything is MIT

*Decided 2026-08-18.*

**Context.** The repo carried two licences split along the old app/surface boundary: the harness's own code — the gate, the mutation instrument, the guard suite — was AGPL-3.0-only (`LICENSE`), and the installed guidance was MIT (`GUIDANCE-MIT.md`), with the boundary held by `registry.yaml`'s copy-list and `tests/unit/test_license_boundary.py`. The AGPL side existed for the runtime: a network-servable app someone could operate as a service without sharing changes. ADR 0015 retired that runtime, and ADR 0017 deleted the licence-boundary machinery with the registry it read. What is left is guidance prose plus thin verification scripts — nothing a copyleft licence protects — while the dual arrangement still cost a boundary file, and its explanation in three prose files.

**Decision.** Everything is MIT. `LICENSE` becomes the standard MIT text, `GUIDANCE-MIT.md` is deleted, and `README.md` / `CONTRIBUTING.md` / `pyproject.toml` state the single licence. The operator's words: "we can just do everything as MIT. There's no real machinery to dual licence."

**Alternatives.**
- *Keep the dual arrangement* — protects nothing since the runtime's retirement, and its enforcement machinery was deleted with `registry.yaml`; a boundary no guard holds is drift waiting to happen.
- *All-AGPL* — would encumber the guidance the plugin carries into consumers' repos, including closed ones — the opposite of the surface's purpose.

**Consequences.** One licence file; GitHub's detector resolves the repo to MIT. Consumers may use everything, scripts included, without copyleft concerns. `CONTRIBUTING.md`'s relicensing grant — kept to preserve the option of moving off the AGPL — loses its original motive; inbound contributions arrive MIT like the rest.

### Decision: The gate's toolchain preflight probes what the suite resolves off `PATH`

*Decided 2026-08-19.*

**Context.** `scripts/verify.sh`'s preflight refuses with the reserved exit 97 — *the gate could not run*, distinct from a red tree — when a tool it needs is unrunnable. Its probe set was remembered rather than derived: `ruff`, `mypy`, `pytest`, `pytest-xdist`, and `node` added by hand at #478 after a live breakage (homebrew moved `simdjson` to soname 33 while `node` stayed linked against 29, and the resulting red read as a defect in a tree nobody had touched). Nothing related the list to the suite, so it could only drift one way: a test admits a host dependency, the preflight never hears of it, and the gate goes green over tests that silently did not run. The severe direction is the *silent* one — a binary the suite **spawns** by name is absent loudly (`FileNotFoundError`, a red test), while a binary the suite **resolves** and skips on is absent invisibly, and the gate marker then claims a tree verified that was verified minus its hook guards. Measured on the tree this decision ships with: 12 test modules resolve `node` that way (13 call sites), one resolves `git`, and the suite has no other conditional-execution mechanism — no `importorskip`, no `skipif`, no `collect_ignore`, no `conftest.py`.

**Decision.** **A binary enters the preflight exactly when a test resolves it off `PATH` at run time**, and that set is *derived from the tracked test sources*, never restated. Concretely: the declared set is the literal names passed to `shutil.which` in the tracked `tests/**/*.py` (spellings resolved from each module's imports; a non-literal argument is a refusal, not a pass); the preflight must probe every member of it and nothing outside it; and both directions are held by **executing** the indexed `scripts/verify.sh` against a stubbed `PATH` rather than by reading its text. The completion condition — what makes the derived set the *whole* set — is that the suite may not make its outcome depend on the host by any other means: every skip-shaped construct in `tests/` must sit in a function that also resolves a binary that way, and anything else fails, so the change introducing a new mechanism answers the question in place. `jq` enters under this rule rather than beside it: the promotion guards resolve a real jq engine to evaluate `scripts/promotion-step.sh`'s three `--jq` programs, which puts jq in the derived set, which obliges the probe. The rule is implemented by `tests/unit/_toolchain.py` and held by `tests/unit/test_verify_toolchain_preflight.py`.

**Alternatives.**
- *Derive the probe set from what the tests **spawn*** — read every binary the suite executes off the tree. **Measured vacuous against the very instance that motivated this decision**: `node` never appears as a literal `argv[0]` in any of the suite's subprocess calls — the only string literals in that position are `git`, `bash` and `/bin/bash`, and every other call site passes a non-literal, because the hook tests pass the already-resolved absolute path. Cost of adopting it anyway: a parser over those dynamic call sites, and the class stays open at the end of it.
- *Keep the list hand-written and guard it against a second hand-written list* — cheaper to write; the guard's "both directions" claim then rests on a constant, which is this repo's most-repeated defect (five separate allowlist/exemption findings, #449 → #458). A guard comparing two remembered lists notices a typo and nothing else.
- *Probe every binary the suite touches, loud or silent* — would add `bash` and the spawn-site `git`. Rejected as a wider net for a class that is already loud: a missing `bash` cannot be misread as a red tree for long. Reversible — the rule's key is the resolution call, so widening later means widening the derivation, not rewriting the guard.

**Consequences.** The preflight gains `jq` and `git`, and the gate refuses to run without either — a contributor or CI image lacking them gets exit 97 and a named diagnostic instead of a confusing red. `git` entering is a developer-visible behaviour change the ticket did not name: a checkout without git now stops at the preflight rather than failing later at the marker stage. `scripts/setup-cloud-env.sh` installs `jq` and checks for `git` rather than installing it, and `specs/infrastructure.md`'s *Local execution* row records them; `ci.yml` needs no change (`ubuntu-latest` resolves to `ubuntu-24.04`, which ships jq 1.7.1 and git 2.54.0). A test that wants a host binary must resolve it through `shutil.which` and may skip only there. Both guards read the **git index** — the corpus and the executed script alike — so they judge the bytes that would ship (#482); the cost is that unstaged work is invisible to them, which their failure messages say, and that `scripts/mutate.py` cannot reach them, so their mutation evidence is by staged probe (#490). If a future change makes the *gate itself* launch a binary directly, the stale direction goes red for a legitimate reason: route it through `uv run`, or extend this rule deliberately and record why — adding a name to the guard's stub set quietly recreates the allowlist this decision exists to avoid. What this does **not** close: a test that swallows a `FileNotFoundError` and passes without asserting anything degrades silently and is outside the rule — it is a test that asserts nothing, and no membership rule can see it.

### Decision: An asset table carries a copy disposition, and absence is not consent

*Decided 2026-09-16.*

**Context.** `/harness:hydrate` step 11 copied every shipped asset "only where that asset's own destination path is absent", which reads *absent* as a proxy for *wanted*. The two come apart on a consumer that already has what the asset provides: a repo that deleted an asset with a stated reason receives it again at the next hydration and re-argues the same decision at every release. Three instances arrived from two consumers on different stacks — `nano-erp` declined `04-primitives/_template.md` and `build_design_tokens.py` (no Python at all, and a working TypeScript builder already in its gate), and `calibrate` declined the same builder from the opposite direction, as a package-emitting repo with no page for it to act on. Neither consumer's own guards catch it: `nano-erp`'s token lint does not scan `.py` and its first-party-JavaScript ban does not reach Python. By default the predicate keeps re-copying, and the consumer keeps deleting.

**Decision.** A producing skill's asset table carries a third column, `Copy`, whose only value is `on request`. An empty cell — and every row of a table that declares no such column — keeps copy-if-absent, so `design-system`'s table is the only one that changes and a future asset-carrying skill inherits a correct default without an edit. Step 11 honours the mark: absence does not license a marked asset, so the run copies nothing and reports where it would have landed. The report needs no new word — a withheld asset is `retained`, and the `reason` cell carries the offer. **The workflow owns what a mark means; the producing skill owns which rows carry one.** A mark is for an asset whose landing does something a deletion does not undo: it acts on the repo, or it contradicts the consumer's own documentation from inside the design directory. Surplus alone does not earn one.

**Alternatives.**
- *A declined-assets list in the consumer's `harness.yaml`* — `nano-erp`'s own proposal, and the only option that could distinguish a decline from a first hydration. Rejected on this repo's *reduce fan-out* principle: it makes the consumer's configuration carry knowledge of the producer's inventory, and a producer names no consumer.
- *Gate the copy on the consumer declaring a token build command* — no such field exists in `harness.yaml`, so adopting it means inventing a config key to decide one file; it answers only two of the three recorded instances, because `calibrate` declares no build command either and would receive the copy it declined; and it makes the disposition a per-consumer predicate every future asset must define instead of a constant the producer states once.
- *A richer vocabulary — `always` / `if absent` / `on request`* — two of the three name the behaviour the blank cell already names, and a contract with two spellings for one meaning drifts into a third.
- *Move the withheld asset out of `assets/` into the skill body* — refused by two standing guards rather than by judgment: `tests/unit/test_design_system_skill_assets.py:90` requires the builder tracked under the assets tree and `:114` pins `paths.design_system` to that same tree, which is this repo's own working design system. The move costs two guard rewrites and relocates a live builder to buy what a table cell buys.

**Consequences.** One column, one clause in step 11, one clause in the producing skill, and a decision per shipped asset. A consumer stops re-litigating a decline at every release, and the plugin stops pushing machinery into repos that already have better. What it does **not** buy: hydration still cannot tell a decline from a first sighting — both present as an absent path — so a decliner reads one report line about the withheld asset at every hydration. The column removes the re-copy, not the re-mention, and recording the decline would need either consumer configuration or a plugin-owned file inside the consumer, which the alternative above and ADR 0022 point 1 respectively refuse. Five sentences elsewhere that enumerated what hydration lands were corrected in the same change; nothing holds the three rule copies equal, so a future edit to that enumeration has to touch all three by hand. **Left open deliberately: precedence between overlapping rows.** `design-system`'s table has rows that overlap — `03-tokens/tokens.json` is named by its own row and contained in the tier range above it — and exactly one marked row, so no shipped table can exercise a conflict. A precedence rule written now would be a mechanism for a case nobody has met, which P0 refuses; the first skill to mark a second row decides it, and this sentence is why there is nothing to find when they look.

**Amendment (2026-09-18, #668) — the table is the membership list.** This block settled which *disposition* a row carries and left the *set* to the directory: step 11 copied every file under a skill's `assets/` and consulted the table only for marks, so an asset no row named copied by default. That default has exactly one instance and it is wrong in both directions. `skills/design-system/assets/AGENTS.md` is not an asset of that skill at all — it is the Codex twin step 5 seeds from `templates/rules/design-system.md`, resident there because this repo's `paths.design_system` resolves to the shipped asset tree — and the unlisted default licensed copying the harness's own instruction file into a consumer as that repo's binding Codex guidance, in the one run where step 5 had written no twin of its own. A `__pycache__` beside the builder is out by the same missing bound, and it is not hypothetical: this repo's own gate produces one every run, because `tests/unit/test_build_design_tokens.py` imports the builder and CPython writes the cache beside the source — which here is the shipped asset tree. It survives only because `tests/unit/test_seeded_assets_are_tracked.py` exempts `__pycache__` by name. **A row reaches every file at or under what it names, and that reach is both the membership and the extent of any mark**: step 11 copies what the table names and nothing else, and a skill that ships assets while naming none copies nothing and is reported. The column's default is untouched — a table declaring no `Copy` column still has every row copy-if-absent — so what narrows is which *files* a table governs, never how a cell reads.

**A third value was considered and refused.** `never`, marking `AGENTS.md` as an asset this skill declines to copy, keeps the directory as the membership list and so answers half the defect: the build artifact would still have no row and still copy. Bounding that other half on the **tracked** files under `assets/` fails at the point of use — an installed plugin runs from a version-pinned copy with no repository in it (`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, eleven such copies on the machine this was measured on, none carrying a `.git`), so `git ls-files` there answers nothing or answers about some enclosing checkout, and the deployment where the artifact *can* appear is the one where git happens to be present. Membership by row is evaluable from the document alone, in every deployment. `never` would also state in the table the thing the table must not say: that this file is one of the skill's assets. `on request` for the same row is worse — it converts a silent wrong copy into a standing offer of the harness's own instruction file at every hydration.

**Precedence stays open, and this change does not trip it.** No row gains a mark here, so the shipped table still carries exactly one and no conflict is reachable. The trigger named above — the first skill to mark a second row — is the wrong predicate, since two marks conflict only where one row reaches the other; correcting it is on the improvement ledger rather than folded in here, because nothing in this change depends on it.

### Decision: The design layer ships one executable, and no raw-value scanner

*Decided 2026-09-16.*

**Context.** ADR 0022 point 1 permits a generator copied out once and owned thereafter by the consumer, and names the design-system builder as the pattern. It permits; it does not oblige, and it says nothing about how many such files the layer should carry. Two questions arrived together and had to be answered together: what disposition `build_design_tokens.py` takes, and whether the layer ships `nano-erp`'s offered raw-value scanner (`scripts/tokens/lint.ts` plus a sanctioned-exceptions file), recorded against #651 and deliberately left unbuilt there pending this answer. Decided separately, the first could be settled in a way the second then contradicts.

**Decision.** The design layer ships the eight-tier structure, the three-tier token model, and exactly **one** executable: `build_design_tokens.py`, marked `on request`. The scanner is **declined**. It is per-language and per-framework, and the sanctioned-exceptions list it needs — the part that makes a scan that wide survivable rather than switched off within a release — is a judgment about a tree the plugin cannot see. What the layer ships instead is the description of what such a scan must certify, which the skill already carries. A second shipped executable is a new decision record, not an extension of this one.

**Alternatives.**
- *Ship the scanner as a second asset, marked `on request`* — the column would make it optional, so the disposition mechanism is not what refuses it. Rejected because marking it optional does not make it correct: the plugin cannot keep a per-framework scan or its exceptions list current in a repo it cannot read, and a stale scanner that is switched off is worse than none, because it reads as coverage.
- *Ship no executable at all and describe the builder instead* — would settle the layer's shape with one rule rather than a count. Rejected: token resolution is language-neutral and fits one stdlib-only file, two consumers transplanted the token model successfully, and removing the builder takes the mechanism away from the fresh consumer this layer exists to serve.

**Consequences.** #651's recorded offer is closed rather than left pending, so no future drain re-derives it; the skill states plainly that the scan is the consumer's to write and wire into its own gate, which answers a reader who would otherwise re-propose it. Nothing in flight is lost — #651 shipped at `8b9bf66` and nothing was queued to build the scanner. The cost is that a consumer wanting a raw-value scan writes it themselves, with only the certification described for them. This decision is cheap to reverse in one direction (add an asset) and expensive in the other, which is why the count is stated rather than left to accumulate.

### Decision: The test lock's governed set is declared roots times declared basename globs

*Decided at the design stage of #659, 2026-09-17.*

**Context.** `hooks/test-lock-guard.js` accepted one prefix and governed every file below it. Two consumer layouts fall outside that. A repo with both a dedicated backend test tree and co-located frontend tests could reach only one of them — naming the frontend source root would also refuse every production edit beside those tests — and the obvious way to name two roots is a yaml sequence, which `scripts/harness-config.js` refuses, taking the **whole** `paths:` map down with it and leaving the lock silently inactive. The same missing predicate failed in the other direction on nano-ERP/ERP-521, whose deliverable was test-harness code: the lock refused the ticket's own implementation, a support module under the test root, while the assertions beside it were the thing that needed locking. There was no ordering of the stages that worked, so the run proceeded with the lock disarmed — law 7 held by builder discipline in exactly the case where the whole diff is tests.

**Decision.** `paths.tests` is a comma-separated list of roots inside one scalar. An optional `paths.test_files` is a comma-separated list of basename globs, anchored at both ends, with `*` the only metacharacter. A file is governed when it sits under a root **and**, where globs are declared, its basename matches one. Absent globs govern everything under a root, which is the shipped rule and is what leaves every existing consumer's refusals exactly where they were, with no configuration change. A declaration the shared reader refuses, or a `test_files` this hook cannot use, leaves the lock inactive and says so on stderr under an armed run. The lock never widens on a configuration error and it never fails closed.

**Alternatives.**
- *Teach `scripts/harness-config.js` to read yaml sequences* — put out of scope by the ticket, and the wrong shape besides: a sequence expresses the roots and says nothing about which files under them carry assertions, so the co-located and support-module cases would both still be open after the reader grew.
- *Per-root globs* — needs a nested mapping the flat reader refuses whole, and buys precision nobody has asked for. The cost is stated as a consequence instead.
- *A malformed `test_files` falling back to blanket root coverage* — preserves protection and refuses every production edit under a declared source root on a typo. That is the catastrophic direction for a hook that blocks work, and the refusal cannot be cleared from inside the hook.
- *Failing closed on an unreadable declaration* — refuses the edit to `harness.yaml` that would fix it.
- *Inferring test naming conventions from the tree* — out of scope by the ticket, and a wrong guess is a false-deny factory with no report, which is the reasoning `declaredPaths`' own docstring already carries.
- *A consumer-side exemption list for ungoverned files* — every allowlist this repo has shipped needed both directions and became the finding. The glob set earns itself from the repo's own naming instead.

**Consequences.** A consumer covering two conventions enumerates both in one flat list, because the globs are repo-wide rather than per-root. **Declaring globs narrows the dedicated tree too**: `tests/conftest.py` and a shared fixture stop being governed the moment a repo declares `test_files`, which is the trade ERP-521 asks for and is not free — a shared fixture is a place a cheat can live. What keeps that residue visible is `/build`'s coverage report, which lists the tracked test-shaped files the declaration does not govern before the lock is set. `/assess`'s assurance-ratio command interpolates a root and now has to pass one pathspec per root. The hook passes `engineering`'s 300-line soft limit, noted in its own header with the reason. And the lock still cannot see a rename through `Bash`, which `specs/harness-assumptions.md` already records with the test that would retire it.
