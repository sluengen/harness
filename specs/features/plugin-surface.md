# The plugin surface

> The harness is a spec-driven development process shipped as native plugins for Claude Code and Codex. Both packages carry the same skills, lifecycle procedures, role guidance, and enforcement hooks under one version, plus the gate and guards that make a green tree the only path to a shared branch. This record is the canonical answer to "what is the harness now" (v5, ADR 0017); its registry-era predecessor, the `guidance-system` record, left the tree with `specs/retired/` at #547 and stays in git history.

## Behaviour

### One plugin, one version

The repository root **is** the plugin. `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json` name the same `harness` release at one semver (`8.1.0` at this record's date). `.claude-plugin/marketplace.json` and `.agents/plugins/marketplace.json` expose that root through each host's native marketplace contract. The manifests are updater-facing selectors; the generated spine markers in `templates/spine.md` and `AGENTS.md` carry the same version (`CLAUDE.md` carries none — since #537 it is a pointer file, not a second spine). `tests/unit/test_spine_template_parity.py` and `tests/unit/test_native_codex_plugin.py` reject a mismatch on every gate run. There are no per-file versions, no `guidance:` headers, no `registry.yaml`, and no consumer lock file — the whole distribution channel ADR 0017 retired. Since #537 each of the nine lifecycle workflows ships **once**, as a skill under `skills/<name>/SKILL.md`, and both hosts read that one artefact: Claude Code exposes it as a slash command (`/build`, and `/harness:init` where the bare name collides with the host's own), and Codex discovers it from `skills/` — the only content key `.codex-plugin/plugin.json` declares. The generated `command-*` and `agent-*` mirror skills are gone.

**When it moves (#556, superseded by #588, owned since #589).** #556 moved the bump off the release hop and onto the *start* of a release cycle, on the integration branch, because nothing in this repo can write at the hop: the automated promotion opens a pull request whose head is the integration branch itself and pushes nothing new, and a bump authored onto the release branch by hand leaves `scripts/promotion-step.sh`'s content-divergence pre-condition non-empty and wedges every later nightly. The occurrence that forced it: the release merged on 2026-09-05 (`a609d5b`) carried both manifests at `6.0.1`, and `7.0.0` reached the integration branch the next day, so a consumer running `claude plugins update harness` in between was told it was already current over bytes that had changed. **#588 retired that obligation and gave it to nobody.** The plan was to hand the bump to `scripts/promotion-step.sh` at the hop; that implementation was built and removed before landing, because the hop's commit slot has to be created by writing a ref and GitHub raises no workflow run from a commit written with `GITHUB_TOKEN` — the bumped head would carry no required check, the script's poll would spend its full wait and exit 1, and the next night would read the same runless SHA, so the promotion would wedge permanently rather than once. Between #588 and #589 the version was therefore raised **by hand at a release**, with no builder owing a bump and no guard checking for one; #589 gave it an owner and the paragraph below records what that owner does. `specs/architecture-principles.md` carries the superseded clause and three dated amendments, the spine's *Repo principles* names `/build` step 1 as the owner and minor as the floor, `skills/promote/SKILL.md` still does not name a version bump as content the release branch may gain, and `skills/build/references/reconcile.md` no longer carves this one value out of the monotonic-field trap by name — it states the general rule instead, that a value both branches compute from a predecessor which cannot move while they run is agreement rather than a collision.

**Who moves it now (#589).** `scripts/plugin-version.js`, run by `/build` step 1 in the new worktree between the worktree's creation and the run-state write — before the first edit of the change being built, so the raise lands inside the tree the gate certifies and the reviewer reads, and no second commit follows the verdict. That ordering is the whole reason `scripts/land.js` is the wrong home despite being the obvious one: a content edit after the certifying gate voids the marker the verdict binds to. The script reads the four homes out of the **working tree** rather than the index, because its operand has to be the bytes it is about to modify; the shipping-tree claim stays where it was, with the index-reading parity guards running inside the gate over the committed raise. It compares the homes' agreed version against the release branch's `.claude-plugin/plugin.json`, read through `refs/remotes/<remote>/<release>` after a fetch of the whole remote, with the release role taken from `harness.yaml` through `declaredBranches` rather than named in the source. Equal versions raise the minor and zero the patch across every home; an integration version already above the release's writes nothing and reports `already-ahead`, which is what every ticket after the cycle's first sees. A release version above the integration's refuses in one of two ways, told apart by `git merge-base --is-ancestor HEAD <release-commit>`: `stale-base` when the release branch already contains this checkout's HEAD, whose remedy is a rebase, and `release-ahead` when it does not, which is `promotion-step.sh`'s own content-divergence condition. A declared release ref that will not resolve refuses at exit 2 rather than skipping — the `NO_RELEASE_REF` behaviour of the deleted guard is the failure this refuses by construction.

Membership in the home set is **positive identification, never absence**, and that is the property with the largest blast radius here. `/build` step 1 is shipped guidance, so this runs in calibrate, nano-erp and lab-book too, and each of those carries an `AGENTS.md` marker naming the harness version that hydrated it. A writer that raised every `spine:generated` marker it found would rewrite three repos' record of which guidance they run, silently, on their next build. A repo is a plugin source only by carrying `.claude-plugin/plugin.json`, and a marker is one of *this* plugin's homes only where the name it carries equals that manifest's `name`. The absence check is the first thing the script does, before the configuration read and before any network call: measured at review by running the shipping script against `/Users/scottluengen/Code/calibrate` with `--repo`, which printed `no-plugin-manifest` at exit 0 and left that repo's `AGENTS.md` byte-identical (`harness@7.0.0`, unmoved). `tests/unit/test_plugin_version_script.py` holds the same property over a fixture, together with the marker-naming-another-plugin case, and every fixture names a plugin and versions this repo has never published so a hardcoded `harness` or `8` would be indistinguishable from nothing.

The homes are rewritten by **substring**, never reserialized. `.codex-plugin/plugin.json` carries `keywords` and `defaultPrompt` as single-line arrays that `JSON.stringify(…, null, 2)` reflows, which would turn a three-character change into a fifteen-line diff in the first review of every cycle. Only the version's own span moves; interior spacing, the marker's name and the line's whitespace survive byte for byte. Reads parse and writes splice: the plugin name comes from `JSON.parse`, the span from a pattern. The marker pattern is `test_spine_template_parity.py`'s `_BEGIN` with its literal `harness` generalised to a capture and otherwise structurally identical, so no marker that guard can see is invisible to this writer, and it is line-anchored — an unanchored pattern makes a marker quoted inside a sentence a second site, which refuses the home rather than raising it. The manifest pattern collects every `"version": "…"` site and requires exactly one, so a future nested `version` refuses loudly instead of having its first hit rewritten. All homes are read and validated before any write, so a refusal never leaves a partial write behind; the four writes are not atomic as a set, and `homes-disagree` is the refusal the next run gives if they ever diverge.

**The level is minor, and the script never decides otherwise.** The compatibility grammar's `patch` — "wording only, no behaviour change" — predates ADR 0015: with a runtime, a reworded skill body changed nothing a consumer executed, and with the runtime retired the shipped product is prose, so a reworded body is a behaviour change. There is no `--level` flag, because a flag would invite a guess at step 1. A raise above the floor is a judgment about the whole diff, so it belongs to the review: `skills/review-discipline/references/certifying.md` gained *The version class*, which puts the version homes in scope for every change that carries them and asks whether the diff exceeds the floor. Verified by use rather than by a wording predicate (law 2; ADR 0017 D5), in two fresh contexts differing only in the diff: a change that flips a hook's verdict from deny to allow returned *raise to major*, and a pure refactor of the same hook — the refusal string extracted into a helper, byte-identical text, identical conditions — returned *the floor is correct*, three times out of three.

A bump moves four files, the two manifests and the `spine:generated` marker in `AGENTS.md` and `templates/spine.md`, and since #588 **nothing measures that it happened**. `tests/unit/test_release_version_cycle.py` — 713 lines — compared the index's `.claude-plugin/plugin.json` version against the highest one any locally present release-role ref carried and failed when this tree's content differed from the release tree without a strictly greater version; #588 deleted it together with the obligation it enforced. Its record is that it enforced nothing where it mattered: under `ci.yml`'s bare shallow checkout it found no release ref, reported `NO_RELEASE_REF` and skipped on every `push: dev`, and the one run that did compare — the nightly promotion of 2026-09-06, run 34046398127 — failed `Kind.EQUAL` and stopped the promotion it was written to protect. #580 had just given that checkout `fetch-depth: 0`, which is what would have made it compare on every push instead. The key stays and `ci.yml`'s comment now records why: no gate stage requires it, removing it is an untested change to the one checkout every gate run depends on, and nothing now fails if a later edit re-shallows the clone. `tests/unit/test_nightly_promotion_workflow.py` lost the two assertions that pinned that key and the single-checkout count, both still green at deletion, because the guard they were a precondition for no longer exists. What survives measures **agreement, not movement**: `tests/unit/test_spine_template_parity.py` derives the reference from the manifest, refuses a reference that is not `X.Y.Z`, and fails when the manifest and the two spine markers disagree, with `tests/unit/test_native_codex_plugin.py` holding the two manifests equal. So a bump that happens must be complete across all four homes, and a bump that never happens is invisible to the gate. #589 left that unmeasured on purpose rather than by omission: the writer at `/build` step 1 either performs the raise or refuses loudly at exit 2, and a gate stage re-reading the same two operands would share them with the mechanism it was meant to back up, which is not a second defence (P0, and #580's shared-operand finding).

**The level, worked (#565).** By the time #565 was reviewed, `main` had been promoted to `7.0.0` (`d7f39e4`) and `dev` had already diverged from it (`2aca9b0` and its merge, neither a version-bearing change), so the cycle-start guard above — deleted at #588 — was already failing `EQUAL` before this ticket touched a byte — any tree shipping `dev`'s current content needed a version strictly greater than `7.0.0`, named in the guard's own remedy message. That settles *whether* to bump, not *how far*. The ticket's own change removes `disable-model-invocation` from `digest` and `assess`, which is precisely a *refusal reason changed* under `specs/architecture-principles.md`'s compatibility grammar — a call that `Skill(digest)` and `Skill(assess)` used to refuse now succeeds — so patch ("wording only, no behaviour change") does not fit, and minor is excluded by name (minor requires invocation and refusal reasons unchanged). The candidate as built declared `7.0.1`; the review raised it to `8.0.0` and re-ran the gate green over the corrected tree, on the reasoning above rather than the cycle-start default, which governs only the *first* bump of a cycle and not a later change's own compatibility class.

The shipped inventory, counted at tree `8281ecf` — the tree #547's build produced, and the one every figure below was measured over. `tests/unit/test_landing_page_inventory.py` derives the skill, agent and hook figures from the tracked tree in both directions and holds `docs/index.html`'s printed counts to them, so those three cannot go stale in silence; the remaining rows are a reviewer's count at that tree.

How and what follows ADR 0017 D3's pattern: the skill body states the method, a plugin asset argues it (`skills/engineering/references/principles.md`; `skills/review-discipline/references/craft.md` is the running precedent), and a repo-owned asset records local reality (`specs/architecture-principles.md` for design, `specs/infrastructure.md` for operations, the spine's *Repo principles* section for build). Two skills carry it since #547, not three: `engineering` for build and `architecture` for design. The `infrastructure` skill was the operate leg and is deleted — `/promote` already transcribed the whole promotion loop and cited the skill exactly once, in a parenthetical, so the skill was a second copy of a procedure the workflow owned. The three obligations it alone held moved into `skills/promote/SKILL.md`: the back-merge after the release hop, *the tree that lands equals the tree the gate certified* where a protected target forces a pull request, and the reserved exit code separating an infrastructure failure from a red tree. The repo-owned *what* stays in `specs/infrastructure.md`, where it already was.

### Evidence follows its subject

ADR 0019 is the one evidence contract. The spine carries its full subject matrix; architecture principles, authoring, engineering, review, the build procedure, roles, and templates cite it and state their own action. Executable behaviour and mechanically enforceable invariants retain RED then the smallest GREEN. A runtime or compatibility floor has a declared floor and functional execution on every supported environment; configuration and generated artifacts use a validator, producer check, or smoke without duplicate consumer suites. Prose is reviewed or used directly, never judged by a predicate or wording guard, and an unobserved preventive guard requires a recorded risk decision. The prose discipline is `skills/authoring/references/prose.md` since #547 folded the `writing-quality` skill into `authoring`: the minimum effective edit, the author's terminology and cadence preserved, and a sentence carrying no decision, constraint, evidence, action or necessary context cut. Developer and reviewer roles load that reference immediately before substantial handoffs and review reports; `/build` and `/capture` load it before authoring change specs, while short status and structured output stay outside it. A criterion may change before implementation only with evidence, a smaller replacement, owner approval, and a tracker amendment; it is never silently descoped.

### The spine

There is **one** always-loaded spine, `AGENTS.md`, and both hosts read it; `CLAUDE.md` is `@AGENTS.md` plus the deltas that apply on that host alone and restates nothing (#537). It is no longer a compiled artifact — nothing generates it, and this repo's copy is 85 lines at #588 against the 120-line ceiling the ticket set. The spine carries, in order, the **operating context** #588 put ahead of everything else — pre-user, pre-revenue; speed and simplicity as the route to quality rather than a trade against it; and a four-line risk appetite whose two refusals are the only protected areas there are, user data, credentials and money; then **P0 Do less**, which takes precedence over the five principles behind it in any conflict (build quality in · reduce waste · flow · stop the line · continuous improvement), each stating what it refuses; the **laws** derived from them, one obligation per line with the rationale in an HTML comment beside it; the lifecycle (a fix / a ticket / a proposal); the shared contract (ticket states, holds, the three lanes, the PASS/FAIL/DEFER verdict vocabulary, the tree-oid binding, configuration, tracker dispatch, the queue and its limit, filing rules); and an enforcement summary. Each repo restates its own stage in one repo-owned line under *This repo* — this one's reads *Stage: pre-user, pre-revenue. Posture: speed and simplicity; a wrong change costs a revert. Protected: user data, credentials, money.* — and that line is what the generated paragraph is read against on the day a product gains a user. It carries **no configuration** — that moved to `harness.yaml`, and the contract's *Configuration* bullet names the file rather than restating a value from it. Skills are conditional depth behind the spine and may assume it is loaded. The generated block sits between `<!-- spine:generated:begin … -->` / `<!-- spine:generated:end -->` markers and is byte-identical to `templates/spine.md`'s block — held since #489 by `tests/unit/test_spine_template_parity.py`, which extracts the delimited region of `AGENTS.md` and of the template from the git index and fails in either direction, anchoring on both the `## Principles` and the `## Laws` headings so an extraction reaching one of them is not mistaken for reaching the block. Everything after an end marker is repo-owned.

Guidance that matters only in one part of the tree lives in `.claude/rules/<name>.md`, with a `paths:` frontmatter of globs, and loads only while a matching file is open — narrower than the spine, never a cheaper spine. This repo ships three: `scripts.md` for `scripts/`, `hooks/` and `tests/` (stdlib-only Python, the no-dependency rule for the shipped JavaScript, the hook fail-open posture, ADR 0018's no-per-invocation-source rule, and *a guard asserts a property of the tracked tree, never the working directory* with its one named carve-out), and two on `design/` and `docs/` that split by subject: `design.md` carries the token-source relationship, and `design-system.md` — seeded at #547 from `templates/rules/design-system.md`, repo-owned since — carries the craft, the states checklist, accessibility, and the visual-evidence capture rules that used to sit in `skills/build/references/visual-evidence.md`. Codex has no path-scoped rules, so where the design layer is on `/harness:init` seeds the equivalent nested instruction file inside the design directory, which Codex reads nearest-wins; this repo's is `design/AGENTS.md`.

#### Scenario: the fix lane

- GIVEN a small fix that changes no documented behaviour, spans one commit, and needs no independent review
- WHEN an agent is asked to "fix X"
- THEN it works on its own branch in its own worktree, runs the gate, and ships without a ticket — no command carries the fix lane, and the hooks enforce exactly as for ticketed work.

### Lanes, intake, and the andon cord

Since #538 that lane has a name the rest of the contract uses. The spine's **Lanes** bullet replaces the old assurance-level list: one lane per ticket, chosen at filing, carried as the same `assurance:<level>` label, and **upgrade-only** — **fix** (`trivial`), **change** (`simple`), **feature** (`complex`). The fix lane's whole assurance is the gate and the push guard: no ticket, no reviewer sub-agent, no as-built record (the accepted proposal's D2). `skills/authoring/SKILL.md` chooses the lane by blast radius and states what earns the fix one — a diff describable in one sentence that touches no protected area and adds tests without editing any — and states why the trade is worth taking: a lane nobody can afford is a lane every one-line fix routes around, which erodes the boundary for the changes that genuinely need a review. The repo-supplied `assurance.trivial_certify` allowlist command that used to earn `trivial` is retired with it; neither `harness.yaml` nor `templates/harness.yaml` declares an `assurance:` block, and no shipped skill names the key.

**A protected area is a tripwire, not a scope note.** Since #588 the list is three and closed — user data and its migrations, credentials and auth, money and billing — because those are the three losses the operating context says this stage does not accept, and anything else on such a list is inherited from a posture this repo is not in. A **directory** is not a protected area: `hooks/` and `scripts/` came off the list, and what decides the lane there is what the diff changes — a decision takes the feature lane, a message, a comment or a test-only edit takes the fix lane. A repo whose own stage line declares a later stage names its own additions there. `templates/change.md`'s *Protected areas* section says the same thing to a filer. A diff that reaches one stops and holds (`input`, assigned) whatever the lane says. Raising the lane is not an alternative to that hold; it is what the operator does when releasing it. What trips it is the **diff**, so a ticket may name an area its diff never touches, and a diff may reach one the ticket never named.

Intake carries the upstream half. `/capture` gains a **clarification loop with a stop condition rather than a cap**: keep asking while any question remains whose answer would change the architecture, a contract, the data model, or the test design; rank by impact; integrate each answer into the spec as it arrives, replacing the sentence it supersedes. Attended that is `AskUserQuestion`; unattended an unanswerable question is a hold, and a material question that should not block the filing becomes an inline `[NEEDS CLARIFICATION: …]` marker, which `/build` refuses to start on. It also gains the workflow's **one refusal**: a filing without a **cost line** — what it costs, what it buys, which principle it serves and which it spends against, and which waste it removes or adds — is incomplete and is filed as nothing until it can state one, because cost is uncomputable later, when the spend is sunk. `templates/change.md` carries the matching sections: **Cost** with its one-line shape, **Assumptions** (decisions taken without the authority to take them, `none` where there are none), **Protected areas** (never omitted — a blank section and an absent one read the same, and only one of them means the question was asked), the **Assurance** heading renamed **Lane**, the verb-plus-where title convention, and the marker's meaning.

`work-discovery` gains **Andon**, checked ahead of ranking: an open ticket that the tracker's own fields say is a **bug** at **top priority** is the only pick until it is closed. The check reads the open queue in **every** state rather than Todo alone, because a P1 bug somebody is already fixing is still the line stopped, and both halves come from the tracker's fields — never from a ticket's prose claiming urgency, which is text anyone who can open an issue may write (law 6). Two consequences are stated where they would otherwise be dropped: a **held** P1 bug is still the cord, so the loop reports the stopped line and stops rather than reaching past it; and a cord that is not actionable stops the tick rather than falling through to the next candidate, which is how an andon rule quietly becomes a ranking tweak. `/routine` step 1 names the same rule, and an attended `/build` on any other ticket reports the open P1 bug before it starts — it does not refuse, because an operator who names a ticket has the authority to build it, but silence would waste the signal. #588 narrowed what earns the cord to a hook or script that **refuses correct work or lands wrong work**, and nothing else: a rough edge, a confusing message, or a hook merely wrong about something nobody is blocked by is a P2 bug on the queue, because a repo whose cord is pulled by every misbehaving script has no cord.

**The queue is bounded, and one step performs the pull (#588).** `queue.wip_limit` (default 6) bounds a project's Todo, In Progress and In Review tickets with held ones excluded; `queue.active_projects` (default 3) bounds how many projects may have anything in flight; and `queue.project_field` names the tracker field a ticket's project is read from — `project` for Linear, `milestone` for GitHub — or declares that the repo is its own single queue, which is what this repo declares. **Backlog** stops meaning *existence uncertain*, which is what the improvement ledger holds, and becomes confirmed work waiting for a slot, ordered by dependencies then priority. What the bounds govern is what *enters*: `tracker`'s `create` grows from four mandatory elements to five — the fifth is the ticket's **project**, inherited from the parent where the filing comes from inside a build — and its existing placement step stops meaning *Todo* and starts meaning Todo where the project has a free slot and Backlog where it has none, a breakdown files its first `wip_limit` into Todo and the rest into Backlog, `/assess`'s drain folds only into Backlog and drops by default, and starting a ticket already in Todo is never blocked by a limit. `work-discovery` gains *The limit*, run after the andon check and before ranking, and it is the only step in the loop that moves a ticket out of Backlog: count, normalise a project over its limit by moving its lowest-ranked Todo tickets to Backlog, pull the highest-ranked eligible Backlog ticket while a slot is free, then rank. Without it the redefinition of Backlog would be one-way — filings and folds enter and nothing carries them back out — so the step is what makes the reservoir a queue rather than a second ledger. It does not run under a stopped line, because a stopped line moves no tickets, and the cord itself is filed into Todo whatever the count with nothing demoted to make room. `/digest` prints the numbers per project beside the R line. **None of this is enforced mechanically**: the limit is guidance a run performs, and the only code the change adds is the reader that returns the keys.

**One improvement channel (#588).** The reviewer's Proposals section is gone from `review-discipline`, its evals, `skills/review/SKILL.md` and both hosts' reviewer agents; the 2×2's non-blocking/large cell now reads *let it go — say nothing*, and the one thing that still leaves a review is a **blocking** finding that is not this ticket's. The builder's three-line reflection is the single channel out of a build. A bug also gains a second half: the tree contradicts its own contract **and** the contradiction breaks a user outcome or a consumer behaviour that can be named — a stale comment, a wording mismatch, or a test asserting the wrong thing is an improvement, not a bug. `templates/change.md`'s cost line gains a **guard-to-change** figure and `engineering` states the bound: above 3 : 1 a guard needs a recorded reason naming the user outcome it protects at this repo's stage, and a mutation table is not that reason, because it says the guard works and never that it was worth writing.

### Configuration, and the one reader

`harness.yaml` at the repo root is the repo's configuration: `repo:`, `tracker:`, the tracker address block, `stack:`, `commands:`, `branches:`, `loop:`, `queue:` (#588), `layers:`, `paths:`, `env:`. Before #537 the same map was a fenced `yaml` block inside the spine's prose, and three hand-rolled parsers read it — `declaredBranches` in each of the two enforcement hooks, and the `commands.verify` reader in `scripts/gate-marker.js`. #487, #488 and #510 are each a bug in one of the three that the other two either shared or were spared by accident. The migration into the file is a **verbatim move**: `/harness:init --refresh` takes the fenced block byte for byte — comments, blank lines, key order — writes it as `harness.yaml`, replaces the fence with a pointer, reports the key-by-key diff and stops on any difference. A move cannot lose a key the plugin does not itself read — `tracker_address` and `conventions`, measured at this tree — nor flatten a shape it reads but never rewrites, such as the list of mappings an `architecture_watchlist` nests; a translating migration could do either. This sentence listed `tools` and `architecture_watchlist` among the unread until #561 measured them: `skills/tracker/references/linear.md` reads `tools.linear_cli`, and `skills/architecture/SKILL.md` reads `architecture_watchlist.files`.

All three parsers are now one module, `scripts/harness-config.js` — CommonJS, Node standard library only, no dependency. Both hooks reach it as `../scripts/harness-config.js` from `__dirname`; `gate-marker.js` reaches it as `./harness-config.js`, and `/harness:init` materializes the two **as a pair**, so a half-materialized install fails loudly at the preflight rather than running an undeclared command. Its source list is `harness.yaml`, `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, in that precedence order, because a repo that has not migrated must keep working on the day this lands: one reader, several sources, is still one reader. The two callers read that list by **different rules, on purpose**, and the difference is failure economics. `branches:` is searched — the first source that *declares* it answers, and a source that exists but is unreadable or declares it in an unparsable spelling is reported on stderr and stepped over — because a missing declaration falls back to a conservative set that over-protects. `commands.verify` takes the **first source that exists** and refuses (exit 3) if that one cannot be read, because an ambiguous gate command decides what may mint evidence and must fail closed rather than shop for a second opinion.

The RED the extraction was built on is security-relevant and was live in both hooks: they cut a value at the first `#` anywhere in it (`raw.indexOf("#")`), while yaml opens a comment at `#` only when whitespace precedes it. So `integration: dev#1` declared a branch named `dev#1` and both hooks read `dev` — the push guard did not recognise the repo's own integration branch as protected. The marker helper's reader already handled it (#510); the fix is that there is now one reader and it is that one. #436's two stated reasons for declining a shared `hooks/lib/` are held rather than overturned: the module sits under `scripts/`, outside the non-recursive `hooks/*.js` scans that `test_hooks_fail_open_is_loud` and `test_hooks_module_type` perform, so those guards keep their meaning; and a module that cannot be **loaded** degrades each hook to the conservative fallback — never an empty set, which would approve a push to the integration branch — measured per hook by `tests/unit/test_harness_config_reader.py`. That load failure is also *loud*: `require` inside a `try` is a Class A site for `test_hooks_fail_open_is_loud`, so a silently swallowed load failure (the #302 shape) is red. `queueSettings` joined the map readers at #588 and is the one home for the queue's defaults: it fills 6 / 3 / `none` where the repo declares nothing, returns the two counts as **numbers** because every caller compares them against a count and raw strings would compare `"10"` below `"6"`, falls back to the default for any value it cannot read as a positive integer rather than handing an unusable bound to each caller, and reads a per-project override as the single flat key `projects.<name>.wip_limit`. Admitting that key widened the `PAIR` and `FLOW_PAIR` key patterns by one character, the dot, which can only make a previously unreadable line readable — no line that parsed before parses differently. A genuinely nested `projects:` block is refused whole by `blockMap`'s existing indentation rule and reported through `onUnreadable`, so an override the repo did declare is never silently dropped for a half-read map. No environment variable may redirect the module: an earlier draft reached it through `HARNESS_CONFIG_DIR`, which is a per-invocation source for the gate command and ADR 0018 forbids it — `test_the_gate_command_can_only_come_from_a_file_the_tree_carries` caught it, the variable is gone, and that guard now follows the read across the `require` boundary rather than going blind where the work moved (#510's shape).

**Decision — the refresh report declares the retired keys; it does not derive them.** *Decided 2026-09-07 by the operator, built as #561.*

**Context.** A consuming repo's `harness.yaml` outlives the mechanisms it configures: a move preserves every key, including keys whose feature the plugin has since retired, and nothing told the consumer which of its declarations were dead. The criterion as filed asked for the complement — every key the plugin does not read — which needs the read set, and the only derivation available to a prose plan is a search over the plugin's own text. Three review cycles failed on that derivation: the first decided membership and retirement against a single corpus, so the retired class was empty by construction; the second relied on the converse and would have emitted `paths.migrations — retired, ADR 0003` for a live consumer key, because a bare leaf name spelled `run`, `source`, `team` or `migrations` is indistinguishable from the ordinary word over a corpus that is mostly English prose.

**Decision.** `--refresh` reports a **declared list** of the keys naming retired mechanisms — `loop.engine_timeout_seconds`, `loop.review_model`, `loop.unconditional_review_cycles` — and derives, deletes and refuses nothing. The complement is dropped. The maintenance trigger is any **shipped decision** that retires a key, an ADR or an accepted proposal; the second half is load-bearing, because this repo's largest retirement was the lifecycle-reset proposal and a trigger naming only ADRs missed the third key for a whole review cycle. A reader can settle which proposals qualify from the `status:` field each one carries. The precedent sits in the same plan: step 5 names its two managed legacy SHA-256 hashes outright rather than computing them.

**Alternatives.** A declared *read* set plus a drift guard was rejected: it adds a second copy of a fact the code already states, to be kept true forever, and retires nothing (P2). A guard over the list's completeness was rejected because it would have to assert what a prose list means, which ADR 0017 D5 forbids.

**Consequences.** The list can fall behind a retirement. That failure under-reports and can never emit a false line, which is the fail-safe direction, so even a stale list is strictly better than the previous behaviour of reporting nothing at all. Completeness is therefore checked in the direction that can find an omission — sweep both consuming configs for keys no executing surface reads, then ask which of those carry retirement evidence — never by confirming the keys already listed, which can only return what is already written down. At this tree every unread key with retirement evidence in `specs/` is one of the three named, and all three sit under `loop:`.

### The enforcement loop

`scripts/verify.sh` is the public gate entry point: unless `HARNESS_GATE_MARKER_RUNNER` is non-empty, it `exec`s `node scripts/gate-marker.js run`. `run` accepts repeated `--scope <path>` operands and nothing else (#539) and selects its trusted command from `commands.verify` through the shared reader, taking the **first configuration source that exists** — `harness.yaml`, then `AGENTS.md`, `CLAUDE.md`, and legacy `CONTEXT.md` — and falling back to `bash scripts/verify.sh` only when none of them exists. A selected source with a missing, empty, duplicate, malformed, or unreadable declaration exits 3 without falling through to the next one. The reader takes a plain or quoted scalar from a `verify:` line inside a top-level `commands:` block, and the spellings this repo's own `harness.yaml` already carries all parse: an inline comment on the `commands:` line, a comment after the value, a `#` inside quotes or with no space before it, an apostrophe in a plain scalar, a tab inside the value, and CRLF endings. Tabs are expanded for the indentation measurement only, so a tab-indented entry lines up with a space-indented sibling while a tab inside a value reaches the shell intact. Three spellings are refused rather than mis-derived: a value opening with a yaml indicator (`|`, `>`, `&`, `*`, `{`, `[`), a value that opens with a quote without being one whole enclosing quoted scalar, and the one-line flow mapping `commands: {verify: …}` — legal yaml that the sibling `branches:` reader in `hooks/push-target-guard.js` does parse and this one deliberately does not. The runner executes the selected declaration through fixed `sh -c` with internal mode set, forwards its output and status, and writes one marker only after measured status 0; red stages preserve their non-zero status and write none. The gate's streams are **inherited, not captured** (#561): `spawnSync` runs it under `stdio: ["ignore", "inherit", "inherit"]`, so there is no `maxBuffer` bound to outgrow and a long gate's stages appear as they are produced rather than arriving at once at the end. Captured, node buffered the child under a one-mebibyte default and failed the *spawn* past it — `status: null`, `error.code = 'ENOBUFS'` — which the runner's `result.error || result.status === null` arm reported as `EXIT_RUNNER_UNAVAILABLE`, so a gate that had **exited 0** was called unable to run and earned no marker; a full-suite gate across several languages clears a mebibyte easily, which is what made the managed `exec node scripts/gate-marker.js run` path unusable for a large consumer gate. stdin is deliberately *not* inherited: `"ignore"` gives the child the immediate EOF the capture pipe gave it, where a bare `"inherit"` would hand it this process's stdin and let a gate that reads stdin consume or block on the caller's, with no operator behind it under an unattended run. Since #539 the payload also carries `started_at` and `finished_at`, the write is atomic (a temp sibling whose name deliberately does not end in `.json`, then `rename`), and a run given a scope records the paths it covered under a `scope` key — see *The landing posture* below. `run` sets `HARNESS_GATE_MARKER_RUNNER` to the **identity of the repository it is gating** — that repository's git common directory, resolved absolute and through `realpath` by the same `gitCommonDir` the marker path uses — and refuses to start at all when it finds the variable already naming *that same* repository (#559), so a declared gate cannot delegate back to `run` and let an inner level mint a marker for a tree whose outer stages are still running. Until #559 the value was the bare flag `1`, which said only that *some* gate was running and so refused every repository's gate; an inherited value naming a different repository, the retired `1`, or nothing at all is not a re-entry and its gate runs. The equivalence class is deliberately the common directory rather than the worktree root, because that is where the evidence goes: two worktrees of one repository share a marker directory and at equal trees would mint each other's evidence, so they compare equal and are refused. Because the identity is resolved once at the head of `runGate` — both the comparison and the child's environment need it — a `run` outside any repository now refuses *before* the declared gate is launched rather than running it first and failing at marker time; the exit status (2) and git's own `not a git repository` message are unchanged. That variable is inherited by everything the gate starts, so the refusal also covers a nested public `run` beneath a running gate **of the same repository** — which since #559 is the whole of it: a gate that runs the runner against a different repository, as a gate-runner test suite does, is no longer refused. `tests/conftest.py` still drops the inherited variable, now on the narrower ground that the suite should mean the same thing however it is launched: measured at this change, neutering that fixture and running the whole suite with the variable inherited passes unchanged, so the drop is no longer what keeps the suite green. The consumer side of the contract is **emptiness, never a value** — `scripts/verify.sh` tests `[ -z "${HARNESS_GATE_MARKER_RUNNER:-}" ]`, and `skills/init/SKILL.md` specifies the skeleton it writes as taking its public path on that variable being empty and never on a comparison, because the value's shape is private to the runner and has now changed once, and because a shell has no portable `realpath` with which to recompute an identity. The skew is one-directional and loud: measured on a scratch repo, a refreshed runner beside a stale `!= "1"` shim exits 3 with no marker written and the existing delegated-back message, while a pre-#559 runner beside a fresh `-z` shim gates green — which is why this change ships as a **major** and reaches a consuming repo as a decision rather than an auto-pull, and why `/harness:init --refresh` rewrites the managed comparison and reports every other file testing the variable against a literal. The no-spine fallback runs through the same `sh -c`, which is where it departs from the launch it replaces: `$0` inside the legacy `scripts/verify.sh` is now that repo-relative path rather than an absolute one, and an `sh` sits between the runner and the gate. The internal `verify.sh` path runs the **host half** of the toolchain preflight — the binaries **node**, **git** and **jq**, each *executed* rather than located → the nested-worktree preflight → the rest of that toolchain preflight (ruff, mypy, pytest and then pytest-xdist under `uv run --extra dev`) → ruff → mypy over `scripts/` → pytest with coverage (floor 82% over `scripts/`) → the design-token drift guard (`scripts/build_design_tokens.py --check`). The Codex drift guard was the sixth stage until #537 deleted the generator it ran; the shell gate now ends at the token guard, and `verify.sh` no longer runs any Python beyond the two checks named here. The retired direct `write` command fails with usage exit 64 rather than minting evidence. Exit 97 is reserved throughout the shell stages for infrastructure that makes the gate unrunnable, so that state never reads as a red or green tree. The host-binary loop runs **first** since #500 because the preflight below it is now itself a `node` invocation: a node that is present but unrunnable — the #478 shape — makes that preflight exit non-zero on account of the runtime rather than the repository, and the wrapper has nothing but the exit code to go on, so it would name the helper at the one moment an operator needs to be told about node. For the same reason the preflight's wrapper splits its diagnostic on the helper's exit code — exactly 2 is a refusal about the repository, any other non-zero is a helper that could not run — and captures that status in `|| _preflight_status=$?` rather than letting `set -e` see it; every non-zero path still ends the shell gate at 97. The marker is `<git-common-dir>/harness/gate/<tree-oid>.json`, named by git tree object, fresh for `HARNESS_GATE_MARKER_MAX_AGE_SECONDS` (default 86400). The runner is `scripts/gate-marker.js` — CommonJS, Node standard library only, no npm dependency and no transpiler, with `scripts/package.json` declaring `"type": "commonjs"` and `engines.node` as `>=14.18.0`. ADR 0018 records the marker-emission boundary: only the non-exported emitter called after the runner's measured success writes payload `exit: 0`; local processes that can alter the checkout or set the internal variable remain in the same trust domain. The marker payload's diagnostic `gate` field records the exact command selected and launched by `run`, including the historical fallback only when no spine exists. Everything else under `scripts/` stays Python. The marker location, tree algorithm, freshness variable, payload schema, and prune retention bound are unchanged by this change. One behaviour departs deliberately: the Node prune skips a marker that has vanished, where the Python original sorted by `stat().st_mtime` and raised if a concurrent gate run in another worktree unlinked one — after the marker was written, so the race turned a green gate red with the evidence already on disk.

`node scripts/gate-marker.js preflight` reads registered worktrees from Git's NUL-delimited porcelain output before any tree materialisation or expensive gate stage. It canonicalizes the current root and each registered path, ignores the current checkout, siblings, parents, and absent prunable registrations, and inspects only live descendants. A descendant Git ignores is safe; a Git-visible descendant or an indeterminate ignore query fails closed, names the path and the `.worktrees/` / `.claude/worktrees/` remedy, writes no marker, and makes `verify.sh` exit 97.

The host half of that preflight is **derived, not remembered** (#491, and the Decision it records in `specs/architecture-principles.md`): a binary belongs there exactly when a tracked test resolves it off `PATH` at run time, and the set is read off the tracked `tests/**/*.py` by `tests/unit/_toolchain.py` — the literal names passed to `shutil.which`, with each module's spelling resolved from its own imports and a non-literal argument refused rather than dropped. Resolution and not spawning is the key because the severe direction is the silent one: a binary spawned by name is absent loudly, while one resolved and skipped on is absent invisibly, and the marker then claims a tree verified minus the guards that never ran. `node` is that shape and is never spawned by name anywhere in the suite. `tests/unit/test_verify_toolchain_preflight.py` holds the correspondence in both directions by **executing** the indexed `scripts/verify.sh` under a stubbed `PATH` rather than reading its text — a resolution with no probe fails naming the binary, and a probe nothing resolves fails too — and a third direction is the completion condition that makes the derived set the *whole* set: every skip-shaped construct in `tests/` must sit in a function that also resolves a binary. Both operands read the git index, so unstaged work is invisible to them and `scripts/mutate.py` cannot reach them; their mutation evidence is by staged probe. `git` entering the preflight is a developer-visible change: a checkout without git now stops at exit 97 instead of failing later. Two residuals are pinned rather than described. The derivation recognises a resolution only where the `shutil.which` spelling is the callee of the call itself — binding it first, aliasing the module by assignment, or passing it to `map` is silent, not refused — and what bounds that is the completion condition, which makes a skip beside such a resolution an offender anyway. The completion rule is positional rather than semantic: it asks where a skip sits, never what its condition tests, so a platform `skipif` on a function that does resolve a binary is admitted.

### Heredocs are data in the shared lexer

Both Bash guards run one lexer, `lex()` in `hooks/git-push-guard.js`, which `push-target-guard.js` imports rather than growing a weaker twin (#436). Until #557 that lexer had no notion of `<<`, so a heredoc's body lines arrived as ordinary commands and any Bash call writing a file whose content quoted a push to a protected branch was refused as that push, in both guards at once. The direction was fail-closed, so nothing unsafe shipped; what it refused was authoring, in a repository whose subject is push discipline. Four occurrences surfaced inside one build, three of them from agents that did not know the ticket existed, and every one was worked around silently by falling back to the `Write` tool.

A `<<` or `<<-` redirection now queues its delimiter and emits the operator as a token; the body is consumed at the newline that ends the command line and never reaches `commands`. The operator stays in the token stream because `isBareShellFedExternally` reads it off the command line to fail closed on `sh <<EOF`. The delimiter word is read the way bash reads it: leading blanks are skipped, so `<< EOF` parses; the word ends at any of ` \t\n;&|<>()`, which is bash's metacharacter set; and quote removal runs across `'...'`, `"..."` and `\`, so `<<"EO"F` and `<<E\OF` both name `EOF`.

The rule is asymmetric because the shell is. A quoted delimiter means the body undergoes no expansion, so it is skipped entirely. An unquoted delimiter means the body is expanded, so every `$(...)` and backtick in it is harvested into `substitutions` and analysed recursively, and `cat <<EOF` ... `$(git push --force ...)` ... `EOF` still denies. The harvest honours a backslash and nothing else, since only a backslash suppresses an expansion inside an unquoted body, and it does not skip `${...}` as a unit: `${x:-$(cmd)}` runs `cmd`, so scanning straight through finds an inner `$(` that a unit-skip would hide. That widens both guards, and the shape denies here where `dev` allowed it. Terminator matching is the whole line, never a substring of one; leading tabs come off the body lines and the terminator for the `<<-` form alone; two documents on one line are consumed in the order their operators appeared. `<<<` is taken as three characters before the heredoc branch sees it, so a here-string never re-enters the scan as `<<` with the delimiter `<`.

A heredoc that starts a body and never meets its terminator is refused by both guards, each in its own words: `hasUnterminatedHeredoc` is exported from the force guard, which checks it before the force check, and `push-target-guard.js` calls it before it looks for a push at all. That refusal is load-bearing rather than cautious. Bash does not reject such a command; it warns (`here-document delimited by end-of-file`) and runs with the body it has, and an unquoted body's `$(...)` expands under that warning, so a push hidden there would run.

A redirection still queued when the input ends is dropped rather than refused. It never met the newline that starts a body, so it has no body, and nothing can hide in a body that does not exist. That single structural condition is also how a `<<` left shift stops being a heredoc: `echo $((1 << 2))`, `(( 1 << 2 ))` and `if (( 1 << 2 )); then ...` queue exactly like a redirection and are dropped identically, so nothing in the lexer tells arithmetic from a command list. Two review cycles shipped a classifier that tried, and both were fail-open in a guard whose posture is fail-closed: it counted parens without honouring quotes, so `echo $(("(" ) ; <a push> )`, which bash runs, read as arithmetic and its commands went unanalysed. Bash agrees with the drop, warning and running with an empty body at exit 0, while `cat <<` with no delimiter word is a genuine syntax error at exit 2 and stays refused.

`tests/unit/test_heredoc_lexing.py` carries the behaviour under ADR 0017 D5 class (a), with an allow and a deny over the new path for each guard, because a kill table cannot see a false positive and that is how a refusal this broad stayed invisible (#511). Fourteen mutants over the lexer each killed exactly the node ids they predicted, re-run at review; the entry that refuses a queued-but-bodyless heredoc kills ten, and those ten are the arithmetic corpus.

### The landing posture

ADR 0020, built as #539. A verdict still binds to a git tree, but the tree that ships may now be **the reviewed tree, or a merge git alone produced from it**. The spine states both paths in law 3, *The binding*, and *Enforcement*, and `templates/spine.md` carries the same generated block byte-identical (`tests/unit/test_spine_template_parity.py`).

`hooks/push-target-guard.js` decides it. Path one is unchanged since #436: a fresh marker over the exact pushed tree that claims the whole of it. Path two holds only when five facts, every one read from git *after* the fact, all hold — the pushed commit has exactly two parents; the first parent's tree carries a fresh **unscoped** marker (git's own convention makes parent 1 the branch you were on, which under the land loop is the commit that received the verdict); the second parent is an ancestor of, or equal to, `refs/remotes/<remote>/<target>`, so only bytes the shared branch already carried may enter this way; the two parents have exactly one merge base; and `git merge-tree --write-tree` over the two parents reproduces the pushed tree. The instrument is **recomputation, not observation**: by push time the index, the worktree and any resolution are gone, so three of the four facts the accepted proposal named were unmeasurable at the enforcement point. Where the recomputation yields a *different* tree, the paths where the two differ are the bytes somebody **authored**, and they are authorised only by a fresh marker over the pushed tree whose `scope` contains every one of them — by exact path, or by a directory entry the path sits under with the `/` required, so `src/app` does not cover `src/application.js`. Each denial names its own condition rather than sharing a message, and each is proven able to fail: an eleven-entry mutation table over this file, every entry killing exactly the tests it predicted. Where `git merge-tree --write-tree` is unavailable (git before 2.38) the second path is simply absent and the strict equality stands — fail-closed, with no new fallback. What the path proves is *no agent authored these bytes*, never *these bytes were gated*; ADR 0020 records the clean-merge-of-two-green-changes case and the `merge=union`/custom-driver case as accepted risks, with the next builder's composite gate as the named backstop.

This is the one place a hook reads the marker **body**, and only the `scope` field; ADR 0018 carries the dated amendment recording the departure. A marker that records a scope authorises **no push by itself** — only a merge whose authored paths it contains — and every way of failing to read a body resolves to *fresh and containing nothing*, which authorises nothing: unparseable JSON, a payload that is not an object, and a `scope` that is not a list of strings all take that arm. Since #560 each of those three arms also carries the fault that produced it, as an `unreadable` field beside `scope`: `its body is not JSON`, `its body is JSON but not a JSON object`, or a `scope` fault naming the field's `typeof` and never its value. A **valid** `"scope": []` never carries one — an empty list is a scope honestly recording that it covers nothing, and `test_a_valid_empty_scope_is_not_reported_as_an_unusable_body` is the discriminator holding that line, because a fix reporting a correct writer as malformed would be the reported defect one layer down. No decision moved with it: `scope` keeps its shape and meaning at all four read sites, `unreadable` implies `scope` is `[]`, and every body #560 names denied before the change and denies after it. `hooks/gate-evidence-guard.js` keeps the filename-only contract, so the two readers of one file now differ on one field; `tests/unit/test_gate_marker_contract.py`'s equivalence — the marker path and the freshness parse — is untouched.

Both refusal sites spend that field on their words. `verdict` selects the lead clause of the protected-branch refusal on it: an absent marker keeps `No gate marker covers tree` verbatim, which the literal-path control in `tests/unit/test_push_target_guard_hook.py` pins, while a marker that was read says so, names the fault and the file it read, and states that another gate run cannot clear it because whatever wrote the file will write the same body again. The surrounding clauses were reordered so the `(looked for …)` path sits with the marker fact it names rather than after the merge reason, and both branches end on the same merge clause and the same closing rule. `mergeAcceptance` makes the same split one level down for the **certified parent's** marker, where an unreadable body used to collapse into the generic first-parent denial that reads as *never gated* — the merge push being the shape a reconcile produces. Nothing from the body reaches either sentence: the fault vocabulary is hook-owned constants plus a `typeof` token, and the marker path passes through the same `reportable()` bound both hooks carry, because a refusal reason is written straight into a model's context while the body is a file any local process can write (law 6). ADR 0018's #539 amendment carries a dated correction from the same ticket: the filename is the whole claim for a marker that **omits** `scope`, never for every marker written before that change. A pre-#539 writer emitting `scope` as a human diagnostic string was correct through 6.0.0 and authorises nothing from #539 on, and the false half of that clause told the first downstream repo to take 6.0.1 that it was safe.

A path a refusal tells the operator to open is bounded to stay resolvable (#568). Each hook carries two caps. `MAX_REPORTED_PATH`, 200, bounds a value echoed as a diagnostic: the `unreadable-declaration` notice names which declaration was skipped and prescribes nothing to open, so a cut name degrades a message that still does its job. `MAX_REPORTED_FILE_PATH`, 4096, bounds a path the refusal tells the operator to open or to act on, and takes the larger of Linux's and macOS's `PATH_MAX`, past which no suffix of the string names a file at all. `reportable()` collapses whitespace, returns a value at or under the cap whole, and past the cap appends `[... truncated at 4096 characters]`, so a reader can tell a path from a stump. The flat 200-character slice could not: a marker path ends in the fixed 64-character tail `/.git/harness/gate/<40 hex>.json`, so any checkout more than 136 characters deep lost part of the filename, and the refusal closing on *Fix the writer that produced it* sent the operator to `…b7c.jso`. Five values sit on the file-path cap and every one of them is a remedy: in `push-target-guard.js` the two `markerPath()` sites and the authored path the scope clause tells the operator to re-gate, in `gate-evidence-guard.js` the expected marker and the directory the block says to run the gate in. Both hooks export the helper, and `tests/unit/test_reportable_path_bound.py` drives it directly in each, pairing a control at the cap that must come back whole with a value past it that must come back marked. That test is also what covers the marked-cut arm, because every per-caller reachability argument written for this ticket read a bound on the directory as a bound on the path `markerPath()` builds by appending that same 64-character tail to it. The refusal-level tests pin the marker path at 201 characters instead of inheriting the host's temp directory, the length at which the shipped code first failed: until this landed the same bytes were green in Linux CI and red on macOS, and which host ran the gate decided whether the suite agreed with itself.

`node scripts/gate-marker.js run --scope <path>` is the scoped re-gate. The operand repeats rather than taking a separator, because a path may contain a comma. An entry is refused before anything runs when it is empty, carries a NUL or a newline, begins `-` (a runner reads that as an *option*, and an operand that changes what the gate does is the ADR 0018 boundary however it arrives), is absolute, or contains a `..` segment. A path git does not track is deliberately **not** refused: a conflict resolved by *deleting* a file yields exactly that, and it is the resolution shape most likely to need a scoped run. The paths never reach a command line — the runner writes them NUL-delimited to a file under the git common directory and names it on the environment as `HARNESS_GATE_SCOPE_FILE`, with `HARNESS_GATE_SCOPE_COUNT` beside it, so the line `sh -c` receives is the checked-in scalar character for character. The command selected is `commands.test_scoped`; a repo declaring none runs its whole `commands.verify` gate, says so on stderr, and earns an **unscoped** marker, which is the same authorisation it always was. This repo declares none, deliberately: its gate is roughly half a minute end to end, and a scoped path would skip ruff, mypy and the coverage floor to save seconds. The key exists for repos whose gate is minutes.

`scripts/harness-refs.js` is the `refs/harness/*` namespace — three record kinds, one script, and every key **flat**, because a key nested beneath an existing one produces a git directory/file conflict. Every component is percent-encoded byte by byte, UTF-8 aware, with only `[A-Za-z0-9_]` passed through, so a branch name or ticket id carrying `/`, `.` or a non-ASCII character still occupies one path component. Gate records are blob refs `refs/harness/gate/<tree>-green|-red`, readable from another clone in one `ls-remote` with no object transfer, and publishing prunes any record whose tree is neither the tree just published nor the tree of one of the integration branch's last `HARNESS_RECORD_WINDOW` (default 200) commits — coherent because a composite tree that *lands* becomes an integration-branch tree, so what ages out is exactly what never landed. Claims are create-wins refs `refs/harness/claim/<ticket>-<bucket>`, never forced in any spelling, the bucket a tumbling `HARNESS_CLAIM_TTL_SECONDS` (default 3600) window; `--now` names the instant the bucket is computed from, which is exposed because a claim is advisory coordination that authorises nothing and a caller who lies about the time can only take a claim it could have taken by waiting. The green pointer is `refs/harness/green/<integration>` and only ever fast-forwards. A publish the remote declines **exits zero**: the record is a courtesy to the next session, and a fact about the network is never a fact about the bytes.

`scripts/land.js` is the landing decision, and it retires the four-step post-verdict git procedure `skills/build/references/re-bind.md` used to carry; `skills/build/SKILL.md` now carries no git invocation for landing beyond law 3's own `HEAD^{tree}` comparison. `plan` reports exactly one `decision`: `push` (the tip had not moved, or git merged it cleanly and the merge is left committed), `resolve` (the merge conflicted, the worktree is left conflicted for a human, `conflicts` names exactly the unmerged paths and `scope_argv` / `scope_command` carry the re-gate with every operand shell-quoted), `hold` (reconciliation spent), or `refused` — a shape it does not decide: a dirty worktree, a detached HEAD, a branch the repo declares no role for, or `case: "uncertified-head"` (#566). That last case is the merge path's own precondition, checked before the merge runs: `plan` reads `HEAD`'s tree marker through `scripts/gate-marker.js`'s exported `markerPath`/`maxAgeSeconds` — the writer itself, not a second copy — and merges only onto a `HEAD` whose tree carries a fresh, unscoped marker, because that is the same first-parent test `hooks/push-target-guard.js`'s `mergeAcceptance` applies at push time. Where it does not, `plan` refuses rather than build the merge, and names `certified`: the nearest first-parent ancestor of `HEAD` a fresh unscoped marker does cover, or `null` when none does. A `recovery_command` rebuilding the branch from `certified` is offered only where every commit between it and `HEAD` is `recomputable` — a two-parent merge whose tree `git merge-tree --write-tree` reproduces from its parents and whose second parent the fetched tip already contains, so nothing the rebuilt merge would drop is bytes only that commit carries. A single-parent commit (work committed after the verdict), a merge with no certified ancestor at all, a merge whose tree the recomputation does not reproduce (a hand resolution), or a merge whose second parent the tip does not already carry (a sibling branch merged in, not a lost-race stack) each withhold the `recovery_command` rather than offer a rebuild that would discard it. This is the defect the stacked-merge case exposed (a lost push race left `HEAD` an ungated merge, and every re-run stacked a new one, each refused silently by the guard) and it reaches wider than that one case: `finish` on a further-moved tip prints ``run `land.js plan --attempt 2` ``, and by then `HEAD` may be a conflict resolution under a **scoped** marker, which the same first-parent test refuses — `plan` now refuses that shape too, up front, and offers no `recovery_command`, saying to re-gate the whole tree or hold. `finish` re-checks the preconditions and hands over the push. The invariant the script holds is **no verb pushes a branch**, not *no verb pushes*: `plan` and `finish` print the push for the agent to run through the tool the hook can see, while `done` does push, and only under `refs/harness/` — a gate record, and the green pointer, which it advances only when the merge was uncontended *and* the push actually landed. The stronger absolute was the weaker check, because it left the one verb that reaches a remote outside the guard named after it. `scripts/harness-refs.js` and `scripts/land.js` run from the plugin root like the hooks and take `--repo <dir>`; they are deliberately **not** in the closed pair `/harness:init` materializes into a consumer repo.

Two consumers read what the new refs and fields record. `worktree-isolation` branches from `harness-refs.js green-read` instead of the integration tip, falls back to the declared integration branch when the pointer is empty, and reports the base it took either way — a run that does not say where it started cannot tell a red base from a red change. **Since #576**, *Creating the worktree* fetches the remote before that pointer read — `green-read`'s oid is already current, but the commit it names still has to exist in this checkout, and the fallback branch name needs a fresh ref too — and the worktree it creates starts **detached** rather than carrying the task branch. *Gating the base* then runs the repo's verify command over that detached worktree, at the fetched base, before anything in it changes: green cuts `<task-id>` there and starts work, red is an andon pull (P4) that files a bug against the integration branch, removes the worktree, and holds the task rather than building on it — whether or not this run caused the red. The branch is cut only after green for exactly this reason: cutting it at creation and removing the worktree on a red base would leave the branch behind, and the retry would die on `fatal: a branch named '<task-id>' already exists`. And `node scripts/gate-marker.js durations` reports the `count` and `median_seconds` across the markers a clone still holds, which `/assess` puts in its report before filing anything; a marker written before #539 carries no `started_at` and is **skipped** rather than counted as a zero-second run, which would drag the median toward zero for weeks and read as an improvement.

### The test lock and the run file

`hooks/test-lock-guard.js` is the sixth hook and the fourth that refuses. It arms only when three facts hold together: the repository resolved from the **edited file's** directory carries `.harness/run.json`, that file is version `1` and says `tests_locked: true`, and `harness.yaml` declares `paths.tests` — read through the shared reader's new `declaredPaths` accessor, a named accessor beside `declaredLoop` rather than a seventh hand-rolled parser. Any one of the three missing leaves the lock inactive, which is the state of every repo that never adopts the run file and of every session in this one that is not a build. Under the lock, an edit to a path under the declared test root is refused in the `change` and `feature` lanes and in any lane value the hook does not recognise — the permissive branch belongs to `fix` alone, so a typo, a truncated write or a lane invented later locks rather than unlocks. The `fix` lane may **add** a test file, where *new* means absent from `base_commit`'s tree: not absent from the filesystem, which would refuse the fix lane's own second edit to the file it just wrote, and not absent from the index, which flips the moment a run stages for review. Because the repository is resolved from the edited file rather than from the hook's own directory, a locked run in one worktree never reaches another worktree of the same repo, which matters where concurrency is the norm (law 5).

Two details are load-bearing and were found rather than designed. The repository is resolved from the edited path's nearest **existing** ancestor directory, because a `Write` creates the file *and* its directory: a `git` probe in a directory that is not there yet fails, no repository resolves, and the lock is simply off — `mkdir tests/new/` was a one-command bypass, and three lookalike controls had been passing vacuously against a predicate the hook never reached. And the refusal names the offending path, the law, and the escape — return the run to `stage: "tests"` with `tests_locked: false`, record why on the ticket, and expect the reviewer to ask — while echoing **nothing** from the model-writable run file into a reason that re-enters a model's context (law 6); the path itself is reduced to path characters and truncated.

The bounds are stated rather than implied. The hook sees `Write`, `Edit` and Codex's `apply_patch`, so a test rewritten through `Bash` is invisible to it, and extending to `Bash` would mean parsing arbitrary shell, which `push-target-guard.js` prices at hundreds of lines that still refuse on ambiguity. Releasing the lock is one edit to a gitignored file — which is the point, not a hole: it makes a bypass deliberate and reviewable instead of silent. The control of record is the reviewer's explicit item per test-file diff.

`.harness/run.json` is the run state `/build` writes at set-up, and `skills/build/references/run-state.md` owns its fields, its stage vocabulary and its resume rules. One rule bounds the file: it records *where the run is*, never *what is true of the tree*, so every oid, marker and verdict it holds is a cache key re-derived from git before use and discarded on a mismatch — `reviewed_tree`, `gate_marker_tree` and `verdict` are trusted only while the freshly derived tree oid still equals `reviewed_tree`, which is the reconciliation rule the resume path inherits rather than restating. **Only the orchestrator writes it**, which is what stops an agent told to make the tests pass from clearing the flag that governs the stage it is in, and a writer rewrites the whole object carrying through keys it does not recognise. Since #587 the file has a second reader: `gate-evidence-guard.js` takes `ticket` alone, to decide whether a derived Stop candidate belongs to another run. The two readers differ on `version` — the test lock requires exactly `1` and treats anything else as unreadable, while the Stop hook never reads the field, so a later version that changed what `ticket` means would disarm the lock and still establish ownership there. Neither echoes a byte of the file into a reason. `tests` and `implement` are separate stages and that separation is the whole mechanism: the failing tests are authored with the lock off, then one write sets `stage: "implement"` and `tests_locked: true` together, before the first line of implementation. A malformed or unknown-version file stops the line at `/build`, where an operator can act on it, while the hook fails open loudly over the same file — denying there would lock a session out of its own tests over a corrupt cache file with no way to clear it from inside the hook.

The file is gitignored, and #538 moved `.harness/` out of a loose `.gitignore` line into the machine-identifiable `harness:gate-ignore` block that `/harness:init` hydrates. Untracked *and* unignored, `run.json` would be swept into the tree identity by `/build`'s own `git add -A && git write-tree` — the exact failure `.evidence/` is in that block to prevent — and a consuming repo hydrated by `/harness:init` had never received the loose line at all. `tests/unit/test_init_gate_ignores.py` holds the block's contents against the hydration copy in both directions and against an explicit set, so a shared omission cannot make the comparison vacuous.

After a successful push, `/build` runs the `worktree-isolation` cleanup procedure: it tears down only temporary resources owned by the task, removes the merged worktree, prunes Git's administrative records, and deletes the merged task branch. A failed cleanup reports the remaining resource; it never substitutes broad host cleanup.

`scripts/mutate.py` — the instrument that proves guards can fail — refuses to `run` before anything else unless a fresh gate marker covers the target tree (the #473 gate lock; `check` mode needs no marker). Since #500 it reaches the convention through one subprocess call — `node scripts/gate-marker.js status`, which prints the tree oid, the marker path and the bound as three facts and no verdict — rather than by importing the retired Python module, which keeps the freshness variable at three parsers instead of four. That call is the module's one permitted non-interpreter spawn, and `tests/unit/test_mutate.py` earns the exemption from the argv **shape** rather than granting it to the name `node`: a three-element list whose first element is the literal `node`, whose second is a module-level name the guard resolves back to an assignment built from the literal `gate-marker.js`, and whose third is the literal `status`. A `node -e`, a fourth element, another verb, another file, or a name bound inside a function all fail the shape, so there is no list of permitted subcommands to go stale and the only widening left is a deliberate edit to the guard. `node` is therefore a hard precondition of `mutate run`, and a host without it raises `RunnerUnavailableError` (exit 3, infrastructure) rather than a refusal about the tree; `mutate check` stays node-free.

### The cloud session bootstrap

`scripts/setup-cloud-env.sh` provisions a bare checkout until `/build` and `/routine` can run in it: the Python toolchain the gate runs under, the host binaries its toolchain preflight probes, and `gh`, which the tracker needs and the gate does not. It checks `git` rather than installing it, on its own reasoning that no reasonable cloud sandbox lacks one. The exact set is the script's own header, and the gate-prerequisite part of it is recorded in `specs/infrastructure.md`'s *Local execution* row and in the toolchain-preflight Decision `specs/architecture-principles.md` carries; this entry cites them rather than adding another copy. Installation is idempotent, and the script probes the result instead of assuming it, so a provisioning gap is reported at setup time rather than surfacing mid-gate. It deliberately does not run under `set -e` — failures accumulate in a status variable and become a non-zero exit at the end, so one missing tool still leaves a complete report — and the severity separates a gate dependency from a tracker one: a missing `jq` fails, a missing or unauthenticated `gh` warns.

`scripts/session-start-bootstrap.sh` is the hook entry point that runs it; both landed at `4beb310`, and the spine's `commands:` block carries the provisioner as `bootstrap:`, which is where an agent reads it. The plugin's `hooks/hooks.json` declares no SessionStart hook, so nothing wires this in a repo that installs the harness and the provisioning stays this repo's own environment concern rather than a capability the plugin ships. That registration is the `hooks.SessionStart` block `tests/unit/test_settings_template_parity.py`'s subtree rule lets the installed settings carry over `settings/harness.json`, which declares no such key. ### The guards

`tests/unit/` holds 45 test modules (~23.4k lines; both derived at this record's tree by `git ls-files 'tests/unit/test_*.py'`, so the suite's shared helper modules are outside the count) admitted under ADR 0017 D5's rule: (a) behaviour of executable code, (b) a property of the spine, (c) integrity of shipped assets, (d) frontmatter compliance, (e) tree-consistency — existence and correspondence of two things both in the tree, never prose meaning. The prose-guard corpus (118 modules on `dev` at 2026-08-17) is deleted; what survives executes the hooks under node, the gate scripts, the mutation instrument, and the workflows' contract modules. ### The assessment layer

### Hydration — `/harness:init`

`skills/init/SKILL.md`: interview for the repo values; write `harness.yaml` from `templates/harness.yaml`; write the spine `AGENTS.md` from `templates/spine.md`, merging without discarding repo-owned content, then `CLAUDE.md` as `@AGENTS.md` plus that host's deltas; seed the path-scoped `.claude/rules/` files (and, for Codex, the equivalent nested instruction file, since Codex has no path-scoped rules) — a rule is repo-owned once seeded and `--refresh` never overwrites it; hydrate `.codex/agents/*.toml` from the plugin, replacing a file only when its first line marks it as one of the plugin's own, in either the current spelling or the legacy `# Generated by scripts/generate_codex_artifacts.py` a pre-#537 repo still carries — the old marker is kept in the list rather than replaced, because a rule keyed only on the current one silently stops firing for every repo hydrated under the old one; scaffold `specs/{proposals,features,decisions}/`; seed `specs/infrastructure.md` with the branch topology; declare both install routes; and add gate plumbing. Before changing gate assets, hydration plans and classifies the flat Node context. It materializes `scripts/gate-marker.js` **and `scripts/harness-config.js` as a pair** — copy both or neither — a CommonJS `scripts/package.json`, and the `scripts/verify.sh` skeleton with its public `exec node scripts/gate-marker.js run` entry point only when every immediate module-bearing source (`*.js`, `*.mjs`, `*.cjs`, `*.ts`, `*.mts`, `*.cts`) is the recognised managed helper and the local manifest is absent or CommonJS. The absence of `*.js` is not consent. Another module source, an incompatible manifest, or a consumer-owned helper retains every gate asset and reports every blocking path. `--refresh` **migrates the configuration first, as a move**: where a repo has no `harness.yaml` and its spine still carries a fenced `yaml` block, that block is written out byte for byte, the fence becomes a one-line pointer, the key-by-key diff is reported and any difference stops the run; where both exist, `harness.yaml` already wins at the reader and the stale fence is reported rather than merged. It then reports every classification, updates the marked block in `AGENTS.md` (offering, never performing unasked, the reduction of a pre-#537 `CLAUDE.md` to `@AGENTS.md`), owned Codex adapters, and gate-ignore content, then only in a safe Node context updates a missing or released managed helper and recognises a legacy preflight/write verify pair by its invocation shape — any prefix of literal words before the helper, the counterpart in the same shape — for migration to `run`. A file already using the public `exec node scripts/gate-marker.js run` line is retained with the terminal migrated classification and is not considered for custom-wiring classification; custom or incomplete wiring is retained and reported. It identifies a legacy Python helper by one of two complete SHA-256 hashes and deletes it only after the completed verify plan leaves no tracked invocation; otherwise it retains and reports every reference. The operation changes only the working tree for the operator to review and commit, never executes arbitrary consumer shell, and never writes a direct marker command.

### Two-branch topology

This repo runs `dev` (integration) → `main` (release) — ADR 0003 as amended by ADR 0017 D6 and again on 2026-08-19, recorded in `specs/infrastructure.md` → *Branch topology*. `main` carries branch protection requiring a pull request, so no direct ref update advances it; `github-actions[bot]` has no bypass, which is why the promotion cannot push.

`.github/workflows/nightly-promotion.yml` checks out `dev` with full history and no persisted git credential, and runs `scripts/promotion-step.sh`. The script gates the exact candidate, then **opens or reuses a pull request whose head is the `dev` branch itself and merges it through the API**, binding the merge to the gated SHA with a server-side `sha=` head match. Head-is-`dev` is what lets it run unattended: that commit already carries the `lint-and-test` check raised by the ordinary `push: dev` trigger, so the check `main` requires is satisfied with no new run, no approval, and no stored credential — the token is the job-scoped `GITHUB_TOKEN`, forwarded to that one step. The workflow grants `contents: write`, `pull-requests: write` and `checks: read`, pinned as a set equality so a fourth grant fails rather than arriving unobserved.

**The published invariant is tree identity, not fast-forward.** A pull-request merge necessarily puts a commit on `main` that `dev` does not contain, so ancestry can no longer be the rule; what is asserted is that the tree landing on `main` equals the tree the gate certified. Two instruments carry it rather than one predicate: a **pre-condition** that, relative to the merge base, `main` contributes no content — the condition under which the merge is content-trivial — and **post-conditions** on the SHA the merge API returned, that the candidate is contained in it and that its tree equals the candidate's. The post-conditions *detect rather than prevent*: `main` has already moved when they run, and the prevention that survives is the pre-condition plus the head match. The property is self-sustaining — each promotion leaves `tree(main) == tree(candidate)`, so the next night's pre-condition holds with no back-merge, and this repo therefore does not back-merge.

Nothing is forced, repaired, or conflict-resolved. The night stops and reports when the gate is red, when the target branch is absent, when `main` carries content `dev`'s history does not, when `dev` moved past the gated commit, when the required check failed or never completed within the poll deadline, when the one open pull request is a draft or has a different head, when the pull-request number GitHub returned is not numeric, or when the merge's containment or tree identity fails. A refused night leaves its pull request open for the next run to reuse, and a night with nothing to promote exits clean without spending the gate.

`.github/workflows/ci.yml` runs the gate on pushes to `main` and `dev`, and on pull requests based on `dev` only. Pull requests into `main` deliberately raise no run: a pull request opened by a workflow using `GITHUB_TOKEN` produces runs in an approval-required state that nothing unattended can approve, and a second, permanently unapproved run carrying the required check's name on the gated commit is a deadlock this removes rather than reasons about. The cost is stated rather than discovered later — a human pull request into `main` from any branch other than `dev` gets no `lint-and-test` and therefore cannot merge, which is fail-closed and deliberate.

Three-role topologies remain available to repos that deploy to staging — the roles are per-repo configuration in `harness.yaml`'s `branches:` block. Fast-forward-only publishing is `/promote`'s default since #547 moved it there with the rest of the retired `infrastructure` skill; this repo is the recorded exception to it, not a rewrite of it, and `skills/promote/SKILL.md` states the substitute assertion a pull-request-only target gets instead.

## Data model

No persistent state beyond the tree itself, the gate marker, and — since #539 — a set of git refs on the shared remote. The marker is one JSON file per verified tree oid under `<git-common-dir>/harness/gate/`, freshness by mtime, written atomically and carrying `started_at`, `finished_at`, and a `scope` key **only** when the run verified less than the whole tree. Markers live in the git directory, so they cannot be committed into the tree they attest, and the scope file a scoped run hands its gate lives beside them for the same reason and is removed on both the green and the red arm. The refs are `refs/harness/gate/<tree>-green|-red`, `refs/harness/claim/<ticket>-<bucket>`, and `refs/harness/green/<integration>`: a cache with the same standing as the local marker directory, pruned on publish, never forced, and never read as authorisation — nothing that decides a push looks at them. This is not a revived run ledger (ADR 0015).

## Interface surface

- `bash scripts/verify.sh` — the canonical gate; exit 0 green, 97 reserved for an unrunnable toolchain, tool exit codes otherwise. Production callers: `.github/workflows/ci.yml`, `scripts/promotion-step.sh`, every completion claim.
- `node scripts/gate-marker.js <preflight|run [--scope <path>]…|tree|path --tree <oid>|durations|status>` — the runner half of the marker convention, in one file. `run` accepts repeated `--scope <path>` operands and nothing else, and executes only the selected trusted `commands.verify` declaration — or `commands.test_scoped` where a scope was given and the repo declares one — through fixed `sh -c`; the source is the first that exists among `harness.yaml`, `AGENTS.md`, `CLAUDE.md` and legacy `CONTEXT.md`, resolved through `scripts/harness-config.js`, and the historical `bash scripts/verify.sh` is used only when none of them exists — through the same `sh -c`, so its `$0` is that relative path rather than an absolute one and an `sh` sits between the runner and the gate. A value opening with a yaml indicator (`|`, `>`, `&`, `*`, `{`, `[`), a quoted value that is not one whole enclosing scalar, and the flow mapping `commands: {verify: …}` are refused rather than read. It forwards the selected gate's output and non-zero exit status, and only after measured success writes and prunes the marker. A selected missing, empty, duplicate, malformed, or unreadable declaration is runner infrastructure (exit 3). The direct `write` command is retired and returns usage exit 64. `preflight` is the nested-worktree check run by the internal shell gate before expensive verification stages, and before anything materialises a tree; a visible registered descendant or an indeterminate ignore query makes the gate unrunnable. `tree`, `path` and `status` are queries that write no marker — `status` is the one `mutate.py` spawns, and `tree` and `status` do create the marker *directory* as a side effect of computing the tree, which is the observable that orders the preflight ahead of them. Exit 0 succeeds, 2 is a refusal about the repository, 3 means the runner could not **resolve** a gate to launch — an unusable `commands.verify`, an absent legacy `scripts/verify.sh`, or a declared gate that delegated back to `run` — and 64 is a usage error. A declared command the shell itself cannot launch is not exit 3: `sh -c` reports it as its own 127, forwarded like any other red result, because a consumer's gate can legitimately exit 127 from an inner command.
- `scripts/harness-config.js` — the one configuration reader, `require`d by the two enforcement hooks, the test-lock guard, and `scripts/gate-marker.js`; not an executable entry point. Exports the source list, the block reader, the named map accessors (`declaredBranches`, `declaredLoop`, `declaredCommands`, `declaredPaths`), and `gateCommand`; the generic `readMap` stays unexported, so a new consumer adds a named accessor rather than a parser. Materialized into a consumer repo by `/harness:init` as a pair with `gate-marker.js`.
- `node scripts/harness-refs.js <gate-publish|gate-list|claim|green-advance|green-read>` (#539) — the `refs/harness/*` namespace: gate records, claims, and the green pointer. Every subcommand takes an optional `--remote <name>` (default `origin`) and `--repo <dir>` (default the working directory). Exit 0 succeeds, 2 is a refusal, 3 a contended claim or a pointer that did not advance, 64 usage; a publish the remote declines is not an error. Runs from the plugin root and is **not** materialized into a consumer repo.
- `node scripts/land.js <plan|finish|done>` (#539) — the landing decision, one JSON object on stdout per call, with `--repo` / `--remote` / `--branch` / `--attempt`. It never pushes a branch, never runs the gate, and never resolves a conflict; the exit vocabulary is `gate-marker.js`'s (0 actionable, 2 not, 3 unrunnable, 64 usage) and it does not extend it. Also plugin-root only.
- `node scripts/plugin-version.js [--repo <dir>] [--remote <name>]` (#589) — the plugin's one version, raised once per release cycle by `/build` step 1. One JSON object on stdout carrying `bumped` and a machine `case`, in `land.js`'s shape: `raised`, `already-ahead`, `no-plugin-manifest` and `no-release-branch` at exit 0, and `stale-base`, `release-ahead`, `release-unresolvable`, `release-manifest-unreadable`, `unreadable-version`, `homes-disagree` and `home-unwritable` at exit 2; 3 when git, the fetch or the configuration reader could not run, and 64 for usage. The exit vocabulary is `gate-marker.js`'s and it does not extend it. It writes the four version homes by substring and nothing else, and never commits, pushes, or runs the gate. Versions outside `X.Y.Z` with no leading zeros refuse rather than sort, because ordering a prerelease needs a SemVer precedence nobody specified. The fetch has no fallback to a local `refs/heads/<release>`: the operand has to be what a consumer can pull, so a plugin source with no reachable remote cannot run `/build` step 1. Runs from the plugin root and is **not** materialized into a consumer repo.
- `scripts/mutate.py check|run` — mutation instrument; usage in `CONTRIBUTING.md`.
- `scripts/promotion-step.sh` — the nightly's whole logic: the gate, the content-divergence pre-condition, pull-request open-or-reuse, the required-check poll, the API merge bound to the gated SHA, and the two post-conditions. Four inputs, all asserted before any work and none of them echoed: `GITHUB_WORKSPACE`, `RUNNER_TEMP`, `GITHUB_REPOSITORY`, `GH_TOKEN`. Called by `nightly-promotion.yml`; **executed**, not read, by `tests/unit/test_promotion_step_script.py` against a stubbed `git` and `gh` that record every invocation to one shared file, so ordering is assertable.

## Known limitations

- **The Stop hook's ownership filter needs both sides to declare a ticket, so visitation still enrols where a run file is absent (#587).** A session whose own worktree carries no `.harness/run.json` — an orchestrator at the repo root, which is #439's motivating shape and stays enrolled deliberately — admits every derived candidate, and the block still names a directory and still prescribes running the gate there. The filter's own failure direction is the false negative: a session that authored ungated work in a worktree whose run file names a different ticket is not nudged about it, and where no live session owns that worktree nothing else nudges either. A protected-branch landing is unaffected — `push-target-guard.js` refuses on the pushed tree and knows nothing of tickets — while a task branch was never guarded by either hook. ## Decisions

### Decision: Re-bind PASS only across clean, disjoint post-verdict drift

*Decided 2026-08-31. **Superseded 2026-09-05 by [ADR 0020](../decisions/0020-authored-tree-binding.md)**, built as #539: the disjoint-path precondition is gone, the proof moved from observing the merge to recomputing it with `git merge-tree --write-tree`, and a conflicted merge now ships under a scoped re-gate instead of returning to the reviewed path. What survives is the shape of the licence — git alone must have produced the bytes — and the two-attempt reconciliation bound. Kept here as the decision this repo actually made and then replaced.*

**Context.** A push can lose a race after PASS has bound a reviewed tree. Repeating the reviewer round trip adds no judgment when the new base changed only disjoint paths, but the prior gate evidence cannot certify the merged tree.

**Decision.** `/build` may inherit PASS only after a unique-base, disjoint-path check and a clean Git-authored merge with the expected parents and no resolution or edit. It then runs the complete configured gate, binds fresh marker evidence to the exact merged tree, reports the incoming range and tree identities, and retains the normal pre-push tree-equality check. Shared paths or conflicts retain delta review and a new final verdict. The shortcut saves the reviewer round trip, never the complete gate.

**Alternatives.** Always repeating delta review was rejected for clean, disjoint drift because it adds no new judgment. A selective or shortened gate was rejected because it weakens exact-tree certification. Conflict resolution, prose parsing, and inferred semantic overlap were rejected because they exceed the mechanical licence.

**Consequences.** The shortcut stays inside the existing two-attempt reconciliation bound. Any ambiguity, authored byte, failed or wrong-tree evidence, or equality mismatch returns the run to the ordinary reviewed path.
